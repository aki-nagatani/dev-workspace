## 3.1. `dump_spec_import_preview.py` CLI 早見・0 件切り分け

- `--kind` … `success`（既定）＝`プレビュー結果:` 行のみ。`failure` ＝`プレビュー失敗:` 行のみ
- `--count` … ヒット件数のみ表示
- `--list --limit N` … 成功時は `[index] timestamp  category=...  rows=...  url=...`。
  **失敗時**は `code` / `jobId` / `requestId` / `url`（`sourceUrl`）/ `message` 先頭。
  **「新しい」順**は既定で `--order time`（各ログ行先頭の
  `[YYYY-MM-DD HH:MM:SS]` を**記録日時**として比較し、**新しい順＝降順**）。
  `grep` のファイル順混在に依存しない
- `--order file` … 従来どおり、入力テキスト上の**出現の逆順**（特殊用途）
- 0 件だった場合の切り分け:
  - **`--kind success` で 0 件・UI は失敗表示** → `--kind failure` と
    `プレビュー失敗:` の grep を試す（**失敗行**は別コードパス。未デプロイ・無効環境変数では両方 0 件になり得る）
  - 環境変数 2 つ（`FISHTRACK_STANDALONE`, `FISHTRACK_SPEC_IMPORT_DEBUG_LOG`）
    が当該環境（本番 `.env` / ローカル compose）で有効か（**成功プレビュー行**の出力条件。**失敗行**は WARNING で別経路）
  - ファイルに出ておらず **stdout** のみの可能性 → **各入口 SKILL §0** の取得元 (2) を参照
  - ローテーション後で別ファイルに移っている（ローカル `docker` 経路）
    → `--include-rotated` を付けて再実行、または本番 EC2 側で連結してから `--stdin`
  - まだ 1 度も**当該環境**でプレビューを実行していない → ユーザーの合意のもと UI で再現依頼

**ローカル Docker（FishTrack）と `restart`（`dump` とは切り離す）**:

- **`restart` の要請**: **`src/` 等アプリ用 Python を変更したあと**、**ユーザーがブラウザでアプリを操作する**（スペック取り込みプレビュー含む）**前**に必要。\
  **WSGI（例: Gunicorn）は起動時にモジュールを読み込む**ことが多く、**bind-mount だけでは**ブラウザ経由のリクエストが**旧コード**のままになり得る（**`local-docker-python-restart`**・**myrules**「ローカル Docker と Python ソース変更」）。
- **`dump_spec_import_preview.py`**: コンテナ内ログを**読むだけ**。**`dump` の実行・ログ照合そのものに `restart` は不要**（**`dump` 検証とは非関係**）。
- **運用の接点**: **`src/` 変更と同一セッション**で**新コードのログ**を**ブラウザで再現**してから `dump` したいときは、**先に `restart`**（**ユーザー操作の前**）。\
  **既に書き込まれたログ**だけを `--count` / `--latest` する**照合**なら **`restart` はスキル上不要**。\
  **エージェントの `restart` 試行・確認文の代用禁止**は **`ai-spec-check-local` 本文**・**myrules** を正とする。

### 5.1. `ai-spec-notes`（プレビュー突合用の本家データ）

**目的**: `ai-spec-notes` は、`resolvedUrl` から取れた文言をそのまま長文保存する場所ではない。\
**次回以降のプレビュー `rows[]` と突合しやすい本家側データ**（行キー・数値・技術名・比較除外列・期待値の根拠）を残す。
**詳細な実行結果・判定・対策の正本は常に `ai_spec_check_report.md`**（§9・§6 等）。

**取りこぼしの優先順位（必須）**:

- **最優先**: **突合ノート（`ai-spec-notes`）側**の取りこぼし防止（**§5.1** の本家取得・`## メタ`・行別期待・同名 `.csv`）。\
  **プレビュー `rows[]` の現状**に合わせて期待値を**削る・弱める**ことは**禁止**（本家根拠がある限りノートを正とする）。
- **次段**: **プレビュー側**の取りこぼし・不一致は **dump 検証後**に **§3 の 🔴／🟡** として記録し、**§4 対策案**（優先度：高／中／低）で対応する（**§5.1 中に FishTrack `src` を直してプレビューに追従させない**。実装は **§8**・**ユーザー明示**の境界どおり）。
- **判定の切り分け**: ノート期待は揃い **プレビューのみ欠落**（例: **ナノピッチ**が全行空）→ **§2／§3 はプレビュー不足として 🔴**、**§4 にサーバ／プロンプト等の対策**。**ノートのメタ・行別が本家より少ない**→ **§5.1 を先に直してから**再 dump（**プレビュー実装を待たない**）。

**モデル個別ページがあるシリーズ（必須・ロッド）**:

- **発火**: シリーズ一覧（`resolvedUrl`）の **LINEUP／SPEC 表**で **型番が個別 `/site/products/` 等へリンク**する、または **`## メタ`／突合方針**で **② モデル個別ページ**を前提としているとき。
- **最優先**: **突合ノート（`ai-spec-notes`）の精度**と**漏れの解消**。プレビュー実装・**§4 対策**より**先**に、**ノートと同名 `.csv` を本家と一致**させる。
- **必須手順**（**省略禁止**。代表 1 件・「多くは 2 件」だけの確認で**完了としない**）:
  1. **全行**の **個別 URL** を **`## モデル個別 URL`**（または同等の行別表）に列挙する（**row**／**modelName期待**／**detailUrl**）。
  2. **各 URL を取得**（`WebFetch` 等）し、**プレビュー `rows[]` と同じ行数**について **個別ページの内容**を突合ノートへ反映する。
  3. **行別で必ず個別ページから取る項目**（本家に載るもの）: **`listPrice`（税別）**、**`technologyLabels`**（**`TECHNOLOGY` 節の見出し**。**モデルごとに異なりうる**）、**`blankMaterial`**（ブランク見出し。**ソリッドティップ等の行差**）、**`releaseYear`**（個別タグ・発売年根拠）等。
  4. **`technologyLabels`**: **代表モデルへの一律コピー禁止**。**「N 行共通」表記だけ**で **未確認行を IFPS 2 件等で埋める**ことも禁止。差分は **`## TECHNOLOGY（行別）`** または **`## 行別スペック`／`## 技術・素材の期待値`** に**行ごと**に書く（**件数・ラベル名・順序**を本家どおり）。
  5. **同名 `.csv`**: 上記を **全行転記**し、**`priceJpy`／`technologyLabels`／`blankMaterial` 列**がノートと**1 行ずつ一致**することを確認する。
  6. **`## メタ`** に **「全 M モデル個別ページ確認済（YYYY-MM-DD）」** を記録する（**M＝プレビュー行数**。**未完了なら書かない**）。

    本家製品表の**継数セルが数値のみ**（例: **6**・**＊2** 脚注を除く素の本数）のとき、**`ai-spec-notes` の期待 `pieces`** および照合時のプレビュー正は\
    **`N（テレスコピック）`**（**全角括弧**・Obsidian **`05_ai_spec_import.md`**）。**本家の継数数値 N と一致**すれば **🔵**。\
    プレビューが**数値のみ**（`6`）・**null**・本家と異なる N は **🔴**（**🟡 に降格しない**）。
    **テレスコピックとみなす根拠**（メーカー別の例。いずれかで可）:
    - **DAIWA**: 型番コアがテレスコ振出（全長ブロック直後が **`T`**）
    - **LEGIT 等**: シリーズ／ページが振出し専用（例: **`/telecast/`** の **TELECAST**）、または表 **`＊2`／`2※`**（実装は **`normalize_legit_pieces_display`** 等）

    継数・ジョイントの**いずれかが本家と食い違う**場合は従来どおり 🔴。

**注**: リールプレビューでロッド用キー（全長・ルアー重量など）が null の場合は本観点では評価しない。

### リール `seriesName` 年式プレフィックス（DAIWA・SHIMANO）

**発火**: `category = "reel"` かつメーカーが **DAIWA** または **SHIMANO**（プレビュー `manufacturer`／本家ページ判定）。

**必須（既定）**:

- **`seriesName` の先頭**に **2 桁年式（00–99）** を付ける（例: **`23ステラ`**, **`20ツインパワー`**）。
- 本家 H1・見出しが **シリーズ呼称のみ**（年式なし）でも、ページ本文・カテゴリ見出し・型番ブロック・**既存マスタ表記**などから **当該ページの年式が特定できるとき**は、**必ず年式付き `seriesName`** とする（ロッド DAIWA の「本文に年式が無いときは付与しない」とは**別ルール**）。

- **`ai-spec-notes` の `## メタ` シリーズ名**・**`reel-daiwa/`／`reel-shimano/`** の **`<ベース名>.md`** も、上記 **`seriesName` と同一**の年式付き表記とする（§5.1 の衝突回避 `_接尾` は従来どおり）。

**例外**:

- **ユーザーがチャット等で別途指示した場合のみ**、当該 URL／シリーズでは年式無し表記を許容する。**例外理由を `## メタ` に 1 行**残す。
- **年式を特定する根拠がページにもマスタにも無い**ときは **🔴**（推測合成は禁止。**`releaseYear` からの合成も不可**）。

**照合・対策**:

- 下記 **§6B E** の `seriesName` 判定は本節を**正**とする。先頭に **2 桁年式が無い**／突合ノート期待と不一致 → **🔴**。

- **A. 件数**
  - `rowsCount` が本家製品スペック表の行数（番手ごとに別行）と一致するか

- **B. reel_type（必須・制約あり）**

## 7. 差異の分類

**原則**: `resolvedUrl` の**本家ページ**とプレビュー JSON を突き合わせ、§6A / §6B の**解釈ルール**（例: 帯分数と小数の同値、単位の表記揺れ）を適用したうえでなお残る**不一致はすべて 🔴**とする。🟡・🔵 は、**本家とプレビューが一致している**（または本家が比較対象外・欠損で「不一致」とは呼べない）前提で付す**別種**の注意・参考に限る。

**最新プレビュー実行を正とする（実行元の優先は置かない）**:

- プレビューは **本番（EC2 ログ・`ai-spec-check`）**・**ローカル Docker（`ai-spec-check-local`／ブラウザ UI）**・**仮実行（`ai-spec-check-virtual`）**のいずれから取得してもよい。\
  **§9 の 🔴／🟡／🔵 の根拠は、当該レポート更新ターンで突き合わせに使ったプレビュー JSON と本家だけ**とする。\
  同一 URL でも**別実行の JSON を並べて「本番だけ 🔴」のように階層化しない**。
- **過去に別実行で本家不一致でも**、**より新しい実行で整合すれば当該差分は解決**。**§9 の 🔴 に旧実行の不一致だけを残さない**（必要なら **§3 の「前回実行との差」**・§6〜§8 の脚注・CursorLog に**履歴**を残す）。
- **逆に**、過去に問題がなくても**最新実行が本家と不一致なら 🔴** とする。

**DAIWA ロッド・本家にテーパー列が無い記事等**: **`infer_action_from_daiwa_model_name`**（突合 **§行別 Pattern 期待値**と整合）と\
**`rows[].action`** が**行ごとに一致しない**ときは **🔴** とする（**正本 §2.3** の **テーパー照合**または **§3**）。\
**🟡 に降格しない**（**決定関数とプレビュー値の乖離は保存品質上の問題**）。

見つけた差異は以下のいずれかに分類する:

- 🔴 **問題（保存前に修正必須）**: **本家との不一致すべて**（件数・数値・シリーズ／型番・技術特性の不足・誤付与・サマリ項目の取りこぼし等）、NOT NULL / 制約違反の懸念
- 🟡 **注意（運用判断）**: **本家一致が確認できたうえで**のマスタ整備、命名ポリシー、税抜／税込など**ページから一意に読めない**ときの方針保留、既存 DB との整合方針（不一致そのものではない注記）
- 🔵 **情報（参考）**: **本家一致**のうえでの補足、表記揺れの統合候補メモ、🔴🟡 に該当しない運用メモ（突き合わせ結果が一致している場合の付記）

## 8. 対策の優先度整理（高 / 中 / 低）

**§8 執筆前に**、上記 **「本 SKILL を Read した時点の必須（対策の練り直し）」**を満たしたうえで本節に入る。以降は形式・粒度のルールである。
