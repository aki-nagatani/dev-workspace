# 仕様書更新（プロジェクト仕様）

## 適用タイミング

- 機能・API・DB・設定・画面の**実装を変更したとき**（同じコミット／同じ作業単位で仕様を直す）
- ユーザーから**仕様書の追記・修正**を指示されたとき
- コードレビュー・調査で**仕様と実装の不一致**を見つけたとき（ユーザーの明示がなくても更新してよい範囲は下記「随時同期」）

## myrules との関係

プロジェクト共通ルールは **`dev-workspace/.cursor/rules/myrules.mdc`** の **「ドキュメント更新規律」「仕様書探索の既定パス」「ドキュメント配置方針」** に従う。本 SKILL はそのうち**仕様書（Obsidian のプロジェクト仕様）に特化した実務手順**をまとめる。

## 必須原則

- **ソースコードを修正したら、仕様書も必ず同時に更新する**（ソースと仕様の正を一致させる）
- **仕様の追記・修正は実装と同時**（「あとで仕様」と残さない）
- **仕様の置き場所は Obsidian**（`DevProject/specifications/`）。各リポジトリの `docs/` に仕様を増やさない

## 仕様書の探索

- 既定: `D:/OneDrive/アプリ/remotely-save/Obsidian/DevProject/specifications/`
- プロジェクト例:
  - FishTrack: `.../specifications/FishTrack`（起点 `INDEX.md`）
  - MyPokedex: `.../specifications/MyPokedex`（起点 `INDEX.md`）
  - おたよりナビ: `.../specifications/おたよりナビ仕様書.md`
- 実装・調査の開始時は **`AGENTS.md`** と仕様を先に確認する（各リポジトリルート）

## 更新の優先マッピング（何が変わったらどこを直すか）

| 変更の種類 | 主に直す仕様の例 |
| --- | --- |
| 画面・遷移・バリデーション | 画面仕様・UI/UX 章、受け入れシナリオ |
| ルート・HTTP・JSON | API 仕様・ルーティング章 |
| テーブル・制約・インデックス | データベース／スキーマ章（例: `06_database.md`） |
| 環境変数・設定・フラグ | 設定・デプロイに関する節 |
| 非機能（認証・権限の扱い） | 該当するセキュリティ・認証の節 |

## 記述の粒度

- **変更内容**（前後の差分が分かるように）
- **理由**（必要に応じて簡潔に）
- 同じファイル内の**他節との矛盾がないか**を確認する

## 計画書（統合作業スケジュール等）との役割分担

- **仕様書**: プロダクトの**振る舞い・データ・API の正**（タスク管理の ID に依存しない）
- **統合作業スケジュール**など: **タスク ID・進捗・完了日・ガント**（Fxx / Pxx / Oxx / Mxx / Ixx 等は**こちら側**で管理）
- **統合作業スケジュール**（タスク一覧・週次・ガント・三本柱）の具体的な更新手順: **`integrated-schedule-update` SKILL** を参照する（計画書はルール最小化。**食い違いは SKILL を正**とし、前倒し等の**メタ注記は計画書**を尊重）
- 実装完了時に**マイルストーンやチェックリストを更新する**必要があれば、計画書も合わせて更新する（myrules の「計画書の進捗状況の反映」）

## 仕様書本文に書かないもの

- **タスク番号・タスク ID**（例: `F16`、`P3`、`O1`、`P1-T30`）。仕様は単体で読めるドキュメントにする
- **Issue 番号だけ**を根拠にした一文（必要なら「要件の要約」や「日付」で補う）
- 変更の経緯が必要な場合は **日付・要件の要約・版**で示す（例: 「2026-03 反映: 整数 PK はサロゲートのまま、ORM で `autoincrement` を明示」）

## 仕様と実装の随時同期（AI の裁量）

- 実装と仕様の**食い違いに気づいたら**、ユーザーが明示しなくても**仕様を実装に合わせて更新してよい**（未記載の実装・誤記の修正）
- **新規ドキュメントファイルを勝手に作らない**ことは myrules の「ドキュメント作成規律」と別。既存仕様ファイルの**更新**は本ルールで随時行う

## 例外

- **リファクタのみで挙動変更がない**場合、仕様変更は任意（ただし設計の前提が変わるなら更新推奨）

## 関連 SKILL（併用）

- **`integrated-schedule-update`**: `統合作業スケジュール.md` の編集・三本柱・ガント
- **`markdown-editing`**: Markdown の構造・Markdownlint（行長・表・見出し等）
- **`markdownlint-fix`**: 指摘された MD0xx の修正フロー
- **`obsidian-cursor-log`**: 作業完了時の CursorLog 追記（ファイル変更時は myrules 通り）
- **`obsidian-update-rules`**: Obsidian ノートのタグ・Wiki リンク方針（仕様書が該当する場合）

## 編集後の確認（推奨）

- `dev-workspace/.markdownlint.json` に基づき、変更した `.md` を **`markdownlint-cli` または `markdownlint-cli2`** で確認する（環境で利用している CLI に合わせる）
