# Obsidian作業ログ（Cursor）

## 報告前の必須アクション（記録漏れ防止）
**ファイルを変更した作業を完了した場合**は、**ユーザーに報告する前に必ず**本SKILLに従い CursorLog を更新すること。報告文の末尾に「CursorLogは更新しました」と明記する。これを省略すると記録漏れとなる。

## 基本ルール
- 保存先は `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM-DD.md`（JST）
- **ログファイルの日付（YYYY-MM-DD）は、追記する時点の「現在の日付（JST）」を使う。** 前日や別の日付のファイルを開いていても、追記先は必ず「今」の日付のファイルとする。0時を過ぎている場合は当日（新しい日付）のファイルに追記し、誤って前日のファイルに書かないこと。
- 先頭にタグ行を置く（`#obsidian`は禁止）
- **タグは作業内容に応じて適宜追加する**
- タイムスタンプは `HH:mm:ss`（JST）。**必ずその時点の実時刻を記載する**。プレースホルダー（`--:--:--` 等）・仮の時刻・固定値の使用は**禁止**。
- 粒度はSlack最終報告の項目に合わせる
- **ファイルを変更しない場合は、ログの更新は不要**
- **追記は基本的にファイルの最下部に行う**（ログの内容が時系列で並ぶようにする。新しい作業は常に末尾に追加する）

## 記録手順

### 🚨 タイムスタンプ（実時刻）の必須手順（失敗防止）
**ログを追記する直前に、必ず以下を実行すること。省略禁止。**

1. **現在時刻（JST）を取得する**  
   ターミナルで以下いずれかを実行し、表示された `HH:mm:ss` をそのまま使う。
   - **PowerShell（推奨）**:
     ```powershell
     [TimeZoneInfo]::ConvertTimeFromUtc((Get-Date).ToUniversalTime(), [TimeZoneInfo]::FindSystemTimeZoneById('Tokyo Standard Time')).ToString('HH:mm:ss')
     ```
   - **Python**: `datetime.now(timezone(timedelta(hours=9))).strftime('%H:%M:%S')` 等
2. **取得した値をエントリ先頭の `HH:mm:ss` にそのまま記載する**。推測・仮の値は使わない。
3. **禁止**: `--:--:--`、`00:00:00` 等のプレースホルダー、または「だいたいこの頃」などの仮の時刻で書かない。

### 記録の流れ
1. **現在の日付（JST）を取得し、その日付のログファイル（YYYY-MM-DD.md）を開く（なければ作成）。** 日付の取り違え防止のため、追記の直前に日付を取得すること。0時過ぎは「当日」のファイルを使用する。
2. **上記「タイムスタンプの必須手順」に従い、現在時刻（JST）を取得する**
3. 先頭にタグ行を置く（内容に応じてタグ追加）
4. **ファイルの最下部**に、取得した `HH:mm:ss` を用いて以下の形式で追記する（`作業ログ:` セクションがある場合はその直下の末尾、またはファイル末尾。時系列を保つため新規エントリは常に最下部に追加）

### 推奨フォーマット構造
```
- HH:mm:ss [作業名]
  - 作業名: [何をしたか]
  - プロジェクト名: [プロジェクト名]
  - 変更ファイル: [ファイル数] ([主要なファイル名、詳細がある場合は説明])
  - 実施内容: [実施内容の詳細説明 - 技術的な詳細、使用した技術、設計判断など]
  - 結果: [結果・動作確認結果 - テスト結果、パフォーマンス改善、影響範囲など]
  - 未解決/保留: [あれば]
```

### 含めるべき情報
1. **作業名**: 何をしたか（必須）
2. **プロジェクト名**: どのプロジェクトか（MyHobbySite、FishTrack、MyPokedex、dev-workspaceなど）
3. **変更ファイル**: ファイル数と主要なファイル名（長い場合は省略または代表的なもの）
4. **実施内容**: 何を実施したかの詳細説明
   - 技術的な詳細（使用したライブラリ、フレームワークなど）
   - 設計判断やアーキテクチャの変更
   - 修正内容の詳細
5. **結果**: 動作確認結果、テスト結果、パフォーマンス改善、エラーや警告の有無、本番環境への影響など

### メッセージの構成比率（目安）
- **作業名**: 約20-30文字（5%）
- **プロジェクト名**: 約20-40文字（5-10%）
- **変更ファイル**: 約50-100文字（12-25%）
- **実施内容**: 約150-200文字（40-50%）
- **結果**: 約100-150文字（25-40%）

### メッセージ例
**例: 機能追加**
```
- 14:30:15 ユーザー認証機能を実装
  - 作業名: 機能追加 - ユーザー認証機能を実装
  - プロジェクト名: MyPokedex
  - 変更ファイル: 10ファイル（routes.py, models.py, forms.py, services/auth_service.py, templates/login.html等）
  - 実施内容: ユーザー認証機能を実装。ログイン/ログアウト/パスワードリセット機能を追加。Flask-Loginを使用してセッション管理を実装。パスワードハッシュ化も実装（bcrypt使用）。CSRF保護も追加。UIはBootstrapを使用してモダンなデザインに。レスポンシブ対応も実施。
  - 結果: 機能実装完了、テストも追加（認証機能のテストカバレッジ95%達成）。動作確認済み。セキュリティテストも実施。ドキュメントも更新。
  - 未解決/保留: なし
```

### 実装時の注意点
1. **情報の優先順位**: 重要な情報を優先的に含める
2. **読みやすさ**: 改行を適切に使用して読みやすくする
3. **省略の判断**: 
   - ファイル名が長すぎる場合は主要なものだけ記載
   - ファイルが多い場合は「等」で省略
   - 技術的な詳細は重要なものだけ記載
4. **エラー情報**: エラーが発生した場合は必ず含める
5. **数値の記載**: パフォーマンス改善などは具体的な数値を含める（例：70%削減、2秒→1秒）

## 作業完了報告テンプレート（推奨）

**ファイルを変更した作業を完了した際は、以下のテンプレートを使用して報告することを推奨：**

```
【作業完了報告】
✅ 作業完了: [作業名]
- 変更ファイル: [ファイル数と主要ファイル名]
- 実施内容: [簡潔な説明]
- 結果: [動作確認結果、テスト結果など]
- ✅ CursorLogは更新しました
```

**テンプレート使用のメリット**:
- 報告時に必ずCursorLog更新の確認が含まれる
- 報告内容が標準化され、確認しやすくなる
- 忘れにくくなる

## 実装上の注意
- **追記位置**: 新規エントリは必ずファイルの最下部に追加する。既存の「作業ログ」セクション内で追記する場合も、そのセクション内の末尾（ファイル最下部に近い位置）に追加し、時系列が保たれるようにする
- 既存の見出しや構造は維持し、最小限の追記で完結させる
- タグは先頭にまとめ、末尾には置かない
