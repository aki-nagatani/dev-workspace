# Obsidian作業ログ（Cursor）

## 報告前の必須アクション（記録漏れ防止）

**ファイルを変更した作業を完了した場合**は、**ユーザーに報告する前に必ず**本SKILLに従い CursorLog を更新すること。報告文の末尾に「CursorLogは更新しました」と明記する。これを省略すると記録漏れとなる。

## 基本ルール

- **Markdown編集時**: CursorLog（.md）を編集する際は、`markdown-editing` SKILLのルールに従う
- 保存先は `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM/YYYY-MM-DD.md`（JST）。月ごとのフォルダ（YYYY-MM）に日付ファイルを格納する。フォルダが存在しない場合は作成する。
- **ログファイルの日付（YYYY-MM-DD）は、追記する時点の「現在の日付（JST）」を使う。** 前日や別の日付のファイルを開いていても、追記先は必ず「今」の日付のファイルとする。0時を過ぎている場合は当日（新しい日付）のファイルに追記し、誤って前日のファイルに書かないこと。
- **タグはファイルの先頭1行にのみ記載する**（`#obsidian`は禁止）。エントリの直後やログの途中にタグを書かない。新規タグが必要な場合は、ファイル先頭のタグ行に追記する（既存タグと重複しなければ追加）。
- **タグは作業内容に応じて適宜、先頭行に追加する**
- タイムスタンプは `HH:mm:ss`（JST）。**必ずその時点の実時刻を記載する**。プレースホルダー（`--:--:--` 等）・仮の時刻・固定値の使用は**禁止**。
- 粒度はSlack最終報告の項目に合わせる
- **ファイルを変更しない場合は、ログの更新は不要**
- **時系列順を厳守する**（HH:mm:ss の昇順で並べる。エントリは必ず時刻順に並んでいること）
- **追記時は適切な位置に挿入する**
  - 通常はファイル最下部に追記（新規エントリの時刻が既存の最末尾より後なら、そのまま末尾に追加）
  - **後から記録する場合**（複数作業をまとめて記録するなど）、時刻順になるよう**正しい位置に挿入**する。単純に末尾追加で時系列が崩れる場合は挿入位置を調整する
  - 追記後に時系列が乱れていないか確認する

## 記録手順

### 🚨 タイムスタンプ（実時刻）の必須手順（失敗防止）

**ログを追記する直前に、必ず以下を実行すること。省略禁止。**

1. **現在時刻（JST）を取得する**  
   ターミナルで以下いずれかを実行し、表示された `HH:mm:ss` をそのまま使う。
   - **PowerShell（推奨）**:

     ```powershell
     [TimeZoneInfo]::ConvertTimeFromUtc((Get-Date).ToUniversalTime(), [TimeZoneInfo]::FindSystemTimeZoneById('Tokyo Standard Time')).ToString('HH:mm:ss')
     ```

   - **Python**: `datetime.now(timezone(timedelta(hours=9))).strftime('%H:%M:%S')` 等
2. **取得した値をエントリ先頭の `HH:mm:ss` にそのまま記載する**。推測・仮の値は使わない。
3. **禁止**: `--:--:--`、`00:00:00` 等のプレースホルダー、または「だいたいこの頃」などの仮の時刻で書かない。

### 記録の流れ

1. **現在の日付（JST）を取得し、その日付のログファイルを開く（なければ作成）。** パスは `CursorLog/YYYY-MM/YYYY-MM-DD.md`。月フォルダ（YYYY-MM）が無ければ作成する。日付の取り違え防止のため、追記の直前に日付を取得すること。0時過ぎは「当日」のファイルを使用する。
2. **上記「タイムスタンプの必須手順」に従い、現在時刻（JST）を取得する**
3. **タグはファイル先頭1行にのみ記載**。ファイルが新規の場合は先頭にタグ行を置く。既存ファイルの場合は、必要なタグが先頭行に無ければ先頭行に追記する。エントリの直後やログ本文中にタグを書かない。
4. **適切な位置**に、取得した `HH:mm:ss` を用いて以下の形式で追記する  
   - 新規エントリの時刻が既存の最末尾より後なら、ファイル最下部に追加  
   - 後から記録する作業で、時刻が既存エントリの間に入る場合は、時系列順になる位置に挿入する  
   - 追記後、HH:mm:ss が昇順になっているか確認する
5. **Lint検証（必須）**: 追記完了後、markdownlint で検証し、**エラーを残さない**  
   - dev-workspace をカレントにし、`npx markdownlint-cli -c .markdownlint.json "対象CursorLogファイルの絶対パス"` を実行  
   - MD013（行長150文字超）等のエラーが出た場合は、`markdown-editing` SKILL に従って修正する（句読点・括弧前で改行、リスト継続は4スペース）  
   - 修正後、再検証してエラーゼロであることを確認してから完了とする

### 推奨フォーマット構造

```markdown
- HH:mm:ss [作業名]
  - 作業名: [何をしたか]
  - プロジェクト名: [プロジェクト名]
  - 変更ファイル: [ファイル数] ([主要なファイル名、詳細がある場合は説明])
  - 実施内容: [実施内容の詳細説明 - 技術的な詳細、使用した技術、設計判断など]
  - 結果: [結果・動作確認結果 - テスト結果、パフォーマンス改善、影響範囲など]
  - 未解決/保留: [あれば]
```

### 含めるべき情報

1. **作業名**: 何をしたか（必須）
2. **プロジェクト名**: どのプロジェクトか（MyHobbySite、FishTrack、MyPokedex、dev-workspaceなど）
3. **変更ファイル**: ファイル数と主要なファイル名（長い場合は省略または代表的なもの）
4. **実施内容**: 何を実施したかの詳細説明
   - 技術的な詳細（使用したライブラリ、フレームワークなど）
   - 設計判断やアーキテクチャの変更
   - 修正内容の詳細
5. **結果**: 動作確認結果、テスト結果、パフォーマンス改善、エラーや警告の有無、本番環境への影響など

### メッセージの構成比率（目安）

- **作業名**: 約20-30文字（5%）
- **プロジェクト名**: 約20-40文字（5-10%）
- **変更ファイル**: 約50-100文字（12-25%）
- **実施内容**: 約150-200文字（40-50%）
- **結果**: 約100-150文字（25-40%）

### メッセージ例

#### 例: 機能追加

```markdown
- 14:30:15 ユーザー認証機能を実装
  - 作業名: 機能追加 - ユーザー認証機能を実装
  - プロジェクト名: MyPokedex
  - 変更ファイル: 10ファイル（routes.py, models.py, forms.py, services/auth_service.py, templates/login.html等）
  - 実施内容: ユーザー認証機能を実装。ログイン/ログアウト/パスワードリセット機能を追加。Flask-Loginを使用してセッション管理を実装。パスワードハッシュ化も実装（bcrypt使用）。CSRF保護も追加。UIはBootstrapを使用してモダンなデザインに。レスポンシブ対応も実施。
  - 結果: 機能実装完了、テストも追加（認証機能のテストカバレッジ95%達成）。動作確認済み。セキュリティテストも実施。ドキュメントも更新。
  - 未解決/保留: なし
```

### 実装時の注意点

1. **情報の優先順位**: 重要な情報を優先的に含める
2. **読みやすさ**: 改行を適切に使用して読みやすくする
3. **省略の判断**:
   - ファイル名が長すぎる場合は主要なものだけ記載
   - ファイルが多い場合は「等」で省略
   - 技術的な詳細は重要なものだけ記載
4. **エラー情報**: エラーが発生した場合は必ず含める
5. **数値の記載**: パフォーマンス改善などは具体的な数値を含める（例：70%削減、2秒→1秒）

## 作業完了報告テンプレート（推奨）

**ファイルを変更した作業を完了した際は、以下のテンプレートを使用して報告することを推奨：**

```markdown

- 変更ファイル: [ファイル数と主要ファイル名]

```

### テンプレート使用のメリット

- 報告時に必ずCursorLog更新の確認が含まれる
- 報告内容が標準化され、確認しやすくなる
- 忘れにくくなる

## 実装上の注意

- **時系列優先**: エントリは HH:mm:ss の昇順で並べること。新規エントリの時刻が既存末尾より後なら末尾に追加。後から記録する作業で時刻が途中になる場合は、正しい位置に挿入する（単純に末尾追加のみでは不十分な場合あり）
- **追記位置**: 原則はファイル最下部に追記。ただし時系列が崩れる場合は、該当時刻の直後へ挿入する
- **Lintエラーを残さない**: 追記・修正後は markdownlint で検証し、MD013 等のエラーが出た場合は必ず修正してから完了とする
- 既存の見出しや構造は維持し、最小限の追記で完結させる
- **タグはファイル先頭の1行にのみ記載する。** エントリの直後・ログ本文中・末尾にタグを書かない。新規タグは先頭のタグ行に追記する。
