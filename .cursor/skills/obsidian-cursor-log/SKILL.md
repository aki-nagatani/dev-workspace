# Obsidian作業ログ（Cursor）

## 報告前の必須アクション（記録漏れ防止）

**ワークスペース内のファイルを追加・更新・削除した作業を完了した場合**
（**`StrReplace` / `Write` / `Delete` / `EditNotebook`** 等。旧ドキュメントの `write` / `search_replace` / `edit_file` と同義）は、
**ユーザーに報告する前に必ず**本SKILLに従い CursorLog を更新すること。

報告文の末尾に「CursorLogは更新しました」と明記する。省略すると記録漏れとなる。
**追記するエントリの「使用AIモデル」行は、記入直前に当該チャットのモデル選択と照合し、誤ったモデル名のままにしないこと。**

### 記録漏れの典型原因（対策の観点）

- **会話要約（summarize）**や長文の打ち切りのあと、「報告直前の自己チェック（CursorLog 更新したか？）」が文脈から消え、次の応答でコード変更が未記録のままになる。
- **「完了」や成果報告の文面**を**先に**心の中・下書きで作り、**CursorLog 追記を同じ最終返答の後回し**にする（**順序の逆転**。**myrules**「**取り扱い終了文の前ゲート**」で禁止）
- 実装に集中し、**本 SKILL を参照せず**に **`StrReplace` / `Write` 等の連打**で終える。
- **チェックリストとツール名の不一致**: ルール文面が旧ツール名だけだと、**自分の操作が「ログ対象」だと結びつかず**漏れる。
    dev-workspace **myrules** は **`StrReplace` / `Write` / `Delete` / `EditNotebook`** を明示していること。
- **対策**: 各プロジェクトの **AGENTS.md** に「コード変更完了時は CursorLog」を短く載せる（dev-workspace の
    **myrules** の「記録漏れが起きやすい状況」参照）、**報告の直前**に必ず Obsidian 側を更新する。成果を**ユーザーに文で述べ始める前**に、
    **同一応答内で** log 用 `Write` / `StrReplace` を**済ませる**（**前ゲート**）

**残作業・課題の記載（推奨・強く推奨）**: マイルストーン区切り、長めのセッションの終わり、またはユーザーが明示したときは、同一日のログに **`### 残作業・課題`** 見出し付きの箇条書きを追記する。内容は次を含めてよい（当日の文脈で重要なものに絞る。詳細は統合作業スケジュール・Issue・仕様のリンクで足りる）。

- 未着手・進行中の実装・調査（タスクIDや簡潔な説明）
- 運用面の保留（例: 通知の一時停止、デプロイ待ち）
- 技術的負債・テスト・カバレッジで次に触るべきこと
- ユーザー・ステークホルダ判断待ち

単純な1ファイル修正のみで引き継ぎ事項がゼロなら、「残作業・課題: なし」と1行でよい。

## 基本ルール

- **Markdown編集時**: CursorLog（.md）を編集する際は、`markdown-editing` SKILLのルールに従う
- 保存先は `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM/YYYY-MM-DD.md`（JST）。月ごとのフォルダ（YYYY-MM）に日付ファイルを格納する。フォルダが存在しない場合は作成する。
- **ログファイルの日付（YYYY-MM-DD）は、追記する時点の「現在の日付（JST）」を使う。** 前日や別の日付のファイルを開いていても、追記先は必ず「今」の日付のファイルとする。0時を過ぎている場合は当日（新しい日付）のファイルに追記し、誤って前日のファイルに書かないこと。
- **タグはファイル先頭（**最初の `##` 作業エントリより前**）にのみ置く**（`#obsidian`は禁止）。\
    **1行に詰め込まず、意味・プロジェクトなどで分けて複数行にしてよい**（各行は短く保つ）。\
    **markdownlint MD018** のため、行頭を `#tag` の裸にせず **`- #tag #tag2 …`** の箇条書き行にまとめる（Obsidian でもタグとして通常認識される）。\
    エントリの直後・本文中・末尾にタグを書かない。新規タグはいずれかの**先頭タグ行**に追記する。
- **タグは作業内容に応じて適宜、先頭ブロックのいずれかの行に追加する**
- **タグは重複しないこと（必須）**: 同一ファイル内で**同じタグを複数回書かない**。追記前に先頭ブロック全行を走査し、**既出タグは再掲しない**（別の行に重複記載も禁止）。\
    大文字小文字・全角半角の違いも同一タグとみなし、表記を揃える（例: `#FishTrack` と `#fishtrack` を混在させない）。\
    既に重複がある場合は、同じ編集セッションで**重複を除去**してから完了する。
- タイムスタンプは `HH:mm:ss`（JST）。**必ずその時点の実時刻を記載する**。プレースホルダー（`--:--:--` 等）・仮の時刻・固定値の使用は**禁止**。
- **使用AIモデル（必須・毎回確認）**: エントリを書く**そのチャット**で、ユーザーが Cursor のモデル選択で指定している名称を記載する。**追記のたびに**（1）チャットヘッダ／モデルピッカー等で**実際のモデル名を確認**し、（2）ユーザーが会話内でモデル名を明示していればそれを優先する。\
    **禁止**: テンプレ・前のエントリ・別セッションからの流用、推測、またはエージェントの内部モデル名をそのまま機械的に書くこと。**判別できないとき**は **「不明」** または **「（チャットUIで確認）」** とし、空欄にしない。
- 粒度はSlack最終報告の項目に合わせる
- **エントリの長さ**: **`## HH:mm:ss [作業名]` 1件あたり、本文を含め概ね30行以内**に収める（長いコマンド・パス列は `\` 改行や代表ファイル名への省略で短縮）。超える場合は**エントリを分割**（別時刻で続き）するか、**詳細はリポジトリ・Issue・仕様への参照**に任せ、ログでは要約のみにする。
- **ファイルを変更しない場合は、ログの更新は不要**
- **時系列順を厳守する**（HH:mm:ss の昇順で並べる。エントリは必ず時刻順に並んでいること）
- **追記時は適切な位置に挿入する**
  - 通常はファイル最下部に追記（新規エントリの時刻が既存の最末尾より後なら、そのまま末尾に追加）
  - **後から記録する場合**（複数作業をまとめて記録するなど）、時刻順になるよう**正しい位置に挿入**する。単純に末尾追加で時系列が崩れる場合は挿入位置を調整する
  - 追記後に時系列が乱れていないか確認する
- **エントリ見出し形式（必須）**: 各エントリの先頭は **`## HH:mm:ss [作業名]`** の見出し形式で統一する。リスト形式（`- HH:mm:ss`）は使用しない。

## 記録手順

### 🚨 日本語 UTF-8 ファイルへの破壊的操作の禁止（文字化け防止）

**CursorLog（および Obsidian vault 配下の日本語 .md ファイル）は BOM なし UTF-8 で保存されている。以下の操作は文字化けで全文破壊する可能性があるため、**絶対に使用しない**。**

**禁止**:

- PowerShell の **`Get-Content -Raw` でファイル全体を読み込み、`[System.IO.File]::WriteAllText` / `Set-Content` で書き戻す** パターン。\
    日本語 Windows 既定の **`cp932`（Shift-JIS）** でファイルを読んでしまい、それを **UTF-8 として再保存**することで、全行の日本語が **mojibake**（`繧ｿ繧ｹ繧ｯ` のような文字列）化する。
- `Get-Content` / `Set-Content` を `-Encoding` 指定なしで使うこと（PowerShell 5.x の既定は **環境依存**でしばしば cp932）。
- PowerShell の `>`・`>>` リダイレクトで **日本語テキスト**を既存ファイルへ追記すること（出力エンコーディングが cp932 になり得る）。
- PowerShell のヒアドキュメント（`@"…"@`）で日本語を含む **ファイル生成**（`commit-message` SKILL に沿って Python で書く）。

**推奨**:

1. 編集は **`StrReplace` ツール**を最優先で使う（エンコーディングを意識しない。差分だけを変更する）。
2. 末尾改行の付与・整形など **バイナリレベルの確定操作**が必要な場合は **Python を使う**。例:

   ```bash
   python -c "
   import pathlib
   p = pathlib.Path(r'D:\OneDrive\アプリ\remotely-save\Obsidian\CursorLog\YYYY-MM\YYYY-MM-DD.md')
   data = p.read_bytes()
   if not data.endswith(b'\n'):
       p.write_bytes(data + b'\n')
   "
   ```

3. どうしても PowerShell を使うなら、**読み書きとも `-Encoding utf8NoBOM`**（PS7+）または\
   `[System.IO.File]::ReadAllText(path, [System.Text.UTF8Encoding]::new($false))` / `WriteAllText` の\
   **両方**で UTF-8 を明示する（片方だけ明示は最も危険）。

**事故検知**: 編集後に `python -c "print(open(path,'rb').read()[:200])"` でバイト列先頭を確認し、\
**`繧`・`縺`・`\uf8f0`・`\x80`** のような Shift-JIS → UTF-8 二重解釈由来のバイト列が出たら **即座に中断**し、\
**Obsidian vault は git 管理外のため OneDrive のバージョン履歴から復元**する（`.md` を右クリック → 「バージョン履歴」）。

**過去事故（2026-04-20）**: `[System.IO.File]::WriteAllText($path, (Get-Content -Raw $path) + "\`n", …)` で `2026-04-20.md` 全文を破壊。git なし・OneDrive 復元が必要になった。

### 🚨 タイムスタンプ（実時刻）の必須手順（失敗防止）

**ログを追記する直前に、必ず以下を実行すること。省略禁止。**

1. **現在時刻（JST）を取得する**  
   ターミナルで以下いずれかを実行し、表示された `HH:mm:ss` をそのまま使う。
   - **PowerShell（推奨）**:

     ```powershell
     [TimeZoneInfo]::ConvertTimeFromUtc((Get-Date).ToUniversalTime(), [TimeZoneInfo]::FindSystemTimeZoneById('Tokyo Standard Time')).ToString('HH:mm:ss')
     ```

   - **Python**: `datetime.now(timezone(timedelta(hours=9))).strftime('%H:%M:%S')` 等
2. **取得した値をエントリ先頭の `HH:mm:ss` にそのまま記載する**。推測・仮の値は使わない。
3. **禁止**: `--:--:--`、`00:00:00` 等のプレースホルダー、または「だいたいこの頃」などの仮の時刻で書かない。

### 🚨 タグ追記の必須手順（重複防止）

**タグを追記・新規作成する直前に、必ず以下を実行する。省略禁止。**

1. **先頭ブロック全体を Read する**（末尾や差分だけを見ない）。\
   対象は `# YYYY-MM-DD` 直後から最初の `## HH:mm:ss` 直前までの **`- #tag …` の全行**。
2. **既存タグを列挙する**。目視で拾う前に、以下の抽出コマンドで機械的に一覧化してもよい。

   ```powershell
   Select-String -Path "<CursorLogファイルの絶対パス>" -Pattern '(?<!\S)#\S+' -AllMatches |
     ForEach-Object { $_.Matches.Value } | Sort-Object -Unique
   ```

3. **新規追加候補と逐一突合する**。既出のものは**捨てる**（別の行に再掲も禁止）。\
   大文字小文字・全角半角は同一タグとみなし、表記を揃える。
4. **特に注意**するタグ（重複頻度が高い）:
   - **プロジェクト名タグ**: `#MyPokedex` / `#FishTrack` / `#otayori-navi` / `#dev-workspace` / `#MyHobbySite` / `#personal-tools`
   - **汎用カテゴリタグ**: `#bugfix` / `#refactoring` / `#pull-request` / `#CursorLog` / `#housekeeping` / `#仕様書` / `#テスト`
5. **完了条件**: 追記後、先頭ブロックのタグを再度抽出し、**完全一致の重複が 0 件**であることを確認してから完了とする（上記抽出コマンドの結果行数と、ソート前の全出現回数が一致すれば重複なし）。

### 🚨 使用AIモデル（毎回確認）の必須手順

**ログ本文に `- 使用AIモデル:` を書く直前に、必ず以下を行う。省略禁止。**

1. **当該チャット**で実際に使われているモデルを確認する（Cursor のモデル表示・会話内のユーザー明示を参照）。
2. **その名称をそのまま**（例: `Composer2`、`GPT-5.4`、`Claude Opus 4.7` 等、UI に表示される表記に合わせる）を1行に記載する。
3. **禁止**: テンプレの例文・直前のエントリ・システムメッセージに出るモデル名を**確認なしで**コピーすること。セッションやチャットが変わるとモデルも変わるため、**毎エントリで再確認**する。
4. ユーザーが「Composer2 を指定した」と言及している場合は、それを正とする。
5. どうしても確信が持てないときだけ **「不明」** または **「（チャットUIで確認）」** とし、空欄にしない。

### 記録の流れ

1. **現在の日付（JST）を取得し、その日付のログファイルを開く（なければ作成）。** パスは `CursorLog/YYYY-MM/YYYY-MM-DD.md`。月フォルダ（YYYY-MM）が無ければ作成する。日付の取り違え防止のため、追記の直前に日付を取得すること。0時過ぎは「当日」のファイルを使用する。
2. **上記「タイムスタンプの必須手順」に従い、現在時刻（JST）を取得する**
3. **上記「使用AIモデル（毎回確認）の必須手順」に従い、当該チャットのモデル名を確定する**（`- 使用AIモデル:` を書く直前でもよいが、**記載前に必ず実施**する）
4. **タグはファイル先頭ブロック（日付見出し直後～最初の `##` より前）にのみ記載**。複数行に分け、各行は **`- #tag …`** の箇条書きとする（**MD018** 防止）。ファイルが新規の場合は `# YYYY-MM-DD` の直後に空行を挟みタグの箇条書きを置く。既存ファイルの場合は、必要なタグを先頭ブロックのいずれかの行に追記する。エントリの直後やログ本文中にタグを書かない。\
   **上記「🚨 タグ追記の必須手順（重複防止）」に従い**、先頭ブロック全体を Read → 既存タグ抽出 → 新規候補と突合 → 完了後の重複ゼロ確認を実施する（**重複禁止**。大文字小文字・全角半角は同一タグとみなす）。既に重複があれば、同じ編集セッションで除去する。
5. **適切な位置**に、取得した `HH:mm:ss` を用いて以下の形式で追記する  
   - 新規エントリの時刻が既存の最末尾より後なら、ファイル最下部に追加  
   - 後から記録する作業で、時刻が既存エントリの間に入る場合は、時系列順になる位置に挿入する  
   - 追記後、HH:mm:ss が昇順になっているか確認する
6. **Lint検証（必須）**: 追記完了後、markdownlint で検証し、**エラーを残さない**  
   - dev-workspace をカレントにし、`npx markdownlint-cli2 -c "<対象ボールトの .markdownlint.json>" "対象CursorLogファイルの絶対パス"` を実行（**Obsidian 側の設定が正本**のことが多い）  
   - **同一ファイルの lint は一括で直す**: ユーザーが **1 行・1 エラーコードだけ**指定した場合でも、当該 `.md` を触る作業の\
       **完了条件は `Summary: 0 error(s)`**。既存の別行の MD013 等が残っていれば、**同じ編集セッションでまとめて解消**する（\
       `markdownlint-fix` SKILL の「同ファイルのエラー一括」と同趣旨）。**例外**: ユーザーが「この行だけ」「他は触らない」と明示したときはその範囲に従う。  
   - MD013（行長超過）等のエラーが出た場合は、`markdown-editing` / `markdownlint-fix` SKILL に従って修正する（句読点・括弧前で改行、リスト継続は4スペース）  
   - 修正後、再検証してエラーゼロであることを確認してから完了とする

### CursorLog 編集時の再発防止（「一部だけ解消」が起きうる理由と対策）

**起きうる理由**: 依頼・会話・IDE の診断が **特定の 1 行**に限定して見えると、エージェントが **その行だけ**を直し、\
`markdownlint-cli2` を **編集したファイル全体**に対して実行せずに完了してしまう。`ReadLints` は表示が片側に偏ることがあるため、\
**行単位の表示だけを正本にしない。**

**必須の対策（省略禁止）**:

1. **CursorLog の当該 `.md` を 1 文字でも変更したら**、**必ず**そのファイルの **絶対パス**を引数に\
   `markdownlint-cli2` を実行する（対象ボールトの `.markdownlint.json` を `-c` で渡す）。  
2. **完了条件**は **CLI 出力の `Summary: 0 error(s)`** のみ。1 行直した時点では完了としない。  
3. エントリの **「テスト結果」**に「当該行の MD013 解消」**のみ**と書き、同一ファイルに別行の違反が残る状態で終了**しない**。  
4. 直前のエントリで「残存」と書いた行があれば、**同じ編集セッションで**まとめて解消するか、続けて解消するエントリを立てる。

### 推奨フォーマット構造

各エントリは **見出し形式 `## HH:mm:ss [作業名]`** で始め、続けてリスト形式で詳細を記載する。

```markdown
## HH:mm:ss [作業名]

- 作業名: [何をしたか]
- プロジェクト名: [プロジェクト名]
- 使用AIモデル: [当該チャットで実際に選ばれているモデル。**追記のたびに**UI／会話で確認。テンプレや前エントリからの流用禁止。不明なら「不明」または「（チャットUIで確認）」]
- 変更ファイル: [ファイル数] ([主要なファイル名、詳細がある場合は説明])
- 実施内容: [実施内容の詳細説明 - 技術的な詳細、使用した技術、設計判断など]
- 結果: [結果・動作確認結果 - テスト結果、パフォーマンス改善、影響範囲など]
- 残作業・課題: [次セッション引き継ぎ。なければ「なし」。箇条書きが長いときはエントリ内に `### 残作業・課題` を別設けしてよい]
```

### 含めるべき情報

1. **作業名**: 何をしたか（必須）
2. **プロジェクト名**: どのプロジェクトか（MyHobbySite、FishTrack、MyPokedex、dev-workspaceなど）
3. **使用AIモデル**: 当該チャットで使ったモデル（必須）。**毎回、追記直前に** Cursor のモデル表示または会話内のユーザー明示と照合する。\
    表示名称をそのまま記載（例: **Composer2**、**GPT-5.4**）。**テンプレ・直前エントリ・システム文言のモデル名を、確認なしで書かない。**\
    ユーザーが明示したモデルがあればそれを優先。判別できないときは **「不明」** または **「（チャットUIで確認）」** とし、空欄にしない
4. **変更ファイル**: ファイル数と主要なファイル名（長い場合は省略または代表的なもの）
5. **実施内容**: 何を実施したかの詳細説明
   - 技術的な詳細（使用したライブラリ、フレームワークなど）
   - 設計判断やアーキテクチャの変更
   - 修正内容の詳細
6. **結果**: 動作確認結果、テスト結果、パフォーマンス改善、エラーや警告の有無、本番環境への影響など
7. **残作業・課題**: 引き継ぎ事項（タスクID・優先度・判断待ち・運用停止など）。なければ「なし」

### メッセージの構成比率（目安）

**行数**: 上記「基本ルール」のとおり、**1エントリは概ね30行以内**を目安とする（見出し・リスト・空行を含む）。

- **作業名**: 約20-30文字（5%）
- **プロジェクト名**: 約20-40文字（5-10%）
- **使用AIモデル**: 約10-40文字（3-8%）
- **変更ファイル**: 約50-100文字（12-25%）
- **実施内容**: 約150-200文字（40-50%）
- **結果**: 約100-150文字（25-40%）

### 実装時の注意点

1. **情報の優先順位**: 重要な情報を優先的に含める
2. **読みやすさ**: 改行を適切に使用して読みやすくする
3. **省略の判断**:
   - **30行を超えそうなとき**は、実施内容・結果を箇条書きで圧縮するか、エントリを分ける
   - ファイル名が長すぎる場合は主要なものだけ記載
   - ファイルが多い場合は「等」で省略
   - 技術的な詳細は重要なものだけ記載
4. **エラー情報**: エラーが発生した場合は必ず含める
5. **数値の記載**: パフォーマンス改善などは具体的な数値を含める（例：70%削減、2秒→1秒）

## 実装上の注意

- **日本語 UTF-8 ファイルの破壊防止**: `Get-Content -Raw` + `Set-Content` / `WriteAllText` で\
    **ファイル全体を読み書きし直すパターンは禁止**。差分編集は `StrReplace`、末尾改行などのバイナリ確定は\
    **Python の `write_bytes`** を使う（詳細は本 SKILL **「🚨 日本語 UTF-8 ファイルへの破壊的操作の禁止」**）。
- **使用AIモデル**: タイムスタンプと同様、**毎エントリで再確認**する。チャットを切り替えた・モデルを変えた直後の追記では特に誤記が起きやすい。
- **エントリ長（30行目安）**: 追記後に行数を確認し、超える場合は省略・分割・参照に置き換える（詳細は `markdown-editing` の MD013 対策と両立させる）。
- **時系列優先**: エントリは HH:mm:ss の昇順で並べること。新規エントリの時刻が既存末尾より後なら末尾に追加。後から記録する作業で時刻が途中になる場合は、正しい位置に挿入する（単純に末尾追加のみでは不十分な場合あり）
- **追記位置**: 原則はファイル最下部に追記。ただし時系列が崩れる場合は、該当時刻の直後へ挿入する
- **Lintエラーを残さない**: 追記・修正後は markdownlint で検証し、MD013 等のエラーが出た場合は必ず修正してから完了とする。**同一 CursorLog ファイル内に、修正していない既存違反を残した状態で完了にしない**（上記「記録の流れ」Lint 項の「同一ファイルは一括で直す」に従う）
- 既存の見出しや構造は維持し、最小限の追記で完結させる
- **タグはファイル先頭ブロック（最初の `##` より前）にのみ記載する。** 複数行に分けてよい。エントリの直後・ログ本文中・末尾にタグを書かない。新規タグは先頭ブロックのいずれかの行に追記する。
- **タグは重複させない**: 同一ファイルの先頭ブロック内で同じタグを複数回書かない（行をまたいだ重複も禁止）。大文字小文字・全角半角は同一タグとみなす。追記前に先頭ブロックを走査し、既出タグは再掲しない。具体手順は**「🚨 タグ追記の必須手順（重複防止）」**に従う。
- **報告前の自問（必須）**:
  - [ ] 新規追加したタグ行は、先頭ブロックの**他のどの行ともタグ重複していないか？**
  - [ ] プロジェクト名タグ（`#MyPokedex` / `#FishTrack` / `#otayori-navi` 等）を**二重に書いていないか？**
  - [ ] 完了条件として、先頭ブロックの**タグ重複ゼロ**と **markdownlint `Summary: 0 error(s)`** の両方を満たしているか？
  - [ ] 編集後に **`Get-Content -Raw` + `Set-Content` / `WriteAllText`** で**全文書き戻し**をしていないか？（禁止。した場合はバイト列先頭を確認し、`繧`・`縺`・`\uf8f0` が出ていれば **OneDrive バージョン履歴から復元**する）
