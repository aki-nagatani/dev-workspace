# コードコメント記載基準

## 目的

- 可読性と保守性を上げるため、**必要十分**なコメントを記載する
- 「コードを読めば分かる説明」は避け、意図・前提・制約を短く補う
- ソースを素早く読めるよう、読解負荷が高い箇所には日本語コメントを**やや多め**に付ける

## 基本方針

- コメントは「What」より「Why/Constraint」を優先する
- 1〜3行で要点を伝える（長文化しない）
- 関数先頭や処理ブロック前に、役割がつかみやすくなる短い導入コメントを許容する
- 既存コメントと矛盾しないように更新する
- 実装変更時はコメントも同時に整合させる

## コメント量の目安

- 厳密な件数基準は設けず、**読者の理解速度が上がるか**で判断する
- 迷ったら「コメントがあると 10 秒以上理解が速くなるか」を目安に追加する
- 長い逐語説明は避けつつ、読解負荷が高いファイルでは通常よりコメント量を増やしてよい
- 特にルート処理、データ整形、複雑な条件分岐、外部I/O前後はコメント追加を優先する

## 追加すべきコメント

- **設計意図**: なぜこの実装を採ったか
- **非自明な制約**: 仕様・外部依存・データ整合性の制約
- **境界条件**: 失敗しやすい分岐や前提条件
- **運用前提**: マイグレーション・互換・安全性に関する注意
- **公開APIの意図**: `__all__` やエクスポートの理由
- **処理の見出し**: 長い関数や処理ブロックで、流れを追いやすくするための短い区切りコメント

## 追加しないコメント

- 変数代入や単純な if 文の逐語説明
- 実装と重複するだけの説明（ノイズ）
- テスト回避のためのコメント（例: `# pragma: no cover` の乱用）
- 数行ごとに機械的に付ける見出しコメント
- **計画用タスク番号**（**Fxx** / **Pxx** / **Oxx** / **Mxx** / **Ixx**）。進捗・割り当ての ID は **`Obsidian/DevProject/plans/統合作業スケジュール.md`** のみで管理し、コメントは**意図・制約（Why）**に留める（myrules「タスク番号の正本」）

## 記載ルール

- コメントは日本語で簡潔に記載する
- 日付/時刻をコメントに書く場合は実日時（JST）を使う
- TODO は「何を、なぜ、いつ判断するか」を最小限で明示する
- コメントが増える場合でも、1コメントあたりの情報は 1 トピックに絞る

## 実施手順（編集時）

1. 対象コードを読み、意図が読み取りにくい箇所を特定する
2. 既存コメントを整理（重複・古い内容を削除/修正）
3. 必要箇所に短いコメントを追加する
4. 必要に応じて、処理ブロックの前に流れをつかむための見出しコメントを追加する
5. コメントと実装の整合性を再確認する

## 出力時チェックリスト

- コメントは無くても動くが、あると理解が速くなる箇所に限定したか
- コメントの主語と対象コードが明確か
- コメントが古い仕様を示していないか
- 1ファイル内で語彙・表現が一貫しているか
- コメントを増やしすぎて、コードよりコメントを読む負担が大きくなっていないか
