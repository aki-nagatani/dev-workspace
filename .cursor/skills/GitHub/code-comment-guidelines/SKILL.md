# コードコメント記載基準

## 目的

- 可読性と保守性を上げるため、**必要十分**なコメントを記載する
- 「コードを読めば分かる説明」は避け、意図・前提・制約を短く補う
- ソースを素早く読めるよう、読解負荷が高い箇所には日本語コメントを**やや多め**に付ける

## 基本方針

- コメントは「What」より「Why/Constraint」を優先する
- 1〜3行で要点を伝える（長文化しない）
- 関数先頭や処理ブロック前に、役割がつかみやすくなる短い導入コメントを許容する
- 既存コメントと矛盾しないように更新する
- 実装変更時はコメントも同時に整合させる（**オーケストレータへ処理段の追加・並び替えをしたときは docstring と見出しも同一変更で更新**）

## メソッド／関数／クラス単位のコメント（必須）

- **すべての関数・メソッド・クラスに、先頭コメント（または docstring）を必ず付ける**。\
  対象には**プライベート関数（`_` 始まり）・ローカル関数・ラムダを除く名前付き内部関数**も含む。
- **書く内容**: **役割（その関数が何のために存在するか）**・**非自明な制約／前提**・**戻り値や副作用のうち重要なもの**を Why/Constraint 寄りに 1〜3 行で記す。\
  シグネチャから自明な引数の逐語説明は書かない（`x: int を受け取る` 等は不要）。
- **形式**:
  - **Python**: 関数・メソッド・クラス本体の先頭に **docstring**（`"""…"""`）を置く。1 行で十分なら 1 行 docstring。複雑なら要点を箇条書きにしてよいが**長文化しない**
  - **JavaScript / TypeScript**: 関数宣言・メソッド・クラスの直前に **JSDoc 風コメント**（`/** … */`）または通常の `//` コメントブロックを置く。**インライン関数式・アロー関数**でも、名前付きで使う中核ロジックには付ける
  - **その他の言語**: その言語の慣習的な docstring／ヘッダコメント形式に合わせる
- **既存コメントとの統合**: すでに役割を説明する近接コメントがある場合は、**重複させず**先頭コメント／docstring に**一本化**する
- **何を書けば足りるかの判断基準**: **シグネチャだけ見た読者が、用途・呼び出し前提・呼び出し後の状態**を 10 秒以内に把握できるか。把握できないなら不足
- **例外として極端に短い純関数**（数式的なワンライナー・自己説明的な定数返し等）は、**役割が名前から自明**であれば 1 行コメントで足りる。**省略は許容しない**
- **テストコード**: テスト関数（`test_*` / `it(...)` 等）も対象。**何を検証する観点か**を 1 行で書く（**前提条件・期待挙動の要点**）。\
  個々の `assert` ごとのコメントは不要

## コメント量の目安

- 厳密な件数基準は設けず、**読者の理解速度が上がるか**で判断する
- 迷ったら「コメントがあると 10 秒以上理解が速くなるか」を目安に追加する
- 長い逐語説明は避けつつ、読解負荷が高いファイルでは通常よりコメント量を増やしてよい
- 特にルート処理、データ整形、複雑な条件分岐、外部I/O前後はコメント追加を優先する

### 長い関数内の見出し（40行超）

**関数本体が 40 行を超える**ときは、先頭 docstring／JSDoc に加え、**論理ブロックの切れ目**に短い見出しコメントを置く（推奨・実質の下限目安）。

- **置き方**: バリデーション → データ取得 → 変換 → 永続化 → 応答組み立て、など**処理の段**が変わる直前に 1 行（長くても 2 行）。\
  **10 行ごとに機械的に付ける**のではなく、読者が「今どの段か」を追える密度にする
- **目安の密度**: 40 行超の関数では、おおむね **10〜20 行に 1 つの見出し**（全体で 2〜4 個程度）が無難。\
  単一の長い分岐だけが続く場合は、その分岐の入り口・例外経路・正常終了の前など、**迷いやすい箇所**に寄せる
- **書く内容**: ブロックの**目的**または**非自明な制約**（What の逐語説明は不要）。先頭コメントと重複する場合は見出し側を短くする
- **対象外**: 40 行以下の関数は見出し不要（先頭コメントのみで足りる）。\
  行数は**空行・コメント行を除かない素の行数**で数えてよい（厳密計測は不要・おおよそで判断）

### オーケストレータ関数（一括適用・ファサード）

**本体が `apply_*` / `handle_*` 等の委譲呼び出しの羅列**で、ロジックの大半が下位関数に分散している関数を指す。

#### よくある誤解（再発防止）

- **委譲先に docstring がある** → オーケストレータは薄くてよい、**とは限らない**
- **先頭 docstring が 1 行ある** → コメント要件を満たした、**とも限らない**（初期実装時の短い説明のまま本体だけ肥大化しているケース）
- **モジュール先頭や別関数付近の設計コメント** → オーケストレータ直上の docstring／見出しの**代替にならない**（読者が一括適用関数から追い始めるため）

#### 必須（40 行超のオーケストレータ）

1. **docstring に処理段の一覧**を書く（3〜7 段程度。箇条書き可）。\
   **初期実装時の 2〜4 段だけ**が残り、後から追加した段（releaseYear 系・lineCapacity 系・製品別分岐など）が docstring に無い状態は**不足**とみなす。
2. **順序依存がある段**は docstring または該当見出しで **Why** を 1 行書く（例: null 矯正の**後**に SL-PLANETS、PE 補完の**前**に lb レンジ）。\
   下位関数側のコメントだけに頼らない（読者はオーケストレータから上から読む）。
3. **論理ブロックの見出し**を段の切れ目に置く（上記「長い関数内の見出し」と同じ密度目安）。\
   **各 `apply_*` 行ごとの逐語コメントは不要**（ノイズ）。段の境界に 1 行で足りる。
4. **戻り値・副作用**（例: 確定した `seriesName`、マスタへコミットする条件）を docstring に含める。

#### 実装変更時の更新トリガー（同一変更で）

次のいずれかをオーケストレータ本体に入れたら、**同じ PR／同一セッション**で docstring（処理段一覧）と見出しを更新する。

- 新しい委譲呼び出し（`apply_*` 等）の追加
- 既存段の**実行順**の入れ替え
- 製品別・条件別の**新しい分岐ブロック**（elif チェーン等）

委譲先だけ docstring を足し、オーケストレータを触らないのは**禁止**。

#### レビュー時の不足判定

次のいずれかに当てはまれば、**コメント不足**として改善対象とする（docstring の有無だけでは合格にしない）。

- 本体 40 行超なのに、見出しが **2 個未満**（順序依存の説明 1 行を除く）
- docstring の処理段数が、本体の**主要段**（series 確定／行フィールド補完／releaseYear／永続化／後処理 等）を**カバーしていない**
- 読者が「今どの段か」「なぜこの順か」を、委譲先を開かずに追えない

## 追加すべきコメント

- **設計意図**: なぜこの実装を採ったか
- **非自明な制約**: 仕様・外部依存・データ整合性の制約
- **境界条件**: 失敗しやすい分岐や前提条件
- **運用前提**: マイグレーション・互換・安全性に関する注意
- **公開APIの意図**: `__all__` やエクスポートの理由
- **処理の見出し**: 長い関数や処理ブロックで、流れを追いやすくするための短い区切りコメント

## 追加しないコメント

- 変数代入や単純な if 文の逐語説明
- 実装と重複するだけの説明（ノイズ）
- テスト回避のためのコメント（例: `# pragma: no cover` の乱用）
- **行数だけを根拠にした機械的な見出し**（例: 10 行ごとに必ず 1 行コメント）。\
  **40 行超関数内の論理ブロック見出し**（上記「長い関数内の見出し」）は対象外
- **計画用タスク番号**（**Fxx** / **Pxx** / **Oxx** / **Mxx** / **Ixx**）。進捗・割り当ての ID は\
  **`Obsidian/DevProject/plans/統合作業スケジュール.md`** のみで管理し、コメントは**意図・制約（Why）**に留める（myrules「タスク番号の正本」）
- **AI 補助スペック取り込み照合レポートの「対策 N」**（例:**対策 14**・**対策 22**）。番号付きの是正履歴は **Obsidian**\
  **`DevProject/FishTrack/ai_spec_check_report.md`** の **§4／§5／§6** にのみ書き、**FishTrack `src/`・`tests/` のコメント／docstring**、および **FishTrack 仕様書**（\
  **`Obsidian/DevProject/specifications/FishTrack/`**・典型 **`05_ai_spec_import.md`**）の本文には**書かない**（経緯はレポート・コミットメッセージへ。仕様は**振る舞い・関数参照・ルール**のみ同期。**エージェント向け**: **`ai-spec-check-report`** SKILL §8.1「ソース・仕様書・対策番号」）。
- **機械検査**: **FishTrack** は **`scripts/check_source_task_ids.py`** を **`.githooks/pre-commit`** から実行し、\
  `src/`・`tests/`・`migrations/versions/` の Python に上記 ID が混入していないか検出する。SKILL の参照だけでは漏れるため、\
  **コミット前に必ず通る状態**を正とする。

## 記載ルール

- コメントは日本語で簡潔に記載する
- 日付/時刻をコメントに書く場合は実日時（JST）を使う
- TODO は「何を、なぜ、いつ判断するか」を最小限で明示する
- コメントが増える場合でも、1コメントあたりの情報は 1 トピックに絞る

## 実施手順（編集時）

1. 対象コードを読み、意図が読み取りにくい箇所を特定する
2. **対象ファイル内のすべての関数・メソッド・クラスに先頭コメント／docstring が付いているか確認**し、未記載のものは追加する（上記「メソッド／関数／クラス単位のコメント（必須）」）
3. 既存コメントを整理（重複・古い内容を削除/修正）
4. 必要箇所に短いコメントを追加する
5. **関数本体が 40 行超**なら、論理ブロックの切れ目に見出しコメントを追加する（上記「長い関数内の見出し」）
6. **オーケストレータ関数**なら、委譲先 docstring の有無に関わらず docstring の**処理段一覧**と順序制約を確認・更新する（上記「オーケストレータ関数」）
7. コメントと実装の整合性を再確認する

## 出力時チェックリスト

- **対象ファイル内のすべての関数・メソッド・クラスに先頭コメント／docstring を付けたか**
- 先頭コメントが Why/Constraint（役割・前提・制約）に寄っており、シグネチャの逐語説明になっていないか
- コメントは無くても動くが、あると理解が速くなる箇所に限定したか
- コメントの主語と対象コードが明確か
- コメントが古い仕様を示していないか
- 1ファイル内で語彙・表現が一貫しているか
- コメントを増やしすぎて、コードよりコメントを読む負担が大きくなっていないか
- **40 行超の関数**に、論理ブロック単位の見出しがあるか（機械的な行数割りではないか）
- **オーケストレータ関数**で、docstring の処理段一覧が本体の主要段と一致しているか（委譲先 docstring だけに説明が分散していないか）
- **順序依存**（null 矯正→付与、補完→prune 等）が docstring または見出しで明示されているか
- **AI 補助スペック取り込み照合の「対策 N」**がコメント／docstring・**FishTrack 仕様書**（`specifications/FishTrack/`）に無いか（番号の正本は **Obsidian** **`DevProject/FishTrack/ai_spec_check_report.md`** の §4／§5／§6 のみ）
