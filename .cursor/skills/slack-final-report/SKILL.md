# Slack最終報告前通知

## 目的
ユーザーへの最終報告前に、必ずSlackへ作業完了通知を送信する。

## 最終報告ゲート運用（必須）
**「最終報告（完了報告・調査結果・提案を含む）」は、以下のゲートを通過するまで送信してはならない。**

1. **作業完了判定**: 依頼に対する作業・保存・検証（必要ならテスト/リンター確認）まで完了
2. **Slack本文の下書き**: 変更点/影響/結果（テスト・カバレッジ等）を400字程度の所定フォーマットに整形
3. **Slack送信**: `mcp_text2slack_send_to_slack` または `send_to_slack` ツールで送信（作業途中送信は禁止）
4. **送信成功確認**: 送信成功を確認。失敗時はエラー内容を記録し、最終報告に失敗を明記
5. **最終報告**: 上記1〜4が完了した直後に、ユーザーへ最終報告を送信

**チェック基準**: 「ユーザーへ報告文を書き始めたくなった時点＝ゲートの実行タイミング」とし、Slack送信が完了するまで最終報告文は送らない。

## 必須実行フロー（最終報告前の強制チェックポイント）
**以下の手順を必ず順番に実行すること。いかなる理由があってもスキップしてはならない：**

1. **作業完了判定**: 作業が完了しているか確認（判定基準を参照）
2. **Slack通知送信**: 以下のいずれかの方法でSlackに通知を送信（優先順位順に試行）
   - **方法1（推奨）**: `mcp_text2slack_send_to_slack` または `send_to_slack` ツールを使用（まず `mcp_text2slack_send_to_slack` を試し、利用できない場合は `send_to_slack` を使用）
   - **方法2（フォールバック）**: Pythonスクリプト経由で送信（`run_terminal_cmd` ツールを使用して `python scripts/send_slack_notification.py "メッセージ"` を実行）
   - **方法3（最終手段）**: 直接HTTPリクエストで送信（`mcp_web_fetch` ツールを使用してSlack Webhook URLにPOSTリクエストを送信）
3. **送信確認**: 送信が成功したことを確認（エラーが発生した場合は記録し、次の方法を試行）
4. **最終報告**: その後、ユーザーへの最終報告を実行

**⚠️ 重要**: 
- ステップ2（Slack送信）をスキップしてはならない
- 方法1が失敗した場合は、必ず方法2を試行すること
- 方法2も失敗した場合は、方法3を試行すること
- すべての方法が失敗した場合でも、エラー内容を記録して最終報告を継続すること
- ユーザーへの最終報告の直前に実行すること
- 「状況確認」「調査」「提案」も作業完了として扱う

## 作業完了の判定基準（拡張版）
以下の**すべて**の条件を満たした場合、作業完了とみなす（**状況確認・調査も含む**）：

- ✅ ユーザーからの依頼に対する**すべての作業**が完了し、結果を報告する準備ができた時点
- ✅ 実装、修正、調査、状況確認、分析などの**すべての作業ステップ**が完了した時点
- ✅ **すべての変更ファイルの保存**が完了した時点
- ✅ リンターエラーの確認など、**必要な検証作業**が完了した時点
- ✅ 調査結果や提案をユーザーに報告する準備ができた時点
- ✅ エラーが発生した場合でも、エラー内容の報告準備ができた時点

**特に注意**:
- **複数の作業ステップがある場合、すべて完了してから送信すること**
- **作業途中での送信は禁止**（例：ファイル編集途中、複数ファイルの編集途中など）
- 「状況確認しました」などの報告も作業完了として扱う
- 「調査結果を提案します」も作業完了として扱う
- 「次のアクションを提案」も作業完了として扱う
- **これらの場合でも必ずSlack通知を送信すること**

## 実行ルール
- **必須実行**: ユーザーからの依頼に対する**すべての作業**が完了した時点で、ユーザーへの報告を行う前に必ず実行する
- **送信方法**: 以下の優先順位で試行（1つが失敗した場合は次の方法を試行）
  1. **MCP経由**: `mcp_text2slack_send_to_slack` または `send_to_slack` ツールを使用（まず `mcp_text2slack_send_to_slack` を試し、利用できない場合は `send_to_slack` を使用）
  2. **Pythonスクリプト経由**: `run_terminal_cmd` ツールを使用して `python scripts/send_slack_notification.py "メッセージ"` を実行（環境変数 `SLACK_WEBHOOK_URL` が必要）
  3. **直接HTTPリクエスト**: `mcp_web_fetch` ツールを使用してSlack Webhook URLにPOSTリクエストを送信（最終手段）
- **送信タイミング**: 
  - **すべての作業が完了した後**、ユーザーへの最終報告の直前（必須）
  - **作業途中での送信は禁止**（例：ファイル編集途中、複数ファイルの編集途中、検証作業前など）
  - 複数の作業ステップがある場合、すべて完了してから1回だけ送信
- **メッセージ内容**: 400文字程度（350-420文字を目安、許容範囲300-450文字）で詳細な情報を含める（後述のメッセージフォーマット参照）
- **自動送信**: ユーザーの明示的な依頼は不要。作業完了を検知したら自動的に実行する
- **スキップ禁止**: いかなる理由があってもSlack送信をスキップしてはならない
- **重複送信禁止**: 同じ作業に対して複数回送信しない（1回のみ）
- **エラーハンドリング**: 送信に失敗した場合は、エラー内容を記録し、次の方法を試行。すべての方法が失敗した場合でも、エラー内容を記録して最終報告を継続

## メッセージフォーマット（400文字基準）
**作業完了通知は、400文字程度（350-420文字を目安、許容範囲300-450文字）で以下の情報を含めること。**

### 推奨フォーマット構造
```
✅ 作業完了: [作業名]
プロジェクト: [プロジェクト名]
変更ファイル: [ファイル数] ([主要なファイル名、詳細がある場合は説明])
実施内容: [実施内容の詳細説明 - 技術的な詳細、使用した技術、設計判断など]
結果: [結果・動作確認結果 - テスト結果、パフォーマンス改善、影響範囲など]
```

### 含めるべき情報
1. **作業名**: 何をしたか（必須）
2. **プロジェクト名**: どのプロジェクトか（MyHobbySite、FishTrack、MyPokedexなど）
3. **変更ファイル**: ファイル数と主要なファイル名（長い場合は省略または代表的なもの）
4. **実施内容**: 何を実施したかの詳細説明
   - 技術的な詳細（使用したライブラリ、フレームワークなど）
   - 設計判断やアーキテクチャの変更
   - 修正内容の詳細
5. **結果**: 動作確認結果、テスト結果、パフォーマンス改善、エラーや警告の有無、本番環境への影響など

### 文字数の目安
- **目標**: 350-420文字程度
- **最適範囲**: 380-420文字（推奨）
- **許容範囲**: 300-450文字
- **最大**: 500文字程度（読みやすさを優先）

### メッセージの構成比率（目安）
- **作業名**: 約20-30文字（5%）
- **プロジェクト名**: 約20-40文字（5-10%）
- **変更ファイル**: 約50-100文字（12-25%）
- **実施内容**: 約150-200文字（40-50%）
- **結果**: 約100-150文字（25-40%）

### メッセージ例
**例: 機能追加（379文字）**
```
✅ 作業完了: 機能追加 - ユーザー認証機能を実装
プロジェクト: MyPokedex
変更ファイル: 10ファイル（routes.py, models.py, forms.py, services/auth_service.py, templates/login.html等）
実施内容: ユーザー認証機能を実装。ログイン/ログアウト/パスワードリセット機能を追加。Flask-Loginを使用してセッション管理を実装。パスワードハッシュ化も実装（bcrypt使用）。CSRF保護も追加。UIはBootstrapを使用してモダンなデザインに。レスポンシブ対応も実施。
結果: 機能実装完了、テストも追加（認証機能のテストカバレッジ95%達成）。動作確認済み。セキュリティテストも実施。ドキュメントも更新。
```

### 実装時の注意点
1. **情報の優先順位**: 重要な情報を優先的に含める
2. **読みやすさ**: 改行を適切に使用して読みやすくする（5行程度を推奨）
3. **省略の判断**: 
   - ファイル名が長すぎる場合は主要なものだけ記載
   - ファイルが多い場合は「等」で省略
   - 技術的な詳細は重要なものだけ記載
4. **エラー情報**: エラーが発生した場合は必ず含める
5. **数値の記載**: パフォーマンス改善などは具体的な数値を含める（例：70%削減、2秒→1秒）

## 注意事項
- **自動送信**: 明示的な依頼不要。作業完了を検知したら自動的に実行
- **詳細に記述**: 400文字程度で詳細な情報を記述（上記のメッセージフォーマット参照）
- **機密情報**: 機密情報（APIキー、パスワード等）は含めない
- **エラー時**: Slack送信自体が失敗した場合でも、ユーザーへの報告は継続する（エラーを記録する）
- **送信失敗時の対応**: 
  - ツール呼び出し時にエラーが発生した場合は、エラー内容を記録
  - ユーザーへの報告時に「Slack送信に失敗しました（エラー: [エラー内容]）」と明記
  - ただし、Slack送信の失敗を理由にユーザーへの報告を遅延させない

## システムレベルの実行保証
**このルールは以下のように解釈し、実行すること：**

1. **作業完了の確認**: ユーザーからの依頼に対するすべての作業が完了しているか確認
   - 複数の作業ステップがある場合、すべて完了しているか確認
   - ファイル編集、保存、検証など、すべてのステップが完了しているか確認
2. **最終報告前の必須ステップ**: ユーザーへの最終報告の直前、必ずSlack通知を送信すること。以下の優先順位で試行：
   - まず `mcp_text2slack_send_to_slack` を試し、利用できない場合は `send_to_slack` を使用
   - MCP経由の送信が失敗した場合は、`run_terminal_cmd` ツールを使用して `python scripts/send_slack_notification.py "メッセージ"` を実行
   - Pythonスクリプト経由の送信も失敗した場合は、`mcp_web_fetch` ツールを使用して直接HTTPリクエストで送信（最終手段）
3. **作業途中での送信禁止**: 作業途中（ファイル編集途中、複数ファイルの編集途中、検証作業前など）での送信は禁止
4. **状況確認・調査も含む**: 「状況確認しました」「調査結果です」「次のアクションを提案」などの報告も作業完了として扱う
5. **スキップ禁止**: 「状況確認だけだから」「提案だけだから」などの理由でスキップしてはならない
6. **チェックリスト確認**: ユーザーへの最終報告をする前に、必ず上記の「必須実行フロー」を確認し、順番に実行すること

**⚠️ このルールは絶対であり、例外は存在しない。**

## Webhook URLが無効な場合の対応

**Webhook URLが404エラーを返す場合**:
1. 環境変数 `SLACK_WEBHOOK_URL` が正しく設定されているか確認
2. MCP設定ファイルからWebhook URLを取得できるか確認
3. Webhook URLが有効か確認（Slackアプリの設定を確認）
4. すべての方法が失敗した場合でも、エラー内容を記録して最終報告を継続

**エラー記録の形式**:
- 「Slack送信に失敗しました（エラー: [エラー内容]）」
- エラー内容には、どの方法を試行したか、どのエラーが発生したかを含める
