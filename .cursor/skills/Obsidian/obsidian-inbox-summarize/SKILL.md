# Obsidian InBox Summarize

## 入口（旧 Cursor Command の統合）

**旧 `.cursor/commands/Obsidian_InBox_Summarize.md` は廃止**し、**手順の正本は本 SKILL のみ**。

### 成果物（2段）

1. **原文全文（必須）**: 取得・読み込んだ内容を **Markdown の全文** として Obsidian に保存する（要約だけでなく、元記事相当の本文を残す）。
2. **Knowledge（必須）**: 従来どおり、実用的な知識をジャンル別ノートに追記・新規作成する。全文ノートへの `[[リンク]]` を参照に含める。

### 既定の入出力パス

- **InBox ディレクトリ**: `D:\OneDrive\アプリ\remotely-save\Obsidian\InBox\`
- **原文全文の保存先（Articles）**: `D:\OneDrive\アプリ\remotely-save\Obsidian\Notes\Knowledge\Articles\`（無ければ作成する）
- **Knowledge 保存先**: `D:\OneDrive\アプリ\remotely-save\Obsidian\Notes\Knowledge\`  
  依頼で上記と異なるパスが明示されていれば、それに従う（下記「適用条件」）。

**重要**: **1 回の実行では 1 件だけ**処理し、完了後に作業を中断する。次のノートは、**同じ依頼を再度出す**（チャット上で本 SKILL を再適用）ことで処理する。

### Cursor ログ更新（必須・要約）

処理完了後、**`obsidian-cursor-log` SKILL** に従い当日の CursorLog へ記録する（作業名・プロジェクト名・変更ファイル・実施内容・結果。タグ例: `#obsidian` `#inbox-summarize` 等）。**詳細手順**は下記「実行手順」および **j. Cursorログの更新**。

## 適用条件

- 対象は以下のいずれか：
  - InBoxディレクトリ配下のMarkdownファイルおよびPDFファイル
  - ユーザーが直接指定したMarkdownファイルまたはPDFファイル（Cursorから直接渡される場合も含む）
- 上記「既定の入出力パス」または、依頼で明示された InBox ディレクトリ、**原文全文保存先（Articles）**、Knowledge 保存先を使用する
  - **原文全文保存先の既定**: `D:/OneDrive/アプリ/remotely-save/Obsidian/Notes/Knowledge/Articles/`（依頼で別パスが指定されていればそれに従う）
- 直接ファイルが指定された場合は、そのファイルを処理対象とする

## 処理フロー

### 1. ノートの読み込み

- **入力ソースの確認**:
  - ユーザーが直接ファイルを指定した場合: そのファイルを処理対象とする
  - ファイルが指定されていない場合: InBoxディレクトリ配下のMarkdownファイルおよびPDFファイルを確認し、1件を選択
- 各ノートの内容を読み込む
  - **Markdownファイルの場合**: ファイルの内容を直接読み込む
  - **PDFファイルの場合**: PDFからテキストを抽出して読み込む。
    `dev-workspace/scripts/extract_pdf_text.py` を使用する
    （pypdf 失敗時は おたよりナビ OCR API → Azure Document Intelligence の順でフォールバック）。
    または Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用する。
- **重要**: 1つのノートに複数の項目が含まれている場合、1つの項目だけを処理対象とする

**入力形式**:
InBoxノートには以下の4種類の形式がある：

1. **URL形式**: ノートの内容がURLのみの場合
   - 例: `https://qiita.com/degudegu2510/items/eff0f63dac99554e6439`
   - URLの内容を取得して分析する（可能な場合）
   - **URLの内容を取得できない場合（タイムアウト、エラー、アクセス不可等）**: 処理を中断する
   - **複数URLがある場合**: 1つのURLだけを処理対象とする（先頭のURL、または最初に見つかったURL）

2. **WEBクリップ形式**: ObsidianのWeb Clipperで保存された形式
   - フロントマターにURLやメタデータが含まれる
   - 本文にWebページの内容がMarkdown形式で保存されている
   - 例:

     ```markdown
     ---
     url: https://example.com/article
     title: 記事タイトル
     ---
     
     # 記事タイトル
     
     記事の本文内容...
     ```

   - **複数のWEBクリップがある場合**: 1つのクリップだけを処理対象とする（先頭のセクション）

3. **PDF形式**: PDFファイルが指定された場合
   - PDFファイルがInBoxディレクトリ配下に配置されている、またはユーザーが直接指定したPDFファイル
   - PDFからテキストを抽出して分析する
   - **PDFの読み込み方法**: `dev-workspace/scripts/extract_pdf_text.py` を使用する（推奨）。
     このスクリプトは (1) pypdf でテキスト抽出を試行し、
     (2) テキストが十分得られない場合におたよりナビ OCR API（`http://localhost:5003/` 固定）でフォールバック、
     (3) それでも失敗時は Azure Document Intelligence でフォールバックする。
   - **代替**: Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用して
     PDFからテキストを抽出することも可能。
   - **おたよりナビ OCR API フォールバック**: ローカル Docker で otayori-navi が
     `http://localhost:5003` で稼働している場合、pypdf 失敗時に検索可能PDF API を呼び出して再抽出する。
     URLは固定のため環境変数不要。認証は不要（`OTAYORI_OCR_API_KEY` は任意）。
   - **Azure Document Intelligence フォールバック**: 上記が失敗または未設定の場合に使用。
     環境変数 `AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT` と `AZURE_DOCUMENT_INTELLIGENCE_KEY` が設定されているとき、
     かつ `azure-ai-documentintelligence` がインストールされているときのみ有効。
   - **PDFの読み込みに失敗した場合（ファイル破損、暗号化、アクセス不可等）**: 処理を中断する
   - **複数PDFがある場合**: 1つのPDFだけを処理対象とする（先頭のPDF、または最初に見つかったPDF）
   - **PDFファイルの処理後**: テキスト抽出が完了したら、PDFファイルを参考資料としてObsidian内に保存する
     - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
     - PDFファイルを`attachments`ディレクトリにコピーして保存
     - ノートの「参照」セクションにPDFファイルへのリンクを追加（例: `[[attachments/ファイル名.pdf]]`）
     - InBoxディレクトリ内のPDFファイルは削除する（直接指定されたPDFファイルは削除しない）

4. **手入力メモ形式**: ユーザーが手動で入力したメモ
   - フロントマターがない、または最小限のフロントマターのみ
   - 本文にユーザーが記述した内容が含まれる
   - 例:

     ```markdown
     Cursorのショートカットキーについて
     
     - Cmd+K: インライン編集
     - Cmd+L: チャット開始
     ```

   - **複数のメモ項目がある場合**: 1つの項目だけを処理対象とする（先頭のセクション、または明確に区切られた最初の項目）

### 1.5 原文全文Markdown（Articles）の作成（必須）

InBox の1件につき、**必ず**原文相当の全文を Markdown ファイルとして保存する。以降の Knowledge ノートでは **要約だけでなく、この全文ノートへのリンクを「参照」に含める**。

- **保存先**: `Notes/Knowledge/Articles/`（依頼で別パスが指定されていればそちら。ディレクトリが無ければ作成する）
- **ファイル名**: `YYYY-MM-DD_<slug>.md`
  - `YYYY-MM-DD` は処理日（JST）または InBox ファイル名の日付のいずれか新しい方を採用してよいが、**同一実行内で一貫**させる
  - `<slug>` は記事タイトルやドメインから、英小文字・ハイフン・数字のみの短い識別子（重複時は `-2` 等を付与）
- **フロントマター（推奨）**:

  ```yaml
  ---
  type: article-archive
  created: YYYY-MM-DD
  source: InBox/ファイル名.md
  title: "記事タイトル（取得できた場合）"
  url: "https://..."  # 該当する場合
  ---
  ```

- **本文**: 次の入力形式に応じて「全文」を埋める（**Knowledge 用に短くしない**。取得できた範囲をそのまま Markdown 化する）

| 入力形式 | 全文ノートの本文の正体 |
| --- | --- |
| **URL形式** | 取得したページの本文を **有効な Markdown** として保存する（HTML の場合は見出し・段落・リスト・コードを崩さないよう変換。取得に失敗した場合は従来どおり中断し、全文ファイルは作らない） |
| **WEBクリップ形式** | Web Clipper が入れた **本文をそのまま**使う（フロントマターは全文ノート側では上記 `source` / `url` / `title` に整理してよい） |
| **PDF形式** | `extract_pdf_text.py` 等で得た **抽出テキスト全文**を本文に入れる（ページ区切りは `\n\n---\n\n` 等で可）。PDF バイナリは従来どおり `attachments/` にコピーし、全文 `.md` と併存させる |
| **手入力メモ形式** | InBox に書かれた **メモ全文**をそのまま本文にする |

- **Markdown としての体裁**: 貼り付けや HTML からの変換後も、**有効な Markdown** として保存する（見出し `##` 以降、リスト、区切り、必要ならコードフェンス＋言語名など。プレーンテキストの一塊のままにしない）。
- **markdownlint（必須・対象外禁止）**:
  - 作成した **Articles** ファイルに対し、`npx markdownlint-cli2` 等で **必ず実行**し、**違反 0 件**まで解消する。
  - **禁止**: `<!-- markdownlint-disable … -->` や `.markdownlintignore` などで **Articles だけ** lint を**除外**して完了とすること。本 SKILL では**対象外にしない**。
  - **本文の内容は変えないこと**: 違反修正は **体裁・構文のみ**（`markdown-editing` / `markdownlint-fix` の手順に従う）。
    **語句の言い換え・要約・段落の削除・事実の改変は禁止**。
    許容例: 200 字超行の**句点・読点前での改行**、表セルの**パイプ周りのスペース**、見出し前後の**空行**、
    重複 H1 解消のための**同一見出し文の `##` への格下げ**、末尾改行、コードフェンスの言語名付与。
    いずれも**表示テキストとして読める文言は元と同一**に保つ（見出し行の `#` 数の変更のみは、lint 上必要なら可）。
- **Knowledge との関係**: ジャンル別ノートの `## 参照`（または既存の参照ブロック）に、必ず `[[Articles/ファイル名（拡張子なし）]]` を追加する（Obsidian のパスに合わせ、Vault ルートからの相対が異なる場合は既存ノートのリンク形式に合わせる）

### 2. 内容分析とKnowledge抽出

- ノートの内容を分析し、記事から得られるKnowledge（知識・知見・実用的な情報）を抽出
- **入力形式に応じた処理**:
  - **URL形式の場合**:
    - URLの内容を取得して分析（可能な場合）
    - **重要**: URLの内容を取得できない場合（タイムアウト、エラー、アクセス不可等）は、処理を中断する
    - URL取得に失敗した場合は、InBoxノートを削除せず、エラーメッセージと共に処理中断の旨を報告する
  - **WEBクリップ形式の場合**: フロントマターからURLやタイトルを抽出し、本文内容を分析（本文が存在する場合は本文を分析）
  - **PDF形式の場合**:
    - PDFファイルからテキストを抽出して分析
    - **PDFの読み込み方法**: まず `dev-workspace/scripts/extract_pdf_text.py <PDFパス>` を実行してテキストを取得する。
      このスクリプトは pypdf → おたよりナビ OCR API（`http://localhost:5003` 固定、otayori-navi 稼働時）
      → Azure Document Intelligence（テキスト不足時）の順で試行する。
      スクリプトが使えない場合は、Pythonの`pypdf`または`pdfplumber`を直接使用する。
    - **PDFの読み込みに失敗した場合（ファイル破損、暗号化、アクセス不可等）**: 処理を中断する
    - PDFファイルを削除せず、エラーメッセージと共に処理中断の旨を報告する
    - テキスト抽出が成功したら、抽出したテキストを分析してKnowledgeを抽出
    - **PDFファイルの保存**: テキスト抽出が完了したら、PDFファイルを参考資料としてObsidian内に保存する
      - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
      - PDFファイルを`attachments`ディレクトリにコピーして保存
      - ノートの「参照」セクションにPDFファイルへのリンクを追加（例: `[[attachments/ファイル名.pdf]]`）
  - **手入力メモ形式の場合**: 本文内容を直接分析（フロントマターがあればメタデータも抽出）
- **ジャンルを特定**（例: Cursor、Python、AWS、Raspberry Pi など）
- **Knowledge（知識）を抽出・整理**:
  - 記事の要約ではなく、記事から得られる実用的な知識・知見・ノウハウを抽出
  - 具体的な手順、ベストプラクティス、注意点、使用例、テンプレート、設定方法など、実際に活用できる情報を整理
  - 単なる記事の要約ではなく、自分が今後参照・活用するための知識として構造化
- 元の内容への参照を保持（URL、引用など。手入力メモの場合は参照セクションは省略可）
- キーワードやタグ候補を抽出（同ジャンルノート検索に使用）

**ジャンルの特定方法（内容優先）**:

- **タイトルや見出しの語句だけで判断しない**。本文全体を読み、知識の再利用先（どのノートに追記すると最も価値が高いか）でジャンルを決める
- 固有名詞（ツール名、サービス名、技術名）は補助情報として扱う
- 主要トピックと適用範囲（特定ツール限定か、横断的な原則か）を判定する
- **適用範囲が広い場合は上位概念を優先**（例: ツール固有TipsではなくAI開発全般の原則なら `AI開発` 系ノート）
- 例: タイトルが「Cursorを使ったAI開発のベストプラクティス」でも、本文がAI開発全般の原則中心 → ジャンル: `AI開発`（`Cursor` 固有ノートを優先しない）
- 例: 「Pythonのデコレータ」に関する記事 → ジャンル: `Python`
- 例: 「AWS Lambda」に関する記事 → ジャンル: `AWS`

### 3. 既存ノートの検索

Knowledge保存先ディレクトリ配下の既存ノートを検索し、同ジャンルのノートを探す。

**同ジャンルの判定基準**（優先順位順）:

1. **内容の関連性（最優先）**: 抽出したKnowledgeの主眼（原則・手順・判断基準）が既存ノートの主題と一致する
2. **適用範囲の一致**: 特定ツール向けか、横断的なベストプラクティスかが既存ノートの粒度と一致する
3. **タグの一致**: 抽出したタグ候補と既存ノートのタグが一致または類似
4. **キーワードの一致**: 主要キーワードが既存ノートのタイトルや内容に含まれる
5. **タイトルの類似性**: タイトルが同じトピックを扱っている（補助的に使用）

**検索方法**:

- Knowledge保存先ディレクトリ配下の全Markdownファイルを確認
- 各ファイルのタイトル、タグ、主要キーワードに加え、`Knowledge` セクションの主題を確認
- InBoxノートの内容（抽出したKnowledgeの主眼・適用範囲）と比較して関連性を判定
- **禁止**: タイトル内の語句一致のみで保存先ノートを決定しない

### 4. ノートの作成または更新

#### 既存ノートが見つかった場合（追記・更新）

**重要**: 既存ノートの内容を読み込み、新しい情報を既存の文章構造に統合する形で追記する。

**追記方法**:

1. **既存ノートの内容を完全に読み込む**
   - 既存ノートの全体構造を把握
   - 既存のセクション、見出し、内容を理解
   - 既存の文章スタイルや記述方法を確認

2. **既存のセクションに統合**
   - **既存のセクションが存在する場合**: そのセクションに新しい情報を自然に追加
     - 例: 「使い方」セクションが既にある場合、新しい使い方の情報をそのセクションに追加
     - 例: 「特徴」セクションが既にある場合、新しい特徴をそのセクションに追加
   - **既存のセクションがない場合**: 適切な場所に新しいセクションを追加
     - 既存の構造に合わせて、適切な見出しレベルで追加
     - 既存のセクションの順序や階層を尊重

3. **参照セクションの更新**
   - **必ず**今回作成した **全文ノート（Articles）** へのリンクを追加する
   - 既存の参照セクションがあれば、そこに新しい参照を追加
   - 既存の参照セクションがない場合は、適切な場所に参照セクションを追加

4. **フロントマターの更新**
   - `updated`フィールドがあれば、現在の日付に更新
   - `updated`フィールドがない場合は追加

**追記時の注意事項**:

- **既存の文章構造を維持**: 既存の見出し階層、セクション構成を壊さない
- **既存の文章スタイルに合わせる**: 既存の記述方法や文体に合わせて新しい情報を追加
- **重複を避ける**: 既存の内容と重複する情報は追加しない（必要に応じて既存の内容を更新）
- **矛盾がある場合**: 既存ノートの内容と新しい情報に矛盾がある場合（例: 既存ノートに「AはBである」と記載されているが、新しい情報に「AはCである」と記載されている場合）は、自動的に統合せず、ユーザーにどちらを採用するか問いかけること
  - 矛盾の内容を明確に示す（既存の内容と新しい情報の両方を提示）
  - ユーザーの判断を待ってから処理を続行する
- **自然な統合**: 新しい情報が既存の文章に自然に統合されるようにする
- **既存のタグは維持**: 既存のタグは維持し、必要に応じて新しいタグを追加
- **既存のリンクを尊重**: 既存のWikiリンクやMarkdownリンクを維持

#### 既存ノートが見つからなかった場合（新規作成）

**ファイル名**:

- **内容分析で決定したジャンル名をファイル名にする**（例: `AI開発.md`、`Python.md`、`AWS.md`）
- タイトル語句ではなく、抽出Knowledgeの主題・適用範囲から名前を決定
- ジャンルが特定できない場合は、主要キーワードではなく「最も再利用性が高い上位概念」を優先して命名
- 既存ファイルと重複しないようにする（重複する場合は、ジャンル名に番号や日付を追加しない。既存ノートに追記する）

**ノート構造**:

```markdown
---
created: YYYY-MM-DD
source: InBox/YYYY-MM-DD.md
---

# [ノートタイトル]

## Knowledge
[記事から得られる知識・知見・実用的な情報]
- 具体的な手順、ベストプラクティス、注意点、使用例、テンプレート、設定方法など
- 単なる記事の要約ではなく、実際に活用できる知識として整理

## 詳細
[必要に応じて詳細情報]

## 参照
- **全文**: [[Articles/YYYY-MM-DD_slug]]（InBox 処理で作成した原文 Markdown）
- [元のURLなど。PDFの場合は `[[attachments/ファイル名.pdf]]` も併記]

## 関連リンク
[関連するノートへのWikiリンク]
```

### 5. タグとリンクの付与

`obsidian-update-rules` のルールに従って：

- 重要語（固有名詞、システム名、機器名、手順名、プロジェクト名）が出たら、可能なら `[[既存ノート名]]` へのWikiリンクを優先
- 該当ノートが存在しない場合は、タグ `#keyword` を付与（英小文字・ハイフン推奨）
- 既存タグ体系がある場合はそれに合わせる（例: `#infra/raspi` のような階層タグ）
- 1ノート内のタグは過剰にならない範囲で付与（目安: 3〜8個）

### 6. 元のノートの処理

- **InBoxディレクトリ内のファイルの場合**:
  - **全文ノート（Articles）の作成**と **Knowledge ノートの作成・更新**が完了したら、処理した項目をInBoxノートから削除
  - **重要**: 1つのノートに複数の項目がある場合、処理した項目だけを削除し、残りの項目はノートに残す
  - ノート内のすべての項目を処理した場合のみ、ノートファイル全体を削除する
  - 削除前に、**全文ノート**および **Knowledge ノート** への保存を確認
- **直接指定されたファイルの場合**:
  - ファイルは削除しない（ユーザーが明示的に指定したファイルのため）
- **重要**: 1件処理したら作業を中断する（次のノートまたは次の項目は別の実行で処理）

## 実行手順

1. **入力ソースの確認**
   - **ユーザーが直接ファイルを指定した場合**: そのファイルを処理対象とする（InBoxディレクトリの確認は不要）
   - **ファイルが指定されていない場合**:
     - InBoxディレクトリ配下のMarkdownファイルおよびPDFファイルの一覧を取得
     - 処理対象のノート数を確認

2. **1件だけ処理する**（この実行では1件のみ）

   処理対象のノートを1つ選び（直接指定された場合はそのファイル、指定されていない場合はInBoxから未処理のノートを1つ選択）、以下を実行：

   a. **ノートの読み込み**
      - 1件のノートファイル（MarkdownまたはPDF）を読み込む
      - 直接指定された場合はそのファイル、指定されていない場合は先頭のノート、または日付が古い順など、1件に限定
      - **Markdownファイルの場合**: ファイルの内容を直接読み込む
      - **PDFファイルの場合**: `python dev-workspace/scripts/extract_pdf_text.py <PDFパス>` を実行してテキストを抽出
        （pypdf 失敗時は おたよりナビ OCR API（localhost:5003 固定）→ Azure Document Intelligence でフォールバック。
        otayori-navi 稼働時は API を利用可）。
        または Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用する。
      - ノート内に複数の項目があるか確認（Markdownファイルの場合）
      - 複数の項目がある場合、1つの項目だけを処理対象とする（先頭の項目、または最初に見つかった項目）

   b. **原文全文Markdown（Articles）の作成**
      - **セクション「1.5」**の手順に従い、`Notes/Knowledge/Articles/` に全文 `.md` を1件作成する（URL 取得失敗時は作成せず中断）
      - **URL形式**: まずページ本文を取得し、**取得に成功したテキスト**を **Markdown として整形したうえで** Articles に保存してから内容分析へ進む
      - **WEBクリップ形式**: クリップ本文をそのまま Articles に保存する（既が Markdown なら体裁確認のうえ、下記 lint）
      - **PDF形式**: ステップ a. で抽出済みのテキスト全文を **Markdown 化**（段落・見出し区切り等。プレーンテキスト一塊を避ける）し Articles の本文に書く（抽出失敗時は Articles は作らず中断）
      - **手入力**: メモ全文を Articles に保存する
      - **完了前**: 当該 Articles に **markdownlint を実行**し、**0 件**（**`markdownlint-disable` 等の対象外化は行わない**）。修正は **1.5** の「本文の内容は変えないこと」に従う
      - 続けて、当該実行で触った **Knowledge ノート**と **CursorLog** も含め、同一ルールで lint を通す

   c. **内容分析**
      - 処理対象の項目の内容を分析し、ジャンル、Knowledge（知識）、キーワードを抽出
      - 入力形式を判定（URL形式、WEBクリップ形式、PDF形式、手入力メモ形式）
      - **URL形式の場合**:
        - ステップ **b.** で取得済みの本文を分析に用いる（再取得は不要）
      - **PDF形式の場合**:
        - ステップ **a.** で抽出済みのテキストを分析に用いる（失敗時は **a.** で既に中断済み。`extract_pdf_text.py` の再実行は不要）
        - 抽出テキストから Knowledge を抽出する
        - **PDFバイナリの保存**: ステップ **e.** で Knowledge ノートを確定したら、同じディレクトリの `attachments/` に PDF をコピーし、Knowledge ノートの「参照」に `[[attachments/ファイル名.pdf]]` を追加する（セクション「1」「6」と同じ運用）

   d. **既存ノートの検索**
      - ジャンル名で既存ノートを検索する際も、タイトル一致だけで確定せず本文主題を照合する
      - 例: タイトルに `Cursor` が含まれていても、抽出KnowledgeがAI開発一般なら `AI開発` 系ノートを優先して検索する
      - Knowledge保存先ディレクトリ配下で既存の同ジャンルノートを検索

   e. **ノートの作成または更新**
      - **既存ノートが見つかった場合**:
        1. 既存ノートの内容を完全に読み込む
        2. 既存の文章構造を理解し、新しい情報と既存の内容を比較
        3. **矛盾がある場合**: 既存ノートの内容と新しい情報に矛盾がある場合は、自動的に統合せず、ユーザーにどちらを採用するか問いかける
           - 矛盾の内容を明確に示す（既存の内容と新しい情報の両方を提示）
           - ユーザーの判断を待ってから処理を続行する
        4. 既存の文章構造を理解し、新しい情報を既存のセクションに統合する形で追記
        5. 既存のセクションがない場合は、適切な場所に新しいセクションを追加
        6. 既存の参照セクションに新しい参照を追加、または参照セクションを作成
        7. フロントマターの`updated`フィールドを現在の日付に更新
      - **既存ノートが見つからなかった場合**: ジャンル名をファイル名として新規ノートを作成（Knowledge保存先ディレクトリ内に作成）

   f. **タグとリンクの付与**
      - タグとリンクを付与（既存ノートの場合は既存タグを維持）

   g. **元のノートの処理**
      - **InBoxディレクトリ内のファイルの場合**:
        - **処理が完了したら、処理した項目をInBoxノートから削除**
        - **Markdownファイルの場合**:
          - **1つのノートに複数の項目がある場合**: 処理した項目だけを削除し、残りの項目はノートに残す
          - **ノート内のすべての項目を処理した場合**: ノートファイル全体を削除する
        - **PDFファイルの場合**:
          - テキスト抽出とKnowledge抽出が完了し、PDFファイルを参考資料として`attachments`ディレクトリに保存したら、InBoxディレクトリ内のPDFファイルを削除する
          - 削除前に、**全文ノート（Articles）** および Knowledge ノートへの保存を確認
        - **Markdown の場合**も、削除前に同様に保存を確認
      - **直接指定されたファイルの場合**:
        - ファイルは削除しない（ユーザーが明示的に指定したファイルのため）
        - 処理完了後、ファイルの場所を報告する

   h. **処理結果の報告**
      - 処理したノートのファイル名（MarkdownファイルまたはPDFファイル）
      - 入力ソース（InBoxディレクトリ内のファイル、または直接指定されたファイル）
      - 処理した項目の内容（URL、メモの内容、PDFの内容など）
      - 抽出したKnowledge（知識）の概要
      - **作成した全文ノート（Articles）のパス**
      - 新規作成したKnowledgeノートの場所、または更新した既存ノートの場所
      - 付与したタグやリンク
      - ジャンル名
      - ノートに残りの項目がある場合は、その旨を報告（Markdownファイルの場合）
      - 直接指定されたファイルの場合は、ファイルが削除されていないことを報告
      - **🚨 適用可能性の検討と提案（必須）**: 下記 i. を実行し、報告の最後に **`## 適用可能性`**（**`### 開発プロジェクト`** と **`### 仕事（本職）`** の2サブセクション）を必ず含める

   i. **🚨 適用可能性の検討と提案（必須・省略禁止）**

      **忘れやすいので必ず実行する。** 報告は **開発** と **仕事（本職）** を**分けて**検討し、**両方**を書く（片方だけで完了禁止）。

      **報告フォーマット（固定）**:

      ```markdown

      ### 開発プロジェクト
      （FishTrack / MyPokedex / otayori-navi / personal-tools / dev-workspace。該当なしなら「該当なし」）
      ```

        1. **技術スタックの一致**（Docker、AWS、Python、PostgreSQL 等）
        2. **アーキテクチャの改善**（構成・デプロイ・マイグレーション実行方法等）

## 注意事項

- **Markdown編集時**: ノート（.md）の作成・更新時は、`markdown-editing` SKILLのルールに従う
- **Articles（原文全文）**: 上記に加え **セクション「1.5」**の **markdownlint 必須・対象外禁止**、**本文内容不変**を厳守する
- 既存のMarkdown構造・見出し階層を維持
- 既存のリンク形式（Wikiリンク `[[...]]` / Markdownリンク `[text](url)`）を尊重
- ノートの文脈を壊さない最小限の編集で完結
- ファイルの改行は既存に合わせる（不用意に整形しない）
- 既存の関連リンクがあるか確認し、重複追加しない
- 既存タグを再利用し、必要に応じて最小限の追加
- **既存ノートに追記する場合**: 単純にKnowledgeの内容を追記するのではなく、既存のノートの内容を読み込み、その文章にマージするように追記すること
  - 既存のセクションが存在する場合は、そのセクションに新しい知識を自然に追加
  - 既存のセクションがない場合は、適切な場所に新しいセクションを追加
  - 既存の文章構造・スタイルを維持し、新しい知識を自然に統合
  - 既存の内容と重複する情報は追加しない（必要に応じて既存の内容を更新）
  - **矛盾がある場合**: 既存ノートの内容と新しい情報に矛盾がある場合は、自動的に統合せず、ユーザーにどちらを採用するか問いかけること。矛盾の内容を明確に示し、ユーザーの判断を待ってから処理を続行する
  - **既存ノートに「要約」セクションがある場合**: 「Knowledge」セクションに統合するか、既存の「要約」セクションを「Knowledge」に変更することを検討
- **URLの取得に失敗した場合**: URL形式のノートでURLの内容を取得できない場合（タイムアウト、エラー、アクセス不可等）は、処理を中断する
  - InBoxノートを削除しない
  - エラーメッセージと共に処理中断の旨を報告する
  - 次のステップ（既存ノートの検索、ノートの作成または更新等）には進まない
- **PDFの読み込みに失敗した場合**: PDF形式のファイルでPDFの読み込みに失敗した場合（ファイル破損、暗号化、アクセス不可等）は、処理を中断する
  - **extract_pdf_text.py 使用時**: pypdf でテキストが得られず、かつ おたよりナビ OCR API・Azure Document Intelligence のフォールバックも失敗または未設定の場合は処理を中断する
  - PDFファイルを削除しない
  - エラーメッセージと共に処理中断の旨を報告する
  - 次のステップ（既存ノートの検索、ノートの作成または更新等）には進まない
- **PDFのテキスト抽出**: PDFからテキストを抽出する際は、可能な限り正確にテキストを抽出する
  - 表や図が含まれるPDFの場合は、`pdfplumber`ライブラリの使用を推奨（より高度なレイアウト解析が可能）
  - テキスト抽出が不完全な場合でも、抽出できた部分からKnowledgeを抽出する
- **PDFファイルの保存**: PDFファイルから解析した場合は、PDFファイルを参考資料としてObsidian内に保存する
  - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
  - PDFファイルを`attachments`ディレクトリにコピーして保存
  - ノートの「参照」セクションにPDFファイルへのWikiリンクを追加（例: `[[attachments/ファイル名.pdf]]`）
  - InBoxディレクトリ内のPDFファイルは、参考資料として保存した後に削除する
  - 直接指定されたPDFファイルは削除しない（ユーザーが明示的に指定したファイルのため）
- **🚨 適用可能性の検討と提案（必須・省略禁止）**: 毎回必ず実行する。忘れやすいが省略してはならない
  - 報告末尾は **`## 適用可能性`** と **`### 開発プロジェクト`** / **`### 仕事（本職）`** の2サブセクション（片方省略禁止）
  - 各サブセクションで該当が無い場合は **その中**に「該当なし」と明記
  - 提案は簡潔に、実用的な内容に絞る。現在の運用との比較・注意点を記載
- **Cursorログの更新（必須）**: 処理完了後、必ずCursorログを更新する
  - `obsidian-cursor-log` SKILLを使用して、当日のCursorLogに作業内容を記録する
  - 記録内容は処理結果の報告の内容を基に、適切な形式で記録する
  - Cursorログの更新を忘れないこと。これは必須の作業である。

## 例

### 例1: URL形式（既存ノートへの追記）

**入力**: InBoxに `2026-01-27.md` があり、内容が `https://azukiazusa.dev/blog/new-design-tool-pencil`

**既存ノート**: Knowledge保存先ディレクトリ内の`Pencil.md`が既に存在し、以下のような構造になっている：

```markdown
# Pencil

## Knowledge
Pencilは、AIがUIデザインを生成できるデザインツール...

## 使い方
### Pencil(アプリ) x Claude Code(CLI)
1. 公式サイトからアプリをインストール
...

## 参照
- [Pencil公式サイト](https://www.pencil.dev/)
```

1. URL形式であることを認識

### 例4: PDF形式（新規ノート作成）

**入力**: InBoxに `Python入門ガイド.pdf` というPDFファイルが配置されている

**処理**:

1. PDF形式であることを認識（`.pdf`拡張子のファイル）
2. Pythonの`pypdf`または`pdfplumber`ライブラリを使用してPDFからテキストを抽出
   - 例: `pypdf`を使用する場合

     ```python
     from pypdf import PdfReader
     reader = PdfReader("Python入門ガイド.pdf")
     text = ""
     for page in reader.pages:
         text += page.extract_text()
     ```

   - 例: `pdfplumber`を使用する場合

     ```python
     import pdfplumber
     with pdfplumber.open("Python入門ガイド.pdf") as pdf:
         text = ""
         for page in pdf.pages:
             text += page.extract_text()
     ```

3. 抽出したテキストを分析してジャンル、Knowledge（知識）、キーワードを抽出
   - ジャンル: 「Python」
   - Knowledge: Pythonの基本的な構文、実用的なコード例、ベストプラクティスなど
4. 既存ノート（Knowledge保存先ディレクトリ内の`Python.md`）を検索
   - **既存ノートが見つかった場合**: 既存ノートに追記（例2と同様の処理）
   - **既存ノートが見つからなかった場合**: 新規ノートを作成
5. **新規ノート作成の場合**:
   - Knowledge保存先ディレクトリ内に`Python.md`を新規作成
   - 抽出したKnowledgeを構造化して記述
   - フロントマターに`created`フィールドと`source`フィールドを追加
   - タグやリンクを付与
6. **PDFファイルの保存**:
   - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
   - PDFファイルを`attachments`ディレクトリにコピーして保存（例: `attachments/Python入門ガイド.pdf`）
   - ノートの「参照」セクションにPDFファイルへのWikiリンクを追加（例: `[[attachments/Python入門ガイド.pdf]]`）
7. InBoxディレクトリ内のPDFファイルを削除
8. 処理結果を報告
9. **適用可能性の検討**（開発 / 仕事の2サブセクション）:
   - 例（開発）: Python 知識を FishTrack / MyPokedex の品質向上に活用
   - 例（仕事）: 該当なし、または Work ナレッジへの転用案
