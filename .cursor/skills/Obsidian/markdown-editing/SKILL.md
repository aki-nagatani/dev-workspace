# Markdown編集ルール

## 適用タイミング

Markdown（`.md`）ファイルを編集・作成する際は、本SKILLのルールに従う。

## 🚨 日本語 UTF-8 ファイルへの破壊的操作の禁止

Obsidian vault・CursorLog・仕様書など**日本語を含む `.md`** は **BOM なし UTF-8** で保存されている。以下の PowerShell パターンは **cp932（Shift-JIS）誤判定**で全文を mojibake 化するため、**禁止**。

- `Get-Content -Raw` で読み、`Set-Content` / `[System.IO.File]::WriteAllText` で**全文書き戻す**操作\
    （末尾改行付与・整形目的でも禁止。`Get-Content` は PS 5.x の既定で cp932 になる）
- `>`・`>>` で**日本語テキスト**を既存 `.md` に追記する操作
- PowerShell のヒアドキュメント（`@"…"@`）で日本語を含むファイルを生成する操作

**推奨**:

1. 差分編集は **`StrReplace` ツール**を最優先（エンコーディング非依存）。
2. 末尾改行付与などバイナリ確定は **Python の `read_bytes` / `write_bytes`**（例: `obsidian-cursor-log` SKILL）。
3. PowerShell を使う場合は **`-Encoding utf8NoBOM`**（PS7+）または `System.Text.UTF8Encoding($false)` を **読み書き両方**で明示（片方だけは最悪のパターン）。

**事故検知**: 編集後にバイト列先頭を `python -c "print(open(path,'rb').read()[:200])"` で確認し、\
`繧`・`縺`・`\uf8f0` 等が出たら **即座に中断**し **OneDrive のバージョン履歴**から復元（Obsidian vault は git 管理外）。

## markdownlint エラー修正（既存違反の解消）

- **MD0xx が既に出ている行・ファイルを直す作業**では、本 SKILL だけを見て進めない
- **先に** `dev-workspace/.cursor/skills/Obsidian/markdownlint-fix/SKILL.md` を **Read ツールで全文読み**、
  そのフロー（同ファイルのエラー一括・検証など）に従う
- 本文の見出し以降のルールは、主に **新規編集時の防ぎ方**と **markdownlint-fix 経由の修正時の参照**として使う

## Markdownlintルール

### MD012（連続空行の禁止）

- 空行は連続して2行以上にしない（最大1行）

### MD013（行長）

- **通常行は200文字以内**に抑える（見出し・表を含む）
- **無断での基準変更は禁止**（200文字等のルールを変更する場合は、必ずユーザーの明示的な許可を得る）
- 長くなる場合は句読点（。、.）や括弧（）】」』）の前後で改行する
- 対象外：コードブロック内部のみ200文字超可
- **テーブルセルが200文字超の場合**：継続行を追加する。前の列を空にして `| | | | 継続テキスト |` のように記述（compact スタイルでは空セルに余分なスペースを入れない）
- リスト継続は**4スペース**でインデント

  ```text
  - 実施内容: 1行目が200文字を超える場合、
      ここから継続。4スペースで揃える。
  ```

### MD022（見出しの前後空行）

- 見出し（`#`〜`######`）の直前・直後に空行を入れる

### MD025（単一H1）

- **文書内の H1（`#`）は1つだけ**とする
- 2つ目以降の H1 は `##` に格下げし、その下位見出し（4-1, 4-2 等）は `###` に揃えて階層を維持する

### MD040（コードブロックの言語指定）

- **フェンス付きコードブロック（` ``` `）には必ず言語を指定する**
- 開始行を ` ``` ` のみにせず ` ```言語名 ` とする（例：` ```text `、` ```python `、` ```mermaid `）
- **一般的な言語指定の例**：
  - プレーンテキスト・出力例：`text` または `plaintext`
  - Markdown/YAML等の例：`md`、`yaml`
  - コード：`python`、`javascript`、`bash` など

### MD031（コードブロックの前後空行）

- **フェンス付きコードブロックの直前・直後に空行を入れる**
- コードブロック開始行（3連バッククォート＋言語指定）の直前に空行1行、終了行（3連バッククォート）の直後に空行1行を置く
- 修正例：段落やリストの直後にコードブロックを書く場合、その間に空行を1行入れる

### MD032（リストの前後空行）

- リスト（`-` や `1.` で始まる行）の直前・直後に空行を入れる

### MD024（重複見出し）

- **同一内容の見出しを複数使わない**（目次・アンカーが曖昧になる）
- 重複する場合は親セクション番号等を付与して一意にする（例：`### 受け入れ条件（AC）` → `### 5-8 受け入れ条件（AC）`）

### MD036（強調の見出し行き違反）

- **見出しとして使うつもりの行は `**太字**` や `_斜体_` にせず、`##` や `###` の見出しにする**
- 1行だけで強調のみの行は MD036 違反になる（例：`**Python（実装）**` → `### Python（実装）`）

### MD034（ベアURL）

- 生のURLは `<https://...>` のように角括弧で囲む
- 例：`（<https://example.com>）` とする

### MD033（インラインHTMLの禁止）

- **角括弧 `<>` で囲んだプレースホルダーは HTML タグと誤判定される**
- **パスパラメータ・API プレースホルダー**：`<id>` や `<modelId>` ではなく `{id}`、`{modelId}` など中括弧を使用する
  - 例：`/fishtrack/rod-model/{modelId}/edit`、`/catch/{id}`
- **実際の HTML 要素名を記述する場合**：`&lt;meta&gt;`、`&lt;body&gt;` のように HTML エスケープする
- **BEM などの記法**：`ft-{block}__{element}` のように中括弧でプレースホルダーを表す

### MD058（テーブルの前後空行）

- **テーブルの直前・直後に空行を入れる**
- テーブルと見出し・リスト・段落が隣接していると MD058 違反になる
- 修正例：テーブル終了行の直後、または直前の内容との間に空行を1行追加する

### MD060（テーブル列スタイル・compact）

- **各パイプ（`|`）の左右に必ずスペース1つを入れる**
- 区切り行：`| --- | --- |`（`|---|` は NG）
- データ行：`| セル1 | セル2 |`（セル直後の `|` の直前にスペースが必要。`セル。|` は NG、`セル。 |` は OK）
- 行末の閉じパイプも同様に直前スペースを入れる
- **継続行の空セル**：長いセルを分割する継続行では、空セルは `| | | |` のように記述（`|   |   |   |` だと MD060「extra space」エラーになる場合あり）

### MD041（先頭行H1）

- **ファイルの先頭行は H1 見出し**（`# タイトル`）であることが推奨される
- YAML frontmatter を使う場合は、frontmatter の直後の行を H1 とする
- 例外：AGENTS.md 等、用途上 H1 が不要なファイルは `.markdownlint.json` で無効化を検討

### MD047（末尾改行）

- **ファイル末尾は改行1つ**で終える（最後の行の直後に空行なし・改行1つのみ）
- 複数の改行や改行なしは違反

### MD051（リンクフラグメント）

- **アンカーリンク**（`[テキスト](#見出し)`）のフラグメントが、実際の見出しIDと一致する必要がある
- 修正：見出しの実際のID（小文字化・スペースはハイフン等）に合わせてリンクを修正する

## 仕様書（プロジェクト仕様）

- 内容・手順・注意点は **`specification-update`** SKILL に集約する（タスク ID を本文に書かないこと、実装との同時更新、計画書との役割分担など）。

## 一般的な記述

- 見出し階層を飛ばさない（`##` の次に `####` を置かない）
- 日本語句読点（。、）は統一して使用する

## 読みやすさ（構造・表・図）

- **長文の段落だけを続けない**。読み手が構造を一目で掴めるように、見出し・箇条書き・表・図のいずれかで区切る。
- **表**：複数項目の対応関係・可否・優先度・用語と説明などは、長い散文より **Markdown 表**にまとめる（前後空行・MD013 の継続行は **MD058／MD060**）。
- **図**：手順の分岐・時系列・構成関係は、必要に応じて **` ```mermaid `** のフローチャート／シーケンス／ガント等で示す（言語指定・前後空行は **MD040／MD031**）。
- **段落の長さ**：1 段落が長くなる場合は、論点ごとに **`###` 以下の見出し**へ分割するか、**番号付き／番号なしリスト**に落とす。
- **Obsidian／仕様書**：プレビューだけでなく **生の Markdown を読む**場面も前提にし、視覚的なチャンク（表・コードフェンス・見出し）を適度に挟む。

## 強調（太字）の使い方

- 既定は無装飾。Markdown をそのまま読んでも追いやすい本文にする。
- `` `**太字**` `` はごく少数に限定する。禁止・警告・運用上の絶対条件など、強調しなくても誤読する恐れがある箇所のみ。
- 技術名・フィールド名・コマンド・ファイル名・パス・識別子は太字ではなくインラインコード（`` `like_this` ``）を優先する。コードフェンス内も同様。
- 同じ段落で太字を連打しない。見出し・箇条書き・表で構造を示せるなら、本文は平文でよい。
- `ai_spec_check_report.md`（Obsidian 正本）は突合レポートとして長文になりやすいため、装飾より平文＋コード体裁を優先する（履歴 §6 の「実施内容」も同様）。

## 編集方針（既存ファイル編集時）

- 既存のMarkdown構造・見出し階層・箇条書きを維持する
- 文脈を壊さない最小限の編集で完結させる
- ファイルの改行は既存に合わせる（不用意に整形しない）

## MD060 設定（.markdownlint.json）

- プロジェクトでは MD060 を `style: "any"` で有効化している（compact / aligned / tight のいずれも許容）
- 新規作成・修正時は **compact スタイル**（`| --- | --- |`）を推奨

## 編集後の確認（推奨）

共通設定は `dev-workspace/.markdownlint.json`。全プロジェクト一括チェックは以下で実行可能：

```powershell
cd dev-workspace; .\scripts\markdownlint-all.ps1
```

- `-Fix` オプションで自動修正を試行
- レポートは `dev-workspace/temp/markdownlint-report.txt` に出力

エラーが残る場合は、該当行を200文字以内に分割し直す（MD013 有効時）。
