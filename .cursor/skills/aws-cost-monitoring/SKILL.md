# AWSコスト監視と改善提案

## 目的
AWSコストを定期的に監視し、コスト分析と最適化推奨事項を取得して、具体的な改善案を提案する。

## 実行フロー

### 1. コスト分析の実行
以下の方法を優先順位に従って実行：

**方法1（推奨）: AWS Billing MCPを使用**
- `cost-explorer` ツールでサービス別・リージョン別のコストを取得
- `cost-optimization` ツールで最適化推奨事項を取得
- `compute-optimizer` ツールでコンピューティングリソースの最適化推奨事項を取得
- `cost-anomaly` ツールでコスト異常を検出
- `budget` ツールで予算情報を取得

**方法2（フォールバック）: 既存スクリプトを使用**
- `python scripts/analyze_aws_cost.py` を実行（コスト分析）
- `python scripts/analyze_aws_resources.py` を実行（リソース詳細分析）

### 2. 分析結果の整理
以下の観点で分析結果を整理：

- **サービス別コスト**: 総コストに占める割合、前月比
- **リージョン別コスト**: リージョン分散の確認
- **日次コスト推移**: コストスパイクの検出
- **最適化推奨事項**: 推定節約額、優先度
- **コスト異常**: 異常なコスト増加の検出
- **予算状況**: 予算超過のリスク

### 3. 改善案の提案
分析結果に基づいて、以下の形式で改善案を提案：

```
## AWSコスト分析レポート

### サマリー
- 期間: [開始日] ～ [終了日]
- 総コスト: $[金額]
- 前月比: [増減率]%

### 主要なコスト要因
1. [サービス名]: $[金額] ([割合]%)
   - 改善案: [具体的な改善案]

### 最適化推奨事項
1. [推奨事項名]
   - 推定節約額: $[金額]/月
   - 優先度: [高/中/低]
   - 実施方法: [具体的な手順]

### コスト異常
- [異常の内容]: [日付]に$[金額]のコストスパイクを検出
  - 原因: [推測される原因]
  - 対応: [推奨される対応]

### 総合的な改善提案
1. [改善案1]: [詳細説明]
2. [改善案2]: [詳細説明]
```

## 分析項目

### 必須分析項目
1. **サービス別コスト分析**
   - 総コストに占める割合
   - 前月比の増減
   - 高コストサービスの特定

2. **リージョン別コスト分析**
   - リージョン分散の確認
   - リージョン集中のリスク評価

3. **日次コスト推移分析**
   - コストスパイクの検出
   - 平均日次コストの算出
   - 変動要因の特定

4. **最適化推奨事項の取得**
   - Compute Optimizerからの推奨事項
   - Cost Optimizationからの推奨事項
   - 推定節約額の算出

5. **コスト異常の検出**
   - 異常なコスト増加の検出
   - 原因の特定

6. **予算状況の確認**
   - 予算超過のリスク評価

### オプション分析項目
- RDSインスタンスの詳細分析
- EC2インスタンスの詳細分析
- NAT Gatewayの使用状況分析
- Elastic IPの使用状況分析
- S3ストレージの使用状況分析

## 改善案の優先順位付け

改善案は以下の基準で優先順位を付ける：

1. **高優先度**: 推定節約額が大きい（$30/月以上）、実施が容易
2. **中優先度**: 推定節約額が中程度（$3-30/月）、実施に中程度の工数
3. **低優先度**: 推定節約額が小さい（$3/月未満）、実施に大きな工数

## 実行時の注意事項

1. **期間の指定**: ユーザーが期間を指定していない場合は、直近1ヶ月を分析
2. **エラーハンドリング**: API呼び出しが失敗した場合は、既存スクリプトにフォールバック
3. **機密情報**: コスト情報は機密情報として扱い、必要に応じてマスク
4. **定期実行**: ユーザーが定期実行を希望する場合は、スケジュールを提案
5. **未使用インスタンスの削除提案**: EC2やRDSなどの未使用インスタンスの削除を提案する場合は、**必ず未使用かどうかを確認すること**
   - CloudWatchメトリクス（CPU、メモリ、ネットワーク、接続数など）を確認
   - タグや環境情報を確認（本番環境かどうか）
   - 使用履歴やログを確認
   - 確認が取れない場合は削除提案を行わない
6. **本番環境の考慮**: AWSは本番環境のため、**「使用時のみ起動」や「営業時間外の自動停止」などの提案は行わないこと**
   - 開発・テスト環境と本番環境を区別する
   - 本番環境では可用性を優先し、コスト削減よりも安定性を重視する
   - 自動停止・起動の提案は開発・テスト環境に限定する
7. **予算アラートの提案**: **予算アラートの作成提案は行わないこと**
   - 予算情報の取得や確認は行うが、予算アラートの設定や作成の提案はしない
8. **VPC Endpointの導入提案**: **VPC Endpointの導入を提案する場合は、必ずその効果を検討してから提案すること**
   - データ転送量の確認: `python scripts/analyze_data_transfer.py` を実行して、S3/DynamoDBへの実際のデータ転送量を確認
   - コスト削減効果の試算: VPC Endpointの固定料金（月額$7.2/サービス）と現在のデータ転送料を比較
   - 損益分岐点の計算: データ転送量が720GB/月以上の場合のみ、コスト削減の観点から導入を推奨
   - 効果が限定的な場合: データ転送量が少ない場合は、コスト削減の観点では導入を推奨しない
   - セキュリティ・パフォーマンス要件: コスト削減効果が限定的でも、セキュリティやパフォーマンス要件で導入が必要な場合は、その旨を明記
   - 提案時の必須項目:
     * 現在のデータ転送量（GB/月）
     * 現在のデータ転送コスト（$/月）
     * VPC Endpointの固定料金（$/月）
     * 導入後のコスト（$/月）
     * 削減額または増加額（$/月）
     * 損益分岐点（GB/月）
     * 推奨理由（コスト削減効果がある場合、またはセキュリティ・パフォーマンス要件がある場合）

## レポート出力形式

レポートは以下の形式で出力：

1. **サマリー**: 総コスト、前月比、主要なコスト要因
2. **詳細分析**: サービス別・リージョン別・日次推移
3. **最適化推奨事項**: 優先度順に整理
4. **改善提案**: 具体的な実施方法を含む

## 使用例

### 例1: 基本的なコスト分析
```
ユーザー: 「今月のAWSコストを分析して改善案を提案して」
→ 直近1ヶ月のコストを分析し、改善案を提案
```

### 例2: 特定期間のコスト分析
```
ユーザー: 「1月のAWSコストを分析して」
→ 2026-01-01 ～ 2026-01-31 のコストを分析
```

### 例3: コスト異常の調査
```
ユーザー: 「AWSコストが急に増えた原因を調査して」
→ コスト異常を検出し、原因を特定
```

### 例4: 定期監視の設定
```
ユーザー: 「AWSコストを定期的に監視する仕組みを作って」
→ 定期実行の仕組みを提案（スクリプト、スケジュールなど）
```
