# 仕事用ナレッジ深掘り（Work Knowledge Deepen）

## Work フォルダの位置づけ

- **会社の規約として明記されているものではない**。正式な規約・ルールは社内の SharePoint 等に集約されている。
- **暗黙知になっているものをまとめる**ためのノート群。手順は決まっているが文書化されていない、言い回しの意味、判断の基準など、形式知化されていない知識を蓄積・整理する。

## 記載不要なもの（Work へ載せない）

- **会社規約・就業規則・公式手順・SharePoint 等の正式文書**に**既に明記されている事項**は、Work に**転記・冗長な要約**をして保管する必要はない。**正本はあちら**とし、Obsidian での二重管理はしない。
- **別ドキュメント・別ツール・チーム Wiki 等でルールが既に定まっている**内容も同様。全文の写しやルール束を Work に複製しない。必要なら**参照先の一行**やリンクだけで足りる。
- 深掘りの結果、内容が「規約・別ルールの写し」になるだけなら**ノート更新は行わない**（ユーザーが「規約に明記」「別のルールで決まっている」と答えた場合の打ち切りと整合）。

## 適用条件

- **呼び出し**: ユーザーが「仕事用のナレッジを深掘りして」「Workのナレッジを整理して」「暗黙知を明文化して」などと依頼したとき、または本スキルを明示的に指定したときに実行する。
- **対象**: Obsidian の **Work** フォルダ配下のノート。業務・人間関係・業務外のメモなど、仕事に関わるあらゆる内容を含む。**規約・正式文書の置き場ではない**（それらは SharePoint 等を参照）。
- **保存先**: 深掘りした結果は必ず **Work** フォルダ内に作成・更新する（他フォルダには保存しない）。ノートは **テーマごとのフォルダ** に配置して管理する。
- **機密**: Work フォルダのノートは **社外秘** として扱う。内容の要約や引用は会話内・ログ内に最小限に留め、ネット検索や外部ツールには送信しない。

## パスとフォルダ構成

- **Work ルート**: `D:/OneDrive/アプリ/remotely-save/Obsidian/Work/`
- **テーマごとのフォルダ**: Work 直下に **テーマ（トピック）ごとのサブフォルダ** を作成し、ノートはそのテーマフォルダ内に配置する。
  - 例: `Work/休日出勤/`、`Work/顧客対応/`、`Work/社内手続き/`、`Work/引き継ぎ/`、`Work/その他/`
  - フォルダ名は短く分かりやすい名前（日本語可）。新規テーマの場合は必要なときにフォルダを新規作成する。
  - テーマが一つに決まらないノートは `Work/その他/` に置くか、ユーザーにテーマを確認する。
- 既存ノートがある場合はそのノートが属するフォルダに合わせる。新規ノートは、扱っているトピックに対応するテーマフォルダに作成する（フォルダが無ければ作成する）。

## ノート分割の基準（必須参照）

- Work フォルダで**ノートの新規作成・更新・分割**を行う際は、必ず **Work 内の「ノート分割の基準」** に従う。
- **基準ノート**: `D:/OneDrive/アプリ/remotely-save/Obsidian/Work/その他/ノート分割の基準.md`
- 新規ノートを作る前に「既存ノートに追記できないか」を検討し、まとめられる場合は 1 ノートにまとめる。分割が必要かどうかは基準ノートの「1フォルダ内でノートを分ける基準」に照らして判断する。

## ネタ帳の運用

- **ネタ帳**: 深掘り用のネタを蓄積するための **専用ノート** を用意する。パス例: `D:/OneDrive/アプリ/remotely-save/Obsidian/Work/ネタ帳.md`（Work 直下でよい）。
- **タンキング（蓄積）**: 次のようなネタは **常にネタ帳に追記** する。**深掘りの最中**（質問・回答・ノート閲覧時など）にも、後で深掘りしたいネタに気づいたら **随時** ネタ帳に追記する。
  - ユーザーや会話から「後で深掘りしたい」と感じたトピック。
  - AI が提案したがまだ深掘りしていないトピック。
  - 既存ノートを読んで「ここはぼんやりしている」と判断した箇所・テーマ。
- **ネタ帳の参照**: ネタの選定時は、まずネタ帳に未処理のネタがあればそこから 1 つ選ぶ。**選び方は上から順ではなく、重要度・優先度が高いと判断できるものから実施する**。ネタ帳が空または無い場合は、既存ノートから選ぶか、AI がトピックを 1 つ提案する。
- **完了したネタ**: 処理が完了したネタ（深掘りしてノート更新・報告まで終えたもの）は、ネタ帳から **削除** する。「済」マークは付けず、該当行をネタ帳から取り除く。
- **追記形式**: ネタ帳には日付（任意）と短い文言でリスト形式で追記する。
- **ネタ帳の構造例**（ファイルが無い場合はこの形で新規作成する）:

  ```markdown
  # 深掘りネタ帳
  - 休日出勤の流れ（誰に報告するか）
  - 社内の言い回し「〇〇」の意味
  ```

## 1 ラウンドで行うこと（これを止まるまで繰り返す）

1. **ネタの選定**
   - **ネタ帳** に未処理のネタがある場合: そこから **1つ** 選ぶ。選び方は **上から順ではなく、重要度・優先度が高いと判断できるもの** から実施する。選んだネタは、そのラウンドで深掘り・更新・報告が完了した時点でネタ帳から **削除** する。
   - ネタ帳が空または無い場合: Work フォルダ（およびそのサブフォルダ）のノートから「ぼんやりしている」「明確になっていない」知識を **1つ** 選ぶ。選んだテーマはネタ帳に追記しておく（タンキング）。深掘り完了後にネタ帳から削除する。
   - ノートが無い、または深掘りするネタが思いつかない場合: AI が **深掘り用のトピック** を 1 つ提案する。提案したトピックは **ネタ帳に追記** する（タンキング）。深掘り完了後にネタ帳から削除する。
   - 選んだ「1つの知識」または「提案トピック」を短く要約してユーザーに示す。**深掘りの最中**に新しいネタに気づいたら、その都度ネタ帳に追記する。

2. **質問**
   - その知識を明確にするために、**1問** 具体的な質問をユーザーにする。
   - 例: 「この手順のあと、守衛室には毎回報告が必要ですか？」「単価の話は誰まで共有してよい想定ですか？」

3. **回答の受領**
   - ユーザーが答える（「分からない」も有効な回答として受け止める）。
   - **規約・別ルールに明記されている**: ユーザーが「規約に明記されてる」「ルールで決まっている」「別ドキュメントにある」などと答えた場合は、**そのトピックの深掘りを打ち切り**、Work への転記は不要、ノートへの追記は行わず、ネタ帳から削除して次のネタに進む。

4. **ナレッジの更新**
   - 回答を元に、該当ノートに対して **追記・更新・削除** を必要に応じて行う。**規約・別途ルールの写し**になるだけの記述は追加しない（上記「記載不要なもの」に従う）。
   - **ノート分割の基準に従う**: 新規ノートを作る必要がある場合は、事前に Work 内の「ノート分割の基準」
     （`Work/その他/ノート分割の基準.md`）を参照し、既存ノートへの追記で足りないか・分割が必要かを判断する。
     該当ノートが無い場合は、必要なら **テーマに応じたフォルダ** に **新規ノート** を作成する。
   - **フォルダの扱い**:
     - 既存ノートを更新する場合: そのノートが属するテーマフォルダは原則変更しないが、テーマに合わない配置やフォルダ名があれば **必要に応じて見直し** を提案する（移動・リネームする場合はユーザーに確認してから実行する）。
     - 新規ノートの場合: 扱っているトピックに対応するテーマフォルダを決め、そのフォルダを存在しなければ作成してから、その中にノートを作成する（例: 休日出勤の話なら `Work/休日出勤/〇〇.md`）。テーマが決まらない場合は `Work/その他/` に作成するか、ユーザーにテーマ（フォルダ名）を確認する。
     - **配置・フォルダ名の見直し**: Work 直下に置かれているノートでも、サブフォルダ内のノートでも、内容やテーマに照らして **ノートの配置先** や **サブフォルダの名称** が適切でないと判断した場合は、見直しを提案し、ユーザー確認のうえで移動・リネームを行う。
     - 更新・作成時は以下を守る:
       - ノートには **追記** だけでなく、必要に応じて **既存文の更新** や **不要になった記述の削除** も行う。**見出しや構成の変更** も必要に応じて行う。必要な箇所に追記・修正・削除・見出し・構成の変更を行う。
       - **tags（タグ）** は、内容やテーマに応じて **必要に応じて追加** する。既存ノートのタグは尊重しつつ、深掘りで扱ったトピックを検索しやすくするため適宜タグを付与してよい。
       - **開示範囲** に触れる内容（単価・個人情報・評価・障害・遅延など）の場合は、ノート内に「開示範囲」を明記する（後述）。

5. **開示範囲の記録（該当する場合）**
   - 次のような情報を扱った場合は、ノート内に **開示範囲** を残す。
     - **単価（契約金額）**: 原則 **PL（本人）のみ**。顧客に利益額、協力会社に他社単価を知られない。
     - **個人情報**: 年齢・趣味・評価など、誰にどこまで開示してよいかを簡潔に。
     - **評価**: 本人に開示してよいもの・悪いものを区別して書く。
     - **障害・遅延**: 顧客や上長に意図的に共有していない場合は「顧客非開示」「上長非開示」などと書く。
   - 記録例:
     - ノート末尾や該当セクションに「開示範囲: PLのみ」「開示範囲: 本人のみ」「開示範囲: 顧客・他社非開示」などを追記。
     - またはフロントマターに `disclosure: "PLのみ"` のような形で残す。

6. **CursorLog（Work ノートを変更したとき必須）**
   - **Work** 配下の `.md` を **作成・更新・削除** したラウンドでは、**myrules** に従い **`obsidian-cursor-log` SKILL** で当日の CursorLog に記録する。\
     記録項目は、作業名・プロジェクト名・変更ファイル・実施内容・結果。タグは `#work-knowledge-deepen` 等。
   - **チャットでの冗長な報告**は不要でも、**CursorLog 省略は不可**。

7. **ネタ帳の整理**
   - このラウンドで扱ったネタをネタ帳から **削除** する。
   - チャット上の**作業完了サマリ**は最小限でよい（詳細は CursorLog とノート差分で確認できる前提）。

8. **繰り返し**
   - 上記 1〜8 を **繰り返し実行する**。止まる条件は次のいずれかだけとする。
     - ユーザーが「止めて」「終わり」「もういい」などと **明示的に止める** まで。
     - ユーザーが **回答せずにチャットを閉じる** まで。
   - つまり、ユーザーが止めるか、回答せずにチャットを閉じるまで、ネタ選定 → 質問 → 回答受領 → 更新 → （必要なら CursorLog）→ ネタ帳整理のサイクルを続ける。

## 注意事項

- **Markdown編集時**: Workフォルダ内のノート（.md）を編集する際は、`markdown-editing` SKILLのルールに従う
- **CursorLog**: Work 配下ノートを **作成・更新・削除** したときは **myrules** に従い **`obsidian-cursor-log` SKILL** で記録する（手順 **6**）。チャットを短く済ませてもログ省略はしない。
- **社外秘**: Work の内容は会話外に持ち出さない。要約も最小限とする。
- **ネット検索**: 業務固有の内容のため、基本的にネット検索で補完しない（ユーザー回答を優先する）。
- **1 回 1 テーマ**: 1 回の実行では「1 つのぼんやりした知識」または「1 つの提案トピック」だけを扱う。
- **分からない**: ユーザーが「分からない」と答えた場合は、その旨をノートにメモ（例: 「〇〇については未整理・要確認」）して更新し、次のネタに進める。
- **規約に明記されている / 別ルールで決まっている**: ユーザーが「規約に明記されてる」「ルールで決まっている」「別ドキュメントに書いてある」などと答えた場合は、**それ以上深掘りしない**。Work へ規約・ルールの写しを載せる必要はない。ノートへの追記は行わず、ネタ帳から削除して次のネタに進む。
- **既存スタイル**: 既存ノートのタグ・見出し・リンク形式は尊重し、必要な範囲でだけ変更する。**tags は必要に応じて追加**してよい（検索・分類のため）。ノートへの反映は追記に限らず、**必要に応じて更新・削除** も行う。
- **テーマフォルダ**: 新規ノートは必ずテーマに応じたサブフォルダに作成する。既存ノート（Work 直下・サブフォルダ内を問わず）については、必要に応じて **ノートの配置先** や **サブフォルダの名称** を見直し、テーマに合うよう移動・リネームを提案する（実行時はユーザーに確認する）。

## ノートの構造例（新規作成時）

```markdown
---
created: YYYY-MM-DD
tags:
  - work
---

# [トピック名]

## 内容
[深掘りして得た知識を記述]

## 開示範囲（該当する場合）
- 単価: PLのみ
- 〇〇: 本人のみ / 顧客非開示 など

## メモ・未整理（該当する場合）
- 〇〇については要確認
```

## 実行手順のまとめ

1. **ネタ帳** を確認し、未処理のネタがあればそこから 1 つ選ぶ（**上から順ではなく、重要度・優先度が高いと判断できるものから実施**）。無ければ Work フォルダ（およびテーマサブフォルダ）のノート一覧を確認するか、トピックを 1 つ提案する。提案・発見したネタはネタ帳に追記（タンキング）する。深掘りの最中も随時ネタ帳に追記する。完了したネタはネタ帳から削除する。
2. 深掘りする「1 つの知識」または「1 つのトピック」を決め、ユーザーに示す。
3. それを明確にするための質問を 1 つする。
4. ユーザーの回答を受け取る。
5. 該当ノートに **追記・更新・削除** を必要に応じて行う（**規約・別ルールの写し**は載せない）。該当ノートが無い場合は **ノート分割の基準**（Work/その他/ノート分割の基準.md）に従い、既存ノートへの追記で足りるか検討したうえで、必要なら **テーマに応じたフォルダ** 内に新規ノートを作成する（開示範囲があれば記録）。
6. Work ノートやネタ帳を **ファイルとして変更**した場合は **`obsidian-cursor-log` SKILL** で CursorLog を更新する。
7. 扱ったネタをネタ帳から削除する（チャット上のサマリは最小限でよい）。
8. **1 に戻り、上記 1〜8 を繰り返す。** ユーザーが「止めて」などと止めるか、回答せずにチャットを閉じるまで継続する。
