# UX 改善アイデア検討

myrules を厳守して作業してください。**品質メトリクス（テスト・カバレッジ等）は対象外**。

## 目的（ビジネス寄りのゴール）

本コマンドで扱うアイデアの**主目的**は次の連鎖を狙うことである。

1. **プロジェクトの価値向上**（ユーザーにとっての有用性・信頼・継続利用のしやすさなど）
2. それに伴う **アクセス数・会員数（利用者数）の向上**
3. さらに **利益の拡大**（収益モデルに照らし、売上・LTV・コスト構造などへの効き方を意識する）

体験・画面の快適さだけでなく、**上記にどう効くか**を返信で意識して書く。数値目標の捏造はしない（**仮説・要確認**で足りない情報を明示する）。

### 2. 統合作業スケジュールへのタスク記載（必須）

本コマンドで挙げた **各アイデア**は、**具体案として起こしたうえで**、次のファイルに **タスクとして追記する**。

- **正本**: `D:/OneDrive/アプリ/remotely-save/Obsidian/DevProject/plans/統合作業スケジュール.md`

**単一情報源の原則（重要）**:

- 後から **本ファイル（統合作業スケジュール）だけ**を開いた人が、**チャット履歴なしで**次をできるように書く。
  - **検討**: 何を判断すればよいか、論点・トレードオフ・関連タスクが分かる。
  - **実装（採用が決まったあと）**: 仕様・コードのどこを読み・どこを変える想定か、着手の手がかりが足りる（実装タスク ID の新設は別手順でもよいが、\
      **曖昧な一行**で終わらせない）。
- **一覧表（[[#タスク一覧]]）** は **`integrated-schedule-update` SKILL** のとおり **1行要約**に収める。\
    **本文の詳細は [[#タスク詳細]] 側**に集約する（一覧に続き行を増やさない）。

**タスクの性質（重要）**:

- **実装タスクにしない**。アイデアそのものを「やること」として一覧に載せない。
- **検討タスク**とする。表記のイメージ: **「UXアイデア（〈具体案の短いラベル〉）採用要否の検討」**。
- **タスク実行時のゴール**は、そのアイデアを **採用するかどうか判断・整理すること**。採用が決まった後の実装は、**別途**仕様・既存バックログに沿ってタスク化する（\
    本コマンドの出力タスクに実装工程を混ぜない）。
- **採用要否の検討**タスクとして、計画書 **[[#タスク詳細]]** の **タスク一覧補足**に既にある **検討のみ** と明記された行と**同じスタンス**で書く。\
    **詳細の書きぶり**は **ねらい／具体案／論点／分担・横断／採用時** 等の構成で、下表の必須項目を満たす**同等以上**の具体度にする。\
    **特定のタスク ID を本コマンドに固定例として書かない**（完了・削除で参照が死ぬため）。計画書内の**現時点の**同種行があれば体裁の手本にし、無ければ下表と本節を正とする。\
    新規 ID の採番・**一覧・週次・ガントの三本柱**は **`integrated-schedule-update` SKILL**（\
    `dev-workspace/.cursor/skills/integrated-schedule-update/SKILL.md`）に**編集前に Read して従う**。

**[[#タスク詳細]] への必須記載（同一作業で追記する）**:

該当プロジェクトの **`### 【詳細】〈製品名〉`** 直下、既存の **「タスク一覧補足」** に、\
    新規タスク ID の **`- **Fxx**:` / `- **Pxx**:` 形式のブロック**を追加または拡張する。\
    次を **漏れなく**含める。\
    体裁は、**同一セクション内に**既にある **採用要否・検討のみ** のブロックがあればそれに揃え、無ければ下表を正とする。

| 観点 | 書くこと（最低限） |
| --- | --- |
| **ねらい・課題** | 誰の・どの状況の UX／事業上の課題を解く案か |
| **具体案** | 画面名・導線・操作・文言・表示条件（「空のときは非表示」等）を **実装イメージが浮かぶレベル**まで |
| **論点・トレードオフ** | 主操作・課金／広告・同意・PP・他機能との兼ね合い・重複する既存タスク |
| **根拠・参照** | 根拠とした **Obsidian 仕様のパス**（`04` / `05` / `07` 等の短縮は計画書の慣例に合わせる）、**関連タスク ID**、計画書内リンク（[[#6]]・[[#7]]） |
| **コード・着手の手がかり** | 分かる範囲で **ブループリント名・テンプレートパス・クエリパラメータ名・JS モジュール** 等（ |
| | 調査時に特定したものを記載。不明なら **要確認** と明記） |
| **採用時** | 仕様書のどれと突合し、**実装は別タスク化**する旨（本タスクの境界）。必要なら **受け入れ条件**（何ができれば採用とみなすか）を短文で |

**アイデアの具体性（タスク追記前の必須条件）**:

- 抽象語だけのタスク名にしない。**どの画面・導線・ユーザー状況に効くか**が一覧の **タスク名／内容概要**から伝わる粒度まで具体化する（長文は **[[#タスク詳細]]** へ）。

## エージェント向け手順（仕様・実装に基づき単独で検討）

**ユーザーに箇条書きで聞き取りするのではなく、AI が仕様とコードを読み、アイデアを具体化してから返す。**\
不足は推測では補わず、**仕様・実装に根拠が薄い箇所は「仮説」「要確認」と明記**する。

1. **対象の把握**\
   会話・開いているファイル・`@` 参照から **検討対象**を決める。**プロダクト名に限定しない**（機能・導線・画面群・リポジトリ・複数プロダクト横断など、文脈で定める）。\
   判別できないときだけ、**1 行で**ユーザーに確認する。

2. **根拠の収集（必須・Read / 検索）**\
   上記 **「全プロダクトを参考にする」** を先に満たす。\
   続けて **検討対象**に応じた **実装**を追う（**ルート・画面テンプレ・フロントの JS・フォーム** など。**SemanticSearch** や **Read** を使う）。\
   検討対象が横断や未指定のときは、三リポジトリのうち **文脈に効く箇所**に絞ってコードを読んでもよい。

3. **チャット返信にまとめる**\
   **チャット返信 1 本**で、仕様・実装に基づく UX 改善の考察を書く。**空枠や「後で埋める」だけの返答はしない。**\
   次は **内容として含める**（見出し名・順序・表の有無は自由）:
   - **根拠**: 読んだ **仕様・`AGENTS.md`・コード**（パスやファイル名を簡潔に）
   - **ユーザー文脈・摩擦**: 仕様・実装から読み取れる困り・機会
   - **改善案**: **画面・導線・文言レベルまで具体化**したアイデア（抽象一行で終わらせない）。\
     **価値向上・流入・会員獲得・利益**のどこに効きうかを、**FishTrack／MyPokedex＝広告・利用継続、おたよりナビ＝課金・継続**の前提で無理のない範囲で一行添える
   - **優先の目安**: 手堅く試せそうなもの、**事業インパクト**が大きそうなものなど、**主観でよい**が理由を一言添える
   - **仮説・要確認**: 根拠が薄い点

4. **統合作業スケジュールを更新する**\
   上記の **各具体アイデア**について、**「採用要否の検討」タスク**を `統合作業スケジュール.md` に追加する（**三本柱**・**SKILL** 準拠）。\
   追加時は **一覧・詳細・週次の末尾に機械的に足すだけ**にせず、**`integrated-schedule-update` SKILL** の **「新規追加時の順序（優先度・影響）」** に従い、優先度・影響・依存を踏まえて **週次・ガント・詳細補足の位置**を検討する。\
   **同一編集**で **[[#タスク一覧]]** に加え、**[[#タスク詳細]]** の **タスク一覧補足** に **上表の必須記載**を満たす本文を書く（**一覧のみで終了禁止**）。\
   チャット本文に、**付与したタスク ID**・**一覧行**・**詳細補足を書いた節**を簡潔に示す。

5. **禁止・注意**\
   **断定やデータの捏造はしない。** アクセスログや利用実態が無い数値は書かない。\
   **勝手に各プロジェクトの `docs/` に新規ドキュメントを作らない**（myrules「ドキュメント作成規律」）。\
   **Obsidian の計画書**（本コマンドで指定した **統合作業スケジュール**）への追記は、上記のとおり **必須**。
