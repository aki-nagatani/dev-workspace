## 11. マイグレーションリセット後の再適用計画

### 11.1 概要

#### マイグレーションリセットとは

**マイグレーションリセット**とは、Alembicのマイグレーション履歴を管理する`alembic_version`テーブルを削除し、マイグレーション履歴をリセットした後、`alembic stamp`を使用して現在のDBの状態を統合マイグレーション（`merge_fishtrack_mypokedex_heads`）としてマークする作業です。スキーマが一致しているため、マイグレーションを再適用する必要はありません。

#### なぜマイグレーションリセットが必要か

1. **マイグレーション履歴の統合**
   - 現在、FishTrackとMyPokedexは個別のマイグレーション履歴を持っている
   - 統合データベース（shared-db）では、両方のマイグレーション履歴を統合する必要がある
   - 統合マイグレーション（`merge_fishtrack_mypokedex_heads`）が、両方のheadをマージしている

2. **本番環境とローカル環境の状態の統一**
   - 本番環境: MyPokedexの最新マイグレーションが適用済み
   - ローカル環境: FishTrackとMyPokedexの個別マイグレーションが適用済み
   - マイグレーションリセットにより、両環境を統合マイグレーションから開始する状態に統一

3. **マイグレーション履歴の統一**
   - 過去のマイグレーション履歴をリセットし、現在のDBの状態をスタート地点として設定
   - 統合マイグレーション（`merge_fishtrack_mypokedex_heads`）を基準点として記録

4. **スキーマの整合性確保**
   - 現在のDBの状態が正しいことを前提に、マイグレーション履歴のみを設定
   - スキーマが既に一致しているため、マイグレーションを再適用する必要はない

#### マイグレーションリセットの手順概要

**目的**: 過去のマイグレーション履歴をなかったことにし、現在のDBの状態をスタート地点として設定します。

**前提**: スキーマが一致しているため、マイグレーションを再適用する必要はありません。`alembic stamp`を使用してマイグレーション履歴のみを設定します。

**手順**:

1. **`alembic_version`テーブルを削除**
   - マイグレーション履歴をリセット
   - データベースのスキーマ（テーブル、カラム、制約など）は削除しない

2. **`alembic stamp`でマイグレーション履歴を設定**
   - 現在のスキーマ状態を統合マイグレーション（`merge_fishtrack_mypokedex_heads`）としてマーク
   - マイグレーションを実行せず、履歴のみを更新
   - これにより、現在のDBの状態が統合マイグレーションの状態として記録される

**結果**:
- 過去のマイグレーション履歴はなかったことになる
- 現在のDBの状態が統合マイグレーション（`merge_fishtrack_mypokedex_heads`）の状態として記録される
- 今後新しいマイグレーションが追加された場合、そのマイグレーションから適用される

**重要**: 
- 統合マイグレーションは、FishTrackとMyPokedexの両方のhead（`make_rod_model_series_id_not_null`と`20251225_change_boxmember_to_composite_primary_key`）をマージするため、現在のDBの状態をこのリビジョンとしてスタンプします
- スキーマが一致しているため、マイグレーションを再適用する必要はありません（既存のスキーマを変更しないため）

2. ✅ **マイグレーション履歴の確認完了**（セクション9参照）

## 13. 今後のマイグレーション運用方針

### 13.1 マイグレーションチェーンの構造

統合マイグレーション（`merge_fishtrack_mypokedex_heads`）以降は、**線形チェーン**として管理します。

```
統合マイグレーション（merge_fishtrack_mypokedex_heads）
  ↓
新しいマイグレーション1（例: rename_rod_holding_constraints）
  ↓
新しいマイグレーション2
  ↓
新しいマイグレーション3
  ...
```

### 13.2 新しいマイグレーションの追加手順

#### ステップ1: マイグレーションファイルの作成

1. **ファイル配置**: `dev-workspace/migrations/versions/shared/`ディレクトリに配置
   - 統合後は共通マイグレーションとして扱うため、`shared/`ディレクトリを使用

2. **ファイル名**: `YYYYMMDDHHMMSS_説明.py`形式
   - 例: `20260103000000_rename_rod_holding_constraints.py`

3. **`down_revision`の設定**: 最新のマイグレーション（または統合マイグレーション）を参照
   ```python
   down_revision = "merge_fishtrack_mypokedex_heads"  # または最新のマイグレーション
   ```

#### ステップ2: マイグレーション内容の実装

- テーブル存在チェックを実装（既存テーブルへの影響を最小化）
- プロジェクト固有の変更は条件分岐で対応
- `upgrade()`と`downgrade()`の両方を実装

#### ステップ3: ローカル環境でのテスト

```bash
# ローカル環境でマイグレーションを実行
python scripts/run_migrations.py

# マイグレーション状態を確認
python scripts/check_migration_status.py
```

#### ステップ4: 本番環境への適用

- **デプロイ経由**: FishTrackまたはMyPokedexの`main`ブランチにプッシュすると、自動的にマイグレーションが実行されます
- `dev-workspace/scripts/run_migrations.py`が実行され、`alembic upgrade head`で最新まで適用されます

### 13.3 この方針のメリット

1. **シンプルで理解しやすい**: 線形チェーンにより、マイグレーションの順序が明確
2. **自動適用**: デプロイ時に`alembic upgrade head`で最新まで自動適用
3. **一貫性**: 統合後は共通マイグレーションとして管理

### 13.4 この方針のデメリットと対策

#### デメリット1: プロジェクト別の独立開発が難しくなる

**問題**: FishTrackとMyPokedexで同時にマイグレーションを作成すると競合しやすい

**対策**:
- マイグレーション作成前にチーム内で調整
- マイグレーションのタイムスタンプで順序を明確化
- 必要に応じて、マイグレーション内でプロジェクト固有の変更を条件分岐で対応

#### デメリット2: マイグレーションの依存関係が複雑になる可能性

**問題**: プロジェクト固有の変更も共通チェーンに入る可能性

**対策**:
- マイグレーション内でテーブル存在チェックを実施（既に実装済み）
- プロジェクト固有の変更は条件分岐で対応

#### デメリット3: ロールバック時の影響範囲

**問題**: 線形チェーンでは、途中のマイグレーションをロールバックすると後続も影響を受ける可能性

**対策**:
- ロールバックは慎重に実施
- 必要に応じて新しいマイグレーションで修正

### 13.5 マイグレーションファイルの配置ルール

- **統合前**: `fishtrack/`または`mypokedex/`ディレクトリ
- **統合後**: `shared/`ディレクトリ（共通マイグレーション）

### 13.6 現在のマイグレーションチェーン

```
統合前:
  FishTrack: ... → make_rod_model_series_id_not_null
  MyPokedex: ... → 20251225_change_boxmember_to_composite_primary_key

統合:
  merge_fishtrack_mypokedex_heads

  merge_fishtrack_mypokedex_heads
    ↓
```

### 13.7 注意事項

1. **統合マイグレーションの`down_revision`は変更しない**: 統合マイグレーションは一度だけ実行されるべきもので、その構造は変更しない
2. **新しいマイグレーションは統合マイグレーションの後に追加**: 統合マイグレーションを起点として線形に追加
3. **マイグレーションの順序**: タイムスタンプで順序を明確化し、競合を避ける
