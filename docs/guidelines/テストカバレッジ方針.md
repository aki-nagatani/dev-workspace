# テストカバレッジ方針

## 基本方針

**原則として、テストの除外は認めません。**

すべてのソースコードはテスト可能であり、テストを書くべきです。テストカバレッジは99%以上を目標とします。

## カバレッジ目標

### Pythonテスト

- **目標カバレッジ**: 99%以上
- **設定**: `pyproject.toml` の `--cov-fail-under=99`
- **測定範囲**: `src/mypokedex` と `src/fishtrack` のすべてのPythonファイル

### JavaScriptテスト

- **目標カバレッジ**: 99%以上
- **設定**: `package.json` の `jest.coverageThreshold` で設定
- **測定範囲**: `src/mypokedex/static/js` と `src/fishtrack/static/js` のすべてのJavaScriptファイル
- **カバレッジ指標**: branches, functions, lines, statements すべて99%以上

## テスト実行ルール

### Pythonテスト

- **基本**: `pytest-xdist` の `-n auto` で並列実行し、実行時間を最適化する
- **例外**: 並列非対応ケース（プロセス間共有リソースなど）は単一プロセス実行を許可。ただし理由と暫定対応を本ガイドや関連計画に記録する
- **推奨コマンド**:
  ```bash
  python -m pytest -n auto --cov=src --cov-branch
  ```

### JavaScriptテスト

- **テストフレームワーク**: Jest（`jest-environment-jsdom` を使用）
- **実行環境**: jsdom環境でブラウザAPIをシミュレート
- **基本**: Jestのデフォルト並列実行を使用
- **推奨コマンド**:
  ```bash
  # 通常のテスト実行
  npm test
  
  # カバレッジ付きテスト実行
  npm run test:coverage
  
  # CI環境でのテスト実行
  npm run test:ci
  ```
- **テストファイル配置**: `tests/js/` ディレクトリに配置
- **テストファイル命名規則**: `*.test.js` または `*.spec.js`

## 除外設定の禁止

### 1. ファイル単位の除外禁止

#### Pythonテスト

`pyproject.toml`の`[tool.coverage.run]`および`[tool.coverage.report]`セクションの`omit`設定は使用しません。

#### JavaScriptテスト

`package.json`の`jest.collectCoverageFrom`設定で、テストファイルやnode_modules以外の除外は行いません。すべてのJavaScriptソースファイルをカバレッジ測定対象に含めます。

**禁止事項**:
- 大きなファイルだからという理由での除外
- 「段階的なテスト追加を前提」という理由での除外
- テストが困難という理由での除外

### 2. 行単位の除外の最小化

#### Pythonテスト

`# pragma: no cover`の使用は最小限に抑えます。

#### JavaScriptテスト

Jestの`/* istanbul ignore */`コメントの使用は最小限に抑えます。Pythonテストと同様の方針を適用します。

**認められる例外**（例外的な場合のみ）:
- **型チェック専用コード**: `if TYPE_CHECKING:`ブロック（実行時には評価されない）
- **開発環境専用コード**: 本番環境では絶対に実行されない開発用ツールやシードデータ生成
- **実装上どうしても再現できない安全弁**: 例えば `_extract_nories_rod_variants` のフォールバックのように、現状のテンプレートや入力仕様では到達しないことを確認済みのコード。*必ず* (1) 再現可能性を調査して記録し、(2) `pragma: no cover` などの除外を明示し、(3) 理由と対策案を本ガイドまたは計画書に記載すること。安易な除外は禁止

**認められない理由**:
- ❌ 「プレースホルダー関数」→ 未実装機能は削除するか、実装する
- ❌ 「デバッグ用コード」→ デバッグ用コードもテスト可能
- ❌ 「防御的プログラミング」→ 例外ハンドリングもテスト可能
- ❌ 「テストが困難」→ テスト方法を検討する
- ❌ 「大きなファイル」→ 段階的にテストを追加する

### 3. テスト実行時のスキップの最小化

#### Pythonテスト

`pytest.skip()`や`@pytest.mark.skip`の使用は最小限に抑えます。

**認められる例外**:
- 環境依存のテスト（特定のライブラリが利用可能な場合のみ実行）
- ただし、その場合も代替テストを用意する

#### JavaScriptテスト

`test.skip()`や`describe.skip()`の使用は最小限に抑えます。

**認められる例外**:
- 環境依存のテスト（特定のブラウザAPIが利用可能な場合のみ実行）
- ただし、その場合も代替テストを用意する

## 実装方針

### プレースホルダー関数の扱い

プレースホルダー関数（未実装機能）は以下いずれかの対応を行います：

1. **実装してテストを追加する**（推奨）
2. **削除する**（使用されていない場合）
3. **実装計画を明確にし、期限を設定する**

この方針はPythonとJavaScriptの両方に適用されます。

### デバッグ用コードの扱い

#### Pythonテスト

`__repr__()`メソッドなどのデバッグ用コードもテストします：

```python
def test_model_repr():
    model = Model(name="Test")
    repr_str = repr(model)
    assert "Test" in repr_str
    assert "Model" in repr_str
```

#### JavaScriptテスト

`console.log()`やデバッグ用の関数もテストします。必要に応じてモックを使用します：

```javascript
test('デバッグ出力のテスト', () => {
    const consoleSpy = jest.spyOn(console, 'log').mockImplementation();
    debugFunction();
    expect(consoleSpy).toHaveBeenCalled();
    consoleSpy.mockRestore();
});
```

### 防御的プログラミングの扱い

#### Pythonテスト

例外ハンドリングもテストします：

```python
def test_exception_handling():
    with pytest.raises(ExpectedException):
        function_that_raises()
```

#### JavaScriptテスト

エラーハンドリングもテストします：

```javascript
test('例外処理のテスト', () => {
    expect(() => {
        functionThatThrows();
    }).toThrow(ExpectedError);
});
```

### 大きなファイルの扱い

大きなファイルは段階的にテストを追加します：

1. 新規機能追加時には必ずテストを追加
2. 既存機能の修正時には該当箇所のテストを追加
3. リファクタリング時にテストを追加

この方針はPythonとJavaScriptの両方に適用されます。

### JavaScriptテストの特殊な考慮事項

#### DOM操作のテスト

ブラウザ環境をシミュレートするため、`tests/js/setup.js`でDOM APIをモックします。必要に応じて、各テストで追加のDOMモックを設定します。

#### 非同期処理のテスト

Promiseやasync/awaitを使用するコードは、適切に非同期テストを記述します：

```javascript
test('非同期処理のテスト', async () => {
    const result = await asyncFunction();
    expect(result).toBe(expectedValue);
});
```

#### イベントリスナーのテスト

DOMイベントを発火させてテストします：

```javascript
test('イベントリスナーのテスト', () => {
    const element = document.createElement('button');
    const handler = jest.fn();
    element.addEventListener('click', handler);
    element.click();
    expect(handler).toHaveBeenCalled();
});
```

## 移行計画

既存の除外設定を段階的に削除します：

### フェーズ1: 除外設定の削除
- `pyproject.toml`の`omit`設定を削除
- すべてのファイルをカバレッジ測定対象に含める

### フェーズ2: テストの追加
- 除外されていたファイルのテストを追加
- `# pragma: no cover`の大部分を削除し、テストを追加

### フェーズ3: カバレッジ目標の達成
- 99%以上のカバレッジを達成
- 継続的に維持

## 例外の申請

やむを得ない理由で除外が必要な場合は：

1. **理由を明確に文書化する**
2. **代替手段を検討する**
3. **承認を得る**
4. **期限を設定する**（一時的な除外の場合）

## チェック方法

### Pythonテスト

- `pytest`実行時に自動的にカバレッジが測定される
- `--cov-fail-under=99`により、99%未満の場合はテストが失敗する
- CI/CDでも自動的にチェックされる

### JavaScriptテスト

- `npm test`または`npm run test:coverage`実行時に自動的にカバレッジが測定される
- `package.json`の`jest.coverageThreshold`により、99%未満の場合はテストが失敗する
- カバレッジレポートは`htmlcov/js/`ディレクトリに出力される
- CI/CDでも自動的にチェックされる

## まとめ

- **原則**: テストの除外は認めない（Python、JavaScript共通）
- **目標**: カバレッジ99%以上（Python、JavaScript共通）
- **方針**: すべてのコードはテスト可能であり、テストを書く（Python、JavaScript共通）
- **例外**: 最小限のみ、理由を明確に文書化（Python、JavaScript共通）

### テストフレームワーク

- **Python**: pytest + pytest-cov
- **JavaScript**: Jest + jest-environment-jsdom

### カバレッジ測定

- **Python**: `pytest --cov=src --cov-branch` で測定
- **JavaScript**: `npm run test:coverage` で測定
