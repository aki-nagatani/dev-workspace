# マイグレーションガイドライン

## 概要

本プロジェクトでは、Alembicを使用してデータベースマイグレーションを管理しています。
FishTrackとMyPokedexが共有データベースを使用しているため、マイグレーションファイルは`dev-workspace/migrations/`で一元管理されています。

**決定日**: 2026-01-08

## マイグレーション管理構造

### ディレクトリ構成

```
dev-workspace/
└── migrations/
    ├── alembic.ini          # Alembic設定ファイル
    ├── env.py               # Alembic環境設定（両プロジェクトのモデルを統合）
    ├── script.py.mako       # マイグレーションファイルテンプレート
    └── versions/
        ├── fishtrack/       # FishTrack専用のマイグレーション（過去のファイル）
        ├── mypokedex/       # MyPokedex専用のマイグレーション（過去のファイル）
        └── shared/          # 共有マイグレーション（現在の作業場所）
```

### マイグレーションファイルの配置場所

**重要**: すべての新しいマイグレーションファイルは、**必ず`dev-workspace/migrations/versions/shared/`に配置してください。**

- ✅ **正しい場所**: `dev-workspace/migrations/versions/shared/`
- ❌ **誤り**: `FishTrack/migrations/versions/`
- ❌ **誤り**: `MyPokedex/migrations/versions/`
- ❌ **誤り**: `dev-workspace/migrations/versions/fishtrack/`（新規作成時）
- ❌ **誤り**: `dev-workspace/migrations/versions/mypokedex/`（新規作成時）

### 理由

- 複数のプロジェクト（FishTrack、MyPokedex）が共有データベースを使用しているため
- マイグレーション管理を一元化するため
- データベーススキーマの整合性を保つため
- マイグレーション履歴を統一するため

## マイグレーション作成手順

### 1. 作業ディレクトリの移動

マイグレーションファイルを作成する際は、**必ず`dev-workspace`ディレクトリで作業してください。**

```bash
cd dev-workspace
```

### 2. 環境変数の設定

データベースURLを環境変数で設定します。

```bash
# 共有データベースURL（推奨）
export SHARED_DATABASE_URL="postgresql://user:password@host:port/database"

# または
export SHARED_DB_URL="postgresql://user:password@host:port/database"

# 下位互換性のための環境変数（可能な限り使用しない）
export FISHTRACK_DATABASE_URL="postgresql://user:password@host:port/database"
export MYPDEX_DATABASE_URL="postgresql://user:password@host:port/database"
export DB_URL="postgresql://user:password@host:port/database"
```

**優先順位**:
1. `SHARED_DATABASE_URL`（最優先）
2. `SHARED_DB_URL`
3. `FISHTRACK_DATABASE_URL`（下位互換性）
4. `MYPDEX_DATABASE_URL`（下位互換性）
5. `DB_URL`（汎用）

### 3. モデルの変更

SQLAlchemyモデルを変更します（`FishTrack/src/`または`MyPokedex/src/`配下のモデルファイル）。

### 4. マイグレーションファイルの自動作成

```bash
cd dev-workspace
alembic revision --autogenerate -m "マイグレーション説明"
```

**推奨事項**:
- マイグレーション説明は簡潔で明確に記述する
- 変更内容を端的に表現する（例: `add_email_to_user_tables`、`remove_username_from_user_tables`）
- 日本語の説明も使用可能

**例**:
```bash
alembic revision --autogenerate -m "add_email_to_user_tables"
alembic revision --autogenerate -m "ユーザーテーブルにメールアドレスカラムを追加"
```

### 5. マイグレーションファイルの確認と修正

作成されたマイグレーションファイルは、`dev-workspace/migrations/versions/shared/`に配置されます。
以下の点を確認してください：

1. **ファイルの配置場所**: `dev-workspace/migrations/versions/shared/`にあるか確認
2. **upgrade()関数**: 期待通りの変更が生成されているか確認
3. **downgrade()関数**: ロールバック処理が正しく生成されているか確認
4. **依存関係**: `down_revision`が正しく設定されているか確認
5. **データ移行**: 必要に応じてデータ移行ロジックを追加

**注意事項**:
- 自動作成されたマイグレーションは必ず確認・修正すること
- 不要な変更（例: インデックス名の変更など）は削除すること
- データ損失を伴う変更は、データ移行処理を追加すること

### 6. マイグレーションの実行

マイグレーションの実行は、環境ごとに適切な手順で行う必要があります。
ローカルのDocker環境と本番環境では、実行方法と注意事項が異なります。

#### 6.2 本番環境での実行

##### 前提条件

1. **バックアップの取得（必須）**
   - マイグレーション実行前に、必ずデータベースのバックアップを取得すること
   - RDSの場合は自動バックアップを確認、または手動スナップショットを作成

2. **メンテナンスウィンドウの確保**
   - 本番環境への影響を最小限に抑えるため、適切なタイミングで実行
   - 必要に応じてメンテナンスモードを有効化

3. **実行計画の確認**
   - 適用するマイグレーションの内容を確認
   - データ損失の可能性がある場合は、特別な注意が必要

##### 実行手順

**推奨方法: GitHub Actions経由での実行**

本番環境では、GitHub Actionsのワークフローでマイグレーションを自動実行します。
デプロイメント時に自動的にマイグレーションが実行されます。

**GitHub Actionsワークフローの例**:

```yaml
name: Deploy to Production

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'
      
      - name: Install dependencies
        run: |
          pip install alembic sqlalchemy psycopg2-binary
      
      - name: Run database migrations
        env:
          SHARED_DATABASE_URL: ${{ secrets.SHARED_DATABASE_URL }}
        run: |
          cd dev-workspace
          python scripts/run_migrations.py
      
      # マイグレーション成功後、アプリケーションをデプロイ
      - name: Deploy application
        # ... デプロイ手順
```

**GitHub Actionsでの実行フロー**:

1. コードを`main`ブランチにプッシュ
2. GitHub Actionsワークフローが自動的にトリガー
3. マイグレーションが自動実行（`run_migrations.py`を使用）
4. マイグレーション成功後、アプリケーションをデプロイ

**重要**: 本番環境でのロールバックは、データ損失のリスクがあるため慎重に行う必要があります。

**手順**:

1. **ロールバックの必要性を判断**
   - マイグレーションが失敗した場合
   - 予期しない問題が発生した場合
   - データ整合性に問題が発生した場合

2. **バックアップからの復元（推奨）**
   ```bash

   aws rds restore-db-instance-from-db-snapshot \
     --db-instance-identifier <new-instance-id> \
     --db-snapshot-identifier <snapshot-id>
   ```

3. **マイグレーションのロールバック（注意が必要）**
   ```bash
   # 1つ前のリビジョンまでロールバック
   alembic downgrade -1
   
   # 特定のリビジョンまでロールバック
   alembic downgrade <revision_id>

   ```

4. **ロールバック後の確認**
   - データベースの整合性を確認
   - アプリケーションの動作を確認

##### 本番環境での注意事項

1. **ダウンタイムの最小化**
   - 可能な限り、データベースロック時間を短くする
   - 大規模なマイグレーションは、段階的に実行を検討

2. **リードレプリカの活用**
   - リードレプリカでマイグレーションをテスト
   - 本番環境での実行前に、リードレプリカで検証

3. **ロールバック計画**
   - マイグレーション実行前に、ロールバック計画を策定
   - バックアップからの復元手順を事前に確認

4. **監視とアラート**
   - マイグレーション実行中・実行後は、監視を強化
   - 異常が発生した場合は、即座にアラートを発報

5. **ドキュメント化**
   - 実行日時、実行内容、実行結果を記録
   - 問題が発生した場合は、詳細を記録

## マイグレーションファイルの命名規則

### ファイル名の形式

```
<YYYYMMDDHHMMSS>_<説明>.py
```

**例**:
- `20260108143000_add_email_to_user_tables.py`
- `20260108083830_remove_username_from_user_tables.py`

### 命名規則

- **日時プレフィックス**: `YYYYMMDDHHMMSS`形式（UTC）
- **説明**: スネークケースで記述（英数字とアンダースコアのみ）
- **明確性**: 変更内容が一目でわかるように記述
- **簡潔性**: 過度に長くならないように記述

### 推奨パターン

- `add_<カラム名>_to_<テーブル名>`: カラム追加
- `remove_<カラム名>_from_<テーブル名>`: カラム削除
- `rename_<旧テーブル名>_to_<新テーブル名>`: テーブル名変更
- `create_<テーブル名>_table`: テーブル作成
- `drop_<テーブル名>_table`: テーブル削除
- `add_index_<インデックス名>_on_<テーブル名>`: インデックス追加
- `merge_heads`: ブランチマージ（マージマイグレーション）

## マイグレーションファイルの記述規約

### 基本構造

```python
"""<マイグレーション説明>

Revision ID: <revision_id>
Revises: <parent_revision>
Create Date: <YYYY-MM-DD HH:MM:SS.ffffff+00:00>

"""
from __future__ import annotations

from alembic import op
import sqlalchemy as sa


# revision identifiers, used by Alembic.
revision = "<revision_id>"
down_revision = "<parent_revision>"  # または tuple (マージマイグレーションの場合)
branch_labels = None
depends_on = None


def upgrade():
    """マイグレーションの実行処理"""
    # 変更処理を記述
    pass


def downgrade():
    """ロールバック処理"""
    # ロールバック処理を記述
    pass
```

### upgrade()関数の記述

- **明確性**: 変更内容が明確にわかるように記述
- **原子性**: 1つのマイグレーションで完結する変更のみ含める
- **データ整合性**: 外部キー制約やチェック制約を適切に設定
- **パフォーマンス**: 大規模な変更は必要に応じてバッチ処理を使用

### downgrade()関数の記述

- **完全性**: upgrade()で行った変更を完全に元に戻す
- **安全性**: データ損失を伴う変更は慎重に処理
- **順序**: upgrade()の逆順で処理

### よく使用する操作

#### テーブル作成

```python
def upgrade():
    op.create_table(
```

## マージマイグレーション

### マージマイグレーションの作成

複数のブランチからマイグレーションが分岐している場合、マージマイグレーションを作成する必要があります。

```bash
cd dev-workspace
alembic merge -m "merge heads: fishtrack and mypokedex" <revision1> <revision2>
```

```python

"""
from __future__ import annotations

from alembic import op
import sqlalchemy as sa


# revision identifiers, used by Alembic.
revision = "merge_fishtrack_mypokedex_heads"
down_revision = ("<revision1>", "<revision2>")  # tupleで複数の親を指定
branch_labels = None
depends_on = None


def upgrade():
    """Merge heads from FishTrack and MyPokedex."""
    pass

    """No-op downgrade for merge migration."""
    pass
```

**注意事項**:
- マージマイグレーションのupgrade()/downgrade()は通常空（`pass`のみ）
- `down_revision`はtupleで複数の親リビジョンを指定
- マージ後に新しいマイグレーションを作成する際は、マージマイグレーションを`down_revision`に指定

## マイグレーションのロールバック

### 特定のリビジョンまでロールバック

```bash
cd dev-workspace
alembic downgrade <revision_id>
```

### 1つ前のリビジョンまでロールバック

```bash
cd dev-workspace
alembic downgrade -1
```

### 全てのマイグレーションをロールバック

```bash
cd dev-workspace

```

**注意事項**:
- 本番環境でのロールバックは慎重に行う
- データ損失を伴う可能性があるため、事前にバックアップを取得すること
- ロールバック前に、影響範囲を確認すること

## ベストプラクティス

### 1. マイグレーションの粒度

- **1つの変更につき1つのマイグレーション**: 関連する変更でも、できる限り分離する
- **原子性**: 1つのマイグレーションは成功または失敗のどちらかになるように設計
- **可逆性**: downgrade()を必ず実装し、元に戻せるようにする

### 2. データ移行

- **段階的な移行**: 大規模なデータ移行は複数のマイグレーションに分割
- **バックアップ**: データ損失を伴う変更の前にバックアップを取得
- **検証**: データ移行後、データの整合性を確認

### 3. パフォーマンス

- **インデックスの一時削除**: 大規模なデータ更新時は、一時的にインデックスを削除してから再作成
- **バッチ処理**: 大量のデータを扱う場合は、バッチ処理を使用
- **トランザクション**: 適切なトランザクション境界を設定

### 4. テスト

- **開発環境での実行**: 本番環境に適用する前に、開発環境でテスト
- **ロールバックテスト**: downgrade()も必ずテスト
- **データ整合性チェック**: マイグレーション後、データの整合性を確認

### 5. ドキュメント

- **コメント**: 複雑な変更は、コメントで説明を追加
- **docstring**: upgrade()/downgrade()にdocstringを追加
- **コミットメッセージ**: 変更内容を明確に記述

## トラブルシューティング

### マイグレーションが作成されない

**原因**: モデルとデータベースの差分が検出されない

**対処**:
1. モデルの変更が正しく反映されているか確認
2. `target_metadata`にモデルが正しく登録されているか確認（`migrations/env.py`を確認）
3. 手動でマイグレーションファイルを作成（`alembic revision -m "説明"`）

### 依存関係エラー

**原因**: `down_revision`が正しく設定されていない、または存在しないリビジョンを参照している

**対処**:
1. `alembic history`でリビジョン履歴を確認
2. `down_revision`を正しいリビジョンIDに修正
3. マージマイグレーションの場合は、tuple形式で複数の親を指定

### データベースURLエラー

**原因**: 環境変数が設定されていない、または不正な形式

**対処**:
1. 環境変数を確認（`echo $SHARED_DATABASE_URL`など）
2. データベースURLの形式を確認（接続文字列が正しいか）
3. データベースが起動しているか確認

### マージコンフリクト

**原因**: 複数のブランチで同じテーブルに対して異なる変更が行われた

**対処**:
1. マイグレーション履歴を確認（`alembic history`）
2. マージマイグレーションを作成
3. 必要に応じて、手動でマイグレーションを調整
