# UI 監査 HTML レポート

## 計画との関係（I3）

統合作業スケジュール **`I3`**（UI・機能改善の定期探索仕組み）で画面・操作性を洗い出すときの\
**診断成果物の正**は本 SKILL（**HTML＋画面スクショ**。Canvas 禁止）。\
改善案の具体化・採用要否の起票は **`ux-ideation`** と分担する（本 SKILL は診断レポート側。**改善の見た目案は本レポート内のサンプル HTML で提示**）。

## 発火条件

次のいずれかで、**着手前に本 SKILL を Read** する。

- ユーザーが **UI の問題点**・**画面診断**・**レイアウト／操作性レビュー**を依頼したとき
- **`I3`** の定期探索・画面監査ランで問題点を残すとき
- 診断結果を **一覧・レポートとして残す**とき（チャット箇条書きだけで終えない）
- 以前 Canvas で UI 監査していたが、**スクショ付きで見せたい**とき
- **採用した改善の製品実装が終わったとき**（**再診断**し、解決なら `index.html` を **RESOLVED** 更新）

## 診断観点（必須）

**全体監査**（「UI に課題はないか」「全画面チェック」、**I3**）では、表幅・sticky だけに偏らない。\
次を**画面ごとに当てる**。該当しない観点はレポートまたは残作業に**対象外と理由を1行**残す（黙ってスキップしない）。\
特定画面・片方製品の限定依頼でも、**中核4つ**のうち該当するものは落とさない。

各 OPEN の「何が問題か」に、主に当てた観点を短く含めてよい。\
**ID 接頭辞は従来どおり**（H／O／M 等）。観点名ごとに ID 体系を増やさない。

### 中核（省略禁止）

2026-08-13 の全体チェックでユーザーが指定。以降の画面監査の既定。

1. **操作性** — 目的の操作が少ない手数で完了するか。検索・絞り込みがあるか。行の詳細／承認など操作列が死んでいないか（「—」だけ）。到達に URL 直打ちが要らないか。
2. **視認性** — 何が主で何が副か分かるか。必須印、空の大きなカードが一覧を押し下げていないか、スキャンできるか、文字切れ。
3. **初回ユーザー** — 初めてでも迷わないか。機能の発見性、空状態の案内、孤立した画面、必須と任意の区別。
4. **管理者の管理しやすさ** — 管理者画面・管理者ナビがあるとき（**admin ログインで確認**）。一覧が主作業か、統計が邪魔していないか、審査・削除・マスタメンテが後から見返せるか。一般ユーザー画面だけの依頼でも、管理者専用機能を黙って除外せず「対象外」と書く。

### 併せて見る（中核の漏れ防止）

中核に含まれうるが、過去 OPEN で落ちやすいので明示する。

- **導線・IA** — ナビ／画面内に入口があるか、現在地が分かるか（孤立 URL になっていないか）
- **主目的と主 CTA** — その画面で一番やりたいことが一番目立つボタンか（データ有で記録 CTA が消える等）
- **空状態とデータ有の一貫** — 0件時と件数ありで入口が逆転していないか
- **必須／任意** — 保存に必要な項目が印・折りたたみ等で分かるか
- **表の密度** — 横スクロール、sticky、列優先（PC 指摘前は overflow 計測。手順のビューポート節）
- **フィルタ** — クリア、件数、連動は双方向（下記「連動プルダウン」）
- **誤アフォーダンス** — リンク／ボタンに見えて押せない死んだテキスト
- **同類画面の一貫性** — 行クリック、追加ボタンの有無が画面間で矛盾していないか
- **危険操作** — 削除・承認・見送りに確認や、後から内容を見返す経路があるか
- **フィードバック** — バリデーション、保存結果。空メッセージが「フィルタ空」と「真の空」で区別できるか
- **SP／PC** — 両ビューポート（下記「手順」）
- **アクセシビリティ（最低限）** — 名前のある操作、キーボード到達、コントラスト。詳細監査ではないが、明らかな欠落は OPEN にする

### 未解決と解決済みの分離（必須・厳格）

`index.html` では課題を**必ず2セクションに分けて記載**する。混在禁止。

| セクション | `id` | 含むもの |
| --- | --- | --- |
| **未解決の課題** | `#open-issues` | `status-open` の article のみ（案選択待ち・実装前・再診断で未解決） |
| **解決済みの課題** | `#resolved-issues` | `status-resolved` の article のみ（再診断済み） |

- **順序**: サマリー → **未解決** → **解決済み** → ギャラリー（任意）
- **目次**: 「未解決」「解決済み」へのリンクと、各セクション内の ID リンクを分ける
- **RESOLVED にしたとき**: 当該 article を **`#resolved-issues` 内へ移動**する（バッジだけ変えて未解決側に残さない）。**`<details>` 既定クローズ**と **`data-resolved-on`** を付け、1ヶ月超の RESOLVED を削除する
- **新規 OPEN**: `#open-issues` に追加する
- **サマリー備考**: **レポート横断の運用ルールだけ**（OPEN／RESOLVED 分離、アコーディオン、1ヶ月削除）。\
  **禁止**: 個別課題の OPEN 追加・RESOLVED・案採用・ID 統合の日記を備考へ積む。\
  それは**当該 article**（`label`・事象・改善策・`data-resolved-on`）へ書く。\
  未解決リードは**現時点の OPEN 件数と ID 列挙**まで（セッション履歴の積み上げ禁止）

#### 解決済みはアコーディオン（既定クローズ・必須）

`#resolved-issues` の各 article は **`<details>` で囲み、`open` を付けない**（閉じた状態が既定）。

- **`summary`**: バッジ＋ ID ＋タイトル（既存の `h2` を `summary` 内へ）
- **本文**（事象・スクショ・改善策）は折りたたみ内。OPEN 側はアコーディオンにしない
- 各 article に **`data-resolved-on="YYYY-MM-DD"`**（再診断日。誤検知クローズもその判定日）
- 目次やページ内リンクで**課題 ID** に来たときは、その `details` を開く（レポート末尾の小さなスクリプト可）。`#resolved-issues` 自体では開かない
- **禁止**: 解決済み本文を常時展開したままにする

#### 解決から1ヶ月経過した課題の削除（必須）

**レポートを更新するたび**（OPEN 追加、RESOLVED 移動、再診断、本節のメンテ）に、解決済みを点検する。

- **判定**: `data-resolved-on` に暦の **1ヶ月を加算した日 ≦ 作業日（JST）** なら削除
  （例: 解決 `2026-07-13` → `2026-08-13` 以降は削除。日が無い月は月末に丸める）
- **削除するもの**: 当該 `article`、目次の ID リンク、**その課題専用**で他 article／OPEN から参照されない PNG・`samples/`
- **残してよい**: 当該 article 内の履歴、他課題からの「RESOLVED」言及
- **禁止**: 削除した課題の日記をサマリー備考へ残す（備考は運用ルールのみ）
- **禁止**: 1ヶ月超を CSS／JS で隠すだけ（HTML に残す）
- 削除後、解決済みが 0 件なら節は残し「1ヶ月以内の解決済みなし」とリードに書く

### レポート表示時の最前面フォーカス（必須・厳格）

**`index.html` を作成・更新した同一ターン**で、Cursor ブラウザにレポートを開くときは次を守る。

1. `browser_navigate`（必要なら先に `browser_tabs` の `select` で当該タブを選ぶ）でレポートを開く  
2. **必ず `position: "active"`** — ブラウザ UI を**最前面**にし、**タブにフォーカスを当てる**  
3. **`position` 省略**（バックグラウンド）・**`"side"`**・裏タブのままは**禁止**（`"side"` は全作業共通で禁止。正本 **`cursor-ide-browser-position`**。本 SKILL のレポート表示は `"active"` 必須）
4. ユーザーがチャットだけ見てレポートを見落とさないようにする（更新後の確認ゲート）

手順 8・禁止リストも同趣旨。

### 各問題エントリに必須の節（省略禁止）

OPEN / RESOLVED を問わず、問題 ID ごとに次を書く。**事象のスクショだけで終えない**。

**1 事象 = 1 ID（厳格・省略禁止）**: 問題点は**必ず事象ごとに分ける**。同一画面・同一部品群でも、\
ユーザーが別々に困る点は**別 article・別 ID**とする。

- **やる**: 観点・影響・改善の指差し先が違うなら分割（例: 表の窮屈さ＝`H2`、操作CTA高さ＝`O2`）
- **やる（フィルタ例）**: 同一ルアーマスタフィルタでも、**クリア欠如**・**件数表示のズレ**・**候補の非連動**は\
  それぞれ別 ID（束ねて「フィルタの操作性」1件にしない）
- **禁止**: 無関係な複数事象を1見出しに箇条書きでまとめる（関連は Mutual リンクでよい）
- **禁止**: 「改善案が同じリリースでまとめて直せるから」**だけ**を理由に診断 ID を合流させる
- 改善案が共通実装になりえても、**ユーザーが別々に困る点**なら診断上の事象は分離する

**同一公開面の第一印象は1事象（LP 等）**: 未ログイン LP のように、困る点が
「登録前に製品が分からない」なら、**レイアウト／実画面画像／コピーを別 ID にしない**。
観点の違いだけで分割しない。ユーザーが「一つにまとめる」と指示したら、**正 ID 1件**にまとめ、
旧 ID の article は**削除**する（RESOLVED にしない＝未解決のまま合流）。正 ID の article に統合履歴を1行残す。
旧 ID へのリンクは正 article 内の節 `id` で受けてよい。

**FishTrack 未ログイン LP の改善案（必須）**: LP は製品説明に加え**宣伝も担う**。
分量を短く抑えることは目的ではない（2026-08-13 ユーザー指摘）。
**禁止**: 「宣伝用の長い LP にしない」「ページが短い」をメリットとして**推奨**する。
**「縦に長くてよい」の意味**（2026-08-13）: 見出し・本文・実画面・写真を**適切な大きさ**で置き、
無理に短く切らない、ということ。
**ヒーロー（先頭）**: ブラウザの幅・高さを**100%**使うフルブリード
（`100dvh` × `width: 100%`。製品 `main` の padding を打ち消す。2026-08-13 ユーザー＋参考）。
コピーは左寄せ・縦中央。写真がビューポートいっぱいに広がる。\
**公開ヘッダーのロゴはヒーロー上を白透過**（2026-08-13）。現行 `fishtrack-logo.png` のインクを白にした\
`samples/fishtrack-logo-white.png`。濃色ロゴは同系色で見えない。ソリッド後は製品の濃色ロゴ。\
サービス名はロゴ内の FishTrack。空ヘッダーは禁止。
ヒーロー上は白透過ロゴ＋ページ内ナビ（紹介節へのアンカー）＋右端 CTA「無料で新規登録」。
ログインはヒーロー／締め CTA。
**禁止**: ヒーロー以外の節で大きな padding や、中身の無いカードを伸ばす等高ストレッチで
**空の余白を増やして**ページを伸ばす。
**やる**: 一つ一つの情報を大きくする。写真と UI スクショは内容に合わせて配置する
（画像の無いカードを伸ばさない。疎な画面スクショは中身が見える位置にクロップ）。\
**同一行の左右**は幅・高さを揃える（列は `minmax(0, 1fr)` 同幅、`align-items: stretch`）。
余った高さは画像を伸ばして埋める（空パディングで揃えない。2026-08-14）。
写真を主役にする LP では、本文を簡潔にし、実写写真を UI スクショより大きく配置する。
実写写真が暗く見える場合は、実写画像だけを明るさ補正する（UI スクショとヒーローの暗幕は対象外）。
画像の占有率を上げても、モバイルでは本文と画像の順序・可読性を維持する。
ストーリー／機能説明／実画面／向きを載せてよい。
汎用生成 LP の定番（オーバーレイ白抜き・左右交互3段・グラデ締め）は採らない（仕様 5-16）。
**方向が決まったあとは案記号を増やさない**（2026-08-13）。正サンプルは
`ui-audit/fishtrack/samples/ft-h8.html` **1本**を上書きブラッシュアップする。\
ヒーローリード（`.ft-lp-hero__lead`）に無料枠・広告の話を書かない。先出しは締め CTA・規約・PP・meta description。\

短い実用ページやフルブリード比較は、ユーザーが明示したとき以外は新規に作らない。

1. **事象** — 何が起きているか（操作・画面）。現状スクショを紐づける  
2. **対象箇所（必須・厳格）** — 読者が画面上で**すぐ指差せる**粒度で書く。省略禁止。  
   - **URL／画面名**（例: `/RGBP/partyBox`）  
   - **画面内の位置**（例: 「弱点提案パネルの直下〜パーティ表の直前」）  
   - **部品名／セレクタ**（例: `.pkCoverage .pkBadge`、見出し文言）  
   - **対象外**があるなら1行で明示（紛らわしい近傍 UI があるとき特に）  
   - スクショ `figcaption` にも「▲ この行」など**指差し文**を付ける  
3. **何が問題か** — ユーザー影響・なぜ直すべきか（発見性・誤操作・到達コスト・アクセシビリティ等）  
4. **改善策** — 具体案。**必ずサンプル HTML を作成**し、その**スクショを掲載**する  
   - **案が1つ**でもサンプル HTML + スクショは必須  
   - **変更前後が分かる（必須・厳格）**: サンプルは**同一ページ内で「変更前／変更後」を並べる**か、\
     レポート側に**何がどう変わるか**（見た目・DOM・操作可否）を箇条書きする。\
     **完成版相当の単一ページ**（例: FT-H8 の `ft-h8.html`）は同一 HTML に変更前を置かない。\
     その場合はレポートの**現状スクショ＋完成版サンプル**で対比する。\
     「改善後スクショだけ」「指摘と別部品に見えるサンプル」は禁止  
   - **上下並びの順序（必須・厳格）**: HTMLレポート（サンプル HTML・`index.html` の対比ブロック含む）で\
     **変更前後を上下に並べるときは、変更前を上、変更後を下とすること**。\
     注記も「下の『変更後』…」とする（「上の変更後」禁止）。左右並びはこの限りでないが、\
     読順が上→下なら同様に前→後  

   - **サンプル UI 文言に監査メタを載せない（必須）**:  
     「閉じた状態が既定」「案A」「変更後」等の**説明・注記は** `sample-note`／見出し／figcaption に置き、\
     **製品に出る部品のラベル（summary・ボタン・legend）には書かない**。\
     現状未実装の状態をスクショするときは「採用後の想定」「現状の製品には無い」と注記する  
   - **既存レイアウト意図を壊さない**: 現行 UI が**密度・縦高・横スクロール抑制**などの目的で
     選ばれている場合、改善案はそれを注記し、サンプルでも**同程度の占有を維持**する
     （例: ピル型は誤アフォーダンス対策と同時に縦抑制。枠だけ外してグリッド密度は維持）。
     「見やすいから」と縦に伸ばす案は、制約を明示しない限り推奨しない  
   - **デザイン踏襲（必須・厳格）**:  
     - **やる**: ローカル Docker の製品 CSS を `<link>`（例: `http://127.0.0.1:5002/static/css/app.css` 等一式）。現行テンプレのヘッダー／表／ボタン DOM を流用（ロゴ画像含む）。**変えるのは改善箇所だけ**  
     - **推奨**: 実ページに改善用 CSS だけ注入してスクショし、同内容を `samples/*.html` に落とし込む  
     - **禁止**: トークン近似の自作 UI・別ブランド風・「それっぽい」ヘッダー／ボタンの描き直し  
     - **禁止**: 指摘対象と**別部品**だけを変えたサンプル（例: カバレッジバッジ指摘なのに敵タイプ選択だけを無効化）  
   - **案が複数**のとき:  
     - 案ごとに **別ファイル**のサンプル HTML（`samples/{id}-{a|b|…}.html`）  
     - 各案のスクショ  
     - **案の違い**（何が異なるか）  
     - **メリット・デメリット**（表または箇条書き）  
     - ユーザーが選べるよう **案ラベル（案A / 案B…）を明示**し、推奨があれば「推奨」と理由を1行  
     - **表示項目が案で違うとき**は、現状と同じ **「項目×画面」表を案ごとに**出す（メリデメ表だけでは足りない）  
     - **「案Xをベースに調整」**したら **案記号を増やさない**。当該案の項目表・サンプル HTML・メリデメを**上書き**する（案Cを足さない）  
   - **画面目的の制約**: 改善案は**その画面の目的を壊さない**こと。例: MyPokedex 図鑑／パーティ一覧は\
     **ポケモンデータの比較**が目的のため、**表形式の維持は最低条件**（**H2・O2 とも**）。\
     カード化など表を捨てる案は比較ができず目的を果たせないので**推奨しない／不採用**。\
     O2（操作CTA）も**表の操作列セル内**で解く。  
   - **列の優先／非表示を提案する前**（表密度系）:  
     1. 製品の **既存 SP CSS**（例: `app-mobile.css`）と仕様のレスポンシブ節で、**すでに非表示の列**を洗い出す  
     2. **画面ごとに主目的が違う**場合は優先列セットを分ける（例: 図鑑＝登録／コンプ、パーティ＝編成／タイプ）  
     3. 既存非表示の再掲を「新規改善」にしない。追加で落とす列だけを案に書く  
   - **連動プルダウン（必須・厳格）**: フィルタ等で複数 select を候補連動させる改善を出すときは、\
     **片方向だけにしない**。A 選択→B を絞る／B 選択→A を絞るの**双方向**を案・サンプルに含める\
     （例: メーカー↔プラグ種別）。片方だけだと先に選んだ側で空結果が残る

RESOLVED は「実施した改善」と**再診断後のアフタースクショ**を必須とする（下記「実装完了後の再診断」）。新規サンプルは任意。

### ユーザーが案を「採用」したとき（必須）

チャットで特定案（例: 「案B 採用」）を選ばれたら、**同一セッション**で次を行う。

1. **製品実装**（テンプレ／CSS／必要なら JS）と **仕様**・**テスト／E2E ID** を同期  
2. **計画**: `integrated-schedule-update` で実装タスクを起票（完了なら W 固定で ✅）  
3. **`ui-audit/index.html`**: 採用案を明示（`recommended` / `rec-tag`）。この時点では **OPEN のまま**でもよい（実装未検証なら RESOLVED にしない）  
4. **実装完了後の再診断**（下記）を実行し、解決を確認してから **RESOLVED**  
5. **CursorLog** に採用案 ID・実装範囲・再診断結果を残す  

**禁止**: レポートだけ「採用／RESOLVED」と書いて製品未実装のまま完了報告する。  
**禁止**: 実装しただけで再診断せず RESOLVED にする。

### ユーザーが案を「保留」したとき（必須）

チャットで特定案（例: 「案A 保留」）と指示されたら、**同一セッション**で次を行う。**製品実装・計画起票はしない**。

1. **`ui-audit/index.html`**: 当該案に **`hold` / `hold-tag`「保留」** を付ける（`recommended`／「推奨」は外す）  
2. article は **`OPEN` のまま** `#open-issues` に残す（RESOLVED にしない）  
3. 判断文を短く残す（例: 「案A は保留。実装・起票しない。再検討待ち」）  
4. **当該 article** に保留を明記する（サマリー備考へは書かない）  
5. **CursorLog** に問題 ID・保留案・実装しない旨を残す  

**禁止**: 保留を採用扱いして実装を始める。  
**禁止**: 保留だけで RESOLVED／課題削除する（ユーザーが明示したときのみ削除・クローズ）。

### ユーザーが案を「検討中」としたとき

チャットで **「検討中」**（**「保留」ではない**）と指示されたら、**同一セッション**で次を行う。**製品実装・計画起票はしない**。

1. **`ui-audit/index.html`**: article は **`OPEN` のまま** `#open-issues` に残す（RESOLVED にしない）  
2. **`hold` / `hold-tag`「保留」は付けない**（「保留」は上記「保留」節専用）  
3. 判断文を短く残す（例: 「案A/Bは検討中。実装・起票しない」）  
4. **当該 article** に検討中を明記する（サマリー備考へは書かない）  
5. **CursorLog** に問題 ID・検討中・実装しない旨を残す  

**禁止**: 検討中を採用扱いして実装を始める。  
**禁止**: 検討中だけで RESOLVED／課題削除する。  
**禁止**: 「検討中」を「保留」と読み替えて `hold-tag` を付ける。

### ユーザーが「案Xをベースに調整」したとき

チャットで既存案の項目・条件を直す指示（例: 「案Bをベースにルアーは設定時」）なら、**同一セッション**で次を行う。

1. **案記号を増やさない**（案C を作らない）。当該案の **項目×画面表**・サンプル HTML・メリデメ・推奨を**上書き**する  
2. article は **`OPEN` のまま**。判断文を短く残す（調整内容と、実装は採用の明示までしない旨）  
3. **製品実装・計画起票はしない**（それは「採用」節）  

**禁止**: 調整だけを採用扱いにして製品実装を始める。  
**禁止**: 調整のたびに新しい案ラベルを増やす。

### 実装完了後の再診断（必須・RESOLVED の前ゲート）

採用案の**製品実装が終わったら**、完了報告の前に**同一セッション**で再診断する。

1. **ローカル Docker** で当該画面を開く（製品の **`local-browser-verify`**。SP/PC は問題のビューポート）  
2. **改善後の現状**をスクショする（命名例: `sp-{screen}-after.png`）。改善前 PNG は残し、ビフォー／アフター対比できるようにする  
3. **判定**:
   - **解決** → 当該 issue を **`RESOLVED`** にし、「実施した改善」＋**改善後スクショ**を載せる。事象節は「改善前」と明記してよい。\
     article を **`#open-issues` から `#resolved-issues` へ移動**する。\
     **`<details>` 既定クローズ**＋ **`data-resolved-on`（再診断日）** を付ける。\
     同時に **1ヶ月超の RESOLVED を削除**する（上記「解決から1ヶ月」）  
   - **未解決／部分解決** → **OPEN のまま**（`#open-issues` に残す。または部分解決と注記）。残課題を「何が問題か／残作業」に書き、完了報告で明示する  
4. レポートをブラウザで開き（手順 8）、未解決／解決済みの分離・バッジ・アフター画像が正しいことを確認する  

**禁止**: チャット目視やコード差分だけで RESOLVED にする（**アフタースクショ必須**）。  
**禁止**: 改善前スクショを上書きして証拠を消す。

**関連事象で再診断を後回しにする場合**（例: 同一 SP 表で操作列 CTA＝O2、列密度＝H2）:

- ユーザーが「A 解決後に B を再診断」と指示したら、レポートの **B に進め方を明記**し、**A の関連にも相互記載**する  
- **B を A より先に実装／RESOLVED しない**（A の見た目変化が B の判定を変えるため）  
- A が RESOLVED になった**同一セッションまたは直後の作業**で B を再診断する  

**禁止**:

- 事象の列挙だけで改善策・サンプル HTML がないレポート  
- 複数案なのに比較（違い・メリデメ）がない提示  
- **表示項目が案で違うのに、現状の「項目×画面」表を案ごとに出さない**（メリデメ表だけにする）  
- **現行と無関係な見た目のサンプル**（近似モック・手書きトークンだけの別アプリ感・製品ロゴ／CSS未使用）  
- **変更前後の上下並びで変更後を上・変更前を下にする**（順序は常に前→後）  

- 診断の主成果物を Canvas のみにする  
- **`temp/ui-audit/`**・Obsidian・日付サブフォルダを正本にする  
- レポートのダークテーマ・スクショ枠の黒背景・透過 PNG のまま掲載  
- ブラウザ表示で **`position: "side"`**／**`position` 省略**／裏タブのまま（**更新後は `active` で最前面・タブフォーカス必須**）
- ユーザー採用後にレポート／実装／仕様を更新せずチャットだけで終える
- **実装完了後に再診断せず RESOLVED にする**／アフタースクショなしで解決扱いする
- **OPEN と RESOLVED を同一セクションに混在**させる（未解決／解決済みの分離を崩す）
- **解決済みを常時展開**する（アコーディオン既定クローズを崩す）
- **解決から1ヶ月超の RESOLVED を HTML に残す**／表示だけ隠して削除しない

## 手順

1. **ローカル起動・ログイン** — 製品の **`local-browser-verify`**  
2. **ビューポート** — CDP で SP / PC。ナビ後は再適用。\
   **PC 診断の前に** `Emulation.clearDeviceMetricsOverride`（またはデスクトップ相当の広い幅）を必ず実行し、\
   SP エミュが残ったまま「PC」と書いて HIGH を付けない。\
   **文字切れ／右端クリップ**を指摘する前に、対象要素の
   `getBoundingClientRect()` と親・`window.innerWidth` を測り、
   `overflowClip`（親からはみ出し）が実害か確認する（スクショ見た目だけ禁止）。\
   Cursor ブラウザのパネル幅が狭いだけの場合は製品バグにしない（手順 8 の切り分けも参照）
3. **観点チェック＋操作込みで再現** — 「診断観点」の**中核4つ**と**併せて見る**を画面に当て、現状スクショ取得。見送りは残作業に理由  
4. **スクショ後処理** — RGBA なら白合成 → RGB。必要なら余白クロップ（グレー余白を PNG に残さない）  
5. **改善サンプル HTML** — `ui-audit/samples/` に案ごと作成。**新規は `sample-template.html` から**。\
   **製品 CSS を `<link>`**し、**現行 DOM を流用**。`width:max-content` を維持。**改善差分以外を描き直さない**  
6. **サンプルをブラウザで開きスクショ** — 各 `samples/*.html` を一時 HTTP 経由で開き撮影・後処理  
   - **文字切れ禁止**: 操作CTA・主ラベルが枠で切れないこと。狭幅で列が多いときは**撮影フレーミング**で非主題列を隠し、改善点（短縮ラベル等）が全文読める状態で撮る  
   - **HC取得時のブラウザ配置**: HTMLレポート作成用の HC（画面キャプチャ／スクリーンショット）を撮るときも、ブラウザは `position: "active"` で開く。`"side"`・`position` 省略・裏タブのまま撮影しない
7. **`dev-workspace/ui-audit/index.html` 最新化**  
   - **新規 or 全面作り直し**: 本 SKILL の **`report-template.html`** を `dev-workspace/ui-audit/index.html` へコピーし、`{…}` と雛形を実データで置換  
   - **既存更新**: 必須節どおり追記。CSS をいじる場合は **先に `report-template.html` を直し**、共有レポートへ反映  
   - **解決済み**: `<details>` 既定クローズ＋`data-resolved-on`。**1ヶ月超は article 削除**（専用 PNG／samples も）  
8. **Cursor ブラウザで開く（必須・最前面）**  
   - `dev-workspace` ルートで `docker compose up -d ui-audit` を実行し、
     常駐する `nginx:alpine` の **`http://127.0.0.1:8990/`** を使う。
     `ui-audit/` は読み取り専用でコンテナへマウントし、Cursor のターミナルと配信プロセスを分離する。
     既存の 8989 番サーバーは重複起動しない。
   - サンプル HTML の CSS/JS は **クエリ無しの相対パス**（`ft-h8.css`）にする。
     8990 番の nginx は開発中の古い CSS が残らないよう `Cache-Control: no-store` を付与する。
     レポート `index.html?v=` のクエリは使用してよい。
   - **レポート表示前に** CDP `Emulation.clearDeviceMetricsOverride`（またはデスクトップ相当の広い `setDeviceMetricsOverride`）を実行する。\
     SP スクショ用に狭幅エミュレーションを残したままだと、**HTML に `max-width` が無くても** `window.innerWidth` が狭く固定され、body がブラウザパネルより小さく見える  
   - `browser_navigate` → `http://127.0.0.1:8990/index.html`
   - **最前面表示（厳格）**: `browser_navigate` に **必ず `position: "active"`** を付ける。\
     ユーザーがレポートをすぐ見られるよう、**ブラウザパネルを最前面にし、当該タブにフォーカスを当てる**。\
     **`position` 省略・`"side"`・バックグラウンドのみのナビは禁止**（更新後にチャットだけで終わらせない）  
   - 既に同じレポートタブがある場合も、**更新後は再度 `position: "active"` 付きでナビ／フォーカス**する（裏タブのままにしない）  
   - 切り分け: body/`main` の `max-width` が `none` かつ `body.clientWidth ≈ window.innerWidth` なら **ページ側は制限なし**（狭いのは Cursor ブラウザのレイアウト幅／残存エミュレーション）
