# ui-audit-html-report

Always respond in Japanese when applying this skill.

## 発火条件

- UI 問題点・画面診断・レイアウト／操作性レビューの依頼時
- 統合作業スケジュール **`I3`** で画面を洗い出すとき
- **採用改善の製品実装完了時**（再診断し、解決なら HTML を RESOLVED 更新）

## 診断観点（必須・詳細は SKILL）

- **中核（省略禁止）**: 操作性・視認性・初回ユーザー（迷わないか）・管理者の管理しやすさ
- **併せて見る**: 導線・IA、主目的と主 CTA、空状態とデータ有の一貫、必須／任意、表密度、フィルタ、誤アフォーダンス、同類画面の一貫性、危険操作、フィードバック、SP／PC、アクセシビリティ（最低限）
- 表幅・sticky だけに偏らない。該当しない観点は**対象外と理由を1行**

## 配置・必須内容

- **正本**: **`dev-workspace/ui-audit/index.html`**（FishTrack / MyPokedex **共有**。製品リポ直下は正本にしない）
- **両製品同時診断**（片方だけで完了報告しない。明示限定時のみ例外）
- **対象は各製品の全画面**（サマリーの URL 列挙はスクショ例。診断範囲の上限ではない）
- 資産: **`ui-audit/fishtrack/`**・**`ui-audit/mypokedex/`**（スクショ・`samples/`）
- 配信: `dev-workspace/docker-compose.yml` の `ui-audit` サービス（nginx、`http://127.0.0.1:8990/`）。8989 番の個別サーバーは使わない
- 問題 ID: 製品接頭辞（`mp-*` / `ft-*`）＋製品バッジ
- テンプレ: 本 SKILL の **`report-template.html`** / **`sample-template.html`**
- 改善サンプル: **製品 CSS を `<link>`＋現行 DOM 流用**（近似モック禁止。改善差分のみ）
- 各問題: **事象**・**対象箇所**（URL／位置／セレクタ／対象外）・**何が問題か**・**改善策**（**サンプル HTML + スクショ必須**）
- サンプルは**変更前後が分かる**こと（同一ページ対比、レポートの現状スクショ対比、または差分箇条書き。指摘と別部品のモック禁止）
- **上下並び**: 同一ページで対比するときは**変更前を上、変更後を下**（必須。注記も「下の変更後」。左右並びは別）
- **監査メタ文言**（「閉じた状態が既定」等）を製品 UI ラベルに載せない（注記は sample-note／figcaption）
- 現行が**密度・縦高**目的なら、改善サンプルも同程度の占有を維持（理由を注記）
- **1 事象 = 1 ID（厳格）**: 問題点は事象ごとに分ける。同一画面・同一フィルタでも観点が違えば別 article\
  （例: クリア欠如／件数ズレ／候補非連動を「操作性」1件に束ねない）。関連は相互リンク可。\
  **例外**: 未ログイン LP の第一印象（レイアウト／実画面／コピー）は1事象。ユーザー合流指示時は正 ID にまとめ旧 article は削除（RESOLVED にしない）。\
  **FishTrack LP**: 宣伝も担う。分量を短く切らない。短い実用ページを推奨しない。\
  「縦に長くてよい」は**余白で伸ばすな**（情報・画像を適切な大きさで置く。`SKILL.md`）。
  同一行の左右は幅・高さを揃える（余白ではなく画像で埋める。`SKILL.md`）。
  写真を主役にする LP は本文を簡潔にし、実写写真を UI スクショより大きく配置する（`SKILL.md`）。
  実写写真が暗く見える場合は、実写画像だけを明るさ補正し、UI スクショとヒーローの暗幕は維持する（`SKILL.md`）。
  **先頭ヒーローはビューポート全面**（幅・高さ 100%。製品 `main` padding を打ち消す）。\
  **ヒーロー上のロゴは白透過**（現行マークのインクを白に。ソリッド後は濃色ロゴ）。
  ヘッダーから紹介節へページ内スクロール（ロゴ＋アンカー＋右端 CTA）。
  方向確定後は `samples/ft-h8.html` 1本をブラッシュアップ（案記号を増やさない。`SKILL.md`）。\
  ヒーローリードに無料枠・広告の話を書かない（締め CTA・規約・PP・meta で先出し）。\
  本文は「ます。」の1字落ち改行を避ける（長さか `text-wrap: pretty`）。\
  アプリ実画面はドラフト。採用時は現行ログイン後画面から全件取り直す（監査 PNG を本番へ流用しない）。\
  外向けコピーは一般ユーザー向け（導線・マスタ・所持・部品等の開発用語は使わない。釣り用語は可）。\
  「向いている使い方」は地域・属性だけで広く括らず、記録したい内容や次の行動まで含む具体的な利用目的で示す。\
  SNSではない旨は「向いていない使い方」へ。ストーリー本文に否定の但し書きを足さない。\
  ストーリー本文に「使うには登録が必要です」など当たり前の利用条件を重ねず、使い始め／CTAで示す。\
  帰宅後の釣行整理は「1件にまとめる」ではなく、「記録にまとめる」等の自然な表現にする。\
  釣行前節は過去の釣行・釣果の振り返りを主訴求にし、水位データを確認できる対象フィールドは随時拡大中と伝える。
  水位・天候・水温は補助的な判断材料として置く。\
  節リードに LP 自身の説明（登録しなくても読める等）を置かない。登録要否は使い始め／CTA。\
  ナビは「機能」。機能節は一般ユーザー向け機能をカードで盛り込む（管理者限定は載せない）。\
  将来一般公開予定の機能は「今後の拡張予定」等の別セクションに分け、現行機能と混同させない。
  将来セクションも機能カードと同じ surface／accent-soft・枠線・角丸・余白・見出しのトークンで統一し、
  独自の横長コールアウト風にしない。\
  一押しに、自分のポイントを地図で見られることと、ポイントごとに釣果を残せることを含める。\
  釣果を残すカードには、使ったタックルやルアーも記録できることを含める。\
  タックルを探すカードには、ロッド・リール・ルアーの検索、登録情報の随時更新、
  FishTrackDB のマスタ登録件数（ロッド・リール・プラグ・ワーム）を、
  UI 上は「登録件数」として表示することを含める。
  件数の即時更新を示す「リアルタイム確認」とは書かない。\
  天候や水温のカードには、天候が自動で反映されることを含める。\
  ホームの実画面は機能カードへ。その年のサイズ BEST5 を振り返れることを主に示す。
  登録後の画面だけの静かな節は置かない。\
  **完成版相当**: 変更前ブロックは置かない。CSS/JS は `ft-h8.css` / `ft-h8.js`。対比はレポートの現状スクショ。
- **連動プルダウン**: 候補連動の改善案は**双方向**（A→B と B→A）。片方向のみ禁止
- **画面目的を壊す案は出さない**: データ比較一覧で表を捨てるカード化は不採用
- 複数案: 案ごとサンプル、**違い・メリット・デメリット**を明示
- **案採用〜実装後**: **再診断**してから **RESOLVED**
- **誤検知クローズ**: ユーザー実ブラウザで再現せず、Cursor 幅／残存 SP エミュが原因なら
  製品実装せず **RESOLVED（誤検知）** とし再診スクショと理由を残す
- **PC 文字切れ指摘前**: `clearDeviceMetricsOverride`＋要素の overflow 計測（見た目スクショだけ禁止）
- **案「保留」**: 実装・起票しない。`hold`／`hold-tag` で明示し **OPEN 維持**（SKILL「保留」節）
- **関連事象で再診断後回し**: レポートに明記（例: MP-H2 は MP-O2 解決後）
- **未解決／解決済みを分離**: `#open-issues` / `#resolved-issues`
- **サマリー備考**: レポート運用ルールのみ。課題の OPEN／RESOLVED 履歴は**各 article**（サマリーへ日記を積まない）
- **解決済みはアコーディオン**（各 article を `<details>`、**既定クローズ**。`data-resolved-on` 必須）
- **解決から1ヶ月経過**した RESOLVED は **HTML から削除**（専用 PNG／samples も。隠すだけ禁止）
- ブラウザ: 更新後は **`position: "active"`**（最前面）。**サイドでは開かない**（**`cursor-ide-browser-position`** SKILL）
- レポート表示前: SP の **DeviceMetrics を解除**

手順の正本は **`SKILL.md`**。
