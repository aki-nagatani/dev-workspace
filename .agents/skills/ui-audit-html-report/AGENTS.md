# ui-audit-html-report

Always respond in Japanese when applying this skill.

## 発火条件

- UI 問題点・画面診断・レイアウト／操作性レビューの依頼時
- 統合作業スケジュール **`I3`** で画面を洗い出すとき
- **採用改善の製品実装完了時**（再診断し、解決なら HTML を RESOLVED 更新）

## 配置・必須内容

- **正本**: **`dev-workspace/ui-audit/index.html`**（FishTrack / MyPokedex **共有**。製品リポ直下は正本にしない）
- **両製品同時診断**（片方だけで完了報告しない。明示限定時のみ例外）
- **対象は各製品の全画面**（サマリーの URL 列挙はスクショ例。診断範囲の上限ではない）
- 資産: **`ui-audit/fishtrack/`**・**`ui-audit/mypokedex/`**（スクショ・`samples/`）
- 問題 ID: 製品接頭辞（`mp-*` / `ft-*`）＋製品バッジ
- テンプレ: 本 SKILL の **`report-template.html`** / **`sample-template.html`**
- 改善サンプル: **製品 CSS を `<link>`＋現行 DOM 流用**（近似モック禁止。改善差分のみ）
- 各問題: **事象**・**対象箇所**（URL／位置／セレクタ／対象外）・**何が問題か**・**改善策**（**サンプル HTML + スクショ必須**）
- サンプルは**変更前後が分かる**こと（同一ページ対比または差分箇条書き。指摘と別部品のモック禁止）
- **上下並び**: **変更前を上、変更後を下**（必須。注記も「下の変更後」。左右並びは別）
- **監査メタ文言**（「閉じた状態が既定」等）を製品 UI ラベルに載せない（注記は sample-note／figcaption）
- 現行が**密度・縦高**目的なら、改善サンプルも同程度の占有を維持（理由を注記）
- **1 事象 = 1 ID（厳格）**: 問題点は事象ごとに分ける。同一画面・同一フィルタでも観点が違えば別 article\
  （例: クリア欠如／件数ズレ／候補非連動を「操作性」1件に束ねない）。関連は相互リンク可
- **連動プルダウン**: 候補連動の改善案は**双方向**（A→B と B→A）。片方向のみ禁止
- **画面目的を壊す案は出さない**: データ比較一覧で表を捨てるカード化は不採用
- 複数案: 案ごとサンプル、**違い・メリット・デメリット**を明示
- **案採用〜実装後**: **再診断**してから **RESOLVED**
- **誤検知クローズ**: ユーザー実ブラウザで再現せず、Cursor 幅／残存 SP エミュが原因なら
  製品実装せず **RESOLVED（誤検知）** とし再診スクショと理由を残す
- **PC 文字切れ指摘前**: `clearDeviceMetricsOverride`＋要素の overflow 計測（見た目スクショだけ禁止）
- **案「保留」**: 実装・起票しない。`hold`／`hold-tag` で明示し **OPEN 維持**（SKILL「保留」節）
- **関連事象で再診断後回し**: レポートに明記（例: MP-H2 は MP-O2 解決後）
- **未解決／解決済みを分離**: `#open-issues` / `#resolved-issues`
- ブラウザ: 更新後は **`position: "active"`**（最前面）
- レポート表示前: SP の **DeviceMetrics を解除**

手順の正本は **`SKILL.md`**。
