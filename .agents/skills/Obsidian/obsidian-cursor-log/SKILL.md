# Obsidian作業ログ（Cursor）

**第二の脳との関係**: CursorLog は**作業証跡**（いつ・何をしたか）。**第二の脳のすべてではない**——仕様・Knowledge・Work・釣行メモ等の**ドメイン正本**への反映は **`obsidian-second-brain` SKILL**（すべての Cursor 利用時の横断原則）に従う。Log のみで終えない。

## 報告前の必須アクション（記録漏れ防止）

**ワークスペース内のファイルを追加・更新・削除した作業を完了した場合**
（**`StrReplace` / `Write` / `Delete` / `EditNotebook`** 等。旧ドキュメントの `write` / `search_replace` / `edit_file` と同義）は、
**ユーザーに報告する前に必ず**本SKILLに従い CursorLog を更新すること。

報告文の末尾に「CursorLogは更新しました」と明記する。省略すると記録漏れとなる。
**追記するエントリの「使用AIモデル」行は、記入直前に当該チャットのモデル選択と照合し、誤ったモデル名のままにしないこと。**

### 記録漏れの典型原因（対策の観点）

- **会話要約（summarize）**や長文の打ち切りのあと、「報告直前の自己チェック（CursorLog 更新したか？）」が文脈から消え、次の応答でコード変更が未記録のままになる。
- **「完了」や成果報告の文面**を**先に**心の中・下書きで作り、**CursorLog 追記を同じ最終返答の後回し**にする（**順序の逆転**。**本 SKILL「作業フローと報告前ゲート」**で禁止）
- 実装に集中し、**本 SKILL を参照せず**に **`StrReplace` / `Write` 等の連打**で終える。
- **チェックリストとツール名の不一致**: ルール文面が旧ツール名だけだと、**自分の操作が「ログ対象」だと結びつかず**漏れる。\
    **`StrReplace` / `Write` / `Delete` / `EditNotebook`** を対象とすること（dev-workspace **myrules**「作業ログ」も同趣旨）。
- **対策**: 各プロジェクトの **AGENTS.md** に「コード変更完了時は CursorLog」を短く載せる。**報告の直前**に必ず Obsidian 側を更新する。成果を**ユーザーに文で述べ始める前**に、\
    **同一応答内で** log 用 `Write` / `StrReplace` を**済ませる**（**前ゲート**。詳細は下記「作業フローと報告前ゲート」）

### エントリ重複の典型原因（対策の観点）

- **会話要約（summarize）・スレッド継続**直後、要約の「未記録の CursorLog」指示だけを見て、**前ターンですでに追記済みの同一作業**をもう一度 `##` ごと複製する。
- **同一チャット内の二重完了**: 中間ステップ（コミットのみ等）と最終報告の両方で、別時刻の `##` を立てて**同じ作業名・同じ変更ファイル**を再記録する。
- **親子 SKILL の二重指示**: 例として **`FishTrack_commit`（コミット後）** と **`FishTrack_pull-request`（PR・CI 後）** の両方が CursorLog を要求し、**1 依頼で 2 エントリ**になる（親 SKILL 側で **1 エントリに統合**する。下記「製品 PR フローとの関係」）。
- **`StrReplace` の非一意アンカー**: ファイル内に**同一ブロックが 2 つ**ある状態で置換すると、片方だけ更新されたり、意図せず複製が残る。新規エントリは**原則ファイル末尾への追記のみ**（下記「エントリ追記の必須手順」）。
- **対策**: 追記前に当日ログを **Read** し、**「エントリ追記の必須手順（重複防止）」** を実施する。既存エントリへ追記・更新で足りるなら **新しい `##` を立てない**。

### ユーザー指摘に伴う SKILL の更新

**ユーザーから** CursorLog の粒度・タグ・「使用AIモデル」記載・markdownlint・UTF-8 注意・時系列挿入などについて**指摘**があった場合は、**同一セッションで**本 SKILL の該当節を修正する（dev-workspace **myrules**「**ユーザー指摘に基づくルール・SKILL の育成**」）。

**残作業・課題の記載（推奨・強く推奨）**: マイルストーン区切り、長めのセッションの終わり、またはユーザーが明示したときは、同一日のログに **`### 残作業・課題`** 見出し付きの箇条書きを追記する。内容は次を含めてよい（当日の文脈で重要なものに絞る。詳細は統合作業スケジュール・Issue・仕様のリンクで足りる）。

- 未着手・進行中の実装・調査（タスクIDや簡潔な説明）
- 運用面の保留（例: 通知の一時停止、デプロイ待ち）
- 技術的負債・テスト・カバレッジで次に触るべきこと
- ユーザー・ステークホルダ判断待ち

単純な1ファイル修正のみで引き継ぎ事項がゼロなら、「残作業・課題: なし」と1行でよい。

## 作業フローと報告前ゲート（必須）

myrules「作業ログ」から移管した手順の正本。報告前チェック・順序ゲートは**本節**を Read して従う。

### ファイル変更の定義

- **`StrReplace` / `Write` / `Delete` / `EditNotebook`** または **シェルでワークスペース配下のファイルを書き換え・生成**
- **CursorLog 本体だけ**を追記し、そのセッションに他の成果物変更がなければ **追加の作業エントリは不要**

### 作業フローの標準化（省略禁止）

1. **ファイル変更**（上記ツール等）
2. **テスト実行**（必要に応じて）
3. **`temp/` クリーンアップ**（触ったリポで `temp/` を使った／残存がある場合。**`temp-file-management`** SKILL。理想は空）
4. **CursorLog 更新**（ファイル変更後は必須）
5. **ユーザーへの報告**（「CursorLogは更新しました」を含む）

### 取り扱い終了文の前ゲート（順序厳守）

- **目的**: 成果報告を先に書き、CursorLog を後回しにする順序誤りを防ぐ
- **禁止**: 「完了」「以上です」「テストは通過」等の締めを**先に**述べ、CursorLog を後回しにする
- **必須**: ファイル変更が1件でもあれば、**ユーザー向け成果本文の前に** CursorLog 用 `Write` / `StrReplace` を**同一ターン内で完了**
- **要約直後**・短い承継メッセージでも、直前ターン群でファイルを変えていれば CursorLog を欠かさない。**ただし**、要約の「未記録」指示だけで追記せず、**当日ログに同一作業が既にないか先に確認**する（重複防止。下記「エントリ追記の必須手順」）

### 作業完了時の質問（必須）

1. **Q1**: ファイルを変更したか？ → NO なら CursorLog 不要（重要作業は記録検討）
2. **Q2**: 当日ログに**同一作業のエントリが既にないか**確認したか？ → あれば **新規 `##` は立てず**既存を更新またはスキップ（下記「エントリ追記の必須手順」）
3. **Q3**: CursorLog を更新したか（新規追記または既存更新）？ → 未記録なら即対応
4. **Q4**: 報告に「CursorLogは更新しました」を含めたか？ → NO なら追加してから送信

### 作業完了時の必須チェックリスト

- [ ] ファイル変更の有無（上記定義）
- [ ] 触ったリポの **`temp/` が空**（`temp-file-management` SKILL。次回も使うものは `scripts/` 等へ昇格済み）
- [ ] CursorLog 更新（本 SKILL の記録手順・日時取得）
- [ ] 追記先が JST 取得日付の `YYYY-MM-DD.md` か、時刻が実時刻か
- [ ] 報告文に「CursorLogは更新しました」

### 記録漏れが起きやすい状況

- **会話要約・スレッド切替**直後（直前セッションのファイル変更を思い出す）
- 実装に集中し SKILL を開かず次依頼へ進む
- **マルチルート**でコード倉庫だけ更新し Obsidian vault を忘れる

### 違反事例（2026-04・要約）

- **事象**: コード変更後、最終返答に CursorLog 追記が先立たない（「CursorLogは更新しました」も欠落）
- **主因**: 完了文を先に考える / マルチルートで Obsidian を忘れる / 要約直後に Q1〜Q3 が起動しない

## 基本ルール

- **Markdown編集時**: CursorLog（.md）を編集する際は、`markdown-editing` SKILLのルールに従う
- 保存先は `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM/YYYY-MM-DD.md`（JST）。月ごとのフォルダ（YYYY-MM）に日付ファイルを格納する。フォルダが存在しない場合は作成する。
- **ログファイルの日付（YYYY-MM-DD）は、追記直前にターミナルで取得した「現在の日付（JST）」を使う。**\
    **会話要約の `Today's date`・IDE で開いているファイル名・前回追記したパスをそのまま使わない**（日付跨ぎで前日ファイルに誤追記しやすい）。\
    0時を過ぎている場合は**当日**のファイルに追記し、誤って前日のファイルに書かないこと。
- **タグはファイル先頭（**最初の `##` 作業エントリより前**）にのみ置く**（`#obsidian`は禁止）。\
    **1行に詰め込まず、意味・プロジェクトなどで分けて複数行にしてよい**（各行は短く保つ）。\
    **markdownlint MD018** のため、行頭を `#tag` の裸にせず **`- #tag #tag2 …`** の箇条書き行にまとめる（Obsidian でもタグとして通常認識される）。\
    エントリの直後・本文中・末尾にタグを書かない。新規タグはいずれかの**先頭タグ行**に追記する。
- **タグは作業内容に応じて適宜、先頭ブロックのいずれかの行に追加する**
- **タグは重複しないこと（必須）**: 同一ファイル内で**同じタグを複数回書かない**。追記前に先頭ブロック全行を走査し、**既出タグは再掲しない**（別の行に重複記載も禁止）。\
    大文字小文字・全角半角の違いも同一タグとみなし、表記を揃える（例: `#FishTrack` と `#fishtrack` を混在させない）。\
    既に重複がある場合は、同じ編集セッションで**重複を除去**してから完了する。
- タイムスタンプは `HH:mm:ss`（JST）。**必ずその時点の実時刻を記載する**。プレースホルダー（`--:--:--` 等）・仮の時刻・固定値の使用は**禁止**。
- **使用AIモデル（必須・毎回確認）**: エントリを書く**そのチャット**で、ユーザーが Cursor のモデル選択で指定している名称を記載する。**追記のたびに**（1）チャットヘッダ／モデルピッカー等で**実際のモデル名を確認**し、（2）ユーザーが会話内でモデル名を明示していればそれを優先する。\
    **禁止**: テンプレ・前のエントリ・別セッションからの流用、推測、またはエージェントの内部モデル名をそのまま機械的に書くこと。**判別できないとき**は **「不明」** または **「（チャットUIで確認）」** とし、空欄にしない。
- 粒度はSlack最終報告の項目に合わせる
- **エントリの長さ**: **`## HH:mm:ss [作業名]` 1件あたり、本文を含め概ね30行以内**に収める（長いコマンド・パス列は `\` 改行や代表ファイル名への省略で短縮）。超える場合は**エントリを分割**（別時刻で続き）するか、**詳細はリポジトリ・Issue・仕様への参照**に任せ、ログでは要約のみにする。
- **ファイルを変更しない場合は、ログの更新は不要**
- **時系列順を厳守する**（HH:mm:ss の昇順で並べる。エントリは必ず時刻順に並んでいること）
- **追記時は適切な位置に挿入する**
  - 通常はファイル最下部に追記（新規エントリの時刻が既存の最末尾より後なら、そのまま末尾に追加）
  - **後から記録する場合**（複数作業をまとめて記録するなど）、時刻順になるよう**正しい位置に挿入**する。単純に末尾追加で時系列が崩れる場合は挿入位置を調整する
  - 追記後に時系列が乱れていないか確認する
- **エントリ見出し形式（必須）**: 各エントリの先頭は **`## HH:mm:ss [作業名]`** の見出し形式で統一する。リスト形式（`- HH:mm:ss`）は使用しない。

## 月次日報の自動作成

CursorLog の日次記録は、当日の最初の Log を書くタイミングで、
過去の日付のうち最も新しく、まだ日報化していない日を要約する。

### 保存形式

- 日報は日単位のファイルにしない。月ごとに 1 ファイルだけ作成する。
- 保存先は日報化する対象日の日付を基準に
  `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM/YYYY-MM 日報.md` とする。
  例: 2026 年 7 月分は `CursorLog/2026-07/2026-07 日報.md`。
- 月次日報の H1 は `# YYYY-MM 日報`、各日分は `## YYYY-MM-DD` 見出しで追記する。
- 同じ日付の見出しが既にある場合は重複作成しない。必要な補足だけ既存節を更新する。
- 1 日分の節は、見出し・空行を含めて **10 行程度**を目安とする。
  ジャンル見出しが必要な場合は、10 行を厳密に守るより分類の明確さを優先する。
- 箇条書きは単純に並べず、`### ジャンル名` の見出しで分類する。
  見出しの下に、そのジャンルの完了事項、検証結果、残作業・課題を箇条書きで記載する。
  大分類は `FishTrack`、`MyPokedex`、`FaiNavi`、`MiteneKeeper`、
  `Work`、`Obsidian`、`dev-workspace` などとし、
  FishTrack 内は必要に応じて `釣行プランAI`、`AIスペック取り込み`、
  `釣行メモ`、`ルアー管理` などの `####` 見出しへ細分化する。
- 分類名は作業内容に合わせて具体化し、同じ日でもジャンルが異なる項目は分ける。
  ファイル列挙や作業経過の再掲はしない。

### 実行タイミングと手順

1. 当日の CursorLog を初めて書く直前に、JST の現在日付を取得する。
2. 当日より前の日次 CursorLog から、月次日報に同じ日付の節がないものを探す。
   対象候補のうち日付が最も新しい 1 日だけを選ぶ。
3. 対象日の日次 CursorLog を全文 Read する。対象月の月次日報が存在する場合は Read して
   日付重複を確認する。存在しない場合は、その月次日報を新規作成してよい。
4. 対象日の主要な完了事項、検証結果、残作業・課題をジャンル別に簡潔に要約し、
   `### ジャンル名` の見出しでまとめて、
   対象日の日付の `## YYYY-MM-DD` 節として追記する。
5. 月次日報の markdownlint を検証してから、当日の CursorLog エントリを書く。

### 禁止事項

- 当日分を当日中に日報化しない。
- `YYYY-MM-DD_日報.md` など、日単位の日報ファイルを新規作成しない。
- 過去の日次 CursorLog がない場合や、すべて日報化済みの場合に空の節を作らない。

## 記録手順

### 🚨 日本語 UTF-8 ファイルへの破壊的操作の禁止（文字化け防止）

**CursorLog（および Obsidian vault 配下の日本語 .md ファイル）は BOM なし UTF-8 で保存されている。以下の操作は文字化けで全文破壊する可能性があるため、**絶対に使用しない**。**

**禁止**:

- PowerShell の **`Get-Content -Raw` でファイル全体を読み込み、`[System.IO.File]::WriteAllText` / `Set-Content` で書き戻す** パターン。\
    日本語 Windows 既定の **`cp932`（Shift-JIS）** でファイルを読んでしまい、それを **UTF-8 として再保存**することで、全行の日本語が **mojibake**（`繧ｿ繧ｹ繧ｯ` のような文字列）化する。
- `Get-Content` / `Set-Content` を `-Encoding` 指定なしで使うこと（PowerShell 5.x の既定は **環境依存**でしばしば cp932）。
- PowerShell の `>`・`>>` リダイレクトで **日本語テキスト**を既存ファイルへ追記すること（出力エンコーディングが cp932 になり得る）。
- PowerShell のヒアドキュメント（`@"…"@`）で日本語を含む **ファイル生成**（`commit-message` SKILL に沿って Python で書く）。

**推奨**:

1. 編集は **`StrReplace` ツール**を最優先で使う（エンコーディングを意識しない。差分だけを変更する）。
2. 末尾改行の付与・整形など **バイナリレベルの確定操作**が必要な場合は **Python を使う**。例:

   ```bash
   python -c "
   import pathlib
   p = pathlib.Path(r'D:\OneDrive\アプリ\remotely-save\Obsidian\CursorLog\YYYY-MM\YYYY-MM-DD.md')
   data = p.read_bytes()
   if not data.endswith(b'\n'):
       p.write_bytes(data + b'\n')
   "
   ```

3. どうしても PowerShell を使うなら、**読み書きとも `-Encoding utf8NoBOM`**（PS7+）または\
   `[System.IO.File]::ReadAllText(path, [System.Text.UTF8Encoding]::new($false))` / `WriteAllText` の\
   **両方**で UTF-8 を明示する（片方だけ明示は最も危険）。

**事故検知**: 編集後に `python -c "print(open(path,'rb').read()[:200])"` でバイト列先頭を確認し、\
**`繧`・`縺`・`\uf8f0`・`\x80`** のような Shift-JIS → UTF-8 二重解釈由来のバイト列が出たら **即座に中断**し、\
**Obsidian vault は git 管理外のため OneDrive のバージョン履歴から復元**する（`.md` を右クリック → 「バージョン履歴」）。

**過去事故（2026-04-20）**: `[System.IO.File]::WriteAllText($path, (Get-Content -Raw $path) + "\`n", …)` で `2026-04-20.md` 全文を破壊。git なし・OneDrive 復元が必要になった。

### 🚨 日時（実日付・実時刻）の必須手順（失敗防止）

**ログを追記する直前に、必ず以下を実行すること。省略禁止。**\
**日付と時刻は別々に推測せず、1回のターミナル実行でまとめて取得する**（日付だけ会話文脈・前日ファイルから取るミスを防ぐ）。\
**一般ドキュメント向けの JST 記載ルール**は **`datetime-jst`** SKILL も参照（本節は **CursorLog 専用**）。

1. **現在日時（JST）をターミナルで取得する**  
   以下いずれかを実行し、表示された **`YYYY-MM-DD`** と **`HH:mm:ss`** をそのまま使う。
   - **PowerShell（推奨・日付と時刻を同時取得）**:

     ```powershell
     $jst = [TimeZoneInfo]::ConvertTimeFromUtc((Get-Date).ToUniversalTime(), [TimeZoneInfo]::FindSystemTimeZoneById('Tokyo Standard Time'))
     "date=$($jst.ToString('yyyy-MM-dd')) time=$($jst.ToString('HH:mm:ss'))"
     ```

     1行でよい場合: `$jst.ToString('yyyy-MM-dd HH:mm:ss')` でも可（前半が日付・後半が時刻）。

   - **Python**:

     ```python
     datetime.now(timezone(timedelta(hours=9))).strftime('%Y-%m-%d %H:%M:%S')
     ```

2. **取得した日付で追記先ファイルを決める**  
   - パス: `D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM/YYYY-MM-DD.md`（`YYYY-MM` は取得日付の年月）  
   - **編集対象のファイル名・先頭 `# YYYY-MM-DD` が、取得した日付と一致しているか確認する**。不一致なら**正しい当日ファイルに切り替えてから**追記する（前日ファイルへの追記は禁止）。
3. **取得した時刻をエントリ見出し `## HH:mm:ss` にそのまま記載する**。推測・仮の値は使わない。
4. **禁止**:
   - 日付: 会話要約の日付・開いているタブのファイル名・「さっきまで書いていたファイル」を**取得コマンドなしで**追記先に使うこと
   - 時刻: `--:--:--`、`00:00:00` 等のプレースホルダー、または「だいたいこの頃」などの仮の時刻

### 🚨 タグ追記の必須手順（重複防止）

**タグを追記・新規作成する直前に、必ず以下を実行する。省略禁止。**

1. **先頭ブロック全体を Read する**（末尾や差分だけを見ない）。\
   対象は `# YYYY-MM-DD` 直後から最初の `## HH:mm:ss` 直前までの **`- #tag …` の全行**。
2. **既存タグを列挙する**。目視で拾う前に、以下の抽出コマンドで機械的に一覧化してもよい。

   ```powershell
   Select-String -Path "<CursorLogファイルの絶対パス>" -Pattern '(?<!\S)#\S+' -AllMatches |
     ForEach-Object { $_.Matches.Value } | Sort-Object -Unique
   ```

3. **新規追加候補と逐一突合する**。既出のものは**捨てる**（別の行に再掲も禁止）。\
   大文字小文字・全角半角は同一タグとみなし、表記を揃える。
4. **特に注意**するタグ（重複頻度が高い）:
   - **プロジェクト名タグ**: `#MyPokedex` / `#FishTrack` / `#otayori-navi` / `#dev-workspace` / `#MyHobbySite` / `#personal-tools`
   - **汎用カテゴリタグ**: `#bugfix` / `#refactoring` / `#pull-request` / `#CursorLog` / `#housekeeping` / `#仕様書` / `#テスト`
5. **完了条件**: 追記後、先頭ブロックのタグを再度抽出し、**完全一致の重複が 0 件**であることを確認してから完了とする（上記抽出コマンドの結果行数と、ソート前の全出現回数が一致すれば重複なし）。

### 🚨 エントリ追記の必須手順（重複防止）

**新しい `## HH:mm:ss` を書く直前に、必ず以下を実行する。省略禁止。**

1. **当日ログファイルを Read する**（末尾だけでなく、**直近 5 件以上の `##` エントリ**を目視または検索で確認）。
2. **今回記録しようとしている作業のキー**を決める（次のいずれか。複数あれば**最も狭い一致**を優先）:
   - `- 作業名:` の本文（`**` 等の装飾を除いた正規化後の文字列）
   - 見出し `## HH:mm:ss […]` の `[…]` 内（装飾除く）
   - **製品 PR フロー**: 同一チャット内のコミット〜PR〜CI を **1 キー**（例: `FishTrack_pull-request` + 主要変更の要約）
3. **重複判定**: 当日ログに、上記キーと**実質同一**のエントリが既にあるか検索する。\
   **実質同一**の例:
   - `- 作業名:` が正規化後に一致（空白・太字のみの差は無視）
   - 変更ファイルの主要パスが同じで、実施内容が同じ作業単位（要約で「済」と書かれた作業の再ログ）
   - 会話要約後に、直前ターンで書いたエントリと同じ成果を再度書こうとしている
4. **重複がある場合**:
   - **新規 `##` は追加しない**（禁止）。
   - 追記すべき情報があるときだけ、**既存エントリ 1 件**を `StrReplace` で更新する（`- 結果:`・`- 残作業・課題:` の追記、PR 番号・CI URL の追記等）。更新アンカーは **`## HH:mm:ss` 見出し行**など**ファイル内で一意**な行に限定する。
   - 追加情報がなければ **CursorLog 操作はスキップ**し、報告には「CursorLogは更新済み（重複追記なし）」と書いてよい。
5. **重複がない場合 — 追記方法**:
   - **原則**: ファイル**最末尾**に新規エントリを追加する（`StrReplace` の `old_string` は**ファイル末尾の一意な数行**、例: 直前エントリの `- 残作業・課題:` 行から EOF まで）。
   - **禁止**: ファイル中盤のブロックを `replace_all` で置換して「追記」すること。同一ブロックが 2 つあると複製・片方残りの原因になる。
   - 時系列挿入が必要なときだけ、挿入位置の前後を Read し、**挿入点のアンカーが一意**であることを確認してから `StrReplace` する。
6. **1 チャット 1 エントリ（原則）**: ユーザーの**1 回の依頼**が完了したときは、原則 **新規 `##` は 1 件まで**。\
   コミット→PR→CI のように段階があっても、**親 SKILL（例: `FishTrack_pull-request`）が 1 エントリにまとめる**ときは子 SKILL 側で別エントリを書かない。
7. **完了条件（重複ゼロ）**: 追記・更新後、以下で確認する（PowerShell 例）:

   ```powershell
   Select-String -Path "<当日CursorLogの絶対パス>" -Pattern '^- 作業名:' |
     ForEach-Object { ($_.Line -replace '\*\*','').Trim() } |
     Group-Object | Where-Object { $_.Count -gt 1 }
   ```

   出力が空なら `- 作業名:` の完全一致重複なし。見出し `## HH:mm:ss […]` の**完全同一行**が 2 つ以上ないことも目視で確認する。

#### 製品 PR フローとの関係

- **`FishTrack_pull-request` / `MyPokedex_pull-request` / `otayori-navi_pull-request`** 実行時: CursorLog は**フロー全体完了後に 1 エントリ**（コミット・PR 番号・マージ・CI 結果をまとめる）。
- 当該フロー内で **`FishTrack_commit` 等を Read して実行する場合**、commit SKILL の CursorLog 節は**適用しない**（親 SKILL の 1 エントリに委譲）。詳細は各 `*_pull-request` SKILL の「Cursorログ更新」。

### 🚨 使用AIモデル（毎回確認）の必須手順

**ログ本文に `- 使用AIモデル:` を書く直前に、必ず以下を行う。省略禁止。**

1. **当該チャット**で実際に使われているモデルを確認する（Cursor のモデル表示・会話内のユーザー明示を参照）。
2. **その名称をそのまま**（例: `Composer2`、`GPT-5.4`、`Claude Opus 4.7` 等、UI に表示される表記に合わせる）を1行に記載する。
3. **禁止**: テンプレの例文・直前のエントリ・システムメッセージに出るモデル名を**確認なしで**コピーすること。セッションやチャットが変わるとモデルも変わるため、**毎エントリで再確認**する。
4. ユーザーが「Composer2 を指定した」と言及している場合は、それを正とする。
5. どうしても確信が持てないときだけ **「不明」** または **「（チャットUIで確認）」** とし、空欄にしない。

### 記録の流れ

1. **上記「日時（実日付・実時刻）の必須手順」に従い、ターミナルで JST の日付・時刻を一括取得する**（手順 1〜2）。取得日付の `CursorLog/YYYY-MM/YYYY-MM-DD.md` を開く（なければ作成。月フォルダが無ければ作成）。**開いているファイルの日付と取得日付が一致していることを確認してから**次へ進む。
2. **上記「使用AIモデル（毎回確認）の必須手順」に従い、当該チャットのモデル名を確定する**（`- 使用AIモデル:` を書く直前でもよいが、**記載前に必ず実施**する）
3. **タグはファイル先頭ブロック（日付見出し直後～最初の `##` より前）にのみ記載**。複数行に分け、各行は **`- #tag …`** の箇条書きとする（**MD018** 防止）。ファイルが新規の場合は `# YYYY-MM-DD` の直後に空行を挟みタグの箇条書きを置く。既存ファイルの場合は、必要なタグを先頭ブロックのいずれかの行に追記する。エントリの直後やログ本文中にタグを書かない。\
   **上記「🚨 タグ追記の必須手順（重複防止）」に従い**、先頭ブロック全体を Read → 既存タグ抽出 → 新規候補と突合 → 完了後の重複ゼロ確認を実施する（**重複禁止**。大文字小文字・全角半角は同一タグとみなす）。既に重複があれば、同じ編集セッションで除去する。
4. **上記「🚨 エントリ追記の必須手順（重複防止）」を実施**する（当日ログ Read → 重複判定 → 新規 `##` または既存更新のどちらかを決定）
5. **適切な位置**に、取得した `HH:mm:ss` を用いて以下の形式で追記する（**重複判定で新規が必要な場合のみ**）  
   - 新規エントリの時刻が既存の最末尾より後なら、ファイル最下部に追加  
   - 後から記録する作業で、時刻が既存エントリの間に入る場合は、時系列順になる位置に挿入する  
   - 追記後、HH:mm:ss が昇順になっているか確認する
6. **Lint検証（必須）**: 追記完了後、markdownlint で検証し、**エラーを残さない**  
   - dev-workspace をカレントにし、`npx markdownlint-cli2 -c "<対象ボールトの .markdownlint.json>" "対象CursorLogファイルの絶対パス"` を実行（**Obsidian 側の設定が正本**のことが多い）  
   - **同一ファイルの lint は一括で直す**: ユーザーが **1 行・1 エラーコードだけ**指定した場合でも、当該 `.md` を触る作業の\
       **完了条件は `Summary: 0 error(s)`**。既存の別行の MD013 等が残っていれば、**同じ編集セッションでまとめて解消**する（\
       `markdownlint-fix` SKILL の「同ファイルのエラー一括」と同趣旨）。**例外**: ユーザーが「この行だけ」「他は触らない」と明示したときはその範囲に従う。  
   - MD013（行長超過）等のエラーが出た場合は、`markdown-editing` / `markdownlint-fix` SKILL に従って修正する（句読点・括弧前で改行、リスト継続は4スペース）  
   - **禁止**: **ユーザー明示なく** `markdownlint-disable` コメントや設定の勝手な緩和・除外で Lint を迂回しない（**`ai-spec-check-report` の §9.0.1** と同旨）。  
   - 修正後、再検証してエラーゼロであることを確認してから完了とする

### CursorLog 編集時の再発防止（「一部だけ解消」が起きうる理由と対策）

**起きうる理由**: 依頼・会話・IDE の診断が **特定の 1 行**に限定して見えると、エージェントが **その行だけ**を直し、\
`markdownlint-cli2` を **編集したファイル全体**に対して実行せずに完了してしまう。`ReadLints` は表示が片側に偏ることがあるため、\
**行単位の表示だけを正本にしない。**

**必須の対策（省略禁止）**:

1. **CursorLog の当該 `.md` を 1 文字でも変更したら**、**必ず**そのファイルの **絶対パス**を引数に\
   `markdownlint-cli2` を実行する（対象ボールトの `.markdownlint.json` を `-c` で渡す）。  
2. **完了条件**は **CLI 出力の `Summary: 0 error(s)`** のみ。1 行直した時点では完了としない。  
3. エントリの **「テスト結果」**に「当該行の MD013 解消」**のみ**と書き、同一ファイルに別行の違反が残る状態で終了**しない**。  
4. 直前のエントリで「残存」と書いた行があれば、**同じ編集セッションで**まとめて解消するか、続けて解消するエントリを立てる。

## 実装上の注意

- **日本語 UTF-8 ファイルの破壊防止**: `Get-Content -Raw` + `Set-Content` / `WriteAllText` で\
    **ファイル全体を読み書きし直すパターンは禁止**。差分編集は `StrReplace`、末尾改行などのバイナリ確定は\
    **Python の `write_bytes`** を使う（詳細は本 SKILL **「🚨 日本語 UTF-8 ファイルへの破壊的操作の禁止」**）。
- **日時**: 日付・時刻は**追記のたびに**ターミナルで一括取得する。前日ファイルが IDE に開いたままでも、**取得日付のファイル**へ書く。
- **使用AIモデル**: 日時と同様、**毎エントリで再確認**する。チャットを切り替えた・モデルを変えた直後の追記では特に誤記が起きやすい。
- **エントリ長（30行目安）**: 追記後に行数を確認し、超える場合は省略・分割・参照に置き換える（詳細は `markdown-editing` の MD013 対策と両立させる）。
- **時系列優先**: エントリは HH:mm:ss の昇順で並べること。新規エントリの時刻が既存末尾より後なら末尾に追加。後から記録する作業で時刻が途中になる場合は、正しい位置に挿入する（単純に末尾追加のみでは不十分な場合あり）
- **追記位置**: 原則はファイル最下部に追記。ただし時系列が崩れる場合は、該当時刻の直後へ挿入する
- **Lintエラーを残さない**: 追記・修正後は markdownlint で検証し、MD013 等のエラーが出た場合は必ず修正してから完了とする。**同一 CursorLog ファイル内に、修正していない既存違反を残した状態で完了にしない**（上記「記録の流れ」Lint 項の「同一ファイルは一括で直す」に従う）
- 既存の見出しや構造は維持し、最小限の追記で完結させる
- **タグはファイル先頭ブロック（最初の `##` より前）にのみ記載する。** 複数行に分けてよい。エントリの直後・ログ本文中・末尾にタグを書かない。新規タグは先頭ブロックのいずれかの行に追記する。
- **タグは重複させない**: 同一ファイルの先頭ブロック内で同じタグを複数回書かない（行をまたいだ重複も禁止）。大文字小文字・全角半角は同一タグとみなす。追記前に先頭ブロックを走査し、既出タグは再掲しない。具体手順は**「🚨 タグ追記の必須手順（重複防止）」**に従う。
