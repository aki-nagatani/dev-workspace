# Obsidian InBox Summarize

## Obsidian の位置づけ（第二の脳）

**横断原則の正本**: **`obsidian-second-brain` SKILL**（すべての Cursor 利用時に適用。Knowledge・Work・釣り・DevProject 等への集約）。

本 SKILL（`obsidian-inbox-summarize`）は、その原則の**入力チャネルの一つ**——**InBox** に溜まった URL・クリップ・PDF・メモ・ボイスメモを脳へ取り込む手順である。

### InBox 処理でのドメイン別正本への反映（必須）

InBox 1 件の処理で **Articles ＋ Knowledge だけで完了してはならない**。内容を分析したあと、**`obsidian-second-brain` SKILL「ドメイン別正本マップ」**に従い、**該当する正本へ同一セッション内で記録**する。

1. **Articles**（通常経路）と **Knowledge**（釣行メモ経路を除く）を作成・更新
2. **領域判定**（複数可）— マップ・委譲 SKILL は **`obsidian-second-brain`** を正とする
3. **報告だけにしない**: §「適用可能性」で「使えそう」と書いて終わらず、**移す価値がある情報は Obsidian 上の正本を更新**する
4. **判断不能**（領域・保存先が一意に決まらない）ときのみユーザーに確認

## 入口（旧 Cursor Command の統合）

**旧 `.cursor/commands/Obsidian_InBox_Summarize.md` は廃止**し、**手順の正本は本 SKILL のみ**。

### 成果物（入力種別で分岐）

1. **原文全文（必須・通常経路）**: 取得・読み込んだ内容を **Markdown の全文** として Obsidian に保存する（要約だけでなく、元記事相当の本文を残す）。**音声**は文字起こし結果を本文とする。
2. **Knowledge（必須・通常経路）**: 実用的な知識をジャンル別ノートに**最新状態として集約**する（新規作成または既存更新）。**加えて**、内容が仕事・釣り・開発等の領域に該当すれば **`obsidian-second-brain` SKILL** に従い各正本も更新する。
3. **釣り関連ボイスメモ（追加・必須）**: **文字起こし後**（**`.m4a` 等は 1.4**、**`voice_` 始まり `.md` は本文抽出**）に**釣り関連と確定**してから、**過去の `釣行メモ.md` を Read**し専門用語を揃え、構造化した内容を **`Fishing/釣行メモ.md`** の**末尾**に追記する（下記「ボイスメモの振り分け」）。
4. **釣り以外のボイスメモ**: **文字起こし済みテキスト確定後**、**領域判定**（仕事／開発／汎用知識等）し、該当正本へ反映。**保存先が一意に決まらないときのみ**ユーザー確認で中断（下記 1.4.1）。

## 適用条件

- 対象は以下のいずれか：
  - InBoxディレクトリ配下のMarkdownファイル、PDFファイル、**音声ファイル**
  - ユーザーが直接指定したMarkdownファイル、PDFファイル、**音声ファイル**（Cursorから直接渡される場合も含む）
- 上記「既定の入出力パス」または、依頼で明示された InBox ディレクトリ、**原文全文保存先（Articles）**、Knowledge 保存先を使用する
  - **原文全文保存先の既定**: `D:/OneDrive/アプリ/remotely-save/Obsidian/Notes/Knowledge/Articles/`（依頼で別パスが指定されていればそれに従う）
- 直接ファイルが指定された場合は、そのファイルを処理対象とする

### InBox の棚卸し（エージェント必須・Glob だけ禁止）

**SKILL 本文は音声（`.m4a` 等）を対象に含む。** 漏れの主因は手順ではなく、**Cursor の Glob だけで InBox を見るとバイナリ（音声・PDF）が 0 件と誤判定されやすい**こと。

- ファイル未指定で InBox を確認するときは、**必ずシェルで全ファイルを列挙**してから件数・種別を報告する（**Glob のみで「InBox は空」と断定しない**）
- **正本コマンド**（PowerShell）:

  ```powershell
  Get-ChildItem -Path "D:\OneDrive\アプリ\remotely-save\Obsidian\InBox" -File -Recurse |
    Sort-Object Name |
    Select-Object Name, Length, LastWriteTime
  ```

- **0 件と報告する直前**: 上記を再実行して確認する（`.m4a` のみ残っている場合も「未処理あり」）
- **1 件の選び方**（未指定時）: 列挙結果の **名前昇順で先頭 1 件**（ファイル名に日時がある場合は **古い順**でも可。同一実行内で一貫させる）

## 処理フロー

### 1. ノートの読み込み

- **入力ソースの確認**:
  - ユーザーが直接ファイルを指定した場合: そのファイルを処理対象とする
  - ファイルが指定されていない場合: InBoxディレクトリ配下のMarkdownファイル、PDFファイル、**音声ファイル**を確認し、1件を選択
- 各ノートの内容を読み込む
  - **Markdownファイルの場合**: ファイルの内容を直接読み込む
    - **`voice_` 始まり**（例: `voice_20260615003619.md`）→ **形式 6（文字起こし済みボイスメモ）**。**whisper は実行しない**
  - **PDFファイルの場合**: PDFからテキストを抽出して読み込む。
    `dev-workspace/scripts/extract_pdf_text.py` を使用する
    （pypdf 失敗時は おたよりナビ OCR API → Azure Document Intelligence の順でフォールバック）。
    または Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用する。
  - **音声ファイルの場合**: **必ず文字起こし**する（下記「6. 音声ファイル形式」および「1.4 音声の文字起こし」）。
- **重要**: 1つのノートに複数の項目が含まれている場合、1つの項目だけを処理対象とする

**入力形式**:
InBoxノートには以下の**6種類**の形式がある：

1. **URL形式**: ノートの内容がURLのみの場合
   - 例: `https://qiita.com/degudegu2510/items/eff0f63dac99554e6439`
   - URLの内容を取得して分析する（可能な場合）
   - **URLの内容を取得できない場合（タイムアウト、エラー、アクセス不可等）**: 処理を中断する
   - **複数URLがある場合**: 1つのURLだけを処理対象とする（先頭のURL、または最初に見つかったURL）

2. **WEBクリップ形式**: ObsidianのWeb Clipperで保存された形式
   - フロントマターにURLやメタデータが含まれる
   - 本文にWebページの内容がMarkdown形式で保存されている
   - 例:

     ```markdown
     ---
     url: https://example.com/article
     title: 記事タイトル
     ---
     
     # 記事タイトル
     
     記事の本文内容...
     ```

   - **複数のWEBクリップがある場合**: 1つのクリップだけを処理対象とする（先頭のセクション）

3. **PDF形式**: PDFファイルが指定された場合
   - PDFファイルがInBoxディレクトリ配下に配置されている、またはユーザーが直接指定したPDFファイル
   - PDFからテキストを抽出して分析する
   - **PDFの読み込み方法**: `dev-workspace/scripts/extract_pdf_text.py` を使用する（推奨）。
     このスクリプトは (1) pypdf でテキスト抽出を試行し、
     (2) テキストが十分得られない場合におたよりナビ OCR API（`http://localhost:5003/` 固定）でフォールバック、
     (3) それでも失敗時は Azure Document Intelligence でフォールバックする。
   - **代替**: Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用して
     PDFからテキストを抽出することも可能。
   - **おたよりナビ OCR API フォールバック**: ローカル Docker で otayori-navi が
     `http://localhost:5003` で稼働している場合、pypdf 失敗時に検索可能PDF API を呼び出して再抽出する。
     URLは固定のため環境変数不要。認証は不要（`OTAYORI_OCR_API_KEY` は任意）。
   - **Azure Document Intelligence フォールバック**: 上記が失敗または未設定の場合に使用。
     環境変数 `AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT` と `AZURE_DOCUMENT_INTELLIGENCE_KEY` が設定されているとき、
     かつ `azure-ai-documentintelligence` がインストールされているときのみ有効。
   - **PDFの読み込みに失敗した場合（ファイル破損、暗号化、アクセス不可等）**: 処理を中断する
   - **複数PDFがある場合**: 1つのPDFだけを処理対象とする（先頭のPDF、または最初に見つかったPDF）
   - **PDFファイルの処理後**: テキスト抽出が完了したら、PDFファイルを参考資料としてObsidian内に保存する
     - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
     - PDFファイルを`attachments`ディレクトリにコピーして保存
     - ノートの「参照」セクションにPDFファイルへのリンクを追加（例: `[[attachments/ファイル名.pdf]]`）
     - InBoxディレクトリ内のPDFファイルは削除する（直接指定されたPDFファイルは削除しない）

4. **手入力メモ形式**: ユーザーが手動で入力したメモ
   - フロントマターがない、または最小限のフロントマターのみ
   - 本文にユーザーが記述した内容が含まれる
   - 例:

     ```markdown
     Cursorのショートカットキーについて
     
     - Cmd+K: インライン編集
     - Cmd+L: チャット開始
     ```

   - **複数のメモ項目がある場合**: 1つの項目だけを処理対象とする（先頭のセクション、または明確に区切られた最初の項目）

5. **文字起こし済みボイスメモ形式（`voice_` 始まり Markdown）**: 端末等で**既に文字起こし済み**のボイスメモを InBox に置いた `.md`
   - **判定**: ファイル名が **`voice_` で始まる**（拡張子 `.md`）。例: `voice_20260615003619.md`
   - **本文レイアウト（固定）**: **1 行目＝録音日時**（例: `2026/06/15 0:36:18`。**MD041 対応で H1 見出しも可**。例: `# 2026/06/15 0:36:18`）→ 空行 → **`----`** → 文字起こし全文
   - **1 行目（録音日時）の扱い**:
     - **先頭の `#` と直後スペースは除去してから**日時パースする
     - **文字起こし本文には含めない**（メタ情報として別保持）
     - **釣行メモの `## YYYY-MM-DD — 場所名` の日付**、Articles の **`YYYY-MM-DD` ファイル名**、状況欄の**時刻**等の**参考根拠として必ず用いる**（文字起こしに日付が無くても **1 行目を優先**）
     - パース例: `2026/06/15 0:36:18` → 日付 **`2026-06-15`**・時刻 **`0:36`**（先頭ゼロは既存釣行メモに合わせてよい）
     - **1 行目が日時らしくない**ときのみ、ファイル名の `voice_YYYYMMDDHHmmss` や処理日 JST を**次点**とする
   - **whisper 禁止**: **1.4 をスキップ**し、本文から文字起こしテキストを抽出して **1.4.1（ボイスメモ振り分け）** へ（抽出規則は下記）
   - **文字起こしテキストの抽出**:
     - 本文に **`----`（4 連ハイフン）行**がある → **その行より後**を文字起こし全文とする（**1 行目の録音日時は除外**）
     - **`----` が無い** → **2 行目以降**（1 行目を除いた本文）を文字起こし全文とする。1 行目のみの場合は文字起こし空として扱う
   - **後続**: 釣り関連なら `釣行メモ.md` 追記経路（**1.4.1**）。音声ファイル（`.m4a` 等）は**同梱されていなければ attachments コピーは不要**
   - **処理後（InBox 内の場合）**: 釣行メモ追記等が完了したら **当該 `.md` を InBox から削除**（直接指定は削除しない）

6. **音声ファイル形式**: InBox またはユーザー指定の音声ファイル（ボイスメモ等）
   - 対象拡張子の例: `.m4a`、`.mp3`、`.wav`、`.aac`、`.ogg`、`.flac`、`.webm`、`.mp4`（動画だが音声文字起こし可）
   - **必ず文字起こし**してから後続処理へ進む（下記「1.4」「1.4.1」）
   - **複数音声がある場合**: 1つのファイルだけを処理対象とする（先頭または最初に見つかった1件）
   - **文字起こしに失敗した場合**（依存未インストール・ファイル破損・アクセス不可等）: 処理を中断する。InBox 内のファイルは削除しない
   - **処理後（InBox 内の場合）**: 釣り関連ボイスメモで `釣行メモ.md` 追記完了後、または釣り以外でユーザー指示に従った後、音声ファイルを削除してよい（直接指定は削除しない）

### 1.4 音声の文字起こし（音声ファイルのみ・必須）

**`.m4a` 等の音声ファイル**を処理するときは、**分析・振り分けの前に必ず文字起こし**する。

**対象外（whisper 実行禁止）**: InBox の **`voice_` 始まり `.md`**（上記 **形式 6**）。本文から文字起こしテキストを抽出し、**1.4.1** へ直接進む。

- **正本ツール**: **personal-tools** の **whisper_transcribe**（Faster-Whisper）
- **実行例**（personal-tools リポジトリ直下）:

  ```powershell
  cd d:\OneDrive\git_work\personal-tools
  python -m src.whisper_transcribe "D:\...\InBox\memo.m4a" -l ja -m small --device auto -o temp\transcript.txt
  ```

- **推奨オプション**:
  - `-l ja`（日本語ボイスメモが主のとき）
  - `-m small`（精度と速度のバランス。過去運用実績あり）
  - `--device auto`（GPU があれば利用、なければ CPU）
- **依存**: `pip install -r requirements-whisper-transcribe.txt`（未導入時はインストールを試行し、失敗なら中断して報告）
- **出力**: 文字起こし全文テキスト。以降の判定・Markdown 化はこのテキストを正とする
- **一時ファイル**: 出力 `.txt` は **personal-tools の `temp/`** に置く（作業完了時に削除）

### 1.4.1 ボイスメモの振り分け（文字起こし後・必須）

文字起こしテキストが確定した後にだけ、個人のボイスメモとして領域（釣り関連・本職・副業開発・汎用知識・領域未確定）ごとに経路を分ける。
判定基準、経路表、`Fishing/釣行メモ.md` への追記ルール、釣り系専門用語、使用ルアー節の検査は [references/voice-memo-routing.md](references/voice-memo-routing.md) を読んで従う。
ボイスメモでない音声・記事では読まない。`釣行メモ.md` は釣り関連と確定してから Read する。

### 1.5 原文全文Markdown（Articles）の作成（必須）

InBox の1件につき**必ず**原文相当の全文を `Notes/Knowledge/Articles/` に Markdown で保存する。Knowledge ノートの `## 参照` には、この全文ノートへのリンクを必ず入れる。
保存先・ファイル名・フロントマター・入力形式別の本文・markdownlint 違反 0 件・本文内容不変の手順は [references/articles-fulltext.md](references/articles-fulltext.md) を読んで従う。

### 2. 内容分析とKnowledge抽出

- ノートの内容を分析し、記事から得られるKnowledge（知識・知見・実用的な情報）を抽出
- **入力形式に応じた処理**:
  - **URL形式の場合**:
    - URLの内容を取得して分析（可能な場合）
    - **重要**: URLの内容を取得できない場合（タイムアウト、エラー、アクセス不可等）は、処理を中断する
    - URL取得に失敗した場合は、InBoxノートを削除せず、エラーメッセージと共に処理中断の旨を報告する
  - **WEBクリップ形式の場合**: フロントマターからURLやタイトルを抽出し、本文内容を分析（本文が存在する場合は本文を分析）
  - **PDF形式の場合**:
    - PDFファイルからテキストを抽出して分析
    - **PDFの読み込み方法**: まず `dev-workspace/scripts/extract_pdf_text.py <PDFパス>` を実行してテキストを取得する。
      このスクリプトは pypdf → おたよりナビ OCR API（`http://localhost:5003` 固定、otayori-navi 稼働時）
      → Azure Document Intelligence（テキスト不足時）の順で試行する。
      スクリプトが使えない場合は、Pythonの`pypdf`または`pdfplumber`を直接使用する。
    - **PDFの読み込みに失敗した場合（ファイル破損、暗号化、アクセス不可等）**: 処理を中断する
    - PDFファイルを削除せず、エラーメッセージと共に処理中断の旨を報告する
    - テキスト抽出が成功したら、抽出したテキストを分析してKnowledgeを抽出
    - **PDFファイルの保存**: テキスト抽出が完了したら、PDFファイルを参考資料としてObsidian内に保存する
      - Knowledgeノートと同じディレクトリに`attachments`サブディレクトリを作成（存在しない場合）
      - PDFファイルを`attachments`ディレクトリにコピーして保存
      - ノートの「参照」セクションにPDFファイルへのリンクを追加（例: `[[attachments/ファイル名.pdf]]`）
  - **手入力メモ形式の場合**: 本文内容を直接分析（フロントマターがあればメタデータも抽出）
  - **音声ファイル形式の場合**:
    - **1.4** で文字起こし済みテキストを分析
    - **釣り関連ボイスメモ**: **1.4.1** に従い `釣行メモ.md` へ追記。Knowledge 抽出は行わない（釣行メモが成果物）
    - **釣り関連以外のボイスメモ**: **1.4.1** に従い領域判定。**本職・開発・汎用**は自動反映。**領域が一意に決まらない**ときのみユーザー確認で中断
    - **記事相当の長尺音声**: 従来どおりジャンル特定・Knowledge 抽出へ
- **ジャンルを特定**（例: Cursor、Python、AWS、Raspberry Pi など）
- **Knowledge（知識）を抽出・整理**:
  - 記事の要約ではなく、記事から得られる実用的な知識・知見・ノウハウを抽出
  - 具体的な手順、ベストプラクティス、注意点、使用例、テンプレート、設定方法など、実際に活用できる情報を整理
  - 単なる記事の要約ではなく、自分が今後参照・活用するための知識として構造化
  - **Knowledge ノートは「最新の正」**。Articles は原文アーカイブ（事実の出典）であり、Knowledge はそこから蒸留した**現時点で有効な知見**を集約する
- 元の内容への参照を保持（URL、引用など。手入力メモの場合は参照セクションは省略可）
- キーワードやタグ候補を抽出（同ジャンルノート検索に使用）

**ジャンルの特定方法（内容優先）**:

- **タイトルや見出しの語句だけで判断しない**。本文全体を読み、知識の再利用先（どのノートに追記すると最も価値が高いか）でジャンルを決める
- 固有名詞（ツール名、サービス名、技術名）は補助情報として扱う
- 主要トピックと適用範囲（特定ツール限定か、横断的な原則か）を判定する
- **適用範囲が広い場合は上位概念を優先**（例: ツール固有TipsではなくAI開発全般の原則なら `AI開発` 系ノート）
- 例: タイトルが「Cursorを使ったAI開発のベストプラクティス」でも、本文がAI開発全般の原則中心 → ジャンル: `AI開発`（`Cursor` 固有ノートを優先しない）
- 例: 「Pythonのデコレータ」に関する記事 → ジャンル: `Python`
- 例: 「AWS Lambda」に関する記事 → ジャンル: `AWS`

### 3. 既存ノートの検索

Knowledge保存先ディレクトリ配下の既存ノートを検索し、同ジャンルのノートを探す。

**同ジャンルの判定基準**（優先順位順）:

1. **内容の関連性（最優先）**: 抽出したKnowledgeの主眼（原則・手順・判断基準）が既存ノートの主題と一致する
2. **適用範囲の一致**: 特定ツール向けか、横断的なベストプラクティスかが既存ノートの粒度と一致する
3. **タグの一致**: 抽出したタグ候補と既存ノートのタグが一致または類似
4. **キーワードの一致**: 主要キーワードが既存ノートのタイトルや内容に含まれる
5. **タイトルの類似性**: タイトルが同じトピックを扱っている（補助的に使用）

**検索方法**:

- Knowledge保存先ディレクトリ配下の全Markdownファイルを確認
- 各ファイルのタイトル、タグ、主要キーワードに加え、`Knowledge` セクションの主題を確認
- InBoxノートの内容（抽出したKnowledgeの主眼・適用範囲）と比較して関連性を判定
- **禁止**: タイトル内の語句一致のみで保存先ノートを決定しない

### 4. ノートの作成または更新

#### Knowledge ノートの役割（Articles との住み分け）

**前提**: Knowledge は第二の脳における**統合理解の正本**（横断原則は **`obsidian-second-brain` SKILL**）。ここが古いままだと、脳を開いても判断に使えない。

| 種別 | 役割 | 更新方針 |
| --- | --- | --- |
| **Articles** | 原文全文のアーカイブ（出典・日付付きの一次記録） | 本文の事実改変は禁止（1.5）。新しい InBox 処理ごとに**別ファイル**を追加 |
| **Knowledge** | ジャンル別の**最新知識の集約先**（開けば現時点の実用知見が揃う） | 同一トピックは**新情報で上書き・差し替え**。履歴の積み上げログにしない |

#### 既存ノートが見つかった場合（集約・更新）

**重要**: Knowledge ノートは**追記専用ログではない**。既存ノートを完全に読み、今回の抽出知識と**トピック単位で突合**し、**最新の正**になるよう本文を更新する。

**更新手順**:

1. **既存ノートの内容を完全に読み込む**
   - 既存ノートの全体構造・セクション・記述スタイルを把握する

2. **トピック単位で突合する**
   - 今回の Knowledge と既存の同一トピック（手順・仕様・ベンチマーク・価格・推奨設定・廃止事項など）を対応づける
   - **新情報が旧情報を置き換える**（バージョン更新・数値変更・非推奨化・手順改訂・訂正）場合 → 該当段落・箇条書きを**新内容で上書き**する。**古い記述を残したまま末尾に追記しない**
   - **補完・別観点**（旧情報と矛盾せず併存できる）場合のみ → 既存セクションへ追記またはサブセクション追加
   - **完全に新規のトピック** → 適切な見出しレベルでセクションを追加

3. **参照セクションの更新**
   - **必ず**今回作成した **全文ノート（Articles）** へのリンクを追加する（出典の履歴は `## 参照` に残す）
   - 既存の参照セクションがあればそこに追加。なければ作成

4. **フロントマターの更新**
   - `updated` フィールドを処理日（JST）に更新（なければ追加）

**更新時の注意事項**:

- **開いたときに最新が読めること**: 同じ事柄について新旧が並ぶ状態を避ける（例: Opus 4.7 のベンチマークの横に 4.8 の数値を追記するだけ、は不可 → 4.8 で**差し替え**）
- **既存の文章構造・スタイルを維持**: 見出し階層は壊さず、差し替え・追記は既存の文体に合わせる
- **重複を残さない**: 上書き後に意味が重なる旧文は削除する
- **矛盾でどちらが正か判断できない場合**: 自動統合せず、ユーザーにどちらを採用するか問いかける（両方の内容を提示し、判断後に一方へ集約）
- **歴史的経緯が参照価値ある場合**: 本文は最新に揃え、必要なら「（旧: …）」を1行に留めるか、**`## 参照` の Articles リンク**で出典を残す（本文に処理履歴ログを増やさない）
- **既存のタグ・Wikiリンクは維持**し、必要に応じて最小限追加

**禁止**:

- 古い情報を残したまま、同トピックの新情報だけを末尾に足す**積み上げ追記**
- Knowledge 本文を「いつどの InBox から来たか」の処理ログ化（出典は `## 参照` と Articles に任せる）

#### 既存ノートが見つからなかった場合（新規作成）

**ファイル名**:

- **内容分析で決定したジャンル名をファイル名にする**（例: `AI開発.md`、`Python.md`、`AWS.md`）
- タイトル語句ではなく、抽出Knowledgeの主題・適用範囲から名前を決定
- ジャンルが特定できない場合は、主要キーワードではなく「最も再利用性が高い上位概念」を優先して命名
- 既存ファイルと重複しないようにする（重複する場合は、ジャンル名に番号や日付を追加しない。既存ノートに追記する）

**ノート構造**:

```markdown
---
created: YYYY-MM-DD
source: InBox/YYYY-MM-DD.md
---

# [ノートタイトル]

## Knowledge
[記事から得られる知識・知見・実用的な情報]
- 具体的な手順、ベストプラクティス、注意点、使用例、テンプレート、設定方法など
- 単なる記事の要約ではなく、実際に活用できる知識として整理

## 詳細
[必要に応じて詳細情報]

## 参照
- **全文**: [[Articles/YYYY-MM-DD_slug]]（InBox 処理で作成した原文 Markdown）
- [元のURLなど。PDFの場合は `[[attachments/ファイル名.pdf]]` も併記]

## 関連リンク
[関連するノートへのWikiリンク]
```

### 5. タグとリンクの付与

`obsidian-update-rules` のルールに従って：

- 重要語（固有名詞、システム名、機器名、手順名、プロジェクト名）が出たら、可能なら `[[既存ノート名]]` へのWikiリンクを優先
- 該当ノートが存在しない場合は、タグ `#keyword` を付与（英小文字・ハイフン推奨）
- 既存タグ体系がある場合はそれに合わせる（例: `#infra/raspi` のような階層タグ）
- 1ノート内のタグは過剰にならない範囲で付与（目安: 3〜8個）

### 6. 元のノートの処理

- **InBoxディレクトリ内のファイルの場合**:
  - **全文ノート（Articles）の作成**と **Knowledge ノートの作成・更新**が完了したら、処理した項目をInBoxノートから削除
  - **重要**: 1つのノートに複数の項目がある場合、処理した項目だけを削除し、残りの項目はノートに残す
  - ノート内のすべての項目を処理した場合のみ、ノートファイル全体を削除する
  - 削除前に、**全文ノート**および **Knowledge ノート** への保存を確認
- **直接指定されたファイルの場合**:
  - ファイルは削除しない（ユーザーが明示的に指定したファイルのため）
- **重要**: 1件処理したら作業を中断する（次のノートまたは次の項目は別の実行で処理）

## 実行手順

1. **入力ソースの確認**
   - **ユーザーが直接ファイルを指定した場合**: そのファイルを処理対象とする（InBoxディレクトリの確認は不要）
   - **ファイルが指定されていない場合**:
     - InBox の **Markdown / PDF / 音声** を **シェルで列挙**（**「InBox の棚卸し」** 節。Glob だけは不可）
     - 処理対象のノート数を確認（種別ごとの件数を報告に含めてよい）

2. **1件だけ処理する**（この実行では1件のみ）

   処理対象のノートを1つ選び（直接指定された場合はそのファイル、指定されていない場合はInBoxから未処理のノートを1つ選択）、以下を実行：

   a. **ノートの読み込み**
      - 1件のノートファイル（Markdown、PDF、**または音声**）を読み込む
      - 直接指定された場合はそのファイル、指定されていない場合は先頭のノート、または日付が古い順など、1件に限定
      - **Markdownファイルの場合**: ファイルの内容を直接読み込む
        - **`voice_` 始まり `.md`**: 本文から文字起こしテキストを抽出（**形式 6**）。**whisper は実行しない**
      - **PDFファイルの場合**: `python dev-workspace/scripts/extract_pdf_text.py <PDFパス>` を実行してテキストを抽出
        （pypdf 失敗時は おたよりナビ OCR API（localhost:5003 固定）→ Azure Document Intelligence でフォールバック。
        otayori-navi 稼働時は API を利用可）。
        または Pythonの`pypdf`または`pdfplumber`ライブラリを直接使用する。
      - **音声ファイル（`.m4a` 等）の場合**: **1.4** に従い `personal-tools` で `python -m src.whisper_transcribe` を実行して文字起こし。失敗時はここで中断
      - **ボイスメモ振り分け**（**形式 6** または **1.4 完了後**）: **1.4.1** を適用（**この時点まで `釣行メモ.md` は Read しない**）
        - **領域が一意に決まらないボイスメモ** → ユーザー確認を報告し、**以降のステップ b.〜g. は実行せず** h.（報告）・j.（CursorLog）までで中断
        - **釣り関連ボイスメモ**（**確定後**）→ **`釣行メモ.md` を Read**（先頭「聞き取り補正」と専門用語。末尾だけ読まない）のうえ追記（1.4.1）のあと、b. で Articles を作成。d.〜f. の Knowledge はスキップ。**e2.** で他領域の有無を再確認
        - **本職・副業開発・汎用知識のボイスメモ** → 1.4.1 の表に従い正本へ反映（Work / DevProject / Articles+Knowledge 等）
      - ノート内に複数の項目があるか確認（Markdownファイルの場合）
      - 複数の項目がある場合、1つの項目だけを処理対象とする（先頭の項目、または最初に見つかった項目）

   b. **原文全文Markdown（Articles）の作成**
      - **セクション「1.5」**の手順に従い、`Notes/Knowledge/Articles/` に全文 `.md` を1件作成する（URL 取得失敗時は作成せず中断）
      - **URL形式**: まずページ本文を取得し、**取得に成功したテキスト**を **Markdown として整形したうえで** Articles に保存してから内容分析へ進む
      - **WEBクリップ形式**: クリップ本文をそのまま Articles に保存する（既が Markdown なら体裁確認のうえ、下記 lint）
      - **PDF形式**: ステップ a. で抽出済みのテキスト全文を **Markdown 化**（段落・見出し区切り等。プレーンテキスト一塊を避ける）し Articles の本文に書く（抽出失敗時は Articles は作らず中断）
      - **手入力**: メモ全文を Articles に保存する
      - **音声（釣り関連ボイスメモ・記事相当）**: 文字起こし全文を Articles に保存する
      - **完了前**: 当該 Articles に **markdownlint を実行**し、**0 件**（**`markdownlint-disable` 等の対象外化は行わない**）。修正は **1.5** の「本文の内容は変えないこと」に従う
      - 続けて、当該実行で触った **Knowledge ノート**と **CursorLog** も含め、同一ルールで lint を通す

   c. **内容分析**
      - 処理対象の項目の内容を分析し、ジャンル、Knowledge（知識）、キーワードを抽出
      - 入力形式を判定（URL形式、WEBクリップ形式、PDF形式、手入力メモ形式、**文字起こし済みボイスメモ（`voice_*.md`）**、**音声ファイル形式**）
      - **URL形式の場合**:
        - ステップ **b.** で取得済みの本文を分析に用いる（再取得は不要）
      - **PDF形式の場合**:
        - ステップ **a.** で抽出済みのテキストを分析に用いる（失敗時は **a.** で既に中断済み。`extract_pdf_text.py` の再実行は不要）
        - 抽出テキストから Knowledge を抽出する
        - **PDFバイナリの保存**: ステップ **e.** で Knowledge ノートを確定したら、同じディレクトリの `attachments/` に PDF をコピーし、Knowledge ノートの「参照」に `[[attachments/ファイル名.pdf]]` を追加する（セクション「1」「6」と同じ運用）

   d. **既存ノートの検索**
      - ジャンル名で既存ノートを検索する際も、タイトル一致だけで確定せず本文主題を照合する
      - 例: タイトルに `Cursor` が含まれていても、抽出KnowledgeがAI開発一般なら `AI開発` 系ノートを優先して検索する
      - Knowledge保存先ディレクトリ配下で既存の同ジャンルノートを検索

   e. **ノートの作成または更新**
      - **既存ノートが見つかった場合**（**§4「集約・更新」**に従う）:
        1. 既存ノートの内容を完全に読み込む
        2. 今回の Knowledge と**トピック単位で突合**する
        3. **置き換え対象**（バージョン・数値・手順・廃止など）→ 該当箇所を**新情報で上書き**（古い記述を残したまま末尾追記しない）
        4. **補完・新規トピック**のみ既存セクションへ追記、または新セクション追加
        5. **矛盾で正否が判断できない場合** → ユーザーに確認（判断後に一方へ集約）
        6. `## 参照` に今回の Articles リンクを追加
        7. フロントマターの `updated` を処理日に更新
      - **既存ノートが見つからなかった場合**: ジャンル名をファイル名として新規ノートを作成（Knowledge保存先ディレクトリ内に作成）

   e2. **ドメイン別正本への反映**（**`obsidian-second-brain` SKILL**・必須検討）
      - Knowledge 更新後、内容が **Work / Fishing / DevProject** のいずれか（複数可）に該当するか判定
      - 該当時は各 SKILL（`work-folder-update`・`specification-update` 等）を Read して**正本を同一セッション内で更新**
      - 反映したファイルパスを後続の報告・CursorLog に記載

   f. **タグとリンクの付与**
      - タグとリンクを付与（既存ノートの場合は既存タグを維持）

   g. **元のノートの処理**
      - **InBoxディレクトリ内のファイルの場合**:
        - **処理が完了したら、処理した項目をInBoxノートから削除**
        - **Markdownファイルの場合**:
          - **1つのノートに複数の項目がある場合**: 処理した項目だけを削除し、残りの項目はノートに残す
          - **ノート内のすべての項目を処理した場合**: ノートファイル全体を削除する
        - **PDFファイルの場合**:
          - テキスト抽出とKnowledge抽出が完了し、PDFファイルを参考資料として`attachments`ディレクトリに保存したら、InBoxディレクトリ内のPDFファイルを削除する
          - 削除前に、**全文ノート（Articles）** および Knowledge ノートへの保存を確認
        - **音声ファイルの場合**:
          - **釣り関連ボイスメモ**: `釣行メモ.md` 追記と Articles 保存、音声を `Fishing/attachments/` にコピーしたら、InBox 内の音声を削除
          - **領域が一意に決まらないボイスメモ**: ユーザー指示前は**削除しない**
        - **Markdown の場合**も、削除前に同様に保存を確認
      - **直接指定されたファイルの場合**:
        - ファイルは削除しない（ユーザーが明示的に指定したファイルのため）
        - 処理完了後、ファイルの場所を報告する

   h. **処理結果の報告**
      - 処理したノートのファイル名（Markdownファイル、PDFファイル、**音声ファイル**）
      - 入力ソース（InBoxディレクトリ内のファイル、または直接指定されたファイル）
      - 処理した項目の内容（URL、メモの内容、PDFの内容など）
      - 抽出したKnowledge（知識）の概要
      - **作成した全文ノート（Articles）のパス**
      - 新規作成したKnowledgeノートの場所、または更新した既存ノートの場所
      - 付与したタグやリンク
      - ジャンル名
      - ノートに残りの項目がある場合は、その旨を報告（Markdownファイルの場合）
      - 直接指定されたファイルの場合は、ファイルが削除されていないことを報告
      - **適用可能性の検討と正本への反映**: **釣り関連ボイスメモ（`釣行メモ.md` 追記経路）のときは省略**。それ以外は下記 i. を実行し、報告の最後に **`## 適用可能性`**（2 サブセクション）を含める。**反映した正本パス**も記載
      - **釣行メモへ追記したとき**: 報告の **`## 次のアクション`** は **`/trip-memo-import`**（追記ルール 11）。import 自体はこのターンで実行しない

   i. **適用可能性の検討と正本への反映（省略禁止 — 釣行メモ経路を除く）**

      **発火**: URL / WEBクリップ / PDF / 手入力 / 記事相当の長尺音声 / 領域判定済みボイスメモの処理完了時。**釣り関連ボイスメモで `釣行メモ.md` へ追記して完了した実行では本節はスキップ**（報告・CursorLog とも `## 適用可能性` を書かない）。

      **報告だけで終わらない。** ステップ **e2.** で正本へ反映していない内容で、開発・仕事に使える知見がある場合は**同一セッション内で Obsidian を更新**してから報告する。

      **忘れやすいので、対象経路では必ず実行する。** 報告は **開発** と **仕事（本職）** を**分けて**検討し、**両方**を書く（片方だけで完了禁止）。**反映した正本のパス**があれば各サブセクションに明記する。

      **報告フォーマット（固定）**:

      ```markdown
      ## 適用可能性

      ### 開発プロジェクト
      （FishTrack / MyPokedex / otayori-navi / personal-tools / dev-workspace。該当なしなら「該当なし」。反映した場合は `DevProject/...` 等のパスを記載）

      ### 仕事（本職）
      （Obsidian `Work/` 等。該当なしなら「該当なし」。反映した場合は更新した Work ノートのパスを記載）
      ```

      **開発プロジェクト**（報告見出し `### 開発プロジェクト`）:

      - **対象**: FishTrack、MyPokedex、otayori-navi、personal-tools、dev-workspace
      - **正本への反映**: 仕様・設計判断は **`specification-update` SKILL** で `DevProject/specifications/` へ。計画変更は **`integrated-schedule-update`**。SKILL・実装方針は dev-workspace `.agents/skills/` 等
      - **検討観点**（該当するものだけ簡潔に。該当時は**反映まで**）:
        1. **技術スタックの一致**（Docker、AWS、Python、PostgreSQL 等）
        2. **アーキテクチャの改善**（構成・デプロイ・マイグレーション実行方法等）
        3. **ベストプラクティスの適用**（記事の手法が現行実装に載せられるか）
        4. **開発環境の改善**（ローカル Docker、SKILL、pre-commit 等）
        5. **本番環境の最適化**（EC2/RDS、コスト、運用）

      **仕事（本職）**（報告見出し `### 仕事（本職）`）:

      - **対象**: 本職（株式会社DTS）の業務。**Obsidian `Work/`** を中心に、定例・人事考課・課題管理・クライアント/プロジェクト運用等
      - **正本への反映**: **`work-folder-update` SKILL を Read** し、該当ノートへ記録（課題は **`work-kadai-update`** 等の専用 SKILL と併用）
      - **参照の起点**:
        - `Work/課題.md` — 継続課題の正本（`work-kadai-update`）
        - `Work/定例・報告/` — 1on1、振り返り等
        - `Work/社内業務/人事考課/` — 目標・評価（`mokuhyo-*`）
        - `work-folder-update` / `work-knowledge-deepen` — Work ノート更新・暗黙知の明文化
      - **検討観点**（該当するものだけ簡潔に。該当時は**反映まで**）:
        1. **PL/PM 運用**: 1on1、振り返り、目標設定、メンバー育成、定例の効率化
        2. **業務プロセス・判断基準**: 禁止事項、承認フロー、エスカレーション、ナレッジ蓄積（記事が非コーディングハーネス・MCP 業務エージェントの場合は特に）
        3. **社内ツール連携**: Slack、Confluence、Google Calendar、Jira、Excel/社内システム等
        4. **`Work/課題.md` との接続**: 記事の知見が継続課題の打ち手・体制改善に効くか
        5. **Work ナレッジへの転用**: 手順・暗黙知を `Work/` 配下のどのノートに残すと再利用しやすいか
      - **注意**: DevProject（FishTrack 等の副業プロダクト）と混同しない。**仕事向けの反映先は `Work/`**

      **共通ルール**:

      - 提案は**簡潔・実用的**（長文分析は避ける）。現在の運用との**比較**と**注意点**を1〜3点に絞る
      - **旧見出し `## プロジェクトへの適用可能性` のみ**で報告を終えない（本 SKILL 更新後は **`## 適用可能性` + 2 サブセクション**が正）

   j. **Cursorログの更新（必須）**
      - **処理完了後、必ずCursorログを更新する**
      - `obsidian-cursor-log` SKILLを使用して、当日のCursorLogに作業内容を記録する
      - 記録内容は処理結果の報告を基に記録（**釣行メモ経路以外**は **適用可能性** を含む）

3. **Cursorログの更新（必須）**
   - **処理完了後、必ずCursorログを更新する**
   - `obsidian-cursor-log` SKILLを使用して、当日のCursorLog（`D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/YYYY-MM-DD.md`）に作業内容を記録する
   - **記録内容**:
     - 作業名: InBoxノート処理（処理したノートのファイル名、ジャンル名を含める）
     - プロジェクト名: dev-workspace、Obsidian
     - 変更ファイル: 処理したファイル数と主要なファイル名（InBoxノート、Knowledgeノート、SKILLファイルなど）
     - 実施内容: 処理したノートの内容、抽出したKnowledgeの概要（**釣行メモ経路以外**は **適用可能性** も記載）
     - 結果: 新規作成または更新したノートの場所、付与したタグやリンク、InBoxノートの残り項目数など
   - **タグ**: 作業内容に応じて適宜追加（例: `#obsidian`、`#inbox-summarize`、処理したジャンルのタグなど）
   - **重要**: Cursorログの更新を忘れないこと。これは必須の作業である。

4. **作業の中断**
   - **1件処理したら、ここで作業を中断する**
   - InBoxに未処理のノートが残っていても、続けて処理しない
   - 次のノートは、本 SKILL を**再度依頼**して処理する
   - **釣行メモへ追記して終えたとき**は、次の InBox より先に **`## 次のアクション`** で **`/trip-memo-import`** を促す（追記ルール 11。このターンでは import しない）

## 注意事項

- **Cursorログの更新（必須）**: 処理完了後、`obsidian-cursor-log` で必ず記録する（上記「Cursor ログ更新（必須・要約）」）
- Markdown・Knowledge 更新の注意、URL・PDF の取得失敗時の中断、PDF の保存・削除、音声の文字起こし失敗時、適用可能性の報告形式は [references/notes.md](references/notes.md) を読んで従う
