# Cursorコスト監視

## 目的

現在の利用パターンを基準に、Cursorの月額総額を最小化できる契約プランを
比較・提案する。Usage画面とCSVの実測値、実際のon-demand spend、
プラン料金・Included枠を分離して扱い、推奨根拠を明示する。

このSKILLは、ユーザーが明示的に呼び出したときだけ実行する。
GitHub ActionsはSKILL呼び出しのリマインダーだけを担当し、ブラウザ操作や
Cursor LLMによるUsage取得は行わない。

## 必須手順

### 1. ブラウザの準備

1. `browser_tabs`で既存タブを確認する。
2. `https://cursor.com/dashboard/usage`が開いていれば、そのタブを使う。
3. 開いていなければ、Cursor内ブラウザで同URLを開く。
4. 既存タブを操作するときは、操作前に`browser_lock`でロックする。
5. `browser_snapshot`で画面の見出し・Usage値・請求サイクルを取得する。
   必要な場合だけ`browser_cdp`のDOM確認を使う。
6. Usageの内訳が必要な場合は、`Export CSV`をクリックして生成された
   readonly URLを取得し、同じ認証済みページの`browser_cdp`から
   `fetch(url, {credentials: "include"})`を実行してCSV本文を自動取得する。
   ダウンロード先やCookieを取得・保存せず、本文は集計に必要な範囲だけ扱う。
7. CSV取得後はHTTPステータス、`text/csv`、ヘッダー、行数を検証し、
   取得失敗時はCSVなしとして扱わず、理由を報告する。

### 2. 認証境界

次の場合は自動操作を止め、ユーザーにブラウザでの対応を依頼する。

- ログイン画面
- 2FA、CAPTCHA、本人確認
- 権限エラー
- Usage画面が表示されない状態

パスワード、Cookie、セッション情報、認証トークンを取得・保存・Slackへ送信しない。
ブラウザ操作が終わったら`browser_lock`を解除する。

### 3. 取得する値

画面に表示されている場合だけ、次の項目を記録する。

- プラン名
- 請求サイクルの開始日・リセット日
- モデルごとの使用量、種別（Included／on-demand等）、Cost表示
- Cursor Models／Other Modelsの分類と合計
- on-demand spendとlimit
- 現行プランと比較候補プランの月額、Included枠、適用条件
- 画面上の警告、超過、支払いに関する表示

画面に表示されない請求額、税額、為替額、残り使用量から推測した金額は記載しない。
取得できない値は「画面表示なし」とする。

### 4-1. 請求サイクルの使用量見積もり

請求サイクルの傾向を把握するため、表示されたトークン使用量に限って
サイクル終了時の見込みを算出する。請求額やon-demand費用は推定しない。

1. `Billing & Invoices`で請求サイクルの開始日・終了日・リセット日を確認する。
2. `Usage`の期間を請求サイクル開始日から確認日までに合わせ、サイクル累計の
   `Total tokens`と`Included`を取得する。7日間などの短い期間しか取得できない
   場合は、サイクル累計ではなく参考値として扱う。
3. 日付ベースの経過日数は「確認日 − リセット日」とし、リセット日を0日目とする。
   Usageの累計に含まれる暦日数は、開始日・確認日を含めて別に記録する。
4. 次の式で見積もる。日数は画面の日付を基準にし、値は表示精度に合わせて
   概算とする。確認日当日は途中までの値である可能性があるため、経過日数と
   観測暦日数の両方で計算し、単一値ではなくレンジで示す。

   - 経過日数ベースの1日平均 = サイクル累計使用量 ÷ 経過日数
   - 暦日数ベースの1日平均 = サイクル累計使用量 ÷ 観測暦日数
   - サイクル終了時見込み = それぞれの1日平均 × サイクル全体の暦日数
   - 残り期間の見込み = サイクル終了時見込み − 現在までの使用量

経過日数、観測暦日数、現在までの使用量、1日平均のレンジ、
サイクル終了時見込みのレンジを通知と履歴へ記載する。確認日がリセット日当日で
割り算できない場合や、累計値を取得できない場合は「見積もり不可」とする。
見積もりは傾向把握に使い、プラン変更や請求額の確定根拠にはしない。

#### Included枠の請求サイクル終了時見通しと切替シナリオ

`Spending`画面の`Cursor Models`と`Other Models`の使用率をそれぞれ取得し、
4-1と同じ経過日数ベース・観測暦日数ベースで請求サイクル終了時の使用率を予測する。
各プールについて、使用率・サイクル終了時見込み・残り枠・100%到達見込みを記録する。

ユーザーの標準運用は、2026-08-24以降次のとおりとする。

- 標準モデルは`cursor-grok-4.6-high`（Cursor Models）
- Cursor Models枠を使い切った後に、Other Models（GPT-5.6 Luna／Terra等）へ切り替える
- Fastは速度が必要な場合だけ使う

評価時は次の2パターンを記録するが、推奨・見通しの主シナリオは1とする。

1. `Cursor Models`を先に使い、枠を使い切った後に`Other Models`へ切り替える（標準）
2. `Other Models`を先に使い、枠を使い切った後に`Cursor Models`へ切り替える（参考）

サイクル終了時見込みが100%未満のプールは切替発生なしとし、もう一方のプールへ
超過分を加算しない。100%を超える場合も、異なるプールの使用率を単純加算
してはいけない。切替後のモデル・トークン内訳・プール換算値が取得できる場合
だけ二次プールの消化見込みを算出し、換算できない場合は「切替後のIncluded
消化率は算出不可」と明記する。

この見通しは、現行プランのIncluded枠を使い切る時期と、候補プランで
on-demandが発生する可能性を判断するために使う。ユーザーが明示した
「枠を使い切ったら別プールへ切替」の運用を無視して、Other Modelsの
超過見込みだけでプランを比較してはいけない。

### 4-2. モデルごとの使用量・費用

モデルごとの価格差を考慮するため、`Usage`の`Group By: Model`表示と明細の
`Model`・`Tokens`・`Cost`列を確認する。可能な場合はUsage画面のCSV Exportを
請求サイクル開始日から確認日までの期間で取得し、CSVを優先してモデル単位で
次を集計する。

- モデル名
- Total tokens
- Included tokens
- on-demand tokens
- 画面に表示されたCost
- `Input (w/ Cache Write)`
- `Input (w/o Cache Write)`
- `Cache Read`
- `Output Tokens`
- サイクル終了時のモデル別使用量見込み

CSVの列はヘッダー名で特定し、`Total Tokens`が
`Input (w/ Cache Write) + Input (w/o Cache Write) + Cache Read + Output Tokens`
と一致することを検証する。前者はCache Write、後者は通常のInputとして扱う。
CSVが取得できない場合は、画面の全ページまたはExport CSV以外の表示値を使い、
取得できない内訳は「画面表示なし」とする。

モデル別の見込みは、各モデルのサイクル累計を4-1と同じ日数計算で外挿する。
モデル別にCostの金額が表示される場合は、表示値をモデルごとに合計して記録する。
Cost欄が`Included`など金額以外の表示の場合、月額プラン料金をモデルへ按分せず、
「モデル別の実額表示なし」とする。Included使用量に対してモデルの公開API単価を
掛けた値は実際の請求額ではないため、入力・出力・キャッシュ等の内訳と適用単価が
表示されない限り、実額の代替として通知しない。ただし、CSVで内訳と公式単価が
確認できる場合は、次のオンデマンド相当額を参考値として算出する。

モデル別のCostが取得できない場合でも、モデル別トークン使用量の集計と見込みは
行う。モデル別の明細自体が取得できない場合は「モデル別使用量: 画面表示なし」
とし、全体値だけでプラン変更を判断しない。

### 4-3. オンデマンド相当額の参考試算

「現在の使用量をすべてオンデマンドで賄った場合」の比較用参考値を、モデル別の
CSV内訳または表示トークン数と判断時点の公式単価から算出する。これは実際の請求額ではなく、
プラン比較の補助情報として扱う。

1. 公式料金表から、対象モデルの入力単価・出力単価・キャッシュ単価と適用条件を
   再確認する。
2. CSVに入力・出力・キャッシュの内訳がある場合、モデル別に次で算出する。

   - 相当額 = （通常Input × 入力単価 ＋ Cache Write × Cache Write単価
     ＋ Cache Read × Cache Read単価 ＋ Output × 出力単価）÷ 1,000,000
   - CSVの`Cost`が`Included`の場合も、相当額は実際の請求額と混同しない
   - 単価が`-`で、該当トークン数が0の場合はその項目を計算から除外する

3. CSVが取得できず内訳がない場合だけ、入力・出力を50:50と仮定した中点を
   参考試算として算出する。50:50は実測値ではなく、入力・出力の実際の平均を
   表すものではないことを明記する。
4. 公式単価が確認できないモデルは、トークン数と内訳を記録したうえで相当額を
   「試算不可」とする。合計額にも含めず、除外モデルと除外トークン数を明記する。

5. 表示Costがあるon-demand実額は相当額試算と分けて記録する。Included分に相当額を
   適用した値を実際の請求額として扱わず、税額・為替・プラン月額の按分も行わない。
6. 4-1の現在までの相当額を、経過日数ベースと観測暦日数ベースで月額換算する。
   月額換算は「利用ペースが続いた場合」の参考値であり、実請求額ではない。
料金表の単価・モデル名・適用条件は毎回確認し、試算の基準URLを記録する。

### 4. 判定

表示値に基づき、次の基準で判定する。

- `要確認`: on-demand spendが0より大きい、超過表示がある、または画面取得に失敗した
- `要注意`: limitが表示され、on-demand spendがlimitの80%以上
- `正常`: 上記に該当せず、表示された使用量が含まれる範囲内
- on-demand spendまたはlimitが画面にない場合は、金額判定を行わず「表示値確認」とする

判定根拠が複数ある場合は、画面に表示された内容を優先して併記する。
不明な値を正常扱いにしてはいけない。

### 5. 契約プランの推奨

目的は、同じ利用量・同じ作業品質を維持した場合の月額総額が最小になる
プランを見つけることである。単月の急増だけで断定せず、直近2〜3請求サイクルの
履歴があれば確度を上げる。ただし、現在のCSVから明らかな差額がある場合は、
暫定推奨と確度を示して提案する。

2026-08-24適用のCursor公式告知では、Autoの料金が固定単価から
リクエストごとのルーティング先モデル基準へ変更される。多くのリクエストでは
現行の固定単価より高くなる可能性がある一方、Cursor Models（Autoを含む）の
含まれる利用上限は増加し、Autoのルーティング動作と対象モデルは変更されない。
告知には具体的な単価・上限値がないため、旧来のAuto単価だけで判断せず、
判断時点の料金表とUsage画面を正とする。

現時点の利用前提は、ユーザー申告のUltra契約中で、標準モデルは
`cursor-grok-4.6-high`とする。Cursor Models枠の枯渇後のみ Other Models
（GPT-5.6 Luna／Terra等）へ切り替える。Usage画面またはユーザーから
最新情報が示された場合は、そちらを優先する。
CSVの過去実績がLuna中心でも、見通しと節約案は標準運用（Grok先行）を
主シナリオとし、過去実績だけの外挿を標準運用として扱わない。

必ず、現行プランだけでなく次の候補を比較する。

1. 現行プランを維持する場合の月額
2. Pro+へ変更し、必要な分だけAPI単価のon-demandで追加する場合
3. Proへ変更し、必要な分だけAPI単価のon-demandで追加する場合

候補プランごとに、次の値を分けて記録する。

- プラン月額
- Other ModelsのIncluded枠
- CSVから外挿したOther Modelsの月間相当額
- 切替なしの場合の`max（Other Models月間相当額 − Included枠, 0）`による超過見込み
- Cursor ModelsのIncluded利用量と制限表示
- `Other Models → Cursor Models`と`Cursor Models → Other Models`の各切替シナリオ
- 切替後の二次プール消化見込み、または換算不可の理由
- プラン月額＋超過見込みの月額総額

**下位プラン見積もりの式（報告で必ず分解する）**:
月額総額 = プラン月額 + max(Other Modelsの月間ドル消化 − そのプランのOther Included, 0)。
Other Includedはプラン月額に含まれるため、Included額を月額へ別途加算しない。
超過はトークン件数ではなく、Otherプールのドル消化（API単価ベース）である。
Cursor Models分は公式ドル枠がない限り候補請求に加算しない。
報告例: `Pro+ = $60 + max($366 − $70, 0) = $356`。

Cursor ModelsはOther Modelsと別プールであり、公式に金額換算できるIncluded枠が
ない場合がある。その場合、Cursor ModelsへAPI単価を適用して候補プランの請求額を
水増しせず、「利用枠の比較不可」または画面上の制限値確認として記録する。
全モデルをオンデマンドで計算した額は利用量の大きさを示す基準値であり、
候補プランの請求額にはそのまま加算しない。ユーザーが別プールへ切り替える
運用をしている場合は、切替なし・Other先行・Cursor先行を分けて比較する。

現在のプランの実際のon-demand spendが取得できる場合は、それを実績として優先し、
CSV相当額を実請求額の代わりに使わない。候補プランの超過見込みだけが参考試算で
あることを明記する。料金またはIncluded枠が確認できない候補は「比較不可」とする。

ユーザーがプール切替を行っている場合、切替なしの超過見込みだけで候補プランを
不利に評価してはいけない。切替先で代替可能なモデル・品質・残り枠を確認し、
切替後もIncluded内に収まる場合はon-demandを加算しない。切替先の消化率を
換算できない場合は、切替なしの値を上限参考値として示し、候補の優劣は
「比較不可」または「追加確認」とする。

候補の月額総額が最小で、利用枠・機能・モデル対応に問題がなければ節約案として
提示する。差額が小さい、未知のIncluded枠がある、または履歴が1サイクル未満の場合は
「暫定推奨」または「次回も観測」とし、変更を断定しない。

プラン変更だけでなく、現在のCSV実測値を使って利用方法の節約案も比較する。
候補は次の順で、月額削減見込み・品質や速度への影響・実施条件を記録する。

- 標準はGrok 4.6（Cursor Models）。品質が不足する作業だけOther Modelsへ戻す案
- 高単価モデルやFast利用を、品質要件を満たす安価なモデルへ置き換える案
- Cursor ModelsのIncluded枠を優先し、Other Modelsの利用を必要な作業へ限定する案
- Cache Readが大半の場合は、削減による効果だけでなく通常Inputの増加も確認する案
- 不要な長文コンテキストや反復処理を減らす案。ただし品質低下が見込まれる場合は
  節約案として断定しない

利用方法を変える案は、CSV内訳から対象モデル・単価・月額削減見込みを算出できる
場合だけ金額を示す。単価や品質条件が不明な場合は「金額比較不可」とし、
最安に見える案を自動推奨しない。

on-demandが無効な場合は自動で有効化せず、
「下位プラン＋API単価on-demand」を節約案として提示するだけに留める。
有効化する場合もdashboardのspend limitで月間上限を設定する。

現行の料金表に表示されるPro、Pro+、Ultraの月額と利用枠は、
判断時点で公式ドキュメントから再確認する。Autoのルーティング先モデル基準の
料金変更後は、固定月額だけでなく、同じ作業量に対する実際の使用額と
CSV内訳による候補プランの超過見込みを比較する。

- 料金表: <https://cursor.com/docs/models-and-pricing>
- Usage制限: <https://cursor.com/help/models-and-usage/usage-limits>

利用実績が不足しているときは「次回も観測」とし、プラン変更を断定しない。

要注意・要確認の場合は、通知と履歴の先頭側に独立した目立つ
「最優先・推奨アクション」ブロックを記載する。最優先の行動を1つに絞り、
必要な場合だけ「次点」と「保留」を続ける。各アクションには、実施条件・
品質への影響・判断確度を添える。
正常で対応不要の場合は、推奨アクションがあるように見せず、
「対応不要」「追加対応なし（現状維持）」と記載する。

Slack送信は既存の`dev-workspace/scripts/send_slack_notification.py`を使う。
Webhook URLを本文、ログ、コマンド引数の表示へ直接書かない。

#### Webhookの保管場所と用途分離

- ローカルの`/cursor-cost-monitoring`専用Webhookは、
  `dev-workspace/.env`の`CURSOR_COST_MONITORING_SLACK_WEBHOOK_URL`へ保存する。
- `SLACK_WEBHOOK_URL`は汎用キーのため、Cursor監視の保存先として新規利用しない。
- `COST_MONITORING_SLACK_WEBHOOK_URL`はGitHub Actions専用Secretであり、
  ローカルから値を取得・推測しない。
- ローカル送信時は、専用キーの値を表示しない子プロセスの環境変数へ一時的に渡し、
  `send_slack_notification.py`を実行する。専用キーがない場合は汎用キーへ
  フォールバックせず、送信を中止して設定不足として報告する。
- 専用WebhookはBot名義で`#コスト監視`へ投稿できるものを使用する。
  Slack APIのユーザー認証による送信や、別チャンネル固定のWebhookは使用しない。

通知に失敗した場合は成功扱いにせず、失敗理由をユーザーへ報告する。

### 7. 実行履歴の保存

Slack通知本文を作成した後、送信成否にかかわらず、同じ確認結果をObsidianの
`Notes/コスト監視履歴.md`へ1回分の記録として追記する。

記録項目は次のとおりとする。

- 確認日時（JST）
- プラン名と請求サイクル
- モデル別のTotal／Included／on-demand／Cost表示
- モデル別の入力・Cache Write・Cache Read・出力、オンデマンド相当額と合計
- Cursor Models、Other Modelsの分類と合計
- on-demand spendとlimit
- リセットからの経過日数、現在までの使用量、1日平均、サイクル終了時見込み、
  モデル別終了時見込み
- Cursor Models／Other Modelsの現在使用率、サイクル終了時Included使用見込み、残り枠、
  100%到達見込み、Other先行／Cursor先行の切替シナリオ
- 利用量ベース月額相当額、候補プラン別の月額総額見積もり、差額
- 判定と判定理由
- 契約プラン推奨、節約案、推奨根拠
- 見積もり注記
- 相当額注記と公式料金表のURL
- Usage画面のURL

画面に表示されない実請求額は「画面表示なし」と記載する。CSV内訳と公式単価から
算出した相当額は、実請求額と分離した参考見積もりとして記録する。トークン数・
使用率・過去の断片的な表示だけで実請求額を推測しない。認証情報、Cookie、
Webhook URLは履歴へ書き込まない。

履歴は次回のプラン比較に使う。直近2〜3請求サイクルがまだ蓄積されていない
場合は、プラン変更を断定せず「次回も観測」とする。

## 実行しないこと

- GitHub ActionsからCursorへログインすること
- Cookieや認証情報を使ったブラウザセッションの複製
- Usage画面のDOM構造だけを根拠に、表示されていない請求額を推測すること
- 固定月額や税額をUsage値として混同すること
- Loopを定期監視の正本にすること
- GHAのリマインダーを、Usage取得済みのレポートとして扱うこと
