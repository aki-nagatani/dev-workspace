# 次のアクション（next-action）

**旧 `.cursor/commands/next_action.md` は廃止**し、手順の正本を本 SKILL に置く。`name` は **`next-action`**（従来 **next_action** 相当）。

myrules を厳守して作業してください。

## 目的

リポジトリの状況・計画・ログと**本チャットの履歴**から **いま取るべき次の一手**を整理する。実装の着手順・依存関係・ブロッカーの有無を意識し、**迷いを減らす**ことを主目的とする（コード変更や実行はこのワークフローの必須ではない）。

**情報源は平等**: チャット履歴・CursorLog・統合作業スケジュール・（指定時）AGENTS／仕様を**同列の候補源**とする。チャットにあるから上げる／ログや計画にあるから下げる、といった**情報源による順位付けはしない**。

## 参照する情報（可能な範囲で）

根拠のない一般論だけの提案はしない。次を**同列**に読む（番号は読む順番の目安であり、優先度ではない）。新規チャットで履歴が空なら、他ソースのみでよい（欠落としない）。

1. **本チャットの履歴** — ユーザー発言、途中判断、未完了の合意、進行中の作業。ログや計画に未記載でも候補に含める。
2. **`D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/`** 当日または直近の **「残作業・課題」**・エントリ本文
3. **`D:/OneDrive/アプリ/remotely-save/Obsidian/DevProject/plans/統合作業スケジュール.md`**
   - 未完了タスク・週次・三本柱を読む。**今週まで（過去週を含む）の未完了タスクを優先**。
   - **次週以降**のタスクで**先行すべき**と判断したものがあれば、それを次の一手として提案してよい。**その場合は、着手内容より先に** 当該ファイル **の変更案**（週次・ガント・タスク一覧の整合など）を示す。
4. ユーザーが **対象プロジェクト** を指定していれば、その **`AGENTS.md`** と Obsidian 側 **仕様**（myrules「仕様書探索の既定パス」。フォルダ型は **`INDEX.md`** 起点）

**食い違い**: チャットとログ／計画が矛盾するときは、**チャット側を自動採用しない**。両方を候補にするか、依存・ブロッカー・今週タスクなど**情報源以外の基準**で選ぶ（件数上限内）。根拠が分かれる点は **推測** と明記する。

**本依頼文**: `/next-action` と同時に書かれた制約（対象プロジェクト指定など）は、履歴ではなく**今回の指示**として従う。

## 提案のルール

- **残作業・課題を最優先**: CursorLog の **「残作業・課題」**、計画書・対象プロジェクトの未完了・進行中、**本チャットで未解消の作業**がある場合は、**それを最優先**で次の一手にする（依存・ブロッカーを解除する順に並べる）。どの情報源の残作業かを理由に順位付けしない。新しい作業の提案を**先に**置かない。
- **件数**: **必ずしも 3 件に揃えない**。残作業が 1 件なら **1 件**でよい。比較・選択の価値があるときのみ複数提示し、**多くても 3 候補**までに絞る。
- **優先順位**: 依存関係（ブロック解除が先）、リスク・影響範囲、ユーザーが明示したゴールを踏まえて並べる。**情報源の別（チャット／ログ／計画）では並べない**。計画書では原則 **今週まで（過去週を含む）の未完了タスク**を優先し、**次週以降を先に進める**場合は **統合作業スケジュールの更新案を先**（上記 3. のとおり）。
- **各候補**に、該当する場合は **タスクID**、計画書の**タスク内容（概要）**、
  短く **何をするか**・**なぜ今か**・**前提・注意** を含める。
  CursorLog由来は作業名と内容（概要）を、チャット由来は発言の要点を明記する。不確実な点は **推測** と明記する。
- **除外（提案に含めない）**: **コミット・プッシュ・デプロイ・PR・マージ**（ユーザーがチャットで明示依頼した場合を除く）。myrules「残作業・次アクションの案内」に従う。
- **除外（Git 作業ツリー）**: **未コミット変更・差分の有無** を理由にした提案、**「未コミットが残っています」等の注意喚起・案内** は含めない。
- **禁止**: 根拠のないテンプレ提案、Git 運用の促し・「次は〜がよいです」系の補足、**件数合わせの水増し**、過度な列挙、**git 状態のリマインド**。チャット履歴だけを根拠にした一般論、履歴の無視。

## 出力形式

- 見出しは短く（例: `## 推奨` または候補ごとの `###`）。
- 箇条書きで簡潔。各候補は **タスクID／タスク内容（概要）／実施内容／優先理由／前提・注意**
  が分かるようにする。長文は避ける。

## 使用タイミング

- **next-action**（本 SKILL）、「次のアクション」「次に何をするか」、計画・残件の整理の依頼があったとき（**コミット系の暗黙依頼ではない**前提）
