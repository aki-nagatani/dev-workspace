# 次のアクション（next-action）

**旧 `.cursor/commands/next_action.md` は廃止**し、手順の正本を本 SKILL に置く。`name` は **`next-action`**（従来 **next_action** 相当）。

myrules を厳守して作業してください。

## 目的

リポジトリの状況・計画・ログと**本チャットの履歴**から **いま取るべき次の一手**を整理する。実装の着手順・依存関係・ブロッカーの有無を意識し、**迷いを減らす**ことを主目的とする（コード変更や実行はこのワークフローの必須ではない）。

**情報源は平等**: チャット履歴・CursorLog・Work（本職）・統合作業スケジュール・
（指定時）AGENTS／仕様を**同列の候補源**とする。チャットにあるから上げる／ログや計画にあるから下げる、
といった**情報源による順位付けはしない**。

ユーザーが `/next-action` または `/next-action-work` の実行時に解除を許可した場合は、
候補判定の前に、Workの単発・繰り返しTodoについて、着手可能日到来による
`🚫 着手不可` の解除だけを `work-folder-update`・`work-todo-update` に従って実施してよい。
単発タスクも解除対象に含める。着手可能日以外に前タスク・キック・
「面談実施後」などの条件がある場合は自動解除せず、条件を満たしているかユーザーへ確認する。
タスクの追加・完了・期限変更、前タスク完了やキック到来の記録は、別途ユーザーが明示した場合だけ行う。

## 参照する情報（可能な範囲で）

根拠のない一般論だけの提案はしない。次を**同列**に読む（番号は読む順番の目安であり、優先度ではない）。新規チャットで履歴が空なら、他ソースのみでよい（欠落としない）。

1. **本チャットの履歴** — ユーザー発言、途中判断、未完了の合意、進行中の作業。ログや計画に未記載でも候補に含める。
2. **`D:/OneDrive/アプリ/remotely-save/Obsidian/CursorLog/`** 当日または直近の **「残作業・課題」**・エントリ本文
3. **本職の `D:/OneDrive/アプリ/remotely-save/Obsidian/Work/`**
   - `Todo.md`（単発）と `Todo-定例作業.md`（繰り返し。週次・月次・3ヶ月次・年次等）の未完了を確認する。
     ユーザーが解除を許可している場合は、着手可能日が到来済みで他の着手不可条件がない行の
     `🚫 着手不可` を解除してから候補を判定する。単発・繰り返しを問わず、
     着手可能日以外の条件がある行は解除せず、条件を満たしているかユーザーへ確認する。
     繰り返しは対象月の `[ ]` 行の期限を見る。`🚫 着手不可` は候補にしない。
     着手可能日が未来の行も候補にしない。キック待ちは到来まで候補にしない。
     着手推奨日があり今日がそれより前なら優先度を落とす（除外しない）。
     期限超過（期限が今日より前）は、推奨日前でも最優先で候補化する。
     出すときは「期限超過」と明記する。
     `課題.md` の継続課題、案件・顧客対応・定例・育成の関連ノートも見る。
     本職の Asana は **`next-action-work` SKILL** の Asana 節に従う
     （自分の未完了は着手候補。配下の期限近傍・未完了はリマインド。GID は出さない）。
   - 本職タスクは副業・趣味のタスクと同列に候補化し、期限、依存関係、影響範囲、リスクで比較する。
     **JST 22:00〜9:00** は下記「夜間の本職」で本職を後ろに下げる。
4. **`D:/OneDrive/アプリ/remotely-save/Obsidian/DevProject/plans/スケジュール.md`**
   - 未完了タスク・週次・三本柱を読む。**今週まで（過去週を含む）の未完了タスクを優先**。
   - **次週以降**のタスクで**先行すべき**と判断したものがあれば、それを次の一手として提案してよい。**その場合は、着手内容より先に** 当該ファイル **の変更案**（週次・ガント・タスク一覧の整合など）を示す。
5. ユーザーが **対象プロジェクト** を指定していれば、その **`AGENTS.md`** と Obsidian 側 **仕様**（myrules「仕様書探索の既定パス」。フォルダ型は **`INDEX.md`** 起点）

**食い違い**: チャットとログ／計画が矛盾するときは、**チャット側を自動採用しない**。両方を候補にするか、依存・ブロッカー・今週タスクなど**情報源以外の基準**で選ぶ（件数上限内）。根拠が分かれる点は **推測** と明記する。

**本依頼文**: `/next-action` と同時に書かれた制約（対象プロジェクト指定など）は、履歴ではなく**今回の指示**として従う。

## 提案のルール

- **期限超過を最優先**: 期限超過（期限 < JST の今日）で実行可能な未完了タスクは、
  情報源や着手状態にかかわらず、期限超過でない残作業・着手中・新規候補より先に提案する。
  着手可能日が今日以前で、`🚫 着手不可`・キック待ちに該当しないものに限る。
- **残作業を新規より先（期限超過を除く）**: CursorLog の **「残作業・課題」**、Work の未完了、計画の進行中、
  チャットで未完了の合意があるときは、**まだ着手していないタスクより先**にそれを提案する。
  どの情報源の残作業かを理由に順位付けしない。新しい作業の提案を**先に**置かない。
- **着手中を終えてから新規**: すでに着手しているタスクが未完了なら、その完了、または止めているブロッカーの解除を次の一手にする。別の新規タスクを先に提案しない。着手不可・判断待ちで進めない残作業だけが残るときは、その旨を前提に書き、進められる残作業を先にする。
- **解消済みは再提案しない**: 提案前に、後のログ・正本・現状で残っているか確認する。後続で「なし」になったもの、一覧から消えたもの、対処済みの生成物は候補にしない。
- **件数**: **`/next-action` など本 SKILL の明示呼び出しだけ**、比較の価値があるとき複数を出し、**多くても 3 件**。1 件なら 1 件。3 件に揃えない。
  **明示呼び出し以外の応答末尾は 1 件**（いま着手すべき残作業か、そのブロッカー解除）。候補を並べて 3 件にしない。
- **優先順位**: 依存関係（ブロック解除が先）、リスク・影響範囲、ユーザーが明示したゴールを踏まえて並べる。**情報源の別（チャット／ログ／計画）では並べない**。計画書では原則 **今週まで（過去週を含む）の未完了タスク**を優先し、**次週以降を先に進める**場合は **統合作業スケジュールの更新案を先**（上記 3. のとおり）。
  **期限超過（期限 < JST の今日）の実行可能な未完了タスクを最優先**とする。
  ここでいう実行可能とは、着手可能日が今日以前で、`🚫 着手不可`・キック待ちに該当しないことをいう。
  期限超過タスクは、当日締切・今週・未来期限のタスクより先に並べ、着手推奨日前でも優先度を下げない。
  期限超過が複数ある場合は、超過日数、依存関係、影響範囲、リスクで比較する。
  Work の **着手推奨日前**（期限超過でない）は他の残作業より後にする。除外はしない。
  **JST 22:00〜9:00** は、その比較のあとで本職を本職以外より後ろにする。期限超過の本職も同じく後ろにする（下記「夜間の本職」）。
- **各候補**に、該当する場合は **タスクID**、計画書の**タスク内容（概要）**、
  短く **何をするか**・**なぜ今か**・**前提・注意** を含める。
  CursorLog由来は作業名と内容（概要）を、Work由来は `Todo.md` / `Todo-定例作業.md`・関連正本の期限や課題を、
  チャット由来は発言の要点を明記する。不確実な点は **推測** と明記する。
- **除外（提案に含めない）**: **コミット・プッシュ・デプロイ・PR・マージ**（ユーザーがチャットで明示依頼した場合を除く）。myrules「残作業・次アクションの案内」に従う。
- **除外（Git 作業ツリー）**: **未コミット変更・差分の有無** を理由にした提案、**「未コミットが残っています」等の注意喚起・案内** は含めない。
- **禁止**: 根拠のないテンプレ提案、Git 運用の促し・「次は〜がよいです」系の補足、**件数合わせの水増し**、過度な列挙、**git 状態のリマインド**。チャット履歴だけを根拠にした一般論、履歴の無視。

## 夜間の本職（JST 22:00〜9:00）

`/next-action` の **推奨の順位** だけに使う。`/next-action-work` は本職専用なので、この下げは適用しない。

- **時刻**: `user_info` の JST。無いときだけターミナルで JST を取る。
- **対象**: **22:00 以上、9:00 未満**。9:00 以降 22:00 未満は通常の比較。
- **本職**: `Work/` の Todo・課題・手続き、Asana の自分担当。
- **本職以外**: 統合作業スケジュール、FishTrack / MyPokedex / おたよりナビ / FaiNavi、CursorLog の製品残作業。
- **下げ方**: 本職は候補から外さない。期限超過かどうかにかかわらず、本職どうしを期限・依存で比べたあと、
  **本職以外を先、本職を後**にする。
- 推奨に出した本職には **「夜間は優先度を下げた」** と書く。期限超過の本職にも付ける。
- `🚫 着手不可`、未来の着手可能日、キック待ちは、時間帯に関係なく候補にしない。
- 配下への **リマインド** 節は順位の対象外。該当があれば節は出す。

## 出力形式

- 見出しは短く（例: `## 推奨` または候補ごとの `###`）。
- 箇条書きで簡潔。各候補は **タスクID／タスク内容（概要）／実施内容／優先理由／前提・注意**
  が分かるようにする。長文は避ける。

## 使用タイミング

- **ユーザーが明示したときだけ**（`/next-action`、「次のアクション」「次に何をするか」、計画・残件の整理）。このとき上記の情報源を読む。
- **通常のユーザー向け応答では本 SKILL を Read しない。** 末尾の 1 件案内は myrules「残作業・次アクションの案内」だけで行う。

## 明示呼び出し以外

本 SKILL の手順・情報源の再読・最大 3 件の比較は、明示呼び出しのときだけ行う。通常応答から本 SKILL を開かない。
