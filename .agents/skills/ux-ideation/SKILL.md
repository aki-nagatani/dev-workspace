# プロダクト改善アイデア検討（UX を含む）

## 単一情報源と適用タイミング（エージェント向け）

**本 SKILL**（`dev-workspace/.agents/skills/ux-ideation/SKILL.md`）が **手順・ルールの唯一の正本**である。旧 `.cursor/commands/ux_ideation.md` は廃止。ユーザーは **`ux-ideation`**・`@ux_ideation` 等で参照する。

**手順・表の更新は本 SKILL のみ**（同内容の重複する別 SKILL は置かない）。

**次のいずれかに該当するとき、本 SKILL を Read してから実行する。**

- UX 改善・プロダクト改善・アイデア出し・体験向上など、**FishTrack／MyPokedex** が文脈に含まれる
- **`ux-ideation`（本 SKILL）**を明示したとき

- 品質・信頼性・運用に効く案を、**仕様に根づけた具体案**まで落とす必要があるとき

**スコープ**:

- **扱う**: 画面・導線・文言（UX）に加え、**信頼性・セキュリティ・可観測性・運用・パフォーマンス体感・オンボーディング**など、**ユーザー価値・事業価値に効く改善案**。具体案は **実装イメージが浮かぶ粒度**まで落とす。
- **本ワークフローの主眼から外す**: **テストカバレッジ数値の運用・閾値の議論そのもの**、**CI ゲートの変更方針**（品質に関するアイデアとして「E2E で守るクリティカルパス」等を挙げることは可。決定・実装は各リポジトリのテスト規律・別タスクに従う）。

## 目的（ビジネス寄りのゴール）

本ワークフローで扱うアイデアの**主目的**は次の連鎖を狙うことである。

1. **プロジェクトの価値向上**（ユーザーにとっての有用性・信頼・継続利用のしやすさなど）
2. それに伴う **アクセス数・会員数（利用者数）の向上**
3. さらに **利益の拡大**（収益モデルに照らし、売上・LTV・コスト構造などへの効き方を意識する）

体験・画面の快適さだけでなく、**信頼・安全・継続利用**にも効く案を含め、**上記ビジネス連鎖にどう効くか**を返信で意識して書く。数値目標の捏造はしない（**仮説・要確認**で足りない情報を明示する）。

**単一情報源の原則（重要）**:

- 後から **本ファイル（統合作業スケジュール）だけ**を開いた人が、**チャット履歴なしで**次をできるように書く。
  - **検討**: 何を判断すればよいか、論点・トレードオフ・関連タスクが分かる。
  - **実装（採用が決まったあと）**: 仕様・コードのどこを読み・どこを変える想定か、着手の手がかりが足りる（実装タスク ID の新設は別手順でもよいが、\
      **曖昧な一行**で終わらせない）。
- **一覧表（[[#タスク一覧]]）** は **`integrated-schedule-update` SKILL** のとおり **1行要約**に収める。\
    **本文の詳細は [[#タスク詳細]] 側**に集約する（一覧に続き行を増やさない）。

**タスクの性質（重要）**:

- **実装タスクにしない**。アイデアそのものを「やること」として一覧に載せない。
- **検討タスク**とする。表記のイメージ: **「プロダクト改善アイデア（〈具体案の短いラベル〉）採用要否の検討」**（従来の **UX** 中心の案もここに含める）。
- **タスク実行時のゴール**は、そのアイデアを **採用するかどうか判断・整理すること**。採用が決まった後の実装は、**別途**仕様・既存バックログに沿ってタスク化する（\
    本ワークフローで起票するタスクに実装工程を混ぜない）。
- **禁止**: 同一セッションで実装し終えた作業を、完了タスクとして後付け起票しない（`integrated-schedule-update`「未予定作業の完了」）。検討タスクの起票は**これから判断する**ためのもの。
- **採用要否の検討**タスクとして、計画書 **[[#タスク詳細]]** の **タスク一覧補足**に既にある **検討のみ** と明記された行と**同じスタンス**で書く。\

    **特定のタスク ID を本 SKILL に固定例として書かない**（完了・削除で参照が死ぬため）。計画書内の**現時点の**同種行があれば体裁の手本にし、無ければ下表と本節を正とする。\
    新規 ID の採番・**一覧・週次・ガントの三本柱**は **`integrated-schedule-update` SKILL**（\
    `dev-workspace/.agents/skills/integrated-schedule-update/SKILL.md`）に**編集前に Read して従う**。

**[[#タスク詳細]] への必須記載（同一作業で追記する）**:

該当プロジェクトの **`### 【詳細】〈製品名〉`** 直下、既存の **「タスク一覧補足」** に、\

    体裁は、**同一セクション内に**既にある **採用要否・検討のみ** のブロックがあればそれに揃え、無ければ下表を正とする。

| 観点 | 書くこと（最低限） |

| **具体案** | 画面名・導線・操作・文言・表示条件、または **監視・リリース・権限・フォールバック**等を **実装イメージが浮かぶレベル**まで |

## エージェント向け手順（仕様・実装に基づき単独で検討）

**ユーザーに箇条書きで聞き取りするのではなく、AI が仕様とコードを読み、アイデアを具体化してから返す。**\
不足は推測では補わず、**仕様・実装に根拠が薄い箇所は「仮説」「要確認」と明記**する。

1. **対象の把握**\
   会話・開いているファイル・`@` 参照から **検討対象**を決める。**プロダクト名に限定しない**（機能・導線・画面群・リポジトリ・複数プロダクト横断など、文脈で定める）。\
   判別できないときだけ、**1 行で**ユーザーに確認する。

2. **根拠の収集（必須・Read / 検索）**\
   上記 **「全プロダクトを参考にする」** を先に満たす。\
   続けて **検討対象**に応じた **実装**を追う（**ルート・画面テンプレ・フロントの JS・フォーム** など。**SemanticSearch** や **Read** を使う）。\
   検討対象が横断や未指定のときは、FishTrack と MyPokedex のうち **文脈に効く箇所**に絞ってコードを読んでもよい。

3. **検討記録へ書く**\
   **「出力の場所」1** の `機能検討.md` に、当該回の案を追記する。チャットへ書く前にファイルへ残す。**空枠や「後で埋める」だけにしない。**\
   次は **内容として含める**（見出し名・順序・表の有無は自由）:
   - **根拠**: 読んだ **仕様・`AGENTS.md`・コード**（パスやファイル名を簡潔に）
   - **ユーザー文脈・摩擦**: 仕様・実装から読み取れる困り・機会
   - **改善案**: **画面・導線・文言**、または **障害時・権限・計測・リリース** 等、**実装イメージが付く粒度**まで具体化（抽象一行で終わらせない）。\
     **価値向上・流入・会員獲得・利益**のどこに効きうかを、**FishTrack／MyPokedex＝広告・利用継続**の前提で無理のない範囲で一行添える
   - **優先の目安**: 手堅く試せそうなもの、**事業インパクト**が大きそうなものなど、**主観でよい**が理由を一言添える
   - **仮説・要確認**: 根拠が薄い点

4. **チャットは要約にする**\
   返信は、記録した日付見出しと案の要点にする。全文の再掲を返信の唯一の成果にしない。

5. **統合作業スケジュールは、指示があるときだけ更新する**\
   ユーザーがスケジュールへの追加を指示していないときは、本手順をスキップする。検討記録はスキップしない。\
   指示があった **その案だけ**、**「採用要否の検討」タスク**を `スケジュール.md` に追加する（**二本柱**・**SKILL** 準拠）。\
   追加時は **一覧・詳細・週次の末尾に機械的に足すだけ**にせず、**`integrated-schedule-update` SKILL** の **「新規追加時の順序（優先度・影響）」** に従い、優先度・影響・依存を踏まえて **週次・詳細補足の位置**を検討する。\
   **同一編集**で **[[#タスク一覧]]** に加え、**[[#タスク詳細]]** の **タスク一覧補足** に **上表の必須記載**を満たす本文を書く（**一覧のみで終了禁止**）。\
   タスクを追加できた案は、**同じ作業で `機能検討.md` から削除する**。その日付に他の案が無ければ見出しも削除する。\
   チャット本文に、**付与したタスク ID**・**一覧行**・**詳細補足を書いた節**を簡潔に示す。

6. **禁止・注意**\
   **断定やデータの捏造はしない。** アクセスログや利用実態が無い数値は書かない。\
   **勝手に各プロジェクトの `docs/` に新規ドキュメントを作らない**（myrules「ドキュメント作成規律」）。\
   **検討段階で `スケジュール.md` へタスクを足さない。** ユーザー指示の無い起票は禁止。
