# 仕様書更新（プロジェクト仕様）

## 役割

仕様書は、**コード・テスト・各リポジトリの `AGENTS.md` を読んでも再現できない決定**の正本。実装の写しではない。読者はユーザーではなく、次の実装をするエージェント。

対象は `DevProject/specifications/` 全体（FishTrack、MyPokedex、FaiNavi、おたよりナビを含む）。

## 適用タイミング

- **決定が変わったとき**（同じ作業で仕様の該当文を直す。後回しにしない）
- ユーザーが仕様の追記・修正を指示したとき
- コードが**決定文**と食い違うとき（下記「食い違い」）

次は仕様を更新しない。

- 既存の決定を実装しただけ
- リファクタ、バグ修正、テスト追加、閾値や設定名のコード側の変更
- スキーマ・ルート・画面手順を仕様の写しへ追随させる作業

## myrules との関係

短い原則は **`dev-workspace/.cursor/rules/myrules.mdc`** の **「ドキュメント更新規律」**。手順の正本は本 SKILL。配置は同ファイルの **「ドキュメント配置方針」「仕様書探索の既定パス」**。

## 書くもの

次のエージェントがコードだけを見て逆の実装をしそうな文だけを書く。1 決定は 1〜3 文。

- 禁止、例外、対象外（誰に見せない、いつ送らない、何を集計しない）
- 画面に出る呼称で、識別子だけでは別名になりそうなもの
- チャットで確定した境界と、その理由がコードに残らないもの
- まだ作らないと決めた範囲

## 書かないもの

- カラム一覧、エンドポイント一覧、技術スタック、カバレッジ閾値、フォルダ構成の転記（正本はコードと `AGENTS.md`）
- 実装済み画面の操作手順の再掲
- 変更の前後差分を仕様へ積むこと
- テストが既に固定している分岐の再説明
- メーカー別の取込規則のうち、FishTrack の `spec-import-notes` など専用 SKILL が正であるもの（仕様へ複製しない）

## ファイルの置き方

製品ごとにフォルダを分ける。入口は `INDEX.md`。決定は `decisions.md`。まだ作らないことは `not_yet.md`。ルートに `*仕様書.md` は置かない。

- FishTrack と MyPokedex は上記。FishTrack だけ取込の別紙 `ai_spec_import.md` と `llm_prompt_token_reduction.md` が残る
- FaiNavi とおたよりナビも同じ。旧名 `FaiNavi仕様書` と `おたよりナビ仕様書` は `decisions.md` の別名
- MiteneKeeper だけルートの `MiteneKeeper仕様書.md`。本文は実装の写しのままなので、`decisions.md` にはしない

## 既存の厚い本文

決定と写しが混ざったままなのは、FishTrack の取込別紙と `MiteneKeeper仕様書.md`。

- **一括削除・一括要約はしない**
- **新規の写し追記は禁止**
- その節を編集するとき、写しだけの段落は削り、決定文だけ残してよい
- 決定の置き場は **`decisions.md`**。まだ作らないことは **`not_yet.md`**
- 章番号のファイルは作らない。FishTrack の取込別紙は `ai_spec_import.md`。決定を `decisions.md` へ移したら、そのファイルは削除する

## 食い違い

- 仕様の文が**決定**で、コードと違うときは、コードを決定に合わせる。決定文を実装に合わせて書き換えるのは、ユーザーがその決定を変えたときだけ
- 仕様の文が**実装の写し**で、コードと違うときは、写しを直して追随しない。その節を編集するなら写しを削る

## 仕様書の探索

- 既定: `D:/OneDrive/アプリ/remotely-save/Obsidian/DevProject/specifications/`
- 各製品はフォルダの `INDEX.md` から、決定が書いてありそうな節だけを読む。スキーマ・API・スタックの確認に仕様を使わない。MiteneKeeper は `MiteneKeeper仕様書.md`
- 実装・調査の開始時は各リポジトリの **`AGENTS.md`** と、上記の決定確認を行う

## 将来に残す文

- 未実装の「まだ作らない」は、FishTrack / MyPokedex では `not_yet.md` に短く残す
- 実装したら、その将来文は削除する。実装手順へ移さない
- 実装後も境界が残るときは、決定文を機能側の既存節へ 1〜3 文で残し、将来節からは削除する

## 計画書（統合作業スケジュール等）との役割分担

- **仕様書**: コードに残らない**決定**の正（タスク管理の ID に依存しない）
- **`DevProject/` 配下**でタスク番号を列挙してよいのは **`plans/スケジュール.md`** **のみ**（myrules「タスク番号の正本」）。仕様・**`plans/` 内の他ファイル**には**書かない**。
- **統合作業スケジュール**など: **タスク ID・進捗・完了日・ガント**（Fxx / Pxx / Oxx / Mxx / Ixx 等は**こちら側**で管理）
- **統合作業スケジュール**（タスク一覧・週次・ガント・三本柱）の具体的な更新手順: **`integrated-schedule-update` SKILL** を参照する（計画書はルール最小化。**食い違いは SKILL を正**とし、前倒し等の**メタ注記は計画書**を尊重）
- 実装完了時に**マイルストーンやチェックリストを更新する**必要があれば、計画書も合わせて更新する（myrules の「計画書の進捗状況の反映」）

## 仕様書本文に書かないもの

- **タスク番号・タスク ID**（例: `F16`、`P3`、`O1`、`P1-T30`）。仕様は単体で読めるドキュメントにする
- **他プロジェクト参照の略記にタスク ID を混ぜない**（例: `MyPokedex P13` のような **製品名＋スペース＋Pxx** も禁止。再同意・公開ポリシー改定の方針など、**振る舞いの説明**に置き換える）
- **Issue 番号だけ**を根拠にした一文（必要なら「要件の要約」や「日付」で補う）
- 変更の経緯が必要な場合は **日付・要件の要約・版**で示す（例: 「2026-03 反映: 整数 PK はサロゲートのまま、ORM で `autoincrement` を明示」）
- **Obsidian の Wiki リンク**の **アンカー／表示名にまでタスク ID を埋め込まない**（例: `[[スケジュール#P13（…F31…）]]` は禁止）。計画側の見出しに依存する深いリンクより、`[[スケジュール]]` ＋ 本文で「該当節を参照」とする。旧名 `[[統合作業スケジュール]]` は別名で開く

### ルールが守られなかった主な原因（再発防止）

- **履歴**: SKILL 制定・明文化より前の仕様に、計画書と照合用の **F10／P11 等**がそのまま残った
- **参照の便利さ**: 複数プロジェクト整合を「タスク番号」で掴もうとし、**仕様に ID を書く短路**が増えた
- **運用ギャップ**: 「書かない」ルールはあるが、**編集完了時の機械的チェック**が標準化されていなかった
- **計画書との同時編集**: **`スケジュール.md`** を開いたまま **`specifications` を更新**すると、一覧に並んだ **Pxx／Fxx** を**そのまま仕様に貼る**動きが起きやすい（**計画の正**と**仕様の正**の混同）
- **SKILL の取り違え**: **`integrated-schedule-update`** は **計画書・SKILL 本文**でタスク ID を扱う。**`specification-update`** は **仕様本文にタスク ID を書かない**。前者の編集直後に後者のファイルを触ると、**前者の慣習が仕様に持ち込まれる**
- **説明の明確化の誤配線**: 「どの作業に対応するか」を示すために **ID 列挙**を選びがちだが、仕様では **`[[スケジュール]]` ＋ プロダクト名／節名（例: MyPokedex・タスク一覧・詳細補足）**で足りる

### 典型パターン（計画連携の追記で混入しやすい）

- **状況**: 収益モデル・広告・課金など、**方針を `decisions.md` に追記**し、「実装の分割」を**計画書のタスク**に紐づけたい
- **誤り**: **P38／P40** 等を仕様に書く → **仕様読者にタスク管理の ID が不要**であり、**リスケで ID の意味が変わっても仕様が追随しない**ため不整合の温床になる
- **正**: **振る舞い・用語・方針**だけを仕様に書き、**作業の割り当て**は **`[[スケジュール]]` の該当プロジェクト節**へ委ねる（ID は計画書のみ）

- **状況**: 収益の「審査」を **AdSense のサイト審査待ち**と同じ語でアフィリエイトに書く
- **誤り**: Amazon／楽天／Yahoo の **登録・ID発行**を、承認メール待ちのサイト審査とみなし、本番表示を止め続ける
- **正**: AdSense は申請後の承認待ち。モール系アフィリエイトは登録・ID発行で足りることがある（待ち画面なしも可）。
  A8.net など ASP は **広告主プログラムごとの提携**が別。混同しない

### 再発防止（編集完了時）

- **仕様書を触ったセッションの終わり**に、下記いずれかで **タスク ID の残り香**を確認する（ヒットしたら除去 or 計画書へ寄せる）
  - **推奨**: `dev-workspace/scripts/check_spec_task_ids.py` に Obsidian の `DevProject/specifications` の絶対パスを渡して実行（終了コード 1＝違反あり）
  - **手動の目安（rg）**: 仕様ルートで `F10` や `O28`、`P1-4-T`、`統合作業スケジュール#P` 付きリンク等を検索（**ゲーム略号 `FRLG` は別物**なので取り違えない）
- **AI エージェント（必須）**: `specifications` 配下を `write` / `search_replace` 等で編集したら、**ユーザーへの報告前**に必ず `check_spec_task_ids.py` を実行する（**終了コード 1 ならタスク ID を除去してから報告**）。\
    **同一セッションで `スケジュール.md` だけを編集した場合は不要**だが、**計画書と仕様の両方に手を入れたセッション**では、**仕様側の編集のあと必ず**本スクリプトを回す（計画書からの**コピペ混入**が最も多い）

## 仕様と実装の食い違い（AI の裁量）

- 未記載の実装を、仕様へ写して埋めない
- 決定文の誤記（呼称の揺れ、禁止の取り違え）は、ユーザーが確定した決定に合わせて直してよい
- FishTrack と MyPokedex の新しい決定は `decisions.md` に足す。章番号のファイルは作らない。既存ファイルの決定文の更新は、本 SKILL の「書くもの」に限る

## 関連 SKILL（併用）

- **`integrated-schedule-update`**: `スケジュール.md` の編集・三本柱・ガント
- **`markdown-editing`**: Markdown の構造・Markdownlint（行長・表・見出し等）
- **`markdownlint-fix`**: 指摘された MD0xx の修正フロー

- **`obsidian-update-rules`**: Obsidian ノートのタグ・Wiki リンク方針（仕様書が該当する場合）
