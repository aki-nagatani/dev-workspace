# 品質分析 共通雛形

**登録状態**:

- **代理店**: 大枠・原因分類はスクショで登録済み。推定値・下限・上限は
  **ユーザーが計算して渡す**。エージェントは算式を推定しない・使わない。
- **申込書**: 未登録。着手時はフォーマット（雛形）の取り込みから行う。代理店の大枠を流用しない。

Excel ファイルは未配置でよい（チャットのスクショ／テキストで足りる）。

| 項目 | 内容 |
| --- | --- |
| Excel 参照 | チャットのスクショ。ファイル名例 `【YYYY年M月対応】品質分析結果(DTS).xlsx` |
| 置き場所 | `Work/MY案件/_共通/品質分析/`（置けるときだけ。置けないときはテキスト／スクショ）。案件フォルダは `{yyyymm}_{案件名}`（展開日。`_共通` は接頭辞なし） |
| シート | `システム品質`（分析本文）、`障害・変更管理台帳`（障害の正） |
| 見出し例 | `【N月対応】品質分析 (Web)` または Excel設計書側の見出し。注記例 `<WEB> ※DTS分のみ` |

案件の数値・結論・考察はここに書かない。確定したシート名・分類・集計ルール・基準値の形だけを追記する。
前案件ブロックの見出し（帳票改定など）と、推定値・実績の数字は次案件へコピーしない。

## 構成（納品済み過去結果が正）

品質分析 MD の見出し・節の並び・表の形は、**当該プロジェクト・当該分野**の直近の納品済み結果をベースにする。
**代理店と申込書でフォーマットは違う**（目的は同じ）。下記 WEB / Excel設計書は **代理店**。
申込書の構成は未登録。申込書着手時は SKILL §2 で取り込む。代理店の節をコピーしない。
WEB の構成を Excel設計書へ、Excel設計書の構成を WEB へコピーしない。
数値と今回に無い事情は写さない。考察の全文コピーは禁止。文章の型は当該分野の過去考察を参考にする。
分野の有無と、混在時の基準値ブロック本数だけ案件に合わせる。

### WEB（登録済み）

1. **規模**と **○テスト項目設定率**・**○障害発生率**（推定値／下限／上限／実績値。IT / ST、行数から／機能数から）と、それらの考察
2. **(2) 障害要因**　＜各フェーズにおける障害内容分析＞　① ITフェーズ／② STフェーズ。
   列は **分類 / 障害No / 発生件数 / 原因の一例**。原因の一例は、代表1件の詳述ではなく、
   同分類で発生した原因を一言で端的に記載し、複数件分を併記してよい。表のあと **＜分析結果＞**。
   ＜分析結果＞は件数・内訳のあと、発生した分類ごとに `- 分類名` の箇条書き。
   WEB と Excel設計書で記載フォーマットを揃える（見出し構成は分野別のまま）
3. **(3) 過去案件との比較**（IT / ST 別）と当該案件の考察
4. **品質全体に関する留意事項** — （3）の次に置く。体制など、IT・STの個別考察に限定できない事情を記載する。
   **品質向上フェーズの実施内容はここに書かない**
5. **品質向上フェーズ** — 品質全体の次に `### 品質向上フェーズ`。今案件の残フェーズで実施する内容だけを書く。
   次回案件の打ち手は＜分析結果＞。`### 次回案件での施策` は置かない

### Excel設計書（登録済み）

1. **(1) テストケース数・障害数** — 規模と ○テスト項目設定率・○障害発生率（IT / ST）と考察。**バグ曲線は作らない**
2. **(2) 障害要因** — ① ITフェーズ／② STフェーズ。列は直近正式結果に合わせる。
   直近の納品済み Excel設計書は **分類 / 発生件数 / 原因の一例**（障害No なし）。
   過去に障害No列があるときは、その案件の転記だけ残す。表のあと **＜分析結果＞**。
   ＜分析結果＞の記載フォーマットは WEB と同じ（件数・内訳のあと分類ごとの箇条書き）
3. **(3) 品質考察** — 比較表は **IT+ST 合算**（テストケース数／障害件数／対テスト数の障害割合）。注記も当該分野の過去結果に合わせる
4. **品質全体に関する留意事項** — 体制など分野固有の事情があるときだけ（3）の次に置く。
   **品質向上フェーズの実施内容はここに書かない**
5. **品質向上フェーズ** — 品質全体または（3）の次に `### 品質向上フェーズ`。今案件の残フェーズで実施する内容だけを書く。
   次回案件の打ち手は＜分析結果＞。`### 次回案件での施策` は置かない

- **顧客指摘・優先指示**: 既知事情に書く。打ち手は＜分析結果＞または (3)。独立節は置かない。
  WEB と Excel設計書に跨る指示は両方に書く。品質向上フェーズは各分野へ書く。
  顧客指摘の「今回の事象」は、ユーザーが特定した障害にだけ当てる。同分類の他件へ広げない。
  同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。
  案件固有の本文は書かない。
- **IT/ST共通の品質要因**: 体制など、IT・STの個別考察に限定できず品質全体に関わる事情は、
  当該分野の（3）過去案件との比較の次に独立した節として記載する。各フェーズの＜分析結果＞へ重複して記載しない。
- **品質向上フェーズ**は今案件の残フェーズ。次回案件の打ち手と混ぜない。
  WEB と Excel設計書それぞれに置く。文書末尾の横断1節は置かない。
  実施内容は当該分野の分だけ。他分野の実施内容を重複しない。
  汎用の「この後取るべきアクション」節とは別である。
  書き方は、実施内容を箇条書きし、補足を文章で続ける。実施内容を一文に連ねない。
  同一の実施を、手段と本体で複数行に分けない。
  `### 品質向上フェーズ`。次回案件の打ち手は＜分析結果＞。`### 次回案件での施策` は置かない。

基準値の形と原因分類は共通。案件の規模・テストケース数・推定値はユーザーが渡す。障害関連は障害管理台帳（障害表）から取る。

### 分野（代理店・厳格）

代理店案件には **WEB** と **Excel設計書** の2分野がある。

- 案件により **いずれか片方** が対象、または **両方** が対象。
- **品質分析は対象分野ごとに実施する**。WEB と Excel設計書を混ぜて1本にしない。
- **並びは必ず WEB → Excel設計書**（対象表、入力状況、分析本文の `##`、次インプット、報告）。
  両方あるとき、Excel の入力が先に来ても節を入れ替えない。
  WEB のみ／Excel設計書のみのときは対象外の節は置かない。
  **品質向上フェーズ**は各分野の分析内に置く（文書末尾の横断1節は置かない）。
  次回案件の打ち手は＜分析結果＞。混ぜない。
- 対象外の分野の節・ブロックは作らない。
- 片方のみの例: WEB だけ、または Excel設計書だけ（対象外の節は置かない）。
- 規模・テストケース数・障害表は **対象分野ごと**。障害表が1冊でも、分野が分かること。
  共通台帳で、一方の分野に IT/ST 障害が**現時点でない**と明示されたら、その分野は **`0`**。
  列が無いことだけを理由に `（未入力）` にしない。他分野の件数を流用しない。
- Excel設計書の規模指標が WEB の表と違うときは、来た指標に合わせる。推測で WEB の行を埋めない。
- 分野内の基準値ブロック本数は、次節（混在しなければ1つ）。

### 基準値ブロックの本数（厳格）

- **1つの品質分析に複数案件が混在するときだけ**、基準値（規模・設定率・発生率）を **案件ごと＋全体** で実施する。
- **混在しなければ全体 1 つだけ**。サブ案件用のブロックを作らない。
- 混在の例（前案件）: 帳票改定・紙スキーム・意向改定が1つの分析に入っていたため、3つ＋全体の4本。
- 混在時に ST ケースが案件横断で共通なら、ST の基準値は全体のみ、というやり方がある。混在しなければ IT / ST ともその1本に載せる。
- 前案件の分割見出しを、混在しない案件へコピーしない。

### 規模（システム品質の左表）

SLOC・マスタ・IF・画面数・帳票数・バッチ・推定FP はユーザーが資源から計算して渡す。
**KSLOC は SLOC / 1000**（小数第1位・四捨五入）。ユーザーが KSLOC を渡したらそれを正。
SLOC が無い間は KSLOC も `（未入力）`。納品済みの過去結果は再計算せず転記する。

| 指標 | 単位の例 |
| --- | --- |
| 改訂プログラム行数（KSLOC） | Kstep |
| 改訂プログラム行数（SLOC） | step |
| マスターファイル・テーブル数 | 件 |
| インターフェース数 | 件 |
| 画面数 | 件 |
| 帳票数 | 件 |
| バッチ数 | 件 |
| 機能数（推定FP） | FP |

画面数と帳票数は**規模の内訳として別行**。設定率・発生率の計算軸には使わない。
帳票修正の推定FP内訳が来たら規模の補足行として書く（率の軸にはしない）。
帳票の新規／改訂内訳が来たら規模の補足行として書く（率の軸にはしない）。
表記は **改訂**（改定ではない）。前案件の分割見出し「帳票改定」「意向改定」は過去結果の名称なので変えない。
**帳票の修正は LOC（SLOC / KSLOC）に含まれない**（ユーザー確定）。
帳票修正が多いときは、行数軸との差を主判断にしない。機能数（推定FP）軸を重点にする。
設定率が機能数軸で推定下のときは、帳票内バリエーションの多寡と新規／改訂の事情が来たら考察の根拠にする。
改訂は改訂箇所中心で、新規よりケースが少なくなりうる。
機能数の大半が帳票修正であることだけでは、設定率が推定下である理由にしない。
規模の内訳（IF 等）が訂正されたら、推定FPと機能数軸の推定値をセットで差し替え、範囲判定と考察をやり直す。

### 基準値（テスト項目設定率・障害発生率）

軸は **行数から**（SLOC）と **機能数から**（推定FP）のみ。IT / ST を分ける。

各セルは **推定値 / 下限 / 上限 / 実績値**。
列名は **推定値**（予測値ではない）。納品済み過去結果の「予測値」は転記どおり残す。

| 指標 | 実績値の取り方 | 推定値・下限・上限 |
| --- | --- | --- |
| ○テスト項目設定率 | テストケース数（ユーザー渡し） | ユーザーが計算して渡す。無い間は `（未入力）` |
| ○障害発生率 | 障害件数（障害表） | 同上 |

入力源の例: **メトリクス(サマリー版)**。推定値／下限／上限を**そのまま**書く（再計算しない）。

- IT/ST の **テスト密度** → ○テスト項目設定率。SLOC は行数から、FP は機能数から
- IT/ST の **欠陥検出密度** → ○障害発生率。同上
- **開発工数予測・工期予測は品質分析に載せない**

算式の類推・係数の保管はしない。

### 発生原因の分類（登録済み）

`システム品質` の障害原因表。IT フェーズと ST フェーズを分ける。分類名は共通。
件数と一例は障害表から取る。列は**当該分野の直近正式結果**に合わせる。
原因の一例は、代表1件の詳述ではなく、同分類で発生した原因を一言で端的に記載する。
複数件で原因が異なるときは、複数の短い原因を併記してよい。
同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。

- WEB: **分類 / 障害No / 発生件数 / 原因の一例**
- Excel設計書: **分類 / 発生件数 / 原因の一例**（障害No 列なし）

1. 要件定義漏れ
2. 外部設計ミス、漏れ
3. 内部設計ミス、漏れ
4. コーディングミス、漏れ
5. 外部システム誤り
6. 環境バージョン起因
7. その他

表の行順もこの並び。これ以外の分類名は使わない。空欄は「その他」に入れない。
分類空で調査中の行は、調査完了（分類確定）するまで件数・分析に含めない。台帳には残す。
分類を推測しない。調査完了後に件数へ戻す。
障害Noの `-0` は枝番である。`-1` 以降が無い障害は、品質分析では `-0` を省略して親番だけを記載する。
台帳上の障害Noは変更しない。
納品済み過去結果の表は転記どおり残し、並びを直さない。

分類は作り込み工程の目安、発生フェーズは検出工程。後工程で前工程起因が出たら、
当該フェーズの＜分析結果＞に見逃しとして書く。独立節は置かない。件数 0 は検知していない。
障害要因の考察は、IT / ST より前のテスト工程で検知して止められずに
流出した観点を主軸にする。ただし、ITのテストケース外の観点をSTで検知した障害は、ITの見逃しとして扱わない。
ITのテストケース外をSTで検知したコーディングミスは、STでの検知は問題無しとして扱う。
ITで突合せを実施済みでも、IT実施パターンでも検知できた面があるときは、
未実施と書かず、次回以降のIT実施パターンで外部設計書・他商品との突合を徹底する、として再発防止に書いてよい。
実施していなかったかのように「実施する」とは書かない。
Excel設計書は UT～ST をテスト観点ごとに分けている。
当該観点を前段では実施していないときは、後工程での検知を前段の見逃しとしない。
前段での検知は難しいため、当該フェーズでの検知は問題無しと判断する。
見逃し分析とは別に、障害の作り込み自体を減らす外部設計・内部設計の改善策は、
根拠のある範囲で再発防止として記載する。テスト工程での検知責任と混同しない。

### 過去案件との比較（雛形の節）

Excel の **(3)**。WEB は **過去案件との比較**（IT / ST 別）。注記例 `<WEB> ※DTS分のみ`。
Excel設計書は **品質考察**（IT+ST 合算）。分野を混ぜない。表の形は当該分野の過去 MD に合わせる。

| 工程の行 | 内容 |
| --- | --- |
| テストケース数 | 過去の品質分析結果 |
| 障害件数 | 過去の品質分析結果 |
| 対テスト数の障害割合 | 上2つから出す。過去結果が無い欄は `（未入力）` |

今回の障害表から他案件の件数は取らない。考察文は案件ごとに書く。前案件の結論は写さない。
入力の正は **過去案件フォルダの `品質分析.md`**。Excel／スクショだけなら、先にその案件の MD を作る。
納品済み・連携済みなら正式版としてそのまま転記する。
比較節には比較表、数値差および基準値との関係による総括だけを置く。
テスト項目設定率の事情は（1）、障害の分類・検知妥当性・対応方針は（2）に記載する。

## 大枠（現行）

成果物 MD の標準構成（`#` は1つのみ）。対象分野が2つなら、分析本文を **分野の `##` の下に繰り返す**。
順序は **WEB → Excel設計書**。対象表・入力状況・出典・未確定事項などの作業情報は、同じ案件フォルダの
`品質分析_作業メモ.md` に置く。`品質分析.md` には顧客提出用 Excel に転記する内容だけを置く。
作業メモの RV指摘節は指摘原文を変えず、取込状況は原文を上書きしない。後から増えた確定は既知事情へ書く。

分析本文は**当該分野の過去結果と同じ並び**（WEB と Excel設計書で節名が違う。template の構成節を正とする）。

下記の追加観点の案は、ユーザーが採用を明示し、かつ障害表に必要な列があるときだけ足す。
**(3) は案ではない**（WEB は過去案件との比較、Excel設計書は品質考察）。

## 追加観点の案（未採用）

**状態**: 案のみ。過去結果の標準構成には入れない（過去案件との比較を除く）。

**採用の前提（厳格）**:

- 追加観点の情報は **障害表だけ**から取る（規模・テストケース数のユーザー渡しと、過去比較の過去品質分析は既存ルール。追加観点の穴埋めには使わない）。
- **障害表に無い情報**を要する案は **採用できない**。
- その観点を分析したいときは、**障害表のフォーマット変更（列の追加・定義）が先行**する。列が無い間は成果物に節を足さない。
- 障害表の列は未登録。列が確定したら、載っている案だけ採用を検討する。列の有無は推測しない。

### 案一覧

障害表に載りうる列の例は典型名。現行フォーマットにあるとは限らない。

| 観点 | 障害表で足りうる列の例 | 列が無いとき |

| 重複・無効・仕様どおりの除外率 | 状態、区分（無効・重複） | 同上 |
| 検出工程（IT で検出か、ST まで漏れたか） | 発生フェーズ、検出工程 | 発生フェーズがあれば既存の要因表＋＜分析結果＞で足りる。独立節は足さない。発生フェーズ以外の切り方が要るときだけ列追加が先 |
| 作り込み工程（設計／製造／結合など） | 分類、混入工程 | 7分類があれば作り込みの目安として既存の＜分析結果＞で足りる。独立節は足さない。分類以外の混入工程列が要るときだけ列追加が先 |
| 発見者（開発／テスト／顧客／運用） | 発見者、起票者 | フォーマット変更が先。採用しない |
| 未クローズ・残件と期限 | ステータス、期限 | 同上 |
| 発生・解決の推移 | 発生日、クローズ日 | 同上 |
| 再オープン・修正不良 | 再オープン回数、再開 | 同上 |
| 修正リードタイム | 発生日と対応完了日 | 同上 |
| テスト消化率・未実施残 | （通常はテスト管理側） | 障害表に載せる設計変更が先。無い間は採用しない |
| 正常／異常／境界の偏り | （通常はテストケース側） | 同上 |
| バッチ・IF など画面・帳票以外への偏り | 対象機能・対象種別 | 規模の再計算はしない。列が無ければ採用しない |
| 顧客指摘・UAT との突合 | 発見者／区分が顧客 | 別リストだけの指摘は障害表に無いので採用しない |
| 出荷・次工程可否の一文 | 新列は不要（既存分析の結論） | ＜分析結果＞に含めうる。独立節は作らない |

列が登録されたら、上表の「列が無いとき」を実列に合わせて見直す。載っていない観点は案のまま残す。

## 分類・集計ルール

- **バグ曲線は作成しない**。MD に節を置かない。過去 Excel にあっても転記しない。
- **プロジェクト**（代理店／申込書）でフォーマットを混ぜない。申込書は未登録。代理店の大枠を流用しない。
- **分野**は対象ごとに分析する。WEB と Excel設計書を混ぜない。対象外の節は置かない。
  両方あるときの並びは **必ず WEB → Excel設計書**。
  品質向上フェーズがあるときは各分野に置く。次回案件の打ち手は＜分析結果＞。混ぜない。
- **基準値ブロック**は混在時のみ案件ごと＋全体。混在しなければ1つ。
- **設定率・発生率の軸**は行数（SLOC）と機能数（推定FP）。画面数・帳票数は規模の内訳であり、合算して率の軸にしない。
  帳票の修正は LOC に含まれない。帳票修正が多いときは行数軸との差に重きを置かず、機能数軸を重点にする。
  帳票修正の推定FP内訳が来たら規模の補足として書く（率の軸にはしない）。
  帳票の新規／改訂内訳と、帳票内バリエーションの多寡が来たら設定率の考察に使う。
  表記は **改訂**（改定ではない）。前案件の分割見出し「帳票改定」「意向改定」は過去結果の名称なので変えない。
  改訂は改訂箇所中心で、新規よりケースが少なくなりうる。
  機能数の大半が帳票修正であることだけでは、設定率が推定下である理由にしない。
- **規模**（SLOC 等）はユーザーが資源から計算して渡す。**KSLOC は SLOC / 1000**（小数第1位）。その他はエージェントが計算しない。
- **推定値・下限・上限**はユーザーが計算して渡す。エージェントは算式を推定しない・使わない・計算しない。
- **`0` は未入力ではない**。件数が 0 なら `0` と書く。
- **テストケース数**はユーザーが渡す。エージェントは台帳や資源から計算しない。
- **障害関連**（障害件数、発生原因、障害No、原因の一例）は障害管理台帳（障害表）から取得する。
  `品質分析.md` には件数・分類・一例。見えている行の全量は同一フォルダの **`障害・変更管理台帳.md`**。
  台帳は DTS 範囲外も含め全行を同じ粒度で残す（要約表だけにしない）。
  フィルタ外は、障害として扱わないもの、または DTS 担当範囲外。**件数・分析に含めない**（台帳からは省略しない）。
  取消・取り下げ（障害ではなかった）もフィルタ外として件数から外し、台帳には残す。
  分類空で調査中の行は、調査完了（分類確定）するまで件数・分析に含めない。台帳には残す。
  空欄を「その他」にしない。分類を推測しない。
- **原因分類**は上記7分類のみ。表の行順も同じ（外部システム誤り → 環境バージョン起因）。
  空欄は「その他」に入れない。納品済み過去結果の表は転記どおり残す。
- **過去案件との比較**は過去案件の `品質分析.md` から取る。今回の障害表から他案件は取らない。
  過去結果が Excel／スクショだけのときは先に MD 化する。
  **納品済み・連携済み**なら正式版として**そのまま転記**（要約・言い換え・再考察はしない）。
- **考察**: 揃っている欄は数値の転記だけで終えない。推定値があるときは範囲判定。
  結果だけでなく、なぜその結果に至ったかを書く。根拠があれば事実。足りなければ「〜と考えられる」とし、確認を取る。
  **AIが独自に推測した因果には `（推測）` を付ける**。「考えられる」はユーザーも使うため、ラベル無しでは区別できない。
  文末の例: 「〜と考えられる（推測）。」。ユーザーが事実として渡した因果には付けない。
  さん付け・作業メモ口調は本文に置かない。確定したら `（推測）` を外す。
  当否確認は障害表とユーザー確定事情だけを正とする。当ならラベルを外す。否なら訂正する。どちらにも無い因果は外す。
  文章の型は当該分野の過去考察を参考。数値と今回に無い事情は写さない。全文コピー禁止。
  再発防止は「確認観点を明確にする」で終えない。実施する行為で結ぶ。
  実施主体・役割分担が未確定のときは、実施すると断定せず次回案件で検討する、と書く。
  ユーザーが品質向上フェーズへ実施と明示した項目は実施すると書く。
  次回案件の打ち手は＜分析結果＞に書く。独立した次回案件節は置かない。
  同一対策を＜分析結果＞で「次回検討」のまま残さない。
  次回案件の施策を品質向上フェーズへ書かない。
  台帳の原因・経緯は開発メモのまま本文へ写さない。
  設定率の結びは IT / ST ともに常用句
  「確認すべき観点は網羅しているため、実績値は問題無しと判断する。」を使ってよい。
  発生率が上限超のときはこの句で済ませない。
  帳票修正が多いときは行数軸との差に重きを置かず、機能数軸を重点にする。
  基準値チェックの考察では分類に深入りしない。分類は (2) 障害要因。
- **追加観点の案**は障害表の列だけで分析する。列が無い観点は採用しない。分析するならフォーマット変更が先。
