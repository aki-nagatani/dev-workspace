# quality-analysis（IT/ST 品質分析）

申込書・代理店など DTS 本職案件の **IT / ST 結果**を分析し、**エージェント成果物は Markdown** とする。
顧客提出の最終成果物は **Excel**（ユーザーが MD から転記）。エージェントは **Excel を書かない**。

**最初の作業**: 本ファイルと [template.md](template.md) を **Read** する。Work 配下を編集する前に **`work-folder-update` SKILL** も **Read** する。

## 発火

- ユーザーが **品質分析**、**IT結果**、**ST結果**、**バグ票**、**障害管理台帳**、**障害表**、**品質レポート** を依頼したとき
- 雛形 Excel・規模の数値・テストケース数・障害管理台帳をチャットへ貼った／パスを示したとき（**テキスト入力も含む**）
- **`Work/MY案件/`** 配下の品質分析フォルダ、または既存の **`品質分析.md`** の追記・修正を依頼したとき

## 原則

- **推測で数値・判定・分類を埋めない**。根拠がない欄は **`（未入力）`**。
  **`0` は未入力ではない**。規模の件数などが 0 なら `0` と書く。
  **考察の因果**は例外。結果だけでなく、なぜその結果に至ったかを書く。
  根拠があれば事実として書く。足りなければ推測して書いてよいが、本文は報告資料の文体とする。
  「〜と考えられる」はユーザーも使う表現である。**AIが独自に推測した因果には `（推測）` を付ける**。
  文末の例: 「〜と考えられる（推測）。」。ユーザーが事実として渡した因果には付けない。
  確認はチャットまたは未確定で取る。確定したら `（推測）` を外す。
  **当否確認**（ユーザー依頼時）: 正は障害表の原因・経緯・調査結果と、ユーザーが渡した事情だけ。
  当なら `（推測）` を外して残す。否なら台帳どおりに訂正する。
  どちらにも無い因果は外す（`（推測）` 付きのまま残さない）。
  数値・推定値セル・分類は推測で埋めない。
- **雛形と共通情報は一度登録したら、同じプロジェクトの次回案件でも使う**。呼び出しごとに再入力させない。
  **代理店と申込書で品質分析のフォーマットは違う**（目的は同じ。見出し・表・シートは別）。
  **登録済みは代理店のみ**。申込書は未登録。申込書の作業を始めるときは **§2 雛形の取り込みから**行う。
  代理店の構成を申込書へ流用しない。
- **構成の正は当該プロジェクト・当該分野の納品済み過去結果**。見出し・節の並び・表の形は、その分野の直近正式
  `品質分析.md`（無ければ納品 Excel）をベースにする。WEB と Excel設計書で構成が違うときは混ぜない。
  代理店の構成を申込書へ使わない。前案件の**数値と、今回に無い事情は写さない**。
  考察の文章（文体・構成・言い回し）は、当該分野の納品済み過去結果を**参考**にする。全文コピーは禁止。
  分野の有無と、混在時の基準値ブロック本数だけ案件に合わせる。
  両方あるときの並びは **必ず WEB → Excel設計書**。
  品質向上フェーズは WEB と Excel設計書それぞれに記載する。
  次回案件の打ち手は＜分析結果＞に書く。独立した次回案件節は置かない。品質向上フェーズに混ぜない。
- **バグ曲線は作成しない**。MD に節を置かない。過去 Excel にあっても転記しない。グラフも作らない。
- **雛形は大枠のみ**。大枠の中身は当該プロジェクト・当該分野の過去構成。独自の節（例: 独立した「この後取るべきアクション」）を足さない。
- **前案件の文言を理解せず使わない**（過去の品質分析で指摘された失敗）。意味が取れない見出しはユーザーに確認する。
- **報告資料と作業メモを分離する**。`品質分析.md` は顧客提出用 Excel に転記する表・考察・注記だけを置く。
  入力状況、出典、作成方針、未確定事項、社内体制・指示系統などの作業情報は、同じ案件フォルダの
  `品質分析_作業メモ.md` に記載する。報告資料本文に作業用のメタ記述を混在させない。
- **作業メモの RV指摘節**: 指摘内容の原文は変えない。
  取込状況（取込済み／訂正済み）は原文を上書きせず、各項の末尾に置く。
  後から増えた確定事項は RV指摘の番号を増やさず、既知事情へ書く。
  顧客指摘の「今回の事象」は、ユーザーが特定した障害にだけ当てる。同分類の他件へ広げない。
  同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。
- **入力は随時**。揃うまで待たず、来た分だけ MD を更新し、足りないものを明示する。
- **実行しながら本 SKILL を更新する**。手順・大枠・判断基準が変わったら同一セッションで本ファイルを直す。
- **機密**: Work は社外秘。外部検索・外部ツールへ結果・障害内容を送らない。Excel 読み取りはローカルのみ。
- **追加観点の案**: [template.md](template.md) に残す。**未採用**。成果物の標準構成に入れない。
  追加観点の情報は **障害表だけ**。障害表に無い情報の案は採用できない。
  分析したいときは **障害表のフォーマット変更が先行**。ユーザーが採用を明示し、かつ必要な列があるときだけ昇格する。
  **(3)** は雛形の節であり案ではない（WEB は過去案件との比較、Excel設計書は品質考察）。
- **基準値ブロックの本数**: 1つの分析に複数案件が混在するときだけ、案件ごと＋全体。
  混在しなければ **全体 1 つ**。前案件の分割見出しをコピーしない。詳細は [template.md](template.md)。
- **過去の品質分析結果**: Excel／スクショだけで終わらせない。**当該案件フォルダの `品質分析.md` に残す**。
  今回案件の「過去案件との比較」は、その過去 MD を参照する。数値の転記は可。
  考察の全文はコピーしない。文章の型は当該分野の過去考察を参考にし、今回分を書く。
- **納品済みの過去結果**: 連携・納品済みの品質分析 Excel は**正式版**。MD 化は**転記**であり、再分析ではない。
  セルの数値・分類・考察文を**そのまま**残す。要約・言い換え・「スクショの文言」等のメタ注記は付けない。
  空セルは空のまま（`（なし）` で埋めない）。読めない欄だけ `（未入力）`。`0` は `0`。
  **例外**: バグ曲線は転記しない。

## 入力の取り方（運用）

| 情報 | 取り方 |
| --- | --- |
| **規模**（KSLOC / SLOC、マスタ、IF、画面数、帳票数、バッチ、推定FP） | SLOC・マスタ・IF・画面数・帳票数・バッチ・推定FP はユーザーが資源から渡す。対象分野ごと。 |
| | **KSLOC は SLOC / 1000**（小数第1位・四捨五入）。ユーザーが KSLOC を渡したらそれを正。 |
| | SLOC が無い間は KSLOC も `（未入力）`。納品済み転記は再計算しない |
| | 規模の内訳（IF 等）が訂正されたら、推定FPと**機能数軸の推定値・下限・上限をセットで差し替え**、範囲判定と考察をやり直す。行数軸は KSLOC が同じなら据え置き。開発工数予測は載せない |
| **テストケース数** | ユーザーが渡す（**対象分野ごと**、IT / ST 別）。エージェントは台帳や資源から計算しない |
| **障害関連**（障害件数、発生原因、障害No、原因の一例など） | **障害管理台帳**（**障害表**ともいう）から取得する。**対象分野ごと**（台帳が分かれていなくても分野が分かること）。台帳に無い値は `（未入力）` |
| | 共通台帳で、一方の分野に IT/ST 障害が**現時点でない**と明示されたら、その分野の件数は **`0`**。列が無いことだけを理由に `（未入力）` にしない。他分野の件数を流用しない |
| | **フィルタ外**は、障害として扱わないもの、または DTS の担当範囲外（ユーザー確定）。**件数・分析に含めない**。 |
| | 取消・取り下げ（障害ではなかった）もフィルタ外。**台帳には残す**。 |
| | **台帳（`障害・変更管理台帳.md`）にはフィルタ外も全行残す**（分析対象と同じ粒度。要約表だけにしない）。 |
| | 横スクロール等で同じ障害が複数のスクリーンショットに分かれる場合、分類など右側の列も照合する。記載済みの分類を空欄として扱わない |
| | 分割されたスクリーンショットから台帳を転記するときは、障害ごとに分類だけでなく、原因・経緯、調査結果・原因・経緯、調査方法、対応状況も照合する。各欄の記載有無を確認してから集計・考察へ反映する |
| | **分類空で調査中**の行は、調査完了（分類確定）するまで件数・分析に含めない。台帳には残す。空欄を「その他」にしない。分類を推測しない。調査完了後に件数へ戻す |
| | **障害Noの表示**は、台帳上の `-0` を枝番として扱う。`-1` 以降が無い障害は、品質分析では `-0` を省略して親番だけを記載する。台帳の番号は変更しない |
| **対象分野** | 代理店は WEB / Excel設計書。案件の対象（片方または両方）を対象表に書く。**並びは必ず WEB → Excel設計書**。申込書の分野は雛形取り込み後に書く |
| **基準値の形・原因分類** | **プロジェクトごと**（代理店／申込書）。代理店は [template.md](template.md) に大枠登録済み。**申込書は未登録**（着手時は §2）。 |
| | 推定値・下限・上限はユーザーが計算して渡す（算式の推定はしない）。メトリクス(サマリー版)は template どおり転記 |
| | 列名は **推定値**（予測値ではない）。納品済み過去結果の「予測値」は転記どおり残す |
| **過去案件との比較** | 過去案件フォルダの `品質分析.md`。無ければ受領した Excel／スクショ／テキストから **同一セッションで MD 化する**（納品済みなら**そのまま転記**）。今回の障害表から他案件は取らない。考察の全文は写さない。文章の型は参考にする |

### 入力の形態（Excel とテキスト）

セキュリティの都合で **Excel を Work / Cursor に置けない**ことがある。その場合は **チャットへテキストで渡す**。テキストは Excel と同等の入力として扱う。

| 形態 | 扱い |
| --- | --- |
| **Excel をフォルダへ置ける** | 共通雛形は `_共通/品質分析/`、案件の台帳は作業フォルダ。`.xlsx` は openpyxl、`.xls` は xlrd で stdout のみ読む |
| **置けない** | 表・CSV 相当・箇条書きをチャットへ貼る。ファイル配置を再要求しない |
| **規模の数値・テストケース数・推定値** | テキストで十分 |

テキストから必要な数値・分類だけを `品質分析.md` / `template.md` へ載せる。
台帳の**全文**は `品質分析.md` に載せない。見えている行の全量は同一フォルダの **`障害・変更管理台帳.md`**。

## 正本

| 用途 | パス |
| --- | --- |
| **作業フォルダ（案件固有）** | ユーザー指定を正とする。型は `Work/MY案件/{yyyymm}_{案件名}/品質分析/`。`{yyyymm}` は展開日。`_共通` は案件ではないので接頭辞なし |
| **MD 成果物** | 作業フォルダ内の `品質分析.md`。**過去案件も同じ型**（Excel のまま残さない）。台帳の全量は同一フォルダの `障害・変更管理台帳.md` |
| **作業メモ** | 作業フォルダ内の `品質分析_作業メモ.md`。入力状況、出典、未確定事項および内部向けの前提を置く |
| **共通雛形 Excel** | 置けるときだけ `Work/MY案件/_共通/品質分析/`。置けないときはチャットのテキスト。抽出結果は [template.md](template.md) |
| **共通大枠・分類・集計ルール** | [template.md](template.md) |
| **案件固有の入力** | 規模の数値、**テストケース数**、**推定値・下限・上限**、**障害管理台帳**（**障害表**）。Excel またはテキスト。置けない場合はチャットへ。雛形の再配置は求めない |
| **顧客提出 Excel** | ユーザーが作成。エージェントは Read のみ |
| **本 SKILL** | `dev-workspace/.agents/skills/DTS/quality-analysis/SKILL.md` |

案件が複数あるときは **案件フォルダを分ける**（1ノートに混ぜない）。1ノートが長すぎるときだけ分割（**`ノート分割の基準.md`**）。
案件フォルダ名は **`{展開日yyyymm}_{案件名}`**。展開日が未確定ならフォルダを作らず確認する。
`_共通` に展開日は付けない。
**正本は作業フォルダの1箇所**。別パスに置いていた MD は移して旧ファイルを削除する。

## 作業フロー

### 0. ゲート

1. 本 SKILL を Read する。続けて [template.md](template.md) を Read する。
2. Work を編集するなら **`work-folder-update`** を Read する。
3. 作業フォルダが指定されていれば配下を一覧する。既存の **`品質分析.md`** と **`品質分析_作業メモ.md`** があれば Read する。
   初回は、両方を作成する。
4. 雛形の**大枠**は **プロジェクトごと**。[template.md](template.md) の登録済みは **代理店**。
   代理店案件では再提出させない。推定値・下限・上限はユーザーが計算して渡す。
   過去結果からの算式推定はしない・使わない。
   **申込書**は未登録。着手したら §2 でフォーマットを取り込む。代理店の大枠をコピーしない。
   ファイル配置は必須ではない。

### 1. 入力の棚卸し

セッション内の入力を次で分類する。無いものは **不足** と記録し、分析を止めない。

| 種別 | 例 | 必須度 |
| --- | --- | --- |
| **雛形（共通）** | 品質分析 Excel のシート構成、またはそのテキスト／スクショ | **プロジェクトごと**。代理店は大枠登録済み。申込書は未登録（着手時に §2） |
| **共通情報** | 分類、集計ルール、指標の定義、書き方 | 来たら template.md に残す。次回も使う |
| **対象の特定（案件）** | 申込書／代理店、案件名、**対象分野**（WEB / Excel設計書 / 両方）、対象工程（IT/ST）、期間 | 案件ごと |
| **規模（案件）** | SLOC、マスタ、IF、画面数、帳票数、バッチ、推定FPはユーザー渡し。**KSLOC は SLOC / 1000**（小数第1位）。**対象分野ごと** | 案件ごと |
| **テストケース数（案件）** | IT / ST 別。ユーザーが渡す。**対象分野ごと** | 案件ごと |
| **障害管理台帳（案件）** | 障害表。Excel またはテキスト。障害件数・発生原因などはここから取得。**対象分野が分かること** | 案件ごと |
| **推定値・下限・上限（案件）** | 設定率・発生率の推定／下限／上限。ユーザー渡し。 | 案件ごと |
| | メトリクス(サマリー版)ならテスト密度→設定率、欠陥検出密度→発生率。開発工数は載せない | |
| **補足（案件）** | WBS、体制、既知の事情、顧客指摘 | 考察の根拠。数値・分類は推測で補わない。因果が足りないときは「考えられる」＋`（推測）` とし、確認はチャット／未確定 |

Excel を置けるときは **Read ツールではセルが読めない**。`.xlsx` は **openpyxl**、`.xls` は **xlrd** で **stdout のみ**読む。
読み取りスクリプトで **`.md` を生成・上書きしない**（myrules「ファイル修正と差分確認」）。
テキスト入力のときは貼られた内容を正とし、ファイルの再提出を求めない。

**対象の特定が来たとき**（プロジェクト名・案件名）:

- 成果物の H1 を `品質分析（{プロジェクト}・{案件名}）` にする
- 対象、入力状況、出典、既知事情および未確定事項は **`品質分析_作業メモ.md`** を即更新する
- 対象分野が来たら対象表に書き、MD は **対象分野の節だけ**置く（対象外は作らない）。
  両方あるときは **必ず `## WEB` を先、`## Excel設計書` を後**。Excel の入力が先でも入れ替えない
- 「未確定・次インプット」から案件名確認を外す
- 他ノートにある終了予定・担当などは **既知事情** として対象に書く。テスト結果からの推測はしない
- **案件名は SKILL に書かない**（今回限りの値）

**過去の品質分析（Excel／スクショ／テキスト）が来たとき**:

- 当該案件の作業フォルダ `Work/MY案件/{yyyymm}_{案件名}/品質分析/品質分析.md` へ残す。フォルダが無ければ新設する（展開日が分かるときだけ。未確定なら確認）
- **納品済み・連携済み**なら正式版。セルの数値・分類・考察文を**そのまま転記**する。
  要約・言い換え・エージェントの再考察はしない。空セルは空。読めない欄だけ `（未入力）`。**`0` は `0`**
- 未納品の下書きや欠けたスクショだけのときは、読めた範囲だけ転記し、欠けは `（未入力）`
- 障害表の全文は `品質分析.md` に載せない（システム品質シートに載っている障害No・件数・一例は転記する）。
  見えている行の全量は同一フォルダの **`障害・変更管理台帳.md`**（空欄は空）。
  **台帳には DTS 範囲外・疎通・取消・取り下げ・非障害も含め、分析対象と同じ粒度で全項目を残す。**
  要約表だけにして詳細を省かない。件数・要因表から外すことと、台帳から省略することは別である。
  フィルタ外（障害として扱わないもの、または DTS 担当範囲外）は **`品質分析.md` の件数・要因表に含めない**。
- 今作業中の別案件へ、過去の考察文をコピーしない
- 今作業中の比較表は、過去 MD を参照（wikilink）し、必要な数値だけ転記してよい

**作業フォルダが指定されたとき**:

- そのパスを正本とする。型は `Work/MY案件/{yyyymm}_{案件名}/品質分析/`
- 配下を一覧し、**案件固有**の規模の数値・テストケース数・障害管理台帳があれば読む。空でもフォルダ確定として MD の対象表を更新する
- MD は作業フォルダへ置く。別場所にあれば移し、旧ファイルは削除する
- 雛形が無いことを理由に、**同じプロジェクトで登録済み**の共通雛形の再提出を求めない
- Excel が置けない旨があれば、テキスト入力で足りるとし、ファイル配置を次インプットに書かない

### 2. 雛形から大枠を取る（そのプロジェクトが未登録のとき）

**申込書**は未登録。申込書の作業を始めるときは本節から行う。代理店の見出し・表を流用して埋めない。

1. 置けるときだけ、Excel を **共通フォルダ** `Work/MY案件/_共通/品質分析/` へ置く（またはパスを [template.md](template.md) に記録する）。置けないときはチャットのテキストを正とする。
2. シート名、見出し、表の軸（基準値、発生原因など）を拾う。
3. **[template.md](template.md) の大枠・分類を実物に合わせて更新**する。登録状態をプロジェクト名付きで「登録済み」にする。
4. 前案件の**数値・考察文は成果物へコピーしない**。別プロジェクトの大枠もコピーしない。
5. 意味不明の見出し・指標はユーザーに確認し、確認待ちを MD の「未確定」に書く。
6. 以降、**同じプロジェクト**の案件では本節を飛ばし、template.md の当該大枠を使う。

### 3. 分析して MD を更新する

成果物は [template.md](template.md) の **過去結果の構成**に沿う。空の項は推測しない。

1. **規模・○テスト項目設定率・○障害発生率と考察** — SLOC 等の規模とテストケース数、推定値・下限・上限はユーザー渡し。KSLOC は SLOC / 1000。
   障害件数は障害表。行数から／機能数から、IT / ST。
   **ブロック本数**は [template.md](template.md) のルール（混在しなければ1つ）。
   **分野ごと**に実施する（対象分野が2つなら2分析。並びは WEB → Excel設計書）。
2. **(2) 障害要因** — IT / ST の表と **＜分析結果＞**。再発防止・次の打ち手もここに書く。
   分類は template.md の7分類（並びもそこが正）。独立した「この後取るべきアクション」節は置かない。
   **＜分析結果＞の記載フォーマット**は件数・内訳のあと、発生した分類ごとに
   `- 分類名` の箇条書きとする。WEB と Excel設計書で揃える（見出し構成は分野別のまま）。
   **原因の一例**は代表1件の詳述ではなく、同分類で発生した原因を一言で端的に記載する。
   複数件で原因が異なるときは、複数の短い原因を併記してよい。
   同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。
   台帳が来たら、同一フォルダの `障害・変更管理台帳.md` に見えている行を全量転記する（`品質分析.md` には全文を置かない）。
3. **(3) 過去案件との比較** — 過去案件の `品質分析.md`。無い欄は `（未入力）`。比較表、数値差および基準値との関係による総括だけを置く。
   テスト項目設定率の事情は（1）、障害の分類・検知妥当性・対応方針は（2）に記載する。考察は今回分だけ書く。

- 基準値が無い間は判定欄を **`（未入力）`**。考察は **データが無い欄だけ**書かない。揃っている欄は書く。
- **数値は入力どおり**。集計する場合は計算過程を短く残す。
- **表を優先**。長文は考察・＜分析結果＞に限る。
- **IT と ST は分けて集計**し、必要なら合計行を置く。混在させない。
- 考察は **結果の言い換えだけで終えない**。なぜその結果に至ったかを書く。
  根拠がある因果は事実として書く。足りないときは推測して書いてよい。
  理由文は直前の判定の言い換えにしない
  （例: 「おおむね沿った結果であった。乖離していないためである。」は不可）。
  件数・割合そのものを「と考えられる」で繰り返さない。
  同じ漏れを、事実と推測で二重に書かない。
  本文は **報告資料の文体**（納品済み過去結果の口調。である調。「〜結果であった」「問題無しと判断する」）。
  「〜と考えられる」はユーザーも使う。**AIが独自に推測した因果には `（推測）` を付ける**。
  文末の例: 「〜と考えられる（推測）。」。ユーザーが事実として渡した因果には付けない。
  さん付け・作業メモ口調は本文に置かない。確定したら `（推測）` を外す。
  当否確認の手順は原則の「当否確認」に従う。
  確認はチャットまたは未確定で取る。
  一般論だけの埋め草は書かない。数値・分類・推定値セルは推測で埋めない。
  **文章の型**は当該分野の納品済み過去結果の考察を参考にする
  （「改訂行数ベース、機能数ベース」「〜結果であった」「問題無しと判断する」
  「過去案件と比較し」など）。全文コピーは禁止。
  **揃っている欄は数値の転記だけで終えない。** 推定値／下限／上限があるときは範囲判定を書く。
  行数軸と機能数軸で判定が割れるときはそれを書く。
  **帳票の修正は LOC に含まれない**（ユーザー確定。件数は規模表の帳票数）。
  帳票修正が多いときは、行数からの推定値との差に重きを置かず、機能数からの基準値チェックを重点にする。
  帳票修正の推定FP内訳が来たら規模の補足として書く（率の軸にはしない）。
  帳票の新規／改訂内訳と、帳票内バリエーションの多寡が来たら設定率の考察に使う。
  表記は **改訂**（改定ではない）。前案件の分割見出し「帳票改定」「意向改定」は過去結果の名称なので変えない。
  改訂は改訂箇所中心で、新規よりケースが少なくなりうる。
  機能数の大半が帳票修正であることだけでは、設定率が推定下である理由にしない。
  **設定率の結び（常用句）**: IT / ST ともに
  「確認すべき観点は網羅しているため、実績値は問題無しと判断する。」を使ってよい。
  表記は **問題無し**。範囲内または今回の事情が型に合うときに使う。
  発生率が上限を超えているときは、この句で済ませない。
  今回に無い事情（手厚い確認をした、帳票の間に追加した等）は借りない。
  推定値が無い欄の範囲判定は書かない。
  **顧客へ出す考察・＜分析結果＞・(3)** は、納品済み過去結果と同じく、人が書いた報告として読めること。
  一文ずつ切った短文の羅列や、作業用のメタ（推測していない、フィルタ外は含めていない、全文はコピーしない、
  見えている、打ち手は同じ、＜分析結果＞に記載した、鳥山さん 等）は本文に書かない。
  `（推測）` は AI 独自の因果の印であり、このメタ禁止の対象外。
  顧客からの優先指示などの出所は、顧客向け資料に明示せず、実施方針として記載する。
  接続は「が」「ため」「ただし」。同じ判定なら IT/ST をまとめてよい。
  **再発防止**は「確認観点を明確にする」で終えない。実施する行為で結ぶ
  （突合する／確認する／徹底する／実施する。過去結果の「運用を徹底する」に寄せる）。
  実施主体・役割分担が未確定のときは、実施すると断定せず次回案件で検討する、と書く。
  ユーザーが品質向上フェーズへ実施と明示した項目は実施すると書く。
  次回案件の打ち手は＜分析結果＞に書く。独立した次回案件節は置かない。
  同一対策を＜分析結果＞で「次回検討」のまま残さない。
  次回案件の施策を品質向上フェーズへ書かない。
  台帳の原因・経緯は開発メモのまま本文へ写さない。原因の一例と考察は報告文として自然な日本語にする。
  **基準値チェックの考察**では障害の分類に深入りしない。分類・見逃しは (2) 障害要因の＜分析結果＞。
- **顧客指摘・優先指示**: 既知事情に書く。打ち手は＜分析結果＞に記載する。独立節は置かない。
  WEB と Excel設計書に跨る指示は両方に書く。品質向上フェーズは各分野へ書く。
  顧客指摘の「今回の事象」は、ユーザーが特定した障害にだけ当てる。同分類の他件へ広げない。
  同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。
  案件固有の本文は SKILL に書かない。
- **IT/ST共通の品質要因**: 体制など、IT・STの個別考察に限定できず品質全体に関わる事情は、
  当該分野の（3）過去案件との比較の次に独立した節として記載する。各フェーズの＜分析結果＞へ重複して記載しない。
  **品質向上フェーズの実施内容は品質全体へ書かない。**
- **品質向上フェーズ**は今案件の残フェーズで実施する内容である。次回案件の打ち手と混ぜない。
  WEB と Excel設計書それぞれに置く。文書末尾の横断1節は置かない。
  実施内容は当該分野の分だけ。他分野の実施内容を重複しない。
  汎用の「この後取るべきアクション」節とは別である。
  書き方は、実施内容を箇条書きし、補足を文章で続ける。実施内容を一文に連ねない。
  同一の実施を、手段と本体で複数行に分けない。
  当該分野の品質全体または（3）の次に `### 品質向上フェーズ` を置く。
  次回案件の打ち手は＜分析結果＞に書く。`### 次回案件での施策` は置かない。
- **分類と発生フェーズ（見逃し）**: 分類は作り込み工程の目安、発生フェーズは検出工程。
  障害要因の考察は、IT / ST より前のテスト工程で検知して止められずに流出した観点を
  ＜分析結果＞で見逃しとして扱う。独立節は置かない。ITのテストケース外の観点を
  STで検知した障害は、ITの見逃しとして扱わない。
  ITのテストケース外をSTで検知したコーディングミスは、STでの検知は問題無しとして扱う。
  ITで突合せを実施済みでも、IT実施パターンでも検知できた面があるときは、
  未実施と書かず、次回以降のIT実施パターンで外部設計書・他商品との突合を徹底する、として再発防止に書いてよい。
  実施していなかったかのように「実施する」とは書かない。
  件数 0 の分類を「検知している」と書かない。
  **Excel設計書**は UT～ST をテスト観点ごとに分けている。
  当該観点を前段では実施していないときは、後工程での検知を前段の見逃しとしない。
  前段での検知は難しいため、当該フェーズでの検知は問題無しと判断する。
  コーディングミスを IT / ST で検出したら、前テスト工程での見逃しとして扱う
  （Excel設計書で前段未実施の観点は除く）。
  内部設計ミスを ST で検出したら、ITを含む前テスト工程での見逃しとして扱う
  （Excel設計書で前段未実施の観点は除く）。
  内部設計ミスを IT で検出したら、IT前のテスト工程での見逃しとして扱う。
  ITでの検出自体はテスト工程の役割であるため、「ITで見つけるべきではない」とは書かない。
  見逃し分析とは別に、障害の作り込み自体を減らす外部設計・内部設計の改善策は、
  根拠のある範囲で再発防止として記載する。テスト工程での検知責任と混同しない。
  台帳凡例があればそれを正とする。
