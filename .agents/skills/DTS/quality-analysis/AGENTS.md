# quality-analysis

Always respond in Japanese when using this skill.

## 発火条件

- ユーザーが **品質分析**、**IT結果**、**ST結果**、**バグ票**、**障害管理台帳**、**障害表**、**品質レポート** を依頼したとき
- 雛形 Excel・規模の数値・テストケース数・障害管理台帳を渡したとき（**テキスト入力も含む**）
- **`Work/MY案件/`** 配下の品質分析フォルダ、または **`品質分析.md`** の作成・更新を依頼したとき

## 必須の最初アクション

**`SKILL.md` と `template.md` を Read ツールで全文読む**。Work 配下を編集する前に **`work-folder-update` SKILL** も Read する。

## 要点

- **作業フォルダ**はユーザー指定を正とする。型は `Work/MY案件/{yyyymm}_{案件名}/品質分析/`（展開日。`_共通` は接頭辞なし）
- **成果物は Markdown**（作業フォルダ内の `品質分析.md`）。顧客提出の **Excel は書かない**。
  ユーザーが確定版と明示したら現行 MD を転記正とする。確定後は再依頼まで本文を書き換えない。
  確定の記録は作業メモ。台帳の全量は同一フォルダの `障害・変更管理台帳.md`（`品質分析.md` には件数・分類・一例）
- **雛形と共通情報は一度登録したら次回案件でも使う**（**同じプロジェクト内**）。呼び出しごとに再入力させない
- **代理店と申込書でフォーマットは違う**（目的は同じ）。登録済みは代理店のみ。申込書着手時は雛形の取り込みから。代理店構成を流用しない
- **構成**は当該プロジェクト・当該分野の納品済み過去結果を踏襲。WEB と Excel設計書で構成が違うときは混ぜない。
  考察の文章は過去を参考。数値と事情は写さない
- **バグ曲線は作成しない**。MD に節を置かない。過去 Excel にあっても転記しない
- **基準値ブロック**は混在時のみ案件ごと＋全体。混在しなければ1つ。前案件の分割見出しはコピーしない
- **分野（代理店）**: WEB と Excel設計書。案件により片方または両方。分析は対象分野ごとに実施する。
  両方あるときの並びは **必ず WEB → Excel設計書**。
  品質向上フェーズは各分野へ書く。次回案件の打ち手は＜分析結果＞。独立節は置かない。混ぜない。
  実施内容は箇条書き、補足は文章。同一の実施を手段と本体で複数行に分けない。
  共通台帳で一方の分野に IT/ST が現時点でないと明示されたら、その分野は `0`（列欠如だけで未入力にしない）
- **過去の品質分析結果**も案件フォルダの `品質分析.md` に残す。比較は過去 MD を参照。
  考察の全文は写さない。文章の型は参考にする。
  **納品済み・連携済み**は正式版としてそのまま転記（要約・言い換え禁止）
- **追加観点の案**は `template.md` に残す（未採用）。障害表に無い情報は採用不可。分析するなら障害表のフォーマット変更が先。
  過去案件との比較は雛形の節（案ではない）
- 共通の正本は **`template.md`** と `Work/MY案件/_共通/品質分析/`
- **雛形は大枠のみ**。構成は納品済み過去結果。数値と今回に無い事情は写し替えない。
  考察の文章の型は参考。全文コピーは禁止
- **入力の取り方**: SLOC 等の規模とテストケース数、推定値・下限・上限はユーザーが渡す。**KSLOC は SLOC / 1000**（小数第1位）。
  メトリクス(サマリー版)はテスト密度→設定率、欠陥検出密度→発生率。開発工数は載せない。
  規模の内訳が訂正されたら推定FPと機能数軸の推定値をセットで差し替え、範囲判定と考察をやり直す。
  障害関連は障害管理台帳（障害表）から取得する。フィルタ外は障害として扱わないもの、または DTS 担当範囲外。
  分類空で調査中の行は、調査完了（分類確定）するまで件数・分析に含めない（その他にしない。分類は推測しない）。
  Excel が置けないときはチャットへテキスト。推定値の算式の類推はしない
- **入力は随時**。無い欄は `（未入力）`。数値・判定・分類は推測で埋めない。**`0` は未入力ではない**。SLOC 等の規模・テストケース数を計算しない（KSLOC は除く）。テキスト入力を不足扱いしない
- **考察**: 揃っている欄は数値転記だけで終えない。結果だけでなく、なぜその結果に至ったかを書く。
  根拠があれば事実。足りなければ「〜と考えられる」とし、チャット／未確定で確認を取る。
  **AIが独自に推測した因果には `（推測）` を付ける**。「考えられる」はユーザーも使う。
  文末の例: 「〜と考えられる（推測）。」。ユーザーが事実として渡した因果には付けない。
  さん付け・作業メモ口調は本文に置かない。確定したら `（推測）` を外す。
  当否確認は障害表とユーザー確定事情だけを正とする。当ならラベルを外す。否なら訂正する。どちらにも無い因果は外す。
  文章の型は当該分野の過去考察を参考。
  数値と今回に無い事情は写さない。全文コピー禁止。
  設定率の結びは IT / ST ともに常用句
  「確認すべき観点は網羅しているため、実績値は問題無しと判断する。」を使ってよい。
  発生率が上限超のときはこの句で済ませない。
  帳票の修正は LOC に含まれない。帳票修正が多いときは行数軸との差に重きを置かず、機能数軸を重点にする。
  帳票修正の推定FP内訳が来たら規模の補足として書く。
  設定率が機能数軸で推定下のときは、帳票内バリエーションと新規／改訂の事情が来たら考察に使う。
  表記は **改訂**（改定ではない）。
  顧客へ出す考察は人が書いた報告文。作業用メタ・短文羅列は本文に書かない。
  基準値チェックの考察では分類に深入りしない（分類は (2)）。
  役割分担が未確定な対策は実施すると断定せず次回案件で検討する。
  ユーザーが品質向上フェーズへ実施と明示した項目は実施すると書く。
  次回案件の打ち手は＜分析結果＞。独立した次回案件節は置かない。
  次回案件の施策を品質向上フェーズへ書かない
- **原因分類**は template の7分類（並びもそこが正。空欄は「その他」にしない）。
  分類×発生フェーズの後工程検出は＜分析結果＞に見逃しとして書く（独立節は置かない。件数 0 は検知していない）。
  ＜分析結果＞は件数・内訳のあと分類ごとの箇条書き。WEB と Excel設計書で記載フォーマットを揃える
  ITケース外のST検知は問題無し。実施済み確認を未実施と書かない。
  IT実施パターンで検知できた面は突合の徹底として対策に書く。
  Excel設計書は観点分割のため、前段未実施観点を前段の見逃しにしない
- **顧客指摘・優先指示**は既知事情と＜分析結果＞または (3)。独立節は置かない。WEB と Excel に跨る指示は両方に書く。品質向上フェーズは各分野。混ぜない。
  顧客指摘の「今回の事象」は、ユーザーが特定した障害にだけ当てる。同分類の他件へ広げない。
  同分類の複数件は、件ごとに原因と再発防止を書く。片方の対策をもう片方へ流用しない。
  作業メモの RV指摘節は指摘原文を変えず、取込状況は原文を上書きしない
- **実行しながら本 SKILL / template.md を更新**する
- 完了後は **`obsidian-cursor-log`**。MD 編集後は **`markdownlint-fix`**

手順の正本は **`SKILL.md`**。
