# work-todo-update（Work Todo 更新・運用）

長谷が**能動的に着手しないと進まない**次アクションは、**単発と繰り返しで別ノート**にする。\
背景・業務の正本は各業務ノートとし、Todo には**期限付きの実施タスク**と、
着手時に必要なタスク単位の詳細を併記できる。\
進捗会議・定例会など**時間が来たら始まる出席・参加は載せない**（開催の正本は `Work/定例・報告/定例会.md`）。

**振り分け（必須）**:

- **単発** → `Work/Todo.md`
- **繰り返し**（週次・月次・3ヶ月次・年次等） → `Work/Todo-定例作業.md`
- 混ぜない。`/next-action-work` は**両方**と **Asana MCP** を読む
（Asana の手順は **`next-action-work` SKILL**）

**最初の作業**: 本ファイルを **Read** する。続けて対象の正本（単発なら **`Work/Todo.md`**、
繰り返しなら **`Work/Todo-定例作業.md`**。横断なら両方）を **Read** する。\
**`Work/` を編集する前**に **`work-folder-update` SKILL** も **Read** する（振り分けゲート）。

myrules を厳守する（**スクリプト一括置換禁止**・**報告前 CursorLog**）。

要約は同ディレクトリの **`AGENTS.md`** と整合させる。

## 使用タイミング（発火）

- **`Work/Todo.md`** または **`Work/Todo-定例作業.md`** の**追加・完了・期限変更・並び替え・セクション整理**を依頼されたとき
- ユーザーが「タスク追加」「完了」「Todo更新」「Work Todo」「繰り返しTodo」「定例作業」等と言ったとき
- **`work-folder-update`** の振り分けで、本人の次アクションが**新規・完了・期限変更**したとき（ユーザーが「Todo更新」と明示しなくても**同一セッションで反映**。単発／繰り返しでノートを分ける）
- **`next-action-work`** 後にユーザーが特定 Todo を完了／追加したとき
- **`/next-action-work` の実行時**。候補抽出より先に、単発・繰り返しを問わず、
  着手可能日が到来した行、または着手可能日が指定されず前タスクがすべて完了した行の `🚫 着手不可` を解除して
  候補判定へ反映する。前提条件・「面談実施後」などの情報は解除・候補化を妨げず、
  候補提示前の確認もしない。
- **`/next-action` の実行時**。単発・繰り返しを問わず、着手可能日が到来し、
  または着手可能日が指定されず前タスクがすべて完了した行の `🚫 着手不可` を解除して候補判定へ反映する。
  前提条件の確認有無は候補化へ影響させない。

## 対象外

- FishTrack / MyPokedex / FaiNavi 等の**副職・趣味**タスク
- **`DevProject/plans/スケジュール.md`** の計画用タスク（Fxx / Pxx 等）
- **`Work/課題.md`** の課題ブロック本体（→ **`work-kadai-update`**）。課題から生じる**実施一手**だけ Todo へ載せる
- コミット・プッシュ・PR・デプロイの案内
- **進捗会議・定例会など、時間が来たら始まる出席・参加**（正本は `Work/定例・報告/定例会.md` とカレンダー）。
  会議前の宿題案内・資料準備・招集など、長谷が先に動かないと進まない実施は載せてよい
- **長谷がオブザーバーで、実施主体がメンバーの作業**（例: 生成AIワーキングのアイデア具現化・導入）。
  正本は業務ノート。長谷が先に動かないと進まない準備・案内だけ載せる
- **単発ノートへ繰り返しを載せる**、または**繰り返しノートへ単発を載せる**（混ぜない）
- **期限が確定しない「次回」・「都度」・「継続」・「通期」の行**。定例の能動作業は日付確定後に
  `Todo-定例作業.md`へ対象回として追加し、継続方針・目標は業務正本へ残す。条件発生時にはじめて、
  期限付き単発タスクとして`Todo.md`へ追加する。**ただしユーザーが未整理として保持を指示した内容**は、
  `Todo.md` の `### 未整理` に**チェックボックスなし**で残してよい

## ノート構造（必須）

| 要素 | ルール |
| --- | --- |
| **大区分** | **`## 未完了`** を**上部**、**`## 完了`** を**下部** |
| **テーマ** | 各大区分の下に **`###`**（例: 人事・評価・生成AIワーキング・財務・CS）。期限・優先度による「直近」「最優先」はテーマにせず、業務領域で統一する |
| **単発タスク（期限未設定）** | ユーザーが保持を指示した、実施内容は確定しているが期限未設定の**単発タスク**を `[ ]` と完了条件付きで置く。`⚠️ 期限設定待ち` を付け、`/next-action` の候補外とする。期限決定後に業務領域の `###` へ移す |
| **未整理** | 単発タスクになっていない、定例・継続方針・条件発生時の対応などを `### 未整理` に**チェックボックスなし**で記録する。`/next-action` の候補外。具体化後に単発タスク・繰り返しTodo・業務正本へ振り分ける |
| **混在禁止** | **単発**は同じ `###` 内に `[ ]` と `[x]` を**置かない**。**繰り返し**は親の下で対象月の `[ ]` と `[x]` が混在してよい |
| **完了時（単発）** | `[x]` にし、**未完了の該当行を削除**して **完了セクション**の同テーマ `###` へ移す。空になった未完了側 `###` は削除してよい。 |
| | 当該タスクの完了条件に関する**未決が正本に残っていたら完了にしない** |
| **完了時（繰り返し）** | **対象月のチェック行だけ** `[x]`。親タスクは未完了に残す。完了セクションへ移さない。実際の完了日を必ず行に記載し、後から削除しない |
| **着手不可** | 次のいずれかならチェック行（単発ならタスク行）に **`🚫 着手不可`**。条件が無くなったら外す。 |
| | (1) **前タスク**（他の Todo）が当該対象月で未完了。複数ある場合はすべての Todo ID が同一対象月で `[x]` になるまで着手不可 |
| | (2) **着手可能日**があり、今日がそれより前（例: 毎月1日まで着手できない） |
| | 親に前タスクがあり、対象回の着手可能日が `YYYY-MM-DD` で指定されていない場合は、同一対象回の前タスクがすべて `[x]` になった時点で着手可能とする。 |
| | 前タスクと前提条件は別。前タスクの行が無くても前提条件がありうる。期限と着手可能日は別 |
| | 着手可能日が到来した後は、前提条件の未確認にかかわらず `🚫 着手不可` を付けず、`/next-action` の候補にする。前タスク未完了は解除しない。 |
| **着手推奨** | **ブロッカーではない**（`🚫 着手不可` にしない）。期限・着手可能日とは別。 |
| | 親に **着手推奨の計算**。対象月行（単発ならタスク行）に **着手推奨日** `YYYY-MM-DD`。 |
| | 例: 期限当日。期限の3営業日前（有休も考慮）。毎月5日以降。不要なら計算行と対象月行を省略する。 |
| | 3営業日前は Excel がある間は Excel で出した日付。Work 側で再計算しない。 |
| | カレンダー日（毎月5日）は対象月の日付を書いてよい。 |
| | 今日が着手推奨日より前なら `/next-action` `/next-action-work` の**優先度を落とす**（除外しない）。 |
| | 期限超過は推奨前でも上げる。印は `⏳ 推奨前`（任意。日付比較が正） |
| **新規** | **未完了**の適切な `###` へ `[ ]` で追加。無いテーマは `###` を新設してよい |
| **詳細** | 正本ノートへ背景・業務詳細を書き、Todoには期限・完了条件に加えて、着手に必要な要点をタスク配下のインデント箇条書きで記載してよい |
| **表記** | Todo本文のカタカナは**全角**で記載する。半角カタカナを混在させない |

### 推奨テーマ例（固定ではない）

人事・評価／生成AIワーキング／若手育成WG／1on1／財務・CS／育成・体制／稼働・労務。
繰り返しノートでは週次／月次／3ヶ月次／年次、または PL カテゴリ（A〜H）も可。

## タスクの書き方

| 観点 | ルール |
| --- | --- |
| **粒度** | 「〜する必要がある」は**背景**。チェックリストの動詞は**実施タスク**（例: 連絡フローを確立する）。背景と実施を混同しない。**出席・参加**だけは実施に見えても、時刻到来で始まる予定なので Todo にしない。**オブザーバーでメンバーが実施する作業**も Todo にしない |
| **期限** | 未完了には **`YYYY-MM-DD`** を必ず書く。`近日中`・`要確認`・`都度`・`継続` 等の曖昧期限は**使わない**。期限の計算式・基準が不明、または外部日付に依存して確定できないときは、**追加前にユーザーへ確認し、推測で登録しない**。ユーザーが明示的に未指定とした場合に限り、`未指定（理由）` を記載し、着手不可にする。 |
| | `次回`・`都度`・`継続`・`通期`は期限の代替ではなく、単発Todoに登録しない。定例・方針・条件発生時の単発のいずれかへ振り分ける。ユーザーが保持を指示した期限未設定の**単発タスク**だけは、`### 単発タスク（期限未設定）` に `⚠️ 期限設定待ち` として置ける。単発でない未整理事項は、**非タスク記録**として `### 未整理` に置く。 |
| | PL 繰り返しを Excel から写すときは、計算済みの日付を使う。Work 側で営業日を再計算しない。 |
| | 祝日・振替休日・国民の休日・会社指定休日は非営業日として扱う。個人の休暇と終日不在は営業日として扱う。終日不在は休暇と同じ扱い（各Todoの休暇時の扱い・「休暇のとき」に含める）。反映方法は各Todoで個別に定義し、全Todoへ一律適用しない。 |
| | 休暇時の扱い（期限不変・前倒し可・後ろ倒し可など）は、各Todoの親定義に明記する。 |
| | 「期限日が休暇の場合は前営業日に前倒し」「期限日が休暇の場合は翌営業日に後ろ倒し」と定義したTodoは、対象月行の期限も前営業日／翌営業日へ変更する。実施だけ前倒しして期限を元のままにしない。 |
| | 「前営業日」「翌営業日」は、期限日を基準にそれぞれ直前・直後の営業日とする。営業日は `Work/休日・休暇予定.md` の区分に従う（祝日・振替休日・国民の休日・会社指定休日・毎年12/29〜1/3・土日は非営業日。長谷の休暇と終日不在は営業日）。 |
| | 「前日」「翌日」は使わない。着手可能日の「〇〇完了の翌日」は「〇〇完了の翌営業日」、前提条件の「〇〇の翌日」も「翌営業日」と書く（C-11 の既存行と同じ）。 |
| | **対象月の追加・完了後の次回行の補充・期限変更を行う前に、必ず `Work/休日・休暇予定.md` を Read する。** 候補日を会社指定休日・長谷の休暇予定・終日不在と照合し、親定義の休暇時の扱いを適用した期限・着手可能日を記載する。終日不在は休暇と同じ。対象月の補充時も例外にしない。 |
| | **要員入れ替え・退職の顧客報告**: 期限は退職日・入替当日ではない。入れ替えが効く月（欠員が契約上効く最初の月）の**前々月末**または**前月頭**。**顧客承認までに交代要員を確定**する。正本は `Work/体制・プロジェクト/ステークホルダ.md`。例: 10月末退職 → 11月から欠員 → 9月末か10月頭 |
| **完了条件** | 各タスクに、成果物・反映先・確認状態など、完了を客観的に判定できる**完了条件**を明記する。既存タスクを更新するときも、完了条件がなければ追記する |
| **着手時の詳細** | 対象・前提・入力・手順・連絡先・参照先・判断待ちなど、実際の着手に必要な情報はタスク配下に記載してよい。正本ノートの全文複製や冗長な経緯は避ける |
| **繰り返しの定義** | **親は1タスク**。完了条件・Excel 列Dの**期限の計算**・**休日調整**・**休暇時の扱い**・**着手可能日の計算**・ |
| | **前タスク**・**前提条件**・**着手推奨の計算**は親に1回だけ書く。休日調整は `前営業日`・`翌営業日`・`基準日より前の営業日`・`基準日より後の営業日`・`外部連携値を使用` のいずれかを親に1回だけ明記する。列F作業内容があれば親に写す。 |
| | すべての親タスクに、`前タスク` または `着手可能日の計算` のいずれかを必ず設定する。両方を `なし` とする、またはいずれも省略する親タスクは登録しない。 |
| | 前タスクだけを着手条件とする場合は、着手可能日の計算に `{前タスク}完了時` を記載する。複数前タスクはすべての完了時とする。 |
| | `〃`・数式は表示結果。前タスク／前提条件／着手推奨の計算が不要なら、その行を省略する。列対応は `PL作業TODO.md` |
| | Excel 列Eは前提条件と前タスクに分けて写す（Todo ID→前タスク、メール等→前提条件） |
| | **対象月ごとにチェック行だけ**出す（通常は `[ ] 対象月: YYYY-MM、期限: YYYY-MM-DD`）。期限未指定の合意がある行は、理由付きの `未指定（理由）` を使う。 |
| | 着手可能日があれば `着手可能日: YYYY-MM-DD`。着手推奨があれば `着手推奨日: YYYY-MM-DD`。 |
| | 同じタスクを対象月の数だけ並列複製しない |
| | 着手不可の対象月は `、🚫 着手不可` を付ける。推奨前は `⏳ 推奨前`（任意） |
| **定例** | 宿題案内・資料準備など**能動着手が必要な実施**だけ載せる。1回完了で定例全体を完了にしない。 |
| | **出席・参加そのものは各回登録しない**。年度始に、当該年度の4月1日から翌年3月31日までに**着手可能日または期限**がある対象月チェック行を全て追加する。表示件数の上限は設けない。 |
| | 対象月が完了したらその行だけ `[x]`。年度途中に日付が確定した行も、同じ年度内の条件を満たせば追加する。1回限りは `Todo.md` |
| **リンク** | 背景の正本は `[[wikilink]]`（例: `[[勤怠]]`） |
| | PL 繰り返しのマニュアルは Todo に `参照:` 名だけ。本文は写さない。 |
| | 現状の本文正本は SharePoint の公式 PDF と、保険第五担当独自の Excel。 |
| | 将来は Cursor 上にマニュアル。現状は手続きノートへ足さない |
| **完了付記** | 完了時は実際の完了日を必ず括弧に `YYYY-MM-DD 完了` として付け、完了日を保持する |

Excelファイルへのリンクは、Excelで開く`ms-excel:ofe|u|file://...`形式にする。
フォルダは`file://`リンクのままとする。

## 作業フロー

1. **`work-folder-update` SKILL** を Read（Work 編集ゲート）
2. **本 SKILL** を Read（未読なら）
3. 対象ノートを Read（単発は **`Work/Todo.md`**、繰り返しは **`Work/Todo-定例作業.md`**。横断なら両方）。
   期限の追加・変更または対象月の補充を行う場合は、あわせて **`Work/休日・休暇予定.md`** を Read し、候補日を休日・休暇予定と照合する。
4. 追加・完了・期限変更を **StrReplace / Write**（**`replace_all` 禁止。ブロック単位**）し、
各タスクの完了条件を明記する。繰り返しは親1つ＋対象月のチェック行。
年度始に、当該年度の4月1日から翌年3月31日までに**着手可能日または期限**がある対象月チェック行を全て追加する。年度途中に日付が確定した行も、同じ年度内の条件を満たせば追加する。完了による表示件数の補充は行わない。
   着手不可（前タスク未完了・着手可能日前）の対象回または単発タスクは
   `🚫 着手不可`。`/next-action-work` の実行時は、候補抽出より先に、
   単発・繰り返しを問わず、**着手可能日 `YYYY-MM-DD` が JST 今日以下**で、
   **前タスクの行が無い、またはすべての前タスクが充足**している行の `🚫 着手不可` を解除してから候補判定する。
   **当日期限・当日着手可能日の行だけに grep を絞らない**（全未完了チェック行を横断。詳細は **`work-todo-update` SKILL「着手不可解除の横断スキャン」**）。
   前提条件・「面談実施後」などの情報の確認有無にかかわらず解除し、
   候補提示前の確認はしない。
   対象回を `[x]` にしたら、それを前タスクに持つ行を再判定する。
   前提条件の更新・着手可能日到達でも再判定する。
   着手推奨日を付けたら、今日より前なら優先度を落とす印を検討する（`⏳ 推奨前`）
5. 単発は未完了／完了の混在がないことを確認。繰り返しは対象月行の `[x]` を親の下に残してよい。
   `🚫 着手不可` の付け忘れ・外れ忘れがないことを確認。
   すべての親タスクに、`前タスク` または `着手可能日の計算` が設定されていることを確認。
   **着手不可解除の横断スキャン**（**A**＝フルは **JST 各日1回**。**B**＝`[x]` 等の局所再判定は都度）を省略しない。
   完了にした単発の完了条件について、正本の未決が残っていないことを確認
6. **markdownlint**（当該ファイル）
7. **`obsidian-cursor-log`** でCursorLog追記
8. 報告に「CursorLogは更新しました」を含め、必要なら残作業を短く案内（コミット案内はしない）

## 着手不可解除の横断スキャン（必須）

**再発防止（2026-11-02）**: **G-3** 対象月行は着手可能日 **2026-11-01** 到来済みなのに `🚫 着手不可` のままだった。
原因は (1) `/next-action-work` で**当日**の期限・着手可能日だけを grep し、**昨日以前に到来した着手可能日**を見落としたこと、
(2) **G-3** の親 **前タスク** が正本に無く、**G-1** 同一対象月完了後も **G-3** を再判定しなかったこと。

### いつ実施するか

**2種類に分ける**（混同しない）。

#### A. フル横断スキャン（全 `[ ]`・着手可能日 ≤ 今日 ＋ 前タスク照合）

- **JST 各日1回で足りる**。着手可能日による新規解除は**日付が変わったときだけ**増えるため、
  同日2回目以降の `/next-action-work`・`/next-action` で**フルスキャンを繰り返す必要はない**。
- **実施タイミング（推奨）**: その日**最初**の `/next-action-work`・`/next-action`、または Todo 正本の横断メンテの直前。
- **当日期限・当日着手可能日だけに grep しない**（G-3 再発防止の要点はここ）。

#### B. 局所再判定（フルスキャンの代替にならないが、同日に都度必須）

- 繰り返し Todo のチェック行を **`[x]`** にした直後（**前タスク** を持つ他 Todo の**同一対象月**）
- 単発完了・期限変更・追加の直後の**前タスクを持つ対象回**の整合

`/next-action-work` 実施時: **その JST 日に A をまだしていなければ A を先に**。
同日2回目以降は **A 省略可**（B は `[x]` 等の編集があればその都度）。

### 判定手順

1. JST の**今日**を取る（**`datetime-jst` SKILL**）。
2. **`Work/Todo.md`** と **`Work/Todo-定例作業.md`** の **すべて**の未完了チェック行（`[ ]`）を対象にする。
   **当日期限・着手可能日が今日の行だけに検索を絞らない**。
3. 行に **`着手可能日: YYYY-MM-DD`** があるとき、**その日付 ≤ 今日**なら着手可能日到達。
   **`未指定（…）`／`未確定（…）`** のみの行は本項の日付比較対象外（別ルール）。
4. **前タスク**の親定義行が無ければ前タスク条件は充足。
   Todo ID が1件以上あるときは、**すべて**の当該 ID の親タスク配下で、**このチェック行と同じ `対象月:` または `対象日:`** の行が **`[x]`** であること（**同一対象回**で照合。枝番だけ揃えない）。
5. **今日より後の着手可能日**・**前タスク未完了**（4 で未充足）のときは **`🚫 着手不可` を維持**。
6. 4 を満たし、着手可能日が今日以下、または着手可能日が指定されず前タスクがあることを満たし、
   5 に該当しなければ **`🚫 着手不可` を外す**。
   前提条件が残る行も **`🚫` は外し**、確認せず候補にする。
7. 変更したら **`Todo-定例作業.md` / `Todo.md`** を **`StrReplace`** で更新し、**markdownlint** → **`obsidian-cursor-log`**（`/next-action-work` で解除だけした場合も同様）。

### 定例 Todo の依存（正本）

- **G-3**（生成AIワーキング定例会設定）の親 **前タスク** は **G-1**（**同一対象月**）。
  正本は **`Work/Todo-定例作業.md`**。定義を変えたら本節も同期する。
