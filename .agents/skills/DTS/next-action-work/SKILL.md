# 仕事の次のアクション

本SKILLは `next-action` の仕事領域版である。副業・趣味・個人開発を候補から除外し、
Obsidian `Work/` と業務に関するCursorLog、当チャットで確定した本職情報、
および **Asana MCP（読み取り）** から、次の一手と配下へのリマインドを示す。

## 対象と対象外

### 対象

- 株式会社DTSにおける本職のタスク、期限、顧客案件、定例、メンバー対応、社内手続き
- `Work/Todo.md` の未完了（単発）
- `Work/Todo-定例作業.md` の未完了（繰り返し。週次・月次・3ヶ月次・年次等）
- `Work/社内手続き/PL作業TODO.md` の定義・未写し分（写し済みなら `Todo-定例作業.md` を正とする）
- `Work/課題.md` の継続課題と、案件・顧客対応・定例に記録された期限やブロッカー
- 当チャットおよび直近CursorLogにある、本職に関する未解消の合意・残作業
- **Asana MCP** の未完了（自分担当は着手候補。配下で期限が迫るものはリマインド）

### 対象外

- FishTrack、FaiNavi、MyPokedex、おたよりナビ等の副業・趣味・個人開発
- `DevProject/` の計画・仕様・タスク
- コミット、プッシュ、デプロイ、PR、マージ
- Git作業ツリーや未コミット差分に関する案内
- 進捗会議・定例会など、**時間が来たら始まる出席・参加**（候補にしない。開催の正本は `Work/定例・報告/定例会.md`）

## 調査手順

コードやObsidianノートは変更しない。ユーザーが更新まで明示した場合だけ、該当する専用SKILLに切り替える。

1. 当チャットの本職に関する未完了事項、期限、依頼、判断待ちを確認する。
2. 当日または直近のCursorLogから、本職に関する「残作業・課題」とエントリ本文を確認する。
3. `Work/Todo.md` を読み、単発の未完了・期限超過・当日・今週を確認する。
4. `Work/Todo-定例作業.md` を読み、繰り返しの**未完了の対象月チェック行**（`[ ]`）の
   期限超過・当日・今週を確認する。`[x]` の対象月は候補にしない。親の定義は参照する。
   **`🚫 着手不可`** の行は候補にしない。前タスク側で着手できるものがあればそちらを候補にする。
   キック待ちはキック到来まで候補にしない。着手可能日が未来なら日付で候補にしない。
   着手推奨日があり、今日がそれより前なら**優先度を落とす**（候補から除外しない）。
   期限超過は推奨前でも上げる。出すときは「推奨前」と明記する。
   出席は候補にしない。
   向こう3か月分が出ていても、候補は期限超過・当日・今週を優先する。
5. `Work/社内手続き/PL作業TODO.md` は定義・写し方。
   未写しの当月未済が残っていれば候補に含める（Excel 単独を正本にしない）。
6. 必要に応じて `Work/課題.md`、案件・顧客対応・定例の関連ノートを確認し、依存関係とブロッカーを確かめる。
7. **Asana MCP** を読む（下記「Asana（MCP）」）。未接続なら理由1行でスキップし、Work 源は続ける。
8. 情報源の違いで優先順位を決めず、期限、依存関係、影響範囲、リスク、ユーザーの明示したゴールで比較する。

## 優先順位の決め方

次の順で候補を絞る。ただし、期限や依存関係などの具体的根拠があれば順序を入れ替えてよい。

1. 期限超過・当日締切・業務停止につながるブロッカーを解消する。
   `🚫 着手不可` は候補にしない。
2. 今週までの未完了から、**着手推奨日が無い、または今日が着手推奨日以降**のものを優先する。
   後続の作業や関係者を待たせるものを先にする。
3. 継続課題は、現時点で具体的に着手できる一手がある場合だけ候補にする。
4. **着手推奨日前**（期限超過でない）は優先度を落とす。上位で件数が埋まるなら出さない。
   出すなら前提に「推奨前」と書く。
5. 期限・依存・影響の根拠が不足する候補は、推測と明記するか、確認事項として示す。

同じ内容が複数の情報源に現れるときは、重複候補にせず、もっとも具体的な期限・前提を統合して1件にする。
チャット、Todo、CursorLog、Asana の内容が矛盾するときは自動で採用せず、矛盾点と確認すべき事項を明記する。

## Asana（MCP）

`/next-action-work` のたびに **読む**。Asana へタスク作成・更新・コメントはしない。
手順の正本は本節。禁止情報は `Work/体制・プロジェクト/申込書・代理店_プロジェクトルール.md` の Asana 使用ルール。

### 接続

- 名前空間は `plugin-asana-asana`。`ready` でなければ Connect を案内し、Asana はスキップする。
- 出力にスキップ理由を **1行**。Work の Todo・課題は続ける。
- **`search_tasks` は使わない**（Premium 専用で `payment_required` になる）。

### 期限窓（JST）

Todo の「今週」とは別。Asana はリマインドのため次を対象にする。

- **期限超過**（`due_on` が今日より前）
- **今日から7日以内**（`due_on` が今日〜今日+7）
- `due_on` が無い未完了は対象外

### 取得手順

1. JST の今日をターミナルで取る（`datetime-jst`）。
2. `get_my_tasks`（`completed_since` は `now`。自分担当の未完了）。
3. `get_projects`（`archived=false`、必要ならページング）。
4. 未完了があるプロジェクトごとに `get_tasks`。
   `completed_since` は **UTC の ISO datetime**（`YYYY-MM-DDTHH:mm:ssZ`）。
   `get_tasks` に `now` は使えない。
   `opt_fields` は `name,assignee,assignee.name,due_on,completed`。
5. プロジェクトが0件なら `get_teams` のあと、業務チームで `get_projects` を足す。
   名前が「の最初のチーム」で終わる個人サンドボックスは対象外。
6. 期限窓で絞る。ユーザー向け文面に **GID を出さない**（名前で示す）。

### 振り分け

- **担当が自分（長谷）**: `## 推奨` の着手候補。Todo と重複なら1件にまとめる。
- **担当が配下**: `## リマインド`。作業本体は担当者。長谷は期限を伝える。
  配下の正本は `Work/体制・プロジェクト/所属・役割・プロジェクト概要.md` の内訳と
  `Work/メンバー情報/`。プロパーと客員を含む。休職中の鈴木美玖は配下。離任の寺崎は対象外。
  Asana の `assignee.name` が配下のフルネームまたは姓と一致するときだけ出す。
- **配下ではない他者**: リマインドしない。
  確定の非配下（Asana 表示名）: 三橋愛理、田中英嗣、Hideki Saito。
- **担当未設定**: リマインドしない。
- 同じ名前・担当・期限は1件にまとめる。

### 禁止

- チャットへ GID を出さない
- タスク本文・添付を長く貼らない（名前・期限・担当・プロジェクト名まで）
- Asana への書き込み（作成・更新・コメント・完了）

## 出力

候補は必要な数だけ示し、最大3件に絞る。残作業が1件なら1件だけでよい。

```markdown
## 推奨

### 1. {タスク名}

- 根拠: `Work/Todo.md` / `Work/Todo-定例作業.md` の期限、Asana（自分担当）、
  CursorLog・チャット上の依頼など
- 実施内容: 今回着手する範囲を具体的に記載する。
- 優先理由: 期限、依存関係、影響範囲、リスクのいずれかを記載する。
- 前提・注意: 判断待ち、確認先、作業開始前に必要な情報があれば記載する。
```

他者のうち **配下** の Asana で期限窓に入る未完了があるとき、推奨の3件とは別に次を出す。
配下でない担当・担当未設定は出さない。該当が無ければ節を出さない。
15件を超えるときは先頭15件と残り件数。

```markdown
## リマインド（Asana・配下）

- {担当名} / {タスク名} / 期限 YYYY-MM-DD（当日 | 超過n日 | 残りn日） / {プロジェクト名}
```

Workの正本を編集していない場合、CursorLogは更新しない。具体的な更新や実装を始める依頼に変わった場合は、
`work-folder-update` を先にReadし、対象に応じて `work-todo-update`、`work-kadai-update`、`quality-analysis`、`mokuhyo-*` 等を併用する。
